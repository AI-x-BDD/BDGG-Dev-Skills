# 觀察紀錄

> 觀察與判斷是我(人類)下的。「從哪個實際結果看出來」那一欄的數字,有一部分是我請 Agent 回頭從對話紀錄、git 歷史與逐筆重建查出來的 —— 查證的方法與完整結果在[索引頁的「查證紀錄」](./README.md#查證紀錄),這裡只引用。
>
> 範圍:[BDGG_blog](https://github.com/YongRui0402/BDGG_blog) 的 8 項功能。功能 1 到 3 用的是 skill 的 `a18acf7`,功能 4 到 8 用的是依前三項心得修訂過的 `f2e8761`。
>
> 有幾格我在開發當下沒有把握,是看過查證結果之後才下的結論,格子裡有寫明。

## 逐原則觀察

題目「你要觀察什麼」列的四項,拆成一條一條看。

### Double Diamond

| 題目要看的 | 我的觀察 | 從哪個實際結果看出來 |
|---|---|---|
| 1. 開發前先理解使用者與問題 | **各項功能開發時,好像都沒有問我小需求的問題。** 可能是因為需求已經寫在 features 檔案裡 | 理解與收斂是在開發前那一場對話做完的:Agent 分三輪問了我 12 題,產出 `requirements.md` 與 `features.md`。進到各項功能之後,功能 4、5、6、8 一題都沒有問;功能 1、2、3、7 各問了 3、4、1、3 題,問的是同意 push、文案、要不要發布這一類,不是需求本身。skill 也是這樣寫的:需求已經很明確時,Discover 縮成查核 |
| 2. 收斂這次要做的範圍 | 同上 | 同上。每一項的範圍內 / 範圍外寫在 [`features.md`](https://github.com/YongRui0402/BDGG_blog/blob/8cc3b6d/docs/features.md?plain=1#L778) 各項底下,是開發前就定好的 |
| 3. 提出可能的做法 | 有做 | [`requirements.md` 的 Develop](https://github.com/YongRui0402/BDGG_blog/blob/8cc3b6d/docs/requirements.md?plain=1#L231):「怎麼搬」比較了 A、B、C 三種做法才選 B |
| 4. 選定後先用小範圍測試 | 有做 | 功能 1 只放兩個互相連結的頁面,先驗「GitHub 建置部署」與「子路徑」才開始搬版型;之後每一項都在暫存區疊假內容實測。見 [`requirements.md` 的 Deliver](https://github.com/YongRui0402/BDGG_blog/blob/8cc3b6d/docs/requirements.md?plain=1#L340) |
| 5. 取得新資訊時回頭修正 | 有做 | [`requirements.md` 的「回頭修正」](https://github.com/YongRui0402/BDGG_blog/blob/8cc3b6d/docs/requirements.md?plain=1#L419)逐次記錄;[淘汰的做法](https://github.com/YongRui0402/BDGG_blog/blob/8cc3b6d/docs/requirements.md?plain=1#L358)那張表每一列都是實測之後改掉的 |

另外一件事:功能 5、6、8 各有一個規格沒料到的決定,Agent 沒有問我,自己決定、做完才在回報最前面告訴我(空的分區自動不掛選單、標籤寫法衝突時讓建置失敗、沒有照規格用 `data-baseurl`)。三個都是推上線之後我才看到。我的結論是**部分遵守** —— 有在回報裡說明,但應該先問我。

### Trunk Based Development

| 題目要看的 | 我的觀察 | 從哪個實際結果看出來 |
|---|---|---|
| 1. 每次只做一個足夠小的功能 | **部分遵循**(當下不確定,看過查證結果後的結論):最大的功能可以切得更小 | 每一場對話從開工到最終回報是 14 到 23 分鐘;變更量(不含文件)最小的是功能 7 的 6 個檔案 +42 行,最大的是功能 2 的 14 個檔案 +855 行。Agent 自己說偏大的只有功能 5 的第一筆 [`8f9830a`](https://github.com/YongRui0402/BDGG_blog/commit/8f9830a)(18 個檔案) |
| 2. 使用 trunk 或短期 branch | 都是直接進 trunk | [`git-log.txt`](./git-log.txt) 是一條直線:39 筆全部在 `main`,沒有 merge commit,remote 上只有 `main` |
| 3. 整合前先跑測試 | **部分遵循**(當下不確定,看過查證結果後的結論):37 筆通過可以接受;功能 4 那一次沒有做到 | 8 場的最終回報都寫每一筆提交前跑過 `make check`。事後把 39 筆逐一取出來重建:37 筆通過,1 筆是刻意弄壞的,1 筆當時還沒有建置指令。例外一次:功能 4 的回報自己寫「內網字樣檢查命中 2 行,指令卻沒有停下來就推了」(事後查是文件裡的字樣) |
| 4. trunk 維持可以執行與發布 | 有做。功能 1 那一筆刻意弄壞的 commit **算符合**,那是我的決定 | GitHub Actions 32 次執行,31 次成功;唯一失敗的是 [`1e09eca`](https://github.com/YongRui0402/BDGG_blog/commit/1e09eca),下一筆 [`fb80377`](https://github.com/YongRui0402/BDGG_blog/commit/fb80377) 還原,紅燈約兩分鐘。Agent 當時問我「建置失敗時公開站仍是上一版」要怎麼驗,我選「照原文推到 main 再 revert」 |
| 5. 較長的變更用 feature flag 或 branch by abstraction | **無法判斷** | 沒有用到,也沒有出現做不完的長變更。沾得上邊的只有 `hugo.toml` 的 `disableKinds`:還沒做到的頁面種類先關掉,做到哪一項打開哪一種 |

另外一件事:有 7 筆 commit 是和後面的一起 push,CI 只跑了最後一筆,這 7 筆沒有自己的 CI 紀錄。事後逐筆重建,除了還沒有建置指令的第一筆,其餘都通過。我的結論是**部分遵循** —— 我認為只要有測試到就可以。

## 無從觀察、無法判斷的

這個專案是單人、每項功能當天做完,下面這些規則沒有被考驗到。做的當下我沒有注意,是事後查證才確認的:

* 短期 branch(沒有開過任何 branch)
* feature flag、branch by abstraction(沒有做不完的長變更;`disableKinds` 那種開關算不算,我無法判斷)
* 破壞相容性的變更(39 筆都沒有標示;唯一沾邊的是刪掉上線約 20 分鐘的測試頁,算不算我無法判斷)
* commit 的 scope(39 筆都沒有用)
* 需求模糊時 Agent 會不會先問(8 項功能都附了完整規格)

## 優化空間

* **做到一半才冒出來的決定要先問**:規格沒料到的事,Agent 應該先停下來問我,而不是做完、上線後才在回報裡說明。
* **功能可以切得更小**:最大的那幾項(功能 2、功能 5 的第一筆)還能再拆。
* **內容型 repo 發一篇文章要用什麼 type**:`post` 我覺得不算正確,但我不知道更好的做法是什麼。
* **Double Diamond 的前兩步要怎麼測**:這次因為 features 檔案把需求都寫好了,看不到 Agent 在每項功能開發前理解問題、收斂範圍的樣子。
