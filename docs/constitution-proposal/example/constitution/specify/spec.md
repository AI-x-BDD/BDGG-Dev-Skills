# Rule 1 [must] - 每個使用者故事至少有一個失敗的驗收情境
- 每個使用者故事的驗收情境裡,至少一個情境的「則」寫的是系統拒絕、提示錯誤或維持原狀,而不只是成功的結果
- 失敗情境寫使用者看得到的反應(畫面、訊息、狀態不變),不寫內部錯誤碼
- 為什麼:這個專案的 API 錯誤與畫面錯誤狀態都從驗收情境推出來;故事裡只有成功路徑,下游的 api-plan 與 uiux-plan 就只會做出 happy path

## good example
- 加入購物車的故事,**第 2 個情境是數量超出範圍時被拒絕**
```markdown
**驗收情境**:

1. **假如**商品有庫存,**當**訪客按下「加入購物車」,**則**購物車數量加 1。
2. **假如**購物車裡這項商品已經有 99 件,**當**訪客再按一次「加入購物車」,**則**畫面提示「單一商品最多 99 件」,購物車數量不變。
```

## bad example
- 同一個故事,但**只有成功路徑**;下游不會替「超過 99 件」設計任何錯誤回應或畫面
```markdown
**驗收情境**:

1. **假如**商品有庫存,**當**訪客按下「加入購物車」,**則**購物車數量加 1。
2. **假如**購物車已經有這項商品,**當**訪客再按一次「加入購物車」,**則**那一項的數量加 1。
```
