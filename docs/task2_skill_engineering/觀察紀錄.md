## 無從觀察、無法判斷的

這個階段主要圍繞在單人開發環境下的 Skill 工程化重構與驗收，以下情況在本次道館中未被充分考驗：

* **長期自動化無人值守迭代的穩定性**：因額度消耗過快（「感覺沒做什麼額度就沒了」），未能實測長時間連續多輪的無人值守自主迭代。
* **短期分支（Short-lived branch）的完整協作實跑**：在實測驗收中僅覆蓋直推 trunk，涉及 Pull Request、Reviewer 審查的分支協作路徑未在範例專案實跑。
* **高頻規則變更下的全庫相容性**：雖然設計了 `skill-conform`，但尚未在大規模現役 Skill 庫中進行長期的版本遷移壓力測試。

## 優化空間

* **大幅減少人類的認知負擔（防止審查疲勞）**：
  * **現況痛點**：根因報告與藍圖資訊量過大，帶來嚴重的資訊過載；審核次數過多容易讓人失去專注，最終淪為「盲目成立」（橡皮圖章）。
  * **改進方案**：Orchestrator 應提煉高密度的「精簡決策摘要」，默認處理純格式問題，只在架構分歧與破壞性變更時才向人類提問確認。
* **以實測失敗為唯一依據，避免憑空修改與疊床架屋**：
  * **現況痛點**：容易在沒有真實錯誤的情況下過度優化，導致問題越修越多、SOP 流程膨脹。
  * **改進方案**：堅持「無實跑紅燈不修」原則；唯有在 `tmp/verify/` 的真實專案實測中出現具說服力的失敗案例時，才啟動 Skill 工程流程。
* **將機械判斷全面抽離為 Python 腳本，降低 Token 消耗與執行延遲**：
  * **現況痛點**：規則越做越細導致執行時間大幅拉長，LLM 額度迅速耗盡。
  * **改進方案**：將語法檢查、填位符對齊、結構驗證等機械邏輯全面下放給單檔 Python 腳本（Deterministic Scripts），把寶貴的大模型上下文保留給高階推理與創意設計。
