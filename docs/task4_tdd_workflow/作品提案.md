# 道館四作品提案:colab-gpu-bridge

> 狀態:提案(2026-11-09),尚未進 `/specify`。專案資料夾目前只有 `git init`。

## 想做什麼

本地服務加一個 UI,把 Google Colab 的執行環境當成一台有 GPU 的虛擬機來用(T4 約 15GB VRAM):

- 在 Colab 上跑 Ollama 與開源模型,本地電腦透過通道(SSH 等)呼叫它,用 Colab 的算力跑本地化模型服務。
- 從 UI 連到或自動開啟 Colab notebook。
- 模型快取在 Google Drive,讓 Colab 從 Drive 取模型,縮短下載時間。

## 第一個迭代的範圍(已拍板)

**工作階段管理 + 模型目錄**:本地 UI 與後端負責開啟、重連、結束工作階段,顯示狀態,選模型,顯示 Drive 快取狀態。Colab、Drive、通道藏在 adapter 後面,自動化測試用替身,最後做一次真實實跑。

建議做法:使用者手動開 notebook,由 notebook 向本地後端報到。自動開啟與 Drive 快取留到後續迭代。

## 為什麼適合這次作業

- 有真的全端,也有清楚的狀態轉換(啟動中、就緒、被收回、重連、餘額歸零停用),適合一個案例一個案例走紅綠燈。
- 外部依賴都在系統邊界上,正好符合「Mock 僅限系統邊界」。
- 題目引導問「測試通過真的代表功能做到了嗎?」:替身全綠,不代表真的 runtime 被收回時偵測得到。這正好用來展示 testplan 的「每個替身至少一次實跑」(作業三 verify-plan 內化後的做法)。

## 已知約束

來源:Colab 官方 FAQ(research.google.com/colaboratory/faq.html),2026-11-09 讀取,頁面沒有標日期。

- 使用者方案是 **Colab Pro(每月 100 compute units)**。免費方案限制「remote control such as SSH shells, remote desktops」與「bypassing the notebook UI to interact primarily via a web UI」;付費且**餘額為正**才解除,餘額歸零會回到免費方案的限制。所以規格要寫出餘額歸零時怎麼處理。
- 所有方案都禁止「connecting to remote proxies」與「web service offerings not related to interactive compute」。反向通道算不算其中之一,條文模糊,列為風險。
- notebook 最長 12 小時(Pro+ 24 小時),閒置會被回收,時限不公開,所以 runtime 隨時可能消失。
- 掛載 Drive「usually require that users manually grant this access every time they connect to a new runtime」,和「全自動開啟」衝突。
- 用程式或 headless 開 notebook,FAQ 沒有提到。

## 開工前要先驗證(technical-research)

1. **手動 spike(約半小時)**:Colab Pro 跑 Ollama 加一條通道,桌機連得到。這是整個題目的前提。
2. 消費版 Colab 有沒有能用程式開 runtime 的官方途徑(尚未查證)。
3. T4 每小時消耗多少 compute units,100 單位實際能跑幾小時(實測,不先猜)。
4. Drive API 抓模型與 Ollama 直接下載的速度比較(同一家雲內傳輸是否較快,條文沒寫)。
