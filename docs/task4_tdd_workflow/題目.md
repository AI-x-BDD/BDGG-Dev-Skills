# 做出自己的 AI x TDD Workflow

第四章中，我們把 TDD 加入原本的 SDD Workflow：

```text
/specify（需求規格）
→ /technical-research（技術研究）
→ /system-analysis（系統分析）
   ├─ /api-plan（介面規劃）
   ├─ /data-plan（資料規劃）
   └─ /ui-plan（畫面規劃）
→ /testplan（測試計畫）
→ /tasks（任務拆解）
→ /implement（依任務實作）
   └─ /tdd（測試驅動開發）：紅燈 → 綠燈 → 重構
```

系統分析會依需求與依賴順序調度三支 Planner。測試計畫交給任務拆解，將每個測試切片拆成紅燈、綠燈、重構任務，再由實作逐任務呼叫 TDD 的對應步驟；完整驗收另依測試計畫執行。

## 第一題：做出自己的 AI x TDD Workflow

請參考第四章的 Skill Workflow，沿用前面道館做出的 Skills，做出自己的 AI x TDD Workflow。把測試計畫接進任務拆解，讓實作能依任務使用 TDD。已經能沿用的 Skills 不必重做；需要建立或調整的部分，可以使用自己做出的 /skill-engineering（技能工程）。

### 第一題完成條件

- 測試計畫能交給任務拆解，任務能交給實作使用。
- 實作能依任務完成紅燈、綠燈與重構，並執行對應的完整驗收。

## 第二題：用自己的 AI x TDD Workflow 完成全端開發

請選擇一個前後端系統，用第一題的 Workflow 完成開發與測試，至少全端能 work。可以延續前面道館的系統，也可以換另一個系統；自己的 Workflow 繼續沿用。

語言與測試框架自由，測試依需求選擇，不要求單元測試、後端 E2E 與前端 E2E 全部做一遍。實際使用時，觀察 Skills 的產出與執行是否符合預期，再調整需要改善的地方；不固定迭代次數。

### 第二題完成條件

有使用自己的 Workflow 完成的全端作品，以及作品與測試的執行方式、實際測試結果。

## 第三題：改進自己的 AI x TDD Workflow

請改進 /testplan（測試計畫）或 /tdd（測試驅動開發）這支 Skill；也可以針對整個 AI x TDD Workflow 提出改進方案，說明為了做到測試驅動開發、提高可靠度，哪些地方需要改進。

從第二題的實際使用結果出發，先對照課程 Skill 的 SOP、Rules 與 Templates，找出目前的做法與你預期的結果有什麼差異，再決定改進哪支 Skill，或調整哪些步驟的配合。課程已經有的相同做法，不當成自己的新增能力。

請說明要解決什麼問題、為什麼這樣改，以及預期如何幫助測試驅動開發或提高可靠度。將改進用在作品中，再以實際結果說明用途、強項與弱項。若方案需要加入新 Skill，請指出放在哪個現行 Skill 之後，以及如何與前後步驟配合。

越通用越好，但也接受局限情境最佳化，只要說得出用途。

可以沿用前面道館的專案、Skills 與關注方向。本館請依新的學習重點，找出仍需要改進的地方，完成新增或改寫，並實際使用。不能只把上一館完全相同的成果重新提交；但本館前兩題已完成的改進，可以直接算入，不必再做一次。

### 引導！可以這樣思考（這是最重要的學習過程，也是提升競爭力的關鍵練習）

先想一想：TDD Workflow 是如何提高可靠度的？

測試計劃先把需求轉成具體的測試意圖、前置條件、操作與預期結果，讓 AI 少一點自行猜測；任務拆解與實作再依照這份計劃，以小步驟完成紅燈、綠燈與重構。紅燈先確認測試會因為預期的功能尚未完成而失敗，綠燈用最小實作讓測試通過，重構後再執行測試，確認原有行為仍然成立。這樣每一步都有實際執行的自動化測試提供回饋，AI 可以依失敗結果修正，後續修改也能重跑測試，檢查是否破壞已完成的功能。不過，可靠度仍取決於測試是否符合需求、是否涵蓋重要情境，以及是否真的執行；測試漏掉或測錯的地方，即使全部通過，也不能證明功能正確。

從實際使用自己的 AI x TDD Workflow 的經驗出發，思考以下問題：

- **哪些地方還需要 AI 自己猜？**
  看你的測試計劃，AI 能不能清楚知道要測什麼、怎麼測、怎麼判斷結果？還是需要自行補上你的意思，才寫得出測試？
- **換一個新對話，還能做到嗎？**
  不依賴前一段對話，只讀 Workflow 產出的文件，AI 還能寫出符合你原本測試意圖的測試，並繼續完成 TDD 嗎？
- **測試通過，真的代表你想要的功能做到了嗎？**
  有沒有只檢查回應，卻沒確認資料或系統狀態真的正確？有沒有重要的情境，現有測試方式還沒涵蓋？
- **這次成功，有哪些是 AI 自己想到的？**
  例如修改功能時，AI 恰好記得先調整測試計劃。這件事在你的 Workflow 中有被交代清楚嗎？哪些判斷值得寫進 Skill，讓下次也能做到？
- **你提出的改進，真的有助於測試驅動開發或提高可靠度嗎？**
  還是只是多增加文件、重複其他 Skill 的工作？有時候，刪掉重複或沒有幫助的內容，也是一種改進。

課程提供的 Skill 已經處理了其中大部分問題。請先檢查現有內容與實際執行結果，再選擇你認為仍需要改進的地方，說明它在什麼情境下會造成什麼問題，以及你的改進如何解決這個問題。

### 第三題完成條件

已改進 /testplan（測試計畫）、/tdd（測試驅動開發），或依提案改進整個 AI x TDD Workflow 的相關部分，並用在作品中。能說明問題、具體改動、理由、實際結果與強項弱項，以及改進與測試驅動開發、可靠度的關係。
