### Source Code (repository root)

```text
package.json                 # npm workspaces: shared, backend, frontend, e2e;"type": "module"
tsconfig.json
.gitlab-ci.yml

shared/
└── src/                     # 前後端共用的純函式(幾 A 幾 B、祕密數字格式)

backend/
├── src/
│   ├── http/                # 送前端建置產物、把 WebSocket 升級;E3 部署與網路的入口
│   ├── ws/                  # E2 後端 WebSocket 訊息協定:連線、心跳、訊息驗證與推送
│   ├── rooms/               # 用例:配對、座位、房主轉移、對局與計時
│   ├── views/               # 每位玩家各自的視圖
│   └── domain/              # 不依賴 I/O 的純函式
└── test/

frontend/
├── src/
│   ├── pages/               # E1 前端畫面
│   ├── components/          # E1 前端可重用的互動
│   └── i18n/                # E1 介面文字(繁體中文)
└── test/

e2e/                         # 跨端點的端對端測試(多 browser context)

scripts/                     # 窮舉驗證與壓測

deploy/                      # E3 部署與網路
```

**Structure Decision**: 前後端分成不同 workspace,但打包成**同一個 image**:`node:http` 在同一個 port 送前端的建置產物,並把 WebSocket 連線升級。好處是同源,不用處理 CORS,前面若有反向代理也只要一個入口。沒有資料庫:房間、玩家與對局都在單一 Node 行程的記憶體裡,配對靠 event loop 的同步執行保證原子性(research R3)。

後端分層是 `http → ws → rooms → (views | domain)`:`http/` 只送靜態檔與升級連線;`ws/` 是 E2 的轉接,驗證玩家送來的訊息、維持心跳、把推送送出去;`rooms/` 是用例,持有記憶體裡的狀態與計時器;`views/` 依玩家各自產生視圖,祕密數字只可能從這裡外洩;`domain` 是不依賴 I/O 的純函式,讓核心邏輯可以用 < 100ms 的單元測試涵蓋。

前端照畫面分 `pages/`,可重用的互動(倒數、猜測紀錄、玩家名單)放在 `components/`,介面文字集中在 `i18n/`。

## 分析流程規劃

> 本段排定分析的順序與每一步指派的 planner;分析由 Phase 3 照波段交給 sub agent 執行,產出寫在 Documentation 樹列的路徑。

### 端點盤點

這次需求涉及 3 個端點。每個端點視為一個獨立系統,分析的對象是它對外的介面:

| # | 端點 | 介面 | 需求出處 |
|---|---|---|---|
| E1 | 前端(瀏覽器,原生 HTML / CSS / JS) | 畫面與互動:畫面、每個畫面的狀態、倒數與輪到誰的顯示、輸入驗證的提示、詞彙、桌機與手機的版面 | FR-001、FR-004、FR-005、FR-006、FR-008、FR-009、FR-010、FR-012、FR-013、FR-015、FR-019、NFR-004、SC-001 |
| E2 | 後端(Node.js 22、`ws`) | WebSocket 訊息協定:玩家送出的操作、伺服器推送的事件、錯誤、推送對象與每位玩家各自的視圖、重連與心跳 | FR-001–FR-019、NFR-001、NFR-002、NFR-003、NFR-005、SC-002、SC-003、SC-005、SC-006 |
| E3 | 部署與網路(Docker、反向代理) | 對外入口:port、靜態檔與 WebSocket 升級的路徑、反向代理的 Upgrade 轉發與閒置逾時 | SC-002、SC-003、Assumptions(線上多人可連入、部署位置不在範圍內) |

### 分析波段

排序原則:**一個介面排在它所依賴的介面都分析完之後**;同一波裡的介面彼此不依賴,可以各開一個 sub agent 平行分析。

第三方端點的介面是對方定好的,我們只能照著接、不能改,所以它不依賴我們任何一個介面;
反過來,我們這邊碰到它的介面都要遷就它。因此**第三方端點排在最前面**,依賴它的介面往後推一波。

| Wave | 步驟 | 介面 | Planner | 平行 | 排在這一波的理由 |
|---|---|---|---|---|---|
| 1 | S1 | E1 前端畫面與互動 | ui-plan | ✅ 與 S2 平行 | 直接由使用者故事推出,不依賴其他介面 |
| 1 | S2 | E2 後端 WebSocket 訊息協定 | api-plan | ✅ 與 S1 平行 | 直接由 FR 推出;前端與後端以同一份需求為準,不必等對方 |
| 2 | S3 | E3 部署與網路 | deploy-plan | — | 要開哪個 port、哪一條路徑要升級成 WebSocket、反向代理的閒置逾時要多長,要等 S2 的連線入口與心跳定下來 |

共 2 個 wave、3 個步驟:Wave 1 兩個介面平行,Wave 2 一個介面。
