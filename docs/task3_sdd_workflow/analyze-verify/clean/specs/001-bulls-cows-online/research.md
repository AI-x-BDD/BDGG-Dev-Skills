## R1. 即時通訊方式(NFR-003、SC-002、FR-016)

**決策**: 瀏覽器用原生 `WebSocket`,伺服器用 `ws` 8;所有房間事件(名單、輪到誰、猜測結果、倒數截止)都由伺服器主動推送,玩家的操作(配對、離開、設定祕密數字、猜測)也走同一條連線。

**理由**:

- 判斷:spec 的每個操作都要在 1 秒內推到同房所有人(SC-002),而且玩家也要送資料上來;雙向、常駐的連線最直接。
- 實測(桌機 i5-9400F,Node v22.23.2,`ws` 8.22.0,本機 loopback,400 個 client):廣播 p95 9.75ms,遠低於 1 秒(數字與量法見 R8)。
- 實測(同一台桌機,Node v22.23.2):`typeof WebSocket` 是 `function`,Node 22 內建 WebSocket client,測試與壓測不必再裝 client 套件。
- 判斷:Socket.IO 提供的房間與重連功能,本專案都要自己依 spec 規則實作(座位、房主轉移、60 秒保留),用不到它的抽象,還要多一個前端 runtime 依賴。

**考慮過的替代方案**:

- SSE + HTTP POST:下行推送可以,但操作要另走 POST,斷線判定要合併兩條通道的狀態。
- Socket.IO:多一個前端 runtime 依賴,房間與重連規則仍要自己寫。
- 輪詢:1 秒內反映要每秒輪詢,400 位玩家等於每秒 400 個請求,大多是空回應。

## R2. 後端執行環境(憲法原則 I、NFR-005)

**決策**: Node.js 22 LTS 直接執行 TypeScript(原生 type stripping,不設編譯步驟),用 `node:http` 提供前端建置產物並把 `/ws` 升級成 WebSocket;不用 HTTP 框架。

**理由**:

- 實測(桌機,Node v22.23.2):`node server.ts` 直接跑起探針伺服器;只出現 `MODULE_TYPELESS_PACKAGE_JSON` 警告,在 `package.json` 加 `"type": "module"` 即可消除。
- 判斷:後端只有兩件事:送靜態檔、處理 WebSocket 訊息。沒有 REST 資源,框架的路由與 schema 驗證派不上用場;訊息驗證寫成純函式即可,也方便單元測試。
- 判斷:TypeScript 嚴格模式滿足憲法原則 I 的型別要求;type stripping 讓測試與執行跑的是同一份原始碼。

**考慮過的替代方案**:

- Fastify / Express:只為了送靜態檔,多一層依賴。
- Go、Elixir:對這個規模沒有必要,前後端也就無法共用祕密數字格式與 A/B 計算的程式碼。

## R3. 狀態存放與配對的原子性(FR-002、FR-003、FR-007、邊界情況)

**決策**: 房間、玩家與對局都放在**單一 Node 行程的記憶體**裡,不用資料庫;配對函式整段同步執行,中間不出現 `await`,靠 event loop 保證同時配對不會交錯。

**理由**:

- 判斷:spec 明確不保留戰績與歷史對局,房間關閉後紀錄即可捨棄;沒有需要持久化的資料。
- 實測(桌機,Node v22.23.2,`ws` 8.22.0,400 個 client 同時連線並送出配對):結果是 100 間房、每間最多 4 人、只有 1 人的房間 0 間。
- 實測(同一組 400 個 client,對照組:在配對的「找房」與「入座」之間插入 5ms 的 `await`):只開出 4 間房,最大一間 299 人。證明上面那組測試測得到「同時配對」的錯誤,也說明配對中間不能有 `await`。
- 判斷:FR-003 因此要用一條測試守住:「配對函式不得是 async」由 lint 規則或型別簽名約束,再加上 400 人同時配對的整合測試。

**考慮過的替代方案**:

- Redis / MySQL 存房間:要另做分散式鎖或交易才能保證 FR-003,而 spec 不需要持久化。
- 多個行程或多台機器:R8 實測單一行程負載很低,不需要水平擴充。

## R4. 計時器與可測試的時鐘(FR-010、FR-015、FR-016、憲法原則 II)

**決策**: 每個計時(設定祕密數字 60 秒、回合 60 秒、斷線保留 60 秒)都由伺服器記下截止時間並用 `setTimeout` 觸發;推給前端的是「剩餘毫秒數」,前端只負責顯示倒數。單元測試用 `node:test` 的 `mock.timers` 快轉,不等真實時間。

**理由**:

- 判斷:NFR-005 要求限制由伺服器決定;倒數若放在前端,改瀏覽器時間就能拖延回合。
- 判斷:推剩餘毫秒數而不是絕對時間,玩家電腦的時鐘不準也不影響顯示。
- 實測(桌機,Node v22.23.2,`node --test`):`mock.timers.enable({ apis: ['setTimeout', 'Date'] })` 後 `tick(59_999)` 不觸發、再 `tick(1)` 觸發,`Date.now()` 為 60000;整個測試檔含啟動 92ms,符合原則 II「單元測試 100ms 內、不依賴真實時鐘」。
- 實測(同一次執行):Node 22 會印出 `The MockTimers API is an experimental feature` 警告,功能正常。

**考慮過的替代方案**:

- 前端計時、逾時由前端通知伺服器:違反 NFR-005。
- 每間房一個每秒執行的 `setInterval`:400 位玩家時要不斷喚醒,而且測試仍要快轉時鐘。
- `@sinonjs/fake-timers`:`node:test` 內建的功能已足夠,不多加依賴。

## R5. 斷線偵測與重連身分(FR-016、FR-017、邊界情況:重新整理)

**決策**:

- **重連身分**:進房時伺服器發一組隨機的重連 token(`crypto.randomUUID()`),前端存在 `sessionStorage`。重新整理或重開連線時帶上 token,60 秒內就回到原座位。
- **斷線偵測**:WebSocket 的 `close` 事件立即判斷斷線;另外每 15 秒送一次 ping,沒收到 pong 就主動斷開,用來處理沒有送出關閉訊號的斷線。
- **保留時間**:60 秒從「最後一次確認在線」起算,不從偵測到斷線的時間起算。

**理由**:

- 實測(桌機,Node v22.23.2,`ws` 8.22.0,client 行程被 `SIGKILL`,重複 3 次):伺服器在 14.3–15.5ms 內收到 `close`(code 1006)。關掉分頁、重新整理屬於這一類。
- 查證(`ws` 8.22.0 README〈How to detect and close broken connections?〉):拔網路線這類斷線兩端都不會察覺,要用 ping/pong 偵測。
- 判斷:用 `sessionStorage` 而不是 `localStorage`:同一台電腦開 5 個分頁測試時(spec US1 的獨立測試),每個分頁要是不同的玩家;`localStorage` 會讓 5 個分頁共用同一個身分。
- 判斷:沒有送出關閉訊號的斷線,最晚 30 秒才偵測到;保留時間從最後一次 pong 起算,玩家實際得到的保留時間仍是 60 秒,不會變成 90 秒。

**考慮過的替代方案**:

- 用暱稱辨識重連:暱稱可以重複(FR-005),別人能冒用。
- cookie:要多處理同站多分頁共用的問題,效果跟 `localStorage` 一樣。

## R6. 祕密數字不外洩(NFR-002、SC-005、FR-010)

**決策**: 伺服器不廣播整份對局狀態,而是**依玩家各自產生一份視圖**再送出:視圖只含自己的祕密數字;別人的祕密數字只在遊戲結束後才放進視圖。A/B 由伺服器計算;逾時代設的祕密數字用 `crypto.randomInt` 產生,只送給本人。

**理由**:

- 判斷:SC-005 是用開發者工具檢查「其他玩家能取得的所有資料」,所以不能只在畫面上不顯示;資料一進瀏覽器就算外洩。
- 判斷:「每人一份視圖」讓外洩只可能發生在一個函式裡,測試只要守住這一個函式:對每位玩家的視圖,斷言其中不含其他人的祕密數字。
- 判斷:端對端測試再加一道:收集每個分頁收到的所有 WebSocket 訊息原文,搜尋其他玩家的祕密數字字串,結束前命中必須是 0。

**考慮過的替代方案**: 廣播共用狀態再由前端過濾(資料已經進了別人的瀏覽器)、加密祕密數字再送出(金鑰也在前端,等於沒加密)。

## R7. 幾 A 幾 B 的計算與正確性(FR-009、FR-012、SC-004)

**決策**: A/B 計算寫成前後端共用的純函式 `score(secret, guess)`。單元測試列出 spec 的案例與邊界案例;另外寫一支**窮舉驗證腳本**,拿另一種寫法的參考實作比對所有合法組合,在 CI 執行。

**理由**:

- 實測(桌機,Node v22.23.2):合法的 4 位數字共 5,040 組,窮舉 5,040 × 5,040 = 25,401,600 組,與參考實作比對不一致 0 組,耗時 5.8 秒;spec 的例子 `score('1234', '1356')` 得到 1A1B。
- 實測(同一支腳本,對照組:故意讓其中一組的 B 多 1):不一致 1 組。證明窮舉比對抓得到單一組的錯誤。
- 判斷:5.8 秒超過原則 II 的「單元測試 100ms」,所以窮舉放在獨立腳本,不放進單元測試。

**考慮過的替代方案**: 只靠手列案例(SC-004 要求 100% 正確,窮舉才能證明全部組合)、隨機抽樣的 property-based test(組合只有 2,500 萬組,直接窮舉更簡單也更完整)。

## R8. 容量:400 位玩家時的推送延遲(SC-002、SC-003、憲法原則 IV)

**決策**: 單一 Node 行程即可承擔 100 間房、400 位玩家,不做水平擴充;延遲預算以 SC-002 的 1 秒為準,伺服器端處理目標 p95 ≤ 200ms(原則 IV 的後端預設)。

**理由**:

- 實測(桌機 i5-9400F 6 核,Node v22.23.2,`ws` 8.22.0,本機 loopback;壓測程式與伺服器在同一台機器;400 個 client 分成 100 間房,每個 client 每秒送 1 次訊息、伺服器轉發給同房 4 人,持續 20 秒):

| 指標 | 結果 |
|---|---|
| 送達次數 | 30,400 |
| p50 / p95 / p99 | 0.75ms / 9.75ms / 12.31ms |
| 最大值 | 16.23ms |
| 伺服器 RSS | 約 90MB |
| 伺服器平均 CPU | 11.8% |

- 估算(真實遊戲每間房同一時間只有 1 人能猜,每回合最多 60 秒):實際訊息量遠低於壓測的「每人每秒 1 次」,壓測是上限情境。
- 估算(行動網路單程延遲以 100ms 計):網路延遲加上伺服器 p99 約 12ms,仍遠低於 1 秒。
- 判斷:loopback 量不到網路與反向代理的延遲,要在部署環境重測(見「待驗證」)。

**考慮過的替代方案**: 多行程加 Redis pub/sub 廣播(實測負載不需要,還會破壞 R3 的單行程原子性)。

## R9. 前端技術(NFR-004、憲法原則 III、憲法原則 IV)

**決策**: Vite + 原生 HTML / CSS / JS,不用框架;型別用 JSDoc 加 `tsc --noEmit --checkJs` 檢查。介面文字集中在 `i18n/zh-TW.json`,視覺數值集中在 `tokens.css`,用 RWD 同時支援桌機與手機。

**理由**:

- 判斷:畫面只有 3 個:輸入暱稱、房間(等待中)、對局;狀態全由伺服器推送,前端只負責把視圖畫出來,不需要框架的狀態管理。
- 判斷:沒有前端 runtime 依賴,首次載入的 JavaScript 不可能接近原則 IV 的 200KB 上限;建置後仍用 gzip 大小檢查守住。
- 查證(npm registry,2026-10-18 `npm view vite version`):目前版本 8.3.4。
- 判斷:原則 III 要求的四種狀態(載入中、空資料、錯誤、成功)在這裡對應到:連線中、等待其他玩家、連線失敗或被拒、正常。

**考慮過的替代方案**: React / Vue / Svelte(3 個畫面用不到,還會增加 bundle)、Socket.IO client(見 R1)。

## R10. 測試工具(憲法原則 II、SC-001–SC-006)

**決策**:

- **單元與整合**:`node:test`(內建,含 R4 的 `mock.timers`),前後端共用的純函式也用它測。
- **端對端**:`@playwright/test`,一個測試開多個 browser context 當成多位玩家。
- **計時設定**:60 秒的各項時限做成設定值;端對端測試用短時限跑,單元測試用快轉時鐘驗證真正的 60 秒。
- **窮舉與容量**:R7 的窮舉腳本與 R8 的壓測腳本放在 `scripts/`,由 CI 執行。

**理由**:

- 實測(桌機,Node v22.23.2):`node --test` 直接執行 `.ts` 測試檔,不需要額外的測試框架或編譯。
- 判斷:spec 的獨立測試都是「多個瀏覽器分頁」,Playwright 的多個 browser context 正好對應,而且每個 context 的 `sessionStorage` 各自獨立(配合 R5)。
- 查證(npm registry,2026-10-18 `npm view @playwright/test version`):目前版本 1.64.1。

**考慮過的替代方案**: Vitest + jsdom(前端沒有框架,邏輯都是純函式,`node:test` 就夠)、Cypress(多分頁測試不方便)。

## R11. 交付與部署(憲法品質關卡、假設:部署不在規格範圍)

**決策**: 打包成**一個** Docker image(`node:22-slim`),同一個 port 送前端檔案與 WebSocket;CI 依序跑 lint、型別檢查、單元測試、窮舉驗證、端對端測試、建置。部署在哪裡、要不要對外開放,依 spec 不在本次決定。

**理由**:

- 判斷:沒有資料庫、沒有系統套件依賴,一個 image 就能跑;前端與 WebSocket 同源,不用處理 CORS。
- 判斷:spec 的假設寫明部署位置不在範圍內,這裡只保證「任何能跑容器、能轉發 WebSocket 的環境」都能部署。
- 判斷:前面若有反向代理,必須轉發 WebSocket 的 Upgrade 標頭,並把閒置逾時設得比 R5 的 ping 間隔(15 秒)長。

**考慮過的替代方案**: 前後端分成兩個 image(多一個 proxy 設定,還要處理跨來源)、serverless(WebSocket 長連線與記憶體內狀態不適合)。
