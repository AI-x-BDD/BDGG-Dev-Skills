# 自己做出 SDD workflow，再用真實開發持續優化

我們在第三章中，學到了如何參考 SpecKit 的 skill，從中進行「基因工程」，並透過老大哥 `/skill-engineering` 自主打造一條更細膩的 SDD workflow。

本道館不會直接給你完成版的 Skills。請依照影片的工作流程，使用你在道館二完成的 `/skill-engineering`，自己把整條 SDD workflow 幹一次。

接著，你要用這套 SDD workflow 來開發一個前後端系統。在 5～10 次完整迭代中持續使用、觀察與優化自己的 Skills，最後再試著加入自己的想法、創建新的 Skill 放進這個流程中。（也就是所謂的 Dogfooding，自己吃自己的狗食，從自己的使用過程中來打造更好的 workflow）

本道館共有四題：

1. 做出自己的 SDD workflow。
2. 做出 `/constitution`（憲法）、`/clarify`（澄清）與 `/analyze`（分析）三支輔助 Skills。
3. 使用自己的 SDD workflow 完成 5～10 次前後端系統迭代，並持續優化 Skills。
4. Dogfooding：從自己的開發過程發現可以補足的地方，再發明一支新的 Skill 加入 workflow，來解決問題。

---

## 第一題：做出自己的 SDD workflow

請依照第三章影片的 workshop 方法，完成以下八支 Skills。

每支 Skill 都先定義它要產出的 Artifact。請先做出一份可以檢查的產出物範例，根據範例調整內容與結構，再使用 `/skill-engineering` 反推這支 Skill 需要的 SOP、Rules、Templates 與 Scripts。

### 第一支：`/specify`（需求規格）

這支 Skill 負責把開發需求整理成明確的規格產出物。它要寫清楚需求目標、使用情境、功能範圍、業務規則，以及仍然需要確認的細節。

### 第二支：`/technical-research`（技術可行性分析和決策研究）

這支 Skill 負責在系統規劃前完成技術研究與技術決策。它要針對需求查找可行方法、比較選項、記錄取捨，並把已拍板的技術選擇交給後續規劃使用。

### 第三支：`/system-analysis`（系統分析的 orchestrator）

這支 Skill 負責對整體系統做初步分析。它要先盤點系統介面、資料、API 與 UI，再判斷哪些面向需要交給對應的 Planner Skill 深入處理。

`/system-analysis`（系統分析）需要調度以下三支 Planner Skills，而不是自己完成所有詳細規劃。

### 第四支：`/api-plan`（API 規劃）

這支 Skill 負責分析後端 API、請求與回應、錯誤處理，以及系統之間的介面。

### 第五支：`/data-plan`（資料規劃）

這支 Skill 負責分析資料模型、資料關係、狀態變化、儲存方式與資料一致性。

### 第六支：`/ui-plan`（UI 規劃）

這支 Skill 負責分析頁面、操作流程、畫面狀態、互動方式與前後端資料需求。

### 第七支：`/tasks`（任務拆解）

這支 Skill 負責讀取需求規格、技術研究與系統分析的產出，再把開發工作拆成可以依序執行的 tasks。每一個 task 都要能指回它負責的需求與系統規劃。

### 第八支：`/implement`（實作）

這支 Skill 負責依照 tasks 逐項開發。它要一次取得下一個可執行 task，完成程式碼與必要驗證，記錄完成結果，再繼續下一個 task。

### 第一題完成條件

請確認你已經完成：

- [ ] `/specify`（需求規格）。
- [ ] `/technical-research`（技術可行性分析和決策研究）。
- [ ] `/system-analysis`（系統分析）。
- [ ] `/api-plan`（API 規劃）、`/data-plan`（資料規劃）與 `/ui-plan`（UI 規劃）。
- [ ] `/tasks`（任務拆解）。
- [ ] `/implement`（實作）。
- [ ] 每支 Skill 都有清楚的輸入、產出、使用時機與職責。
- [ ] `/system-analysis`（系統分析）可以依需求調度三支 Planner Skills，而不是自己完成所有詳細規劃。
- [ ] 前一個步驟的產出能直接交給下一個步驟使用。

## 第二題：做出三支輔助 Skills

SDD workflow 除了主要開發步驟，還需要三支可以在適當時機介入的輔助 Skills。

### `/constitution`（憲法）

這支 Skill 負責管理整個專案需要共同遵守的原則與各支 Skills 對應的規則。請讓 workflow 中需要使用這些規則的 Skills 主動讀取它們，並在規則更新後檢查相關 Skill 與產出物是否仍然一致。

### `/clarify`（澄清）

這支 Skill 負責判斷需求或產出物有哪些細節不足，再從不同面向提出問題。它要在取得回答後，把答案寫回正確的產出物，讓後續步驟可以繼續執行。

### `/analyze`（分析）

這支 Skill 負責在實作前交叉檢查需求規格、技術決策、系統分析與 tasks。它要找出互相矛盾、遺漏、無法追溯或無法實作的地方，並指出應該回到哪一個步驟修正。

### 第二題完成條件

請確認你已經完成：

- [ ] `/constitution`（憲法）、`/clarify`（澄清）與 `/analyze`（分析）的完整 Skill packages。
- [ ] 每支輔助 Skill 都寫清楚什麼情況會被呼叫，以及完成後要修改哪一份產出物。
- [ ] `/clarify`（澄清）至少實際完成 3~5 次提問與回寫。
- [ ] `/analyze`（分析）至少實際找出一次跨產出物的問題，並完成修正。
- [ ] `/constitution`（憲法）至少有一條規則被 SDD workflow 中的 Skill 主動讀取與遵守。

## 第三題：用自己的 SDD workflow 開發一個更複雜的前後端系統

請選擇並開發一個前後端系統。它的複雜度必須高於課程示範的 1A2B（猜數字遊戲）線上對戰平台，好比一個資訊系統、課程平台等等。

你需要說明這個系統為什麼更複雜。請至少從兩個面向比較，例如業務規則、角色與權限、狀態變化、即時或非同步互動、資料模型、外部系統整合、前端操作流程。

請把系統拆成 5～10 次功能迭代。每一次迭代都要完整執行：

```text
/specify
→ /technical-research
→ /system-analysis
   → /api-plan
   → /data-plan
   → /ui-plan
→ /tasks
→ /analyze
→ /implement
```

`/clarify`（澄清）與 `/constitution`（憲法）不必被限制在固定位置。請在需求不清楚或需要檢查共同規則時呼叫它們。

每次迭代完成後，請檢查自己的 Skills 是否真的按照預期工作。

並仔細觀察不順暢或是產出內容不精準的地方，請使用 `/skill-engineering` 來優化 SDD workflow。

請為每一次 Skill 優化留下以下紀錄，並儲存於 git commit 紀錄中：

- 哪一支 Skill 發生了什麼問題。
- 你原本預期它產出什麼結果。
- 你判斷的根因是什麼。
- 你修改了哪一個部位。
- 修改後再次執行的結果。

完成 5～10 次迭代後，請整理你觀察到的 SDD 流程不足。請寫出問題發生在哪一個步驟、它造成什麼影響，以及你已經嘗試過哪些優化。

### 第三題完成條件

請準備以下內容：

- [ ] 一個可以實際執行的前後端系統。
- [ ] 5～10 次從 `/specify`（需求規格）到 `/implement`（實作）的迭代紀錄。
- [ ] 每次迭代對應的規格、研究、系統分析、tasks 與程式碼變更。
- [ ] 使用 `/skill-engineering` 優化 Skills 的前後差異與 git commit 紀錄。

## 第四題：從 SDD 流程的不足發明一支新的 Skill

請找出一件既有 SDD workflow 比較做不到，或流程上沒有讓 AI 花費足夠注意力處理的事情。

接著，請發明一支新的 Skill，並把它放在 workflow 的某一個步驟之後。這支 Skill 要讓 AI 在進入下一個步驟前，花更多注意力去規劃或處理你發現的問題。

你可以從以下方向發想，但不必限制在這些題目：

- **Observability**：在系統分析後，專門規劃 logs、metrics、traces 與故障判讀方式。
- **資安**：在系統分析後，專門檢查身分驗證、權限、敏感資料、輸入風險與攻擊面。
- **Pencil UI**：在 `/ui-plan`（UI 規劃）後，使用 Pencil 畫出可以檢查與修改的 UI，再把結果交給 tasks。
- **架構與模組分析**：在系統分析後，進一步分析模組邊界、依賴方向、變更影響與可替換性。

### 第四題完成條件

請確認你已經完成：

- [ ] 說明既有 SDD workflow 為什麼沒有充分處理它。
- [ ] 說明新 Skill 應該放在哪一個步驟之後，以及它會讀取什麼、產出什麼。
- [ ] 完成新 Skill 的 Skill package。
- [ ] 把新 Skill 接進自己的 SDD workflow。
- [ ] 使用第三題的系統實際執行新 Skill 一次。
- [ ] 比較加入新 Skill 前後的結果。
