# Rule 1 [must] - 提問時列出每一步與它已委派的腳本
- 問之前先用一張表列出目標 skill 的每一步:步驟位址、那一行的原文、那一行執行的腳本(沒有就寫「沒有」)
- 為什麼:只問「要委派哪一步」,使用者答不出來;看到每一步的原文與動詞,才指得出哪一步做的是結果只由輸入決定的事、哪一步已經交給腳本了

## good example
- **先列出四步的原文與各自的腳本,再問**;使用者一眼看得出 Phase 1 Step 2 是在數東西,而且還沒有腳本
```
| 步驟 | 原文 | 執行的腳本 |
|---|---|---|
| Phase 1 Step 1 | Read 目標 skill 的 SKILL.md 與 `rules/` 底下的 Rule File。 | 沒有 |
| Phase 1 Step 2 | Think 統計每個 Rule File 的 Rule 條數與各條的強度。 | 沒有 |
| Phase 1 Step 3 | Think 依 `rules/體檢-規範.md` 判斷哪些 Rule 該拆、該併。 | 沒有 |
| Phase 1 Step 4 | Ask 提出體檢報告,問使用者要處理哪幾條。 | 沒有 |

要委派哪一步?腳本吃什麼、吐什麼?
```

## bad example
- 同一次提問,但**只丟出問題**;使用者得自己去翻 SKILL.md 和 `scripts/`,才知道有哪幾步、哪幾步已經在跑腳本
```
要委派哪一步(Phase N Step M)?腳本吃什麼、吐什麼?
```

# Rule 2 [must] - 提到的候選標明依據
- 提問時若提到可以委派的候選,每一個都標明依據是下表哪一種

| 依據 | 意思 |
|---|---|
| 實際遇到 | 跑流程時發生過:這一步每次的結果不一致,或花了很久 |
| 文字上看得到 | 讀那一行就看得出這一步的結果只由輸入決定 |
| 推測 | 還沒發生,文字上也看不出,只是想到 |

- 為什麼:三種混在一起,使用者會把推測當成已經發生的問題,替一個本來沒有事的步驟多維護一支腳本

## good example
- 兩個候選**各自標了依據**;使用者看得出第一個有憑據、第二個只是想到
```
- Phase 1 Step 2「統計 Rule 條數與強度」——文字上看得到:這一行做的是數標題,同樣的 Rule File 每次都該數出同樣的數字。
- Phase 1 Step 1「讀 Rule File」——推測:Rule File 很多的時候可能要讀很久,這支 skill 還沒跑過,只是想到。
```

## bad example
- 同樣兩個候選,但**沒有標依據**;兩個看起來一樣值得寫成腳本
```
- Phase 1 Step 2 可以委派「統計 Rule 條數與強度」。
- Phase 1 Step 1 可以委派「讀 Rule File」。
```

## good example
- 邊界:這一步還沒有實際數錯過,但**讀那一行就指得出它只是在數標題**,所以標「文字上看得到」
```
- Phase 1 Step 2「統計 Rule 條數與強度」——文字上看得到:這一行做的是數標題,同樣的 Rule File 每次都該數出同樣的數字。
```

## bad example
- 邊界:同一個候選,因為覺得「用讀的一定會數錯」就**標成實際遇到**;這支 skill 還沒有人跑過
```
- Phase 1 Step 2「統計 Rule 條數與強度」——實際遇到:每次數出來的條數都不一樣。
```
