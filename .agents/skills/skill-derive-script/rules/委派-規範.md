# Rule 1 [must] - 結果只由輸入決定的步驟才委派
- 那一步的結果只由輸入決定(同樣的輸入每次都該得到同樣的結果:計數、比對、轉檔、套公式)時,才委派給腳本
- 那一步需要判斷(該不該、好不好、選哪一種)時不委派,在回覆裡說明這一步要留給 agent 做,由使用者決定要不要改用 skill-derive-rule 替它加把關
- 為什麼:腳本只會照寫死的條件做;把判斷寫成腳本,寫的人當下想到的那幾種情況就成了全部,遇到沒想到的情況,腳本不會停下來,只會照樣給出一個結果

## good example
- 使用者要委派的是「判斷該拆、該併」,**所以不寫腳本,只在回覆裡指出這一步要留給 agent**
```
使用者:Phase 1 Step 3 判斷哪些 Rule 該拆、該併,寫成腳本吧。

scripts/ 不新增任何檔案

回覆:「該拆、該併」要讀懂每條 Rule 在管什麼才能決定,腳本做不到,這一步要留給 agent;需要的話請改用 skill-derive-rule 替這一步加把關。
```

## bad example
- 同一句話,但**把判斷寫成了腳本**;「bullet 超過三個就該拆」只是寫的人當下想到的一種情況,之後每一次都照這個條件判
```
使用者:Phase 1 Step 3 判斷哪些 Rule 該拆、該併,寫成腳本吧。

scripts/judge_rules.py
  if len(rule.bullets) > 3:
      verdict = "該拆"
```

## good example
- 邊界:這句話聽起來像審查,但**它要的只是比對兩個標題在不在**,同一個檔每次比對的結果都一樣,所以委派
```
使用者:Phase 2 Step 1「檢查每條 Rule 有沒有 good example 與 bad example 兩段」寫成腳本。

scripts/check_examples.py   ← 新開,逐條比對 `## good example` 與 `## bad example` 兩個標題
```

## bad example
- 邊界:同一句話,因為聽起來像審查就**沒有委派**;但標題在不在不需要判斷,留給 agent 用讀的,反而每次漏的不一樣
```
使用者:Phase 2 Step 1「檢查每條 Rule 有沒有 good example 與 bad example 兩段」寫成腳本。

scripts/ 不新增任何檔案

回覆:「檢查 example」屬於審查,需要判斷,這一步要留給 agent。
```

## good example
- 邊界:這句話看起來也只是檢查一個欄位,但**「是不是換句話說」要讀懂兩句話的意思**,所以不委派
```
使用者:Phase 2 Step 2「檢查每條 Rule 的『為什麼』是不是只把要求換句話說」也寫成腳本。

scripts/ 不新增任何檔案

回覆:「是不是換句話說」要讀懂要求與理由各自在講什麼,腳本做不到,這一步要留給 agent;需要的話請改用 skill-derive-rule 替這一步加把關。
```

## bad example
- 邊界:同一句話,因為提到「檢查欄位」就**寫成了腳本**;它只能算兩句話重複了幾個字,重複的字少、意思卻一樣的,一律放行
```
使用者:Phase 2 Step 2「檢查每條 Rule 的『為什麼』是不是只把要求換句話說」也寫成腳本。

scripts/check_why.py
  if overlap(rule.desc, rule.why) > 0.6:
      verdict = "換句話說"
```

# Rule 2 [must] - 一次委派只動一步與一支腳本
- 委派前後的差異只有兩處:指定那一步的那一行,以及那一步的腳本,樣子如下

```
首次委派(那一步還沒有在執行腳本)
  before  <M>. <動詞> <動作描述>
          scripts/ 底下沒有這一步的腳本
  after   <M>. Delegate 依 `rules/腳本執行-規範.md` 執行 `uv run scripts/<腳本名>.py <參數>` <取得什麼或留下什麼>
          scripts/<腳本名>.py   ← 新開

再次委派(那一步已經在執行腳本)
  before  <M>. Delegate 依 `rules/腳本執行-規範.md` 執行 `uv run scripts/<腳本名>.py <參數>` <取得什麼或留下什麼>
          scripts/<腳本名>.py   ← 已有的腳本
  after   <M>. Delegate 依 `rules/腳本執行-規範.md` 執行 `uv run scripts/<腳本名>.py <參數>` <取得什麼或留下什麼>   ← 參數有變才改
          scripts/<腳本名>.py   ← 改成這次要的處理
```

- 目標 skill 的其他步驟、其他腳本、所有 Rule File 與樣板都不動;要委派另一步,就再跑一次
- 目標 skill 第一次有腳本時,`rules/` 會多出 `腳本執行-規範.md`;那是 skill-form-script 補上的固定內容,不算動到別的步驟
- Rule File 裡若已經有 Rule 在講腳本接手的那件事,只在回覆裡提,由使用者決定要不要另外處理
- 為什麼:腳本是流程跑過之後才一步一步換上的,一次只動一步,換上之後結果哪裡變了,才對得回是哪一支腳本造成的

## good example
- 使用者指定 Phase 1 Step 2;**前後只差那一行與一支新的腳本**,Step 1、Step 3、Step 4 一字未動
```
before
  ## Phase 1: 提出體檢報告
  1. Read 目標 skill 的 SKILL.md 與 `rules/` 底下的 Rule File。
  2. Think 統計每個 Rule File 的 Rule 條數與各條的強度。
  3. Think 依 `rules/體檢-規範.md` 判斷哪些 Rule 該拆、該併。
  4. Ask 提出體檢報告,問使用者要處理哪幾條。

after
  ## Phase 1: 提出體檢報告
  1. Read 目標 skill 的 SKILL.md 與 `rules/` 底下的 Rule File。
  2. Delegate 依 `rules/腳本執行-規範.md` 執行 `uv run scripts/count_rules.py --skill <目標 skill 路徑>` 取得每個 Rule File 的 Rule 條數與各條的強度。
  3. Think 依 `rules/體檢-規範.md` 判斷哪些 Rule 該拆、該併。
  4. Ask 提出體檢報告,問使用者要處理哪幾條。

  scripts/
  └── count_rules.py   ← 新開
```

## bad example
- 同一次委派,但**順手把 Step 1 也換成了腳本**;使用者只指定了 Step 2,這一次就動了兩步與兩支腳本
```
before
  ## Phase 1: 提出體檢報告
  1. Read 目標 skill 的 SKILL.md 與 `rules/` 底下的 Rule File。
  2. Think 統計每個 Rule File 的 Rule 條數與各條的強度。
  3. Think 依 `rules/體檢-規範.md` 判斷哪些 Rule 該拆、該併。
  4. Ask 提出體檢報告,問使用者要處理哪幾條。

after
  ## Phase 1: 提出體檢報告
  1. Delegate 依 `rules/腳本執行-規範.md` 執行 `uv run scripts/list_rule_files.py --skill <目標 skill 路徑>` 取得 `rules/` 底下的 Rule File 清單。
  2. Delegate 執行 `uv run scripts/count_rules.py --skill <目標 skill 路徑>` 取得每個 Rule File 的 Rule 條數與各條的強度。
  3. Think 依 `rules/體檢-規範.md` 判斷哪些 Rule 該拆、該併。
  4. Ask 提出體檢報告,問使用者要處理哪幾條。

  scripts/
  ├── list_rule_files.py   ← 也新開
  └── count_rules.py       ← 新開
```

## good example
- 邊界:`rules/體檢-規範.md` 已經有一條 Rule 在講「強度照標題裡的標記數」,和這次的腳本重疊;**Rule File 不動,只在回覆裡提**
```
scripts/
└── count_rules.py          ← 新開

rules/體檢-規範.md           ← 一字未動

回覆:〈強度照標題裡的標記數〉和這次的腳本做的是同一件事,這次沒有動它,要不要拿掉由你決定。
```

## bad example
- 邊界:同一次委派,覺得重複了就**順手把那條 Rule 刪掉**;看起來是在收尾,但使用者同意的只有換上腳本,Rule File 被改了他並不知道
```
scripts/
└── count_rules.py          ← 新開

rules/體檢-規範.md           ← 刪掉〈強度照標題裡的標記數〉
```

# Rule 3 [must] - 腳本只做那一步原本的職責
- 腳本吃的輸入,就是那一步原本讀的東西;腳本吐的結果,就是那一步原本要得到的東西
- 使用者沒提的處理不寫進腳本;想到腳本可以順便做的事,只在回覆裡提,由使用者決定要不要再委派一次
- 為什麼:使用者同意的是把這一步換成腳本來做,不是讓這一步多做事;腳本多吐出來的東西,每次執行都會進到輸出裡,卻沒有任何一步接它

## good example
- 那一步原本要的是「Rule 條數與各條的強度」,**腳本吐的就只有這兩樣**;想到的另一件事留在回覆裡
```
before  2. Think 統計每個 Rule File 的 Rule 條數與各條的強度。

scripts/count_rules.py 的輸出
  {"RuleFile-格式規範.md": {"must": 8, "should": 2}}

回覆:另外想到可以順便列出缺 example 的 Rule,這次沒有寫進去,需要的話再委派一次。
```

## bad example
- 同一次委派,但**腳本多吐了兩樣使用者沒提過的東西**;之後每次執行,輸出裡都有沒有人用的 `lines` 與 `missing_examples`
```
before  2. Think 統計每個 Rule File 的 Rule 條數與各條的強度。

scripts/count_rules.py 的輸出
  {"RuleFile-格式規範.md": {"must": 8, "should": 2, "lines": 360, "missing_examples": []}}
```

## good example
- 邊界:那一步的原文沒有提到「找不到 `rules/` 怎麼辦」,但**這是把原本的職責做完所必需的**,所以腳本會回報這個錯誤
```
$ uv run scripts/count_rules.py --skill .claude
錯誤: .claude 底下沒有 rules/ 目錄。--skill 要給 skill 的根目錄(含 SKILL.md 的那一層)。
```

## bad example
- 邊界:替腳本加了一個 `--format markdown`,看起來只是多一種輸出的樣子;但**沒有任何一步用得到它**,那一步要的仍然只是條數與強度
```
$ uv run scripts/count_rules.py --skill <目標 skill 路徑> --format markdown
| Rule File | must | should |
|---|---|---|
| RuleFile-格式規範.md | 8 | 2 |
```

# Rule 4 [must] - 指定那一步改成 Delegate 並寫出完整指令
- 〈一次委派只動一步與一支腳本〉的首次委派,把那一步改寫成下面的寫法;編號與行尾的分支照原樣

```
<M>. Delegate 依 `rules/腳本執行-規範.md` 執行 `uv run scripts/<腳本名>.py <參數>` <取得什麼或留下什麼>
```

- 指令寫完整:`uv run`、腳本的完整路徑、每一個參數;執行時才知道的值寫成 `<說明>`
- 目標 skill 已經有別的步驟點名 `rules/腳本執行-規範.md` 時,省略「依 `rules/腳本執行-規範.md`」,指令仍然寫完整
- 為什麼:執行的人是照步驟裡那一行去跑的;指令少了一段他就得猜,猜的結果通常是改用 `python` 直接跑,腳本檔頭宣告的套件就沒有人裝。編號一變,別處的「跳至 Phase N Step M」也會跟著指錯

## good example
- 動詞改成 Delegate,**`uv run`、路徑與參數都在**,照抄就能執行
```
before  2. Think 統計每個 Rule File 的 Rule 條數與各條的強度。
after   2. Delegate 依 `rules/腳本執行-規範.md` 執行 `uv run scripts/count_rules.py --skill <目標 skill 路徑>` 取得每個 Rule File 的 Rule 條數與各條的強度。
```

## bad example
- 同一次委派,但**只說「用腳本」,沒有指令**;執行的人得自己去 `scripts/` 找是哪一支、猜它要什麼參數、決定用什麼跑
```
before  2. Think 統計每個 Rule File 的 Rule 條數與各條的強度。
after   2. Delegate 依 `rules/腳本執行-規範.md` 用腳本統計每個 Rule File 的 Rule 條數與各條的強度。
```

## good example
- 邊界:那一步原本在行尾有分支,**分支照原樣留在行尾**,編號也沒有變
```
before  2. Think 統計每個 Rule File 的 Rule 條數與各條的強度;若沒有任何 Rule File → 跳至 Phase 1 Step 4。
after   2. Delegate 依 `rules/腳本執行-規範.md` 執行 `uv run scripts/count_rules.py --skill <目標 skill 路徑>` 取得每個 Rule File 的 Rule 條數與各條的強度;若沒有任何 Rule File → 跳至 Phase 1 Step 4。
```

## bad example
- 邊界:同一次委派,指令是完整的,但**動詞留著原本的 Think**;因為「還是在統計」看起來沒有錯,只讀動詞的人卻看不出這一步的職責已經交給腳本
```
before  2. Think 統計每個 Rule File 的 Rule 條數與各條的強度;若沒有任何 Rule File → 跳至 Phase 1 Step 4。
after   2. Think 依 `rules/腳本執行-規範.md` 執行 `uv run scripts/count_rules.py --skill <目標 skill 路徑>` 統計每個 Rule File 的 Rule 條數與各條的強度;若沒有任何 Rule File → 跳至 Phase 1 Step 4。
```

# Rule 5 [must] - 腳本以它做的事命名
- 檔名寫成 `<動詞>_<受詞>.py`(全小寫、用底線分隔),動詞與受詞取那一步做的事,不取這次使用者提到的那一個細節
- 為什麼:之後再次委派同一步,改的是同一支腳本;檔名綁在第一次提到的細節上,腳本多做一樣事之後就名不符實,要改名,步驟裡的指令也得跟著改

## good example
- 檔名是**動詞加受詞**,只看 `scripts/` 的清單就知道這一支在數 Rule
```
scripts/
└── count_rules.py
```

## bad example
- 同一支腳本,但**檔名沒有說它做什麼**;之後有了第二支腳本,分不出哪一支是哪一步在用的
```
scripts/
└── helper.py
```

## good example
- 邊界:這次使用者只提到「數 must 的條數」,但**檔名取的是那一步做的事「數 Rule」**,之後 should 的條數也算得進同一支
```
使用者:Phase 1 Step 2 數 must 條數的部分寫成腳本。

2. Delegate 依 `rules/腳本執行-規範.md` 執行 `uv run scripts/count_rules.py --skill <目標 skill 路徑>` 取得每個 Rule File 的 Rule 條數與各條的強度。

scripts/
└── count_rules.py
```

## bad example
- 邊界:同一次委派,檔名取自這次提到的那個細節,看起來更精確,但**腳本數的是每一條 Rule 的強度**,不只有 must,名字從第一天就對不上
```
使用者:Phase 1 Step 2 數 must 條數的部分寫成腳本。

2. Delegate 依 `rules/腳本執行-規範.md` 執行 `uv run scripts/count_must_rules.py --skill <目標 skill 路徑>` 取得每個 Rule File 的 Rule 條數與各條的強度。

scripts/
└── count_must_rules.py
```

# Rule 6 [must] - 沿用已確認的具體轉換
- 使用者先前直接確認，或上游傳入可追溯的已確認方案，且內容涵蓋目標步驟、腳本路徑、參數、輸出、第三方套件與改寫後的步驟時，核對本次轉換一致後跳過重複確認。
- 確認只涵蓋原有的局部操作範圍；缺少資訊、新增要求或轉換結果超出方案時，提出該差異並等待確認。「同意優化」不等於已確認具體轉換。
- 上游需刪減其他部件時，由上游另外編排；沿用確認不擴大本 Deriver 的修改邊界。
- 為什麼:完整方案已經讓使用者做過相同決定，重問只增加往返；缺少具體內容則無法判定是否仍在已確認範圍內。

## good example
- 同一項具體轉換已有確認，核對後直接執行。
使用者已確認「將指定步驟的 Rule 計數委派成使用標準函式庫、輸出 JSON 的腳本」，上游附上完整操作資料與確認紀錄；本次產出符合該方案，進入 Phase 2，不再詢問同一件事。

## bad example
- 同一項具體轉換已有確認，卻再次要求相同決定。
使用者已確認「將指定步驟的 Rule 計數委派成使用標準函式庫、輸出 JSON 的腳本」，上游也附上完整操作資料與確認紀錄；本次產出沒有差異，仍停在 Phase 1 Step 4 問一次是否可以寫入。

## good example
- 邊界：確認內容不足時只詢問缺口。
使用者只說「同意優化」，沒有目標步驟、腳本路徑、參數、輸出、第三方套件與改寫後的步驟；先補齊資訊、提出具體轉換並等待確認。

## bad example
- 邊界：同樣只有籠統同意，卻跳過確認。
使用者只說「同意優化」，agent 自己決定目標步驟、腳本路徑、參數、輸出、第三方套件與改寫後的步驟，直接進入 Phase 2。

# Rule 7 [must] - 產出不符預期的直接請求不委派
- 使用者是因為目標 skill 跑出來的產出不符預期而直接要求寫成腳本,又沒有上游傳入的已確認方案時,不委派:不動任何檔,在回覆裡說明要先用 skill-engineering 找出根因
- 上游傳入已確認的方案時,照〈沿用已確認的具體轉換〉承接
- 為什麼:使用者指出的那一步是他看到問題的地方,不一定是問題的來源;直接把那一步換成腳本,真正寫錯、多出來或放錯位置的文字會原封不動留著

## good example
- 使用者講的是**哪裡的產出不對**,不是要把哪件事交給腳本;不動任何檔,只在回覆裡指出該走哪一條路
```
使用者:Phase 1 Step 2 統計出來的 Rule 條數常常和實際對不上,寫成腳本。

scripts/ 不新增也不修改任何檔

回覆:這是因為產出不符預期而要求的修改,請先用 skill-engineering 找出根因;寫成腳本是不是對的修法,要看根因落在哪一步。
```

## bad example
