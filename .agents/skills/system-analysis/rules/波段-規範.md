# Rule 1 [must] - 介面排在它依賴的介面都分析完之後
- 一個介面的分析要用到另一個介面定下的東西,就排在那個介面所在的 wave 之後
- 理由欄寫出依賴哪一步定下的什麼,例如「要存什麼由 S3 的資源與操作決定」
- 為什麼:依賴的介面還沒分析就先分析,只能自己假設對方的樣子;等對方分析完和假設不同,這一步要整個重做,而且同一波平行的 sub agent 彼此看不到對方的結果

## good example
- 資料庫要存什麼由後端 API 決定;**資料庫排在後端的下一波**,理由欄寫出依賴的是哪一步的什麼
```
| 2 | S3 | E2 後端 REST API | api-plan | ✅ 與 S2 平行 | 由 FR 推出;建立訂單、接收付款通知的端點要照 S1 的參數與簽章 |
| 3 | S4 | E3 資料庫 | data-plan | ✅ 與 S5、S6 平行 | 要存什麼由 S3 的資源與操作決定(含訂單與付款狀態) |
```

## bad example
- 同一組介面,但**資料庫和後端排在同一波平行**;分析資料庫的 sub agent 拿不到後端的資源與操作,只能自己猜要存什麼
```
| 2 | S3 | E2 後端 REST API | api-plan | ✅ 與 S4 平行 | 由 FR 推出 |
| 2 | S4 | E3 資料庫 | data-plan | ✅ 與 S3 平行 | 由 Key Entities 推出 |
```

## good example
- 邊界:前端呼叫後端的 API,看起來前端依賴後端;但**兩者都直接由同一份需求推出,前端的畫面不用等 API 的細節定下來**,所以同一波平行
```
| 2 | S2 | E1 前端畫面與互動 | uiux-plan | ✅ 與 S3 平行 | 由使用者故事推出;結帳、導向付款頁與付款完成頁的流程要照 S1 的導轉方式 |
| 2 | S3 | E2 後端 REST API | api-plan | ✅ 與 S2 平行 | 由 FR 推出;前端與後端以同一份需求為準,不必等對方 |
```

## bad example
- 邊界:同一組介面,因為前端會呼叫後端,就**把前端往後推一波**;理由欄寫的依賴其實是需求,不是後端分析出來的東西,多了一波卻沒有換到任何資訊
```
| 2 | S2 | E2 後端 REST API | api-plan | — | 由 FR 推出 |
| 3 | S3 | E1 前端畫面與互動 | uiux-plan | — | 前端會呼叫 S2 的 API |
```

# Rule 2 [must] - 第三方端點排在第一波
- 網路上的第三方服務(例如金流)、硬體、雲端服務這類介面由對方定好、由我們連過去使用的端點,排在第一波
- 依賴它們的介面往後推一波
- 我們自己呼叫的外部程式(命令列工具、函式庫)不算:它的參數雖然是別人定的,這次要它交出什麼卻由呼叫它的介面決定,照〈介面排在它依賴的介面都分析完之後〉排
- 為什麼:我們只能照著接、不能改它們的介面;先分析它們,前端與後端碰到它們的地方才有根據,反過來排,前端與後端得照自己的想像設計,再被對方的規格推翻

## good example
- 相簿沖印要串第三方金流;**金流單獨排在第一波**,前端的付款導轉與後端的建單、收通知都在第二波
```
| 1 | S1 | E7 第三方金流 | api-plan | — | 金流商的介面已經定好,不依賴任何介面;前端的付款導轉與後端的建單、收通知都要照它設計 |
| 2 | S2 | E1 前端畫面與互動 | uiux-plan | ✅ 與 S3 平行 | 由使用者故事推出;結帳、導向付款頁與付款完成頁的流程要照 S1 的導轉方式 |
| 2 | S3 | E2 後端 REST API | api-plan | ✅ 與 S2 平行 | 由 FR 推出;建立訂單、接收付款通知的端點要照 S1 的參數與簽章 |
```

## bad example
- 同一個需求,但**金流排在後端之後**;後端的建單與收通知端點在 S2 就定了,S3 分析金流時才發現參數與簽章要整個改
```
| 1 | S1 | E1 前端畫面與互動 | uiux-plan | ✅ 與 S2 平行 | 由使用者故事推出 |
| 1 | S2 | E2 後端 REST API | api-plan | ✅ 與 S1 平行 | 由 FR 推出 |
| 2 | S3 | E7 第三方金流 | api-plan | — | 後端要呼叫金流 |
```

## good example
- 邊界:需求沒有任何第三方端點;**第一波就由不依賴其他介面的前端與後端開始**,不為了這條 Rule 硬留一個空的第一波
```
| 1 | S1 | E1 前端畫面與互動 | uiux-plan | ✅ 與 S2 平行 | 直接由使用者故事推出,不依賴其他介面 |
| 1 | S2 | E2 後端 REST API | api-plan | ✅ 與 S1 平行 | 直接由 FR 推出;前端與後端以同一份需求為準,不必等對方 |
```

## bad example
- 邊界:同一個沒有第三方的需求,把**部署與網路當成第三方排進第一波**;但它的 port 與路徑要等我們的介面都定下來,並不是對方定好的
```
| 1 | S1 | E6 部署與網路 | deploy-plan | — | 外部的基礎設施 |
| 2 | S2 | E1 前端畫面與互動 | uiux-plan | ✅ 與 S3 平行 | 直接由使用者故事推出 |
```

## good example
- 邊界:影像處理工具的參數是 libheif 定的,看起來和金流一樣是對方定好的;但**它是後端自己呼叫的命令列程式,要產出哪些縮圖由後端決定**,所以排在後端的下一波
```
| 2 | S3 | E2 後端 REST API | api-plan | ✅ 與 S2 平行 | 由 FR 推出;建立訂單、接收付款通知的端點要照 S1 的參數與簽章 |
| 3 | S6 | E5 影像處理工具 | api-plan | ✅ 與 S4、S5 平行 | 要產出哪些縮圖、失敗要回報什麼由 S3 決定 |
```

## bad example
- 邊界:同一個工具,因為參數是別人定的就**當成第三方排進第一波**;這時還不知道後端要哪幾種縮圖,只能把工具的每個參數都分析一遍
```
| 1 | S1 | E7 第三方金流 | api-plan | ✅ 與 S2 平行 | 金流商的介面已經定好,不依賴任何介面 |
| 1 | S2 | E5 影像處理工具 | api-plan | ✅ 與 S1 平行 | libheif 的參數已經定好,不依賴任何介面 |
```

# Rule 3 [must] - 每個介面排在它能排的最早一波
- 一個介面依賴的介面都已排完,就排在下一波,不再往後推
- 依賴都排完的介面放在同一波平行
- 為什麼:每多一波,整個分析就多等一輪;本來可以平行的介面被拆到不同波,等的時間變長,卻沒有多拿到任何資訊

## good example
- 資料庫、檔案系統、影像處理工具都只依賴後端;**三個一起排在後端的下一波**
```
| 3 | S4 | E3 資料庫 | data-plan | ✅ 與 S5、S6 平行 | 要存什麼由 S3 的資源與操作決定 |
| 3 | S5 | E4 檔案系統 | deploy-plan | ✅ 與 S4、S6 平行 | 要讀哪些原檔、寫哪些縮圖由 S3 的匯入與重新掃描決定 |
| 3 | S6 | E5 影像處理工具 | api-plan | ✅ 與 S4、S5 平行 | 要產出哪些縮圖、失敗要回報什麼由 S3 決定 |
```

## bad example
- 同一組介面,但**檔案系統與影像處理工具被一個一個往後排**;它們不依賴資料庫,多出兩波只是在等
```
| 3 | S4 | E3 資料庫 | data-plan | — | 要存什麼由 S3 的資源與操作決定 |
| 4 | S5 | E4 檔案系統 | deploy-plan | — | 要讀哪些原檔、寫哪些縮圖由 S3 決定 |
| 5 | S6 | E5 影像處理工具 | api-plan | — | 要產出哪些縮圖由 S3 決定 |
```

## good example
- 邊界:部署與網路只剩它一個介面,單獨成一波;但**它依賴 S3–S6 都定下來**,最早就只能排在第 4 波
```
| 4 | S7 | E6 部署與網路 | deploy-plan | — | 要開哪些 port、掛哪些路徑、DB 放哪個網路,要等 S3–S6 都定下來 |
```

## bad example
- 邊界:為了讓第 3 波多一個平行,把**部署與網路提早到第 3 波**;它要的 DB 網路與掛載路徑,在同一波的 S4、S5 還沒定
```
| 3 | S4 | E3 資料庫 | data-plan | ✅ 與 S5、S6、S7 平行 | 要存什麼由 S3 的資源與操作決定 |
| 3 | S7 | E6 部署與網路 | deploy-plan | ✅ 與 S4、S5、S6 平行 | 要開哪些 port 由 S3 決定 |
```

# Rule 4 [must] - Planner 欄照端點的種類指派
- 每一步的 Planner 欄照下表指派;一個端點有不只一個要分析的角度時,指派多支,用「、」分隔,每一支只寫自己那個角度

| 端點的種類 | Planner |
|---|---|
| 前端、手機 App | uiux-plan |
| 後端對外的 API、第三方服務、我們呼叫的外部程式(命令列工具、函式庫) | api-plan |
| 資料庫 | data-plan |
| 部署與網路、檔案系統、雲端基礎設施 | deploy-plan |

- 下表沒有一支適合的端點(例如硬體韌體),Planner 欄寫「無合適的 planner」;這一步在 Phase 3 不交出去,提出分析波段時一併問使用者怎麼處理
- 為什麼:Phase 3 是照 Planner 欄把步驟交給 sub agent 的;指派錯了,交出來的檔格式就錯(例如資料庫交出 OpenAPI),硬塞給一支不適合的 planner,它會照自己的格式交出一份看起來完整、其實沒分析到重點的檔

## good example
- 檔案系統要分析的是掛載與唯讀,**照表指派 deploy-plan**;影像處理工具是後端呼叫的命令列程式,**照表指派 api-plan**
```
| 3 | S5 | E4 檔案系統 | deploy-plan | ✅ 與 S4、S6 平行 | 要讀哪些原檔、寫哪些縮圖由 S3 的匯入與重新掃描決定 |
| 3 | S6 | E5 影像處理工具 | api-plan | ✅ 與 S4、S5 平行 | 要產出哪些縮圖、失敗要回報什麼由 S3 決定 |
```

## bad example
- 同兩步,但**檔案系統被當成資料指派給 data-plan**;它只會交出 DBML,原檔唯讀、縮圖目錄要掛在哪裡,沒有任何一份檔寫到
```
| 3 | S5 | E4 檔案系統 | data-plan | ✅ 與 S4、S6 平行 | 要讀哪些原檔、寫哪些縮圖由 S3 的匯入與重新掃描決定 |
| 3 | S6 | E5 影像處理工具 | api-plan | ✅ 與 S4、S5 平行 | 要產出哪些縮圖、失敗要回報什麼由 S3 決定 |
```

## good example
- 邊界:雲端物件儲存要決定存什麼、怎麼命名,也要決定權限與網路;**兩個角度各指派一支**
```
| 3 | S4 | E9 雲端物件儲存(S3 相容) | data-plan、deploy-plan | — | 要存哪些檔由 S3 的匯入決定 |
```

## bad example
- 邊界:同一個端點,**只挑了一支**;存什麼有人分析,bucket 的權限與誰連得到卻沒有任何一份檔寫到
```
| 3 | S4 | E9 雲端物件儲存(S3 相容) | data-plan | — | 要存哪些檔由 S3 的匯入決定 |
```

## good example
- 邊界:燒錄到裝置裡的韌體,四支 planner 都不適合;**寫「無合適的 planner」**,提出分析波段時問使用者
```
| 1 | S1 | E10 門禁讀卡機韌體 | 無合適的 planner | — | 韌體的指令格式是廠商定好的,不依賴任何介面 |
```

## bad example
- 邊界:同一個韌體,因為它也有「指令」就**硬指派給 api-plan**;交出來的 OpenAPI 描述的是一個不存在的 HTTP 服務
```
| 1 | S1 | E10 門禁讀卡機韌體 | api-plan | — | 韌體的指令格式是廠商定好的,不依賴任何介面 |
```

# Rule 5 [must] - 理由欄只寫排序的依據
- 理由欄只寫為什麼排在這一波:依賴哪幾步定下的什麼
- 不寫分析的方法、要交出的格式細節,也不寫委派給誰(那是 Planner 欄)
- 為什麼:每個介面怎麼分析由指派的 planner 決定;plan.md 先寫了做法,委派出去時兩邊的寫法會打架,執行的人不知道該照哪一份

## good example
- 理由欄**只寫為什麼排在這一波**
```
| 3 | S4 | E3 資料庫 | data-plan | ✅ 與 S5、S6 平行 | 要存什麼由 S3 的資源與操作決定(含訂單與付款狀態) |
```

## bad example
- 同一步,但**理由欄寫了要怎麼分析**;這些不是排序的依據
```
| 3 | S4 | E3 資料庫 | data-plan | ✅ 與 S5、S6 平行 | 先畫 ER 圖再寫 migration,訂單表要加軟刪除 |
```

## good example
- 邊界:理由欄提到「訂單與付款狀態」,看起來像在講資料庫要存什麼;但**它說的是這一步依賴 S3 定下的哪一部分**,是排序的依據
```
| 3 | S4 | E3 資料庫 | data-plan | ✅ 與 S5、S6 平行 | 要存什麼由 S3 的資源與操作決定(含訂單與付款狀態) |
```

## bad example
- 邊界:同一步,也在講要存什麼,但**直接定了怎麼存**;這是分析資料庫那一步的結果,不是它為什麼排在第 3 波
```
| 3 | S4 | E3 資料庫 | data-plan | ✅ 與 S5、S6 平行 | 訂單存成 print_orders 表,付款狀態用 ENUM |
```
