# Rule 1 [must] - 採證必須提取日誌原文與工具參數
- 檢索執行紀錄（transcript 或 event log）時，必須直接提取該步驟的 thinking 原文、tool 調用名稱與參數、以及回傳輸出，作為研判 agent 行為的客觀事實
- 禁止在沒有日誌原文佐證的情況下主觀臆測 agent「當時可能忘了」或「應該是覺得做完了」
- 為什麼:不看日誌原文只憑推論，會把主觀猜想當成事實，導向錯誤的修法

## good example
- **直接引用 Step 45 的 thinking 原文與工具調用**，清楚證實 agent 判定通過後直接轉向撰寫診斷檔
```markdown
檢索 transcript_full.jsonl Step 45:
thinking: "Good, the original project is untouched, just copy differences. Now I'll write the diagnosis report."
事實依據: agent 內部判定完成後直接執行 write_to_file 寫入診斷檔，漏交表格主因在於步驟職責混雜與判定跳轉。
```

## bad example
- **沒有任何日誌截圖或原文引用**，只憑直覺猜測
```markdown
agent 應該是看到實跑通過了很開心，所以忘記讀模板就結束了。
```

# Rule 2 [must] - 排除假說必須列出反證事件與依據
- 宣告某個可疑原因被排除時，必須在紀錄中寫出排查時看過哪一個具體事件或檔案，以及看到了什麼足以構成反證的事實
- 為什麼:沒有反證依據的排除只是盲目剔除，可能將真正隱藏的複合問題提早略過

## good example
- **明確指明事件編號與內容**作為排除依據
```markdown
假說: 模板讀取失敗或路徑錯誤
排除依據: 事件 31 與 32 記錄 view_file 成功讀取 `templates/驗收紀錄.md` 完整 15 行，證明模板存在且成功載入。
```

## bad example
- **只有結論沒有反證事實**
```markdown
假說: 模板讀取失敗
排除依據: 這個應該不可能發生，予以排除。
```
