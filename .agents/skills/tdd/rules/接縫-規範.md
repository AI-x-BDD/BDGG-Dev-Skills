# Rule 1 [must] - 接縫只取公開介面
- 接縫是測試觀察行為的那個邊界,只取呼叫端本來就會用的公開介面:公開的函式、方法、屬性、HTTP 端點、CLI 指令
- 在介面上就看得到行為,不伸進內部:private 方法、內部協作者、資料庫的表都不當接縫
- 為什麼:接在內部的測試綁住的是實作的形狀,重構時行為沒變,測試卻跟著壞;壞掉的測試多了,大家就不再相信紅燈

## good example
- 結帳功能的接縫**都是呼叫端會用的公開介面**,結果在介面上就看得到
```
接縫
- `checkout(cart, payment_method)`:回傳的 `status` 就是結帳成不成功
- `get_order(order_id)`:結帳後查得到訂單,就知道訂單有存下來
```

## bad example
- 同一個功能,但**接縫伸進了內部**:private 的計價方法與資料庫的 `orders` 表,呼叫端都碰不到
```
接縫
- `Cart._apply_discount()`:檢查折扣有沒有算對
- `orders` 表:結帳後直接 SELECT 看有沒有多一列
```

## good example
- 邊界:要驗的是「訂單有存下來」,看起來非查資料庫不可;但**公開的 `get_order` 就看得到這件事**,接縫取它
```
接縫
- `get_order(order_id)`:結帳後用回傳的訂單編號查得到同一張訂單
```

## bad example
- 邊界:同一件事,因為「存下來」聽起來是資料庫的事就**把資料表當接縫**;改了表結構,行為沒變,測試卻壞了
```
接縫
- `orders` 表:結帳後 `SELECT * FROM orders WHERE id = ?` 查得到一列
```

# Rule 2 [should] - 接縫集中在關鍵路徑與複雜邏輯
- 接縫挑這次改動的關鍵路徑(使用者真正會走的那條)與邏輯複雜、容易寫錯的地方
- 不必每個邊界情況都佔一個接縫:同一個公開介面能涵蓋的邊界情況,寫成那個接縫底下的不同測試
- 這次的改動本身就是某個邊界情況(例如修一個只在空購物車時出現的 bug)時,它就是這次的關鍵路徑,可以單獨列一個接縫
- 為什麼:沒辦法什麼都測,接縫一多,使用者要確認的清單就長到看不完,測試的工夫也平均攤到不重要的地方

## good example
- 結帳只列**兩個接縫**:主要的結帳流程,與折扣計算這段複雜邏輯;空購物車、數量為零都是 `checkout` 底下的測試
```
接縫
- `checkout(cart, payment_method)`:主要結帳流程,含空購物車、數量為零的情況
- `price_with_discounts(cart, coupons)`:多張折價券疊加的計價
```

## bad example
- 同一個功能,但**每個邊界情況各佔一個接縫**;使用者得確認五個接縫,其中四個其實是同一個介面
```
接縫
- `checkout`:正常結帳
- `checkout`:空購物車
- `checkout`:數量為零
- `checkout`:付款失敗
- `price_with_discounts(cart, coupons)`:多張折價券疊加的計價
```

## good example
- 邊界:這次要修的就是「空購物車結帳會丟例外」,**這個邊界情況就是這次的關鍵路徑**,單獨列出來
```
接縫
- `checkout(cart, payment_method)`:空購物車時回傳 `status == "rejected"`,不丟例外
```

## bad example
- 邊界:同一個 bug,因為「邊界情況不佔接縫」就**只列一般的結帳流程**;使用者確認的清單裡看不到這次真正要修的事
```
接縫
- `checkout(cart, payment_method)`:主要結帳流程
```
