# Rule 1 [must] - 每一小步之後任務的測試檔要綠燈,前後各跑一次全部,變紅就撤回那一步
- 開始重構前全部測試必須是綠燈;每做完一小步(一次改名、一次搬移、一次抽函式)就執行任務的測試檔;最後一步做完再執行一次全部測試
- 任務的測試檔是呼叫方的指示或任務描述寫到的測試檔,沒有寫時改跑快速層;快速層與全部的指令依序取自呼叫方的指示、`testplan.md` § 測試指令,兩處都沒有時跑專案的完整測試指令
- 測試變紅時,先把這一步的改動整個撤回,回到上一個綠燈的狀態,再換一個更小的步驟重做;不在紅燈的狀態下接著修
- 為什麼:重構的前提是行為不變,測試是唯一的證據;紅燈時接著改,改的就不再是結構而是行為,也分不出是哪一步弄壞的。每一小步都跑全部,colab-gpu-bridge 一次要 5 到 6 分鐘,重構反而沒人敢做小步;任務的測試檔一秒內就給回饋,前後兩次全部補上其他地方的回歸

## good example
- 抽函式之後測試變紅;**先撤回到上一個綠燈,再拆成更小的一步**
```
重構前  全部測試 40 passed
步驟 1  把 _enter_digit 的兩個條件合併成一個   任務的測試檔 12 passed
步驟 2  把 "=" 分支抽成 _on_equals()            任務的測試檔 1 failed → 撤回步驟 2
步驟 2' 只把 "=" 分支的計算搬進 _on_equals(),判斷留在 press   任務的測試檔 12 passed
重構後  全部測試 40 passed
```

## bad example
- 同一次重構,**測試變紅後不撤回,直接在紅燈上修**;最後雖然綠了,但說不出是哪一步改了行為
```
步驟 1  把 _enter_digit 的兩個條件合併成一個   任務的測試檔 12 passed
步驟 2  把 "=" 分支抽成 _on_equals()            任務的測試檔 1 failed
步驟 3  在 _on_equals() 補上沒有運算元時的判斷  任務的測試檔 12 passed
```

## good example
- 邊界:開始前跑一次全部測試,**有一個是紅的,所以不開始重構**,回報那個失敗
```
重構前  全部測試 11 passed, 1 failed(test_pressing_equals_twice...)
→ 不開始重構,回報這個失敗
```

## bad example
- 邊界:同一個狀態,心想「那個紅燈跟這次要整理的地方無關」就**照樣開始重構**;之後每一步的結果都混著那個紅燈,看不出有沒有弄壞別的
```
重構前  全部測試 11 passed, 1 failed
步驟 1  合併 _enter_digit 的條件   全部測試 11 passed, 1 failed
```

# Rule 2 [must] - 只動結構,不改行為也不改測試的斷言
- 重構只改程式碼的結構:改名、搬移、抽出或內聯函式、合併重複;公開介面的行為與回傳值不變
- 測試檔的斷言與預期值不改;只有被測的公開介面改名時,才跟著改測試裡呼叫它的名稱
- 為什麼:測試是證明行為沒變的那一把尺;改了斷言,等於一邊重構一邊換尺,綠燈就不再證明任何事

## good example
- **只把重複的判斷合併**,測試檔一行都沒動
```
src/calculator.py   合併 _enter_digit 的兩個條件
tests/              沒有改動
```

## bad example
- 同一次重構,順手**把一個斷言的預期值改成新寫法的輸出**,讓它通過
```
src/calculator.py   把 display 的格式化改用 f-string
tests/test_calc.py  assert calc.display == "7"  →  assert calc.display == "7.0"
```

## good example
- 邊界:公開介面 `Calculator.press` 改名為 `Calculator.tap`;**測試只跟著換呼叫的名稱**,斷言與預期值不變
```
tests/test_calc.py  calc.press("7")  →  calc.tap("7")
                    assert calc.display == "7"   (不變)
```

## bad example
- 邊界:同一次改名,順便**把幾個測試合併成一個、少了兩個斷言**;看起來只是整理測試,但被拿掉的斷言保護的行為已經沒有測試了
```
tests/test_calc.py  test_equals_once、test_equals_twice 合併成 test_equals
                    原本 3 個 assert 剩 1 個
```

# Rule 3 [must] - 只處理重構清單裡的項目
- 這一輪只做重構清單(紅綠階段記下的、或呼叫方交來的)裡的項目;清單以外看到值得整理的地方,記進清單留給下一輪
- 為什麼:範圍沒有邊界,重構會一路長到和這次的功能無關的地方,改動越大,出錯時越難撤回、也越難審查

## good example
- 清單有兩項;做完兩項時又看到 `parse_input` 可以整理,**只記下來,不在這一輪做**
```
重構清單  1. 合併 _enter_digit 的條件   ✔
          2. 把 "=" 分支抽成 _on_equals  ✔
新記下    3. parse_input 的錯誤處理可以集中(留給下一輪)
```

## bad example
- 同一輪,**順手把清單以外的 `parse_input` 也改了**;它和這次的功能無關,改壞了也沒有這次的測試會抓到
```
重構清單  1. 合併 _enter_digit 的條件   ✔
          2. 把 "=" 分支抽成 _on_equals  ✔
另外改了  parse_input 的錯誤處理集中到 _fail()
```

## good example
- 邊界:做清單第 2 項時,抽出的 `_on_equals` 需要把一個區域變數改名才不衝突;**這是完成第 2 項必需的,不算清單以外**
```
2. 把 "=" 分支抽成 _on_equals   附帶把區域變數 result 改名為 total
```

## bad example
- 邊界:同一項,抽完之後覺得**整個檔案的變數命名都該統一**,一路改了十幾個名稱;那已經不是第 2 項需要的
```
2. 把 "=" 分支抽成 _on_equals   另外把整個檔的 val、tmp、res 改成完整的英文名稱
```

# Rule 4 [should] - 重構和功能分開 commit
- 重構的改動自己成一個 commit,不和紅燈、綠燈的改動混在同一個 commit;commit 訊息的 type 用 `refactor`
- 為什麼:混在一起時,事後看 diff 分不出哪幾行改了行為、哪幾行只是搬動,要撤回其中一邊也撤不乾淨

## good example
- **綠燈與重構各一個 commit**
```
a1b2c3d feat(calc): 沒有運算元時按 = 保留輸入的數字
d4e5f6a refactor(calc): 把 = 分支抽成 _on_equals
```

## bad example
- 同樣的改動,**塞進同一個 commit**
```
a1b2c3d feat(calc): 沒有運算元時按 = 保留輸入的數字,並整理 press
```

## good example
- 邊界:重構清單有三項,**三項可以一起成一個 refactor commit**,只要裡面沒有行為的改動
```
d4e5f6a refactor(calc): 合併 _enter_digit 條件、抽出 _on_equals、移除重複的 clear
```

## bad example
- 邊界:同一個 refactor commit 裡**夾了一個修正行為的改動**(沒有運算元時的判斷);type 寫 refactor,實際上改了行為
```
d4e5f6a refactor(calc): 抽出 _on_equals,並修正沒有運算元時的判斷
```
