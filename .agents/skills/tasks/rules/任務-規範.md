# Rule 1 [must] - ⚙ 只列這個任務做出來或測到的介面元素
- ⚙ 列的是這個任務做完時必須照規格成立的元素:實作任務列它做出來的,測試任務列它斷言的
- 這個任務只是讀到、拿來對照、不負責做出來的元素,寫進 📎,不寫進 ⚙
- 為什麼:⚙ 是這個任務的完成範圍,執行的人會逐一對照每個錨點;混進只是讀到的元素,他會去改不屬於這個任務的檔,真正要做的那幾個反而被淹沒

## good example
- 測試任務**只列它斷言的兩個 operation**;要知道錯誤碼怎麼寫,是從 📎 的 Q12 查
```
- [ ] T050 [P] [US2] 撰寫 `backend/test/rooms/secret.test.ts`:合法時只有本人收到 `secret.confirmed`、"1123" 回 `DIGITS_REPEATED`…
  - ⚙ `contracts/game.asyncapi.yaml` § `operations.receiveSecretSet`、`operations.sendSecretConfirmed`
  - 📎 `spec.md` § FR-009、FR-010;`plan.md` § 待決問題 Q12
```

## bad example
- 同一個任務,但**把讀到的 `Digits` 與 `Error` 也列進 ⚙**;執行的人以為這個測試要負責 `Digits` 的格式,又寫了一遍 T010 已經測過的案例
```
- [ ] T050 [P] [US2] 撰寫 `backend/test/rooms/secret.test.ts`:合法時只有本人收到 `secret.confirmed`、"1123" 回 `DIGITS_REPEATED`…
  - ⚙ `contracts/game.asyncapi.yaml` § `operations.receiveSecretSet`、`operations.sendSecretConfirmed`、`components.schemas.Digits`、`components.schemas.Error`
  - 📎 `spec.md` § FR-009、FR-010
```

## good example
- 邊界:前端畫面任務**做出原型的狀態,也送出與接收訊息**;兩種都是它做出來的,都列進 ⚙
```
- [ ] T064 [US2] 在 `frontend/src/pages/room.js` 加入「開始遊戲」:只有房主看得到;按下送 `game.start`
  - ⚙ `prototype/room.html` § `.js-start`、`[data-state="host-ready"]`;`contracts/game.asyncapi.yaml` § `operations.receiveGameStart`
  - 📎 `spec.md` § FR-008
```

## bad example
- 邊界:同一個任務,覺得前端只是「照著合約送」,**把它送出的 operation 移到 📎**;覆蓋表的 `receiveGameStart` 就少了前端這一端,前端漏送也沒有人發現
```
- [ ] T064 [US2] 在 `frontend/src/pages/room.js` 加入「開始遊戲」:只有房主看得到;按下送 `game.start`
  - ⚙ `prototype/room.html` § `.js-start`、`[data-state="host-ready"]`
  - 📎 `spec.md` § FR-008;`contracts/game.asyncapi.yaml` § `operations.receiveGameStart`
```

# Rule 2 [must] - 介面元素歸到第一個需要它的 phase
- 每個介面元素第一次列進介面覆蓋表,是在第一個要把它做出來的 phase
- 後面的 phase 擴充同一個元素的行為時,任務照樣在 ⚙ 列它,並在那個 phase 的覆蓋表再列一列,錨點後面標出擴充的範圍(例如 `reason` 的值或遊戲中的路徑)
- 為什麼:元素放在最後才用到的 phase,前面的故事會缺一塊、做不成獨立可交付;同一個元素不標範圍地重複列,看不出哪一列的實作才算數

## good example
- `receiveRoomLeave` **在 US1 做出等待中的離開**,US3 擴充遊戲中的路徑時標出範圍
```
介面覆蓋(US1)| `game.asyncapi.yaml` § `operations.receiveRoomLeave`(等待中) | T039、T043 | T032 |
介面覆蓋(US3)| `game.asyncapi.yaml` § `operations.receiveRoomLeave`(遊戲中) | T077、T081 | T072 |
```

## bad example
- 同一個元素,因為遊戲中離開最複雜就**只放在 US3**;US1 做完時房間不能離開,它的獨立測試跑不過
```
介面覆蓋(US3)| `game.asyncapi.yaml` § `operations.receiveRoomLeave` | T039、T077、T081 | T032、T072 |
```

## good example
- 邊界:`sendError` 每個故事都會送,**歸到第一個做出它的 US1**;後面的故事只在任務的 ⚙ 列它送出的錯誤情境
```
介面覆蓋(US1)| `game.asyncapi.yaml` § `operations.sendError`、`components.schemas.Error` | T015b、T019b | T015a、T019a |
```

## bad example
- 邊界:同一個元素,因為每個故事都用到就**每張表各列一次、不標範圍**;三列看起來都對,但看不出哪一列的實作才是 `sendError` 本身
```
介面覆蓋(US1)| `game.asyncapi.yaml` § `operations.sendError` | T019b | T034a |
介面覆蓋(US2)| `game.asyncapi.yaml` § `operations.sendError` | T019b | T050a |
介面覆蓋(US3)| `game.asyncapi.yaml` § `operations.sendError` | T019b | T070a |
```

# Rule 3 [must] - 📎 指到最小的那一段
- 📎 的每個引用寫到能直接找到那句話的位置:FR、NFR、SC、驗收情境的編號,research 的 R 編號,plan.md 的 Q 編號,或段落名
- 不寫整份文件或整個章節;`§ 全檔` 只用在原樣複製整個檔的任務
- 為什麼:📎 是執行的人判斷細節時回頭查的地方;指到一整章,他得自己猜是哪一句,猜錯了就照著錯的那句做

## good example
- 依據**指到兩條 FR 與一個 Q**
```
  - 📎 `spec.md` § FR-009、FR-010;`plan.md` § 待決問題 Q10
```

## bad example
- 同一個任務,但**指到整個故事與整張待決問題表**;故事 2 有 7 條 FR、待決問題有 22 題,執行的人不知道該看哪一條
```
  - 📎 `spec.md` § 使用者故事 2;`plan.md` § 待決問題
```

## good example
- 邊界:跨端點驗收任務要照的就是**故事的獨立測試與整組驗收情境**;寫段落名與情境範圍,已經是最小的那一段
```
  - 📎 `spec.md` § 使用者故事 1 獨立測試、驗收情境 1–5
```

## bad example
- 邊界:同一類任務,寫了 `§` 看起來有錨點,但**錨點是整份文件的大標題**;和只寫檔名沒有差別
```
  - 📎 `spec.md` § 使用者情境與測試
```

# Rule 4 [must] - 一個任務裡有依序的幾件事才拆成帶字尾的子任務
- 任務的完成範圍(⚙ 與要改的檔)已經是一件事,就維持單一編號,不拆
- 一個三位數底下要依序做兩件以上、各自能單獨驗收的事(例如先寫失敗的測試、再實作),才拆成 `T012a`、`T012b`…;每個子任務自己寫 ⚙ 與 📎
- 字尾從 `a` 起、依序不跳號;同一個三位數拆了就沒有不帶字尾的 `T012`,不能 `T012` 與 `T012a` 並存
- 為什麼:拆成帶字尾的子任務,後面的任務與覆蓋表仍引用同一個三位數系列,不必整份重新編號;跳號或並存會讓檢查腳本認不得編號,也看不出缺了哪一步

## good example
- `T050` 要先寫測試再實作,**拆成 `T050a`、`T050b`**,字尾從 `a` 起、沒有不帶字尾的 `T050`
```
- [ ] T050a [US2] 撰寫 `backend/test/rooms/secret.test.ts`:"1123" 回 `DIGITS_REPEATED`,先確認失敗
  - ⚙ `contracts/game.asyncapi.yaml` § `operations.receiveSecretSet`
- [ ] T050b [US2] 實作 `backend/src/rooms/secret.ts`,讓 T050a 轉綠
  - ⚙ `contracts/game.asyncapi.yaml` § `operations.receiveSecretSet`
```

## bad example
- 同一個三位數**跳過 `a` 從 `b` 開始,又保留不帶字尾的 `T050`**;檢查腳本不認這種編號,讀的人也不知道 `T050` 與 `T050b` 誰先誰後
```
- [ ] T050 [US2] 撰寫 `backend/test/rooms/secret.test.ts`:"1123" 回 `DIGITS_REPEATED`
- [ ] T050b [US2] 實作 `backend/src/rooms/secret.ts`,讓 T050 轉綠
```

## good example
- 邊界:一個任務只改一個檔、做一件事,**維持 `T051` 不加字尾**
```
- [ ] T051 [P] [US2] 建立 `backend/src/rooms/secret-view.ts`:只回傳本人的 `secret.confirmed`
```

## bad example
- 邊界:同樣是一件事,**只因為想「留彈性」就寫成 `T051a`、後面沒有 `T051b`**;字尾只用在真的拆成兩件以上
```
- [ ] T051a [P] [US2] 建立 `backend/src/rooms/secret-view.ts`:只回傳本人的 `secret.confirmed`
```

# Rule 5 [must] - 為了讓介面元素成立而必須改的既有檔都有任務
- 介面元素要照規格成立、卻不在介面元素清單上的既有檔,每一個都要有任務負責,或寫進某個任務的檔案清單:
  - 原型增補的樣式要搬到的共用樣式檔
  - 讓樣板與路由共用同一個函式的註冊點
  - 被改掉或移除的符號在既有程式裡的每一個呼叫端;呼叫端從既有程式搜出來,不憑記憶列
  - 新增列舉值、狀態或類型時,同一個概念的每一份清單(常數、對應表、樣板裡的列表);以既有的同類值從既有程式搜出來,逐份判斷新值要不要加
- 為什麼:介面元素清單只列規格檔裡的元素,為了讓它們成立而要跟著改的既有檔不在任何規格檔上;沒有任務提到它們,implement 做到一半才發現要改,只能塞進某個任務再回 plan.md 追認,使用者確認任務清單時看不到這些改動,任務的完成範圍也對不上實際改到的檔

## good example
- `app/config.py` 拿掉推導屬性,**搜出用到它們的 4 個檔,寫進同一個任務的檔案清單**
```
- [ ] T031 [US2] 建立 `app/services/ai_settings.py`:`resolve(conn, env) -> EffectiveSettings`(每項的值與來源、要不要帶 key)、`validate_base_url`、`LOCAL_MODELS`;`app/config.py` 只保留讀環境變數的預設值,拿掉推導屬性後,呼叫端 `app/main.py`、`app/services/batch_ops.py`、`app/routes/notes.py`、`app/routes/home.py` 改讀 `ai_settings.resolve` 的生效設定(讓 T028 轉綠)

  - 📎 `research.md` § R4、§ R5;`plan.md` § 待決問題 Q7、Q15
```

## bad example
- 同一個任務,只寫了 `app/config.py` 要改成什麼,**沒有搜呼叫端**;implement 拿掉推導屬性後 4 個檔一起壞掉,只好自己改完再到 plan.md 登記一題追認(迭代 002 的 Q46)

  - 📎 `research.md` § R4、§ R5;`plan.md` § 待決問題 Q7、Q15

# Rule 6 [must] - 被取代的既有元素寫進第一個破壞舊測試的綠燈任務
- 增量迭代時,規格檔標為被取代或移除的既有元素(例如 OpenAPI 根層的 `x-removed-operations`,以及 `x-change` 寫明改掉的行為),每一個都要寫進第一個破壞舊測試的綠燈任務:移除舊實作,並改寫或淘汰斷言舊行為的既有測試
- 那個綠燈任務的「執行全部測試確認都通過」包含這些舊測試,不留 skip
- 為什麼:介面元素清單只列這次規格檔裡還在的元素,被取代的舊元素不在清單上;沒有任務負責,第一個改掉舊行為的綠燈一做完舊測試就紅,implement 只能先加 skip、等後面的故事再刪,中間每一個 Checkpoint 的「全綠」都少算了這些測試

## good example
- US1 的 T014b 刪掉單一 Markdown 筆記的 `build_markdown`,001 斷言單一筆記編輯的測試就在這裡壞掉;**改寫它們寫進同一個綠燈任務**,路徑照 001 tasks.md 介面覆蓋表 `paths./notes/{noteId}/edited.put` 的測試欄
```
- [ ] T014b [US1] 🟢 /tdd 綠燈:在 `app/services/ingest.py` 只寫讓 US1-BE-03 通過的程式碼:刪除 `build_markdown`,整理完成時以 `repos.documents` 建立逐字稿文件與有摘要時的筆記文件;同一個任務改寫 `tests/acceptance/test_us6_edit.py`、`tests/integration/test_routes_us6.py`,刪掉斷言單一 Markdown 筆記與 `PUT /notes/{noteId}/edited` 的案例,執行全部測試確認都通過、不留 skip(依賴 T014a)
  - 🧪 `testplan.md` § US1-BE-03
  - 📎 `contracts/web.openapi.yaml` § `x-removed-operations`(`saveEditedNote`、`restoreOriginalNote`)
```

## bad example
- 同一個情況,**US1 的綠燈任務沒有提到舊測試**,只在 US4 的紅燈任務寫「001 的路由已移除」;US1 一做完 `test_routes_us6.py` 就紅,implement 先加 `@pytest.mark.skip(reason="002 US4 取代")`,US1 到 US3 的 Checkpoint 都沒有跑到它

## good example

# Rule 7 [must] - 要改寫或淘汰的舊測試在任務裡寫成確切的路徑
- 〈被取代的既有元素寫進第一個破壞舊測試的綠燈任務〉的綠燈任務,舊測試從前一迭代 tasks.md 的介面覆蓋表或 `tests/` 找出來,在任務裡一個檔一個檔寫成確切的路徑
- 為什麼:只寫「受影響的測試」,implement 得自己再搜一次,搜漏的那個檔照樣要靠 skip 撐過去

## good example
- 舊測試**寫成確切的路徑**,從 001 tasks.md 的介面覆蓋表查到,一個檔一個檔列
```
- [ ] T017b [US1] 🟢 /tdd 綠燈:在 `app/templates/note.html` 只寫讓 US1-FE-02 通過的程式碼;同一個任務改寫 `tests/integration/test_pages_us1.py`、`tests/integration/test_pages_us6.py`、`tests/integration/test_pages_us7.py`,刪掉斷言單一筆記頁版面、單一份編輯與「原始版本已更新」的案例(依賴 T017a)
  - 📎 `contracts/web.openapi.yaml` § `paths./notes/{noteId}.get`(`x-change`)
```

## bad example

```

# Rule 9 [must] - 外部程序端點的替身依收到的參數產生輸出

# Rule 10 [must] - 從 spec package 複製的檔寫出要改的相對路徑

```
specs/003/deploy/compose.yaml:context: ../../..、dockerfile: specs/003/deploy/Dockerfile

- [ ] T026 把 spec package 的 `deploy/compose.yaml` 複製到 repo 的 `deploy/compose.yaml`,內容不改

- [ ] T027 把 spec package 的 `deploy/.env.example` 複製到 repo 的 `deploy/.env.example`,內容不改(打開確認過沒有相對路徑)

# Rule 16 [must] - 量測與人工驗證的案例排成量測任務
- testplan.md 驗證方式為 `📏 量測` 或 `📏 人工` 的案例,各排一個 `📏 量測` 任務(人工驗證寫成 `📏 量測(人工)`),🧪 指到那個案例
- 任務照案例寫的樣本、環境與門檻量:描述寫出同一份樣本、同一個環境、要記下的數字、和門檻的比較,以及結果寫到哪個檔;只準備樣本、只跑相關測試或用替身跑的不算量到

# Rule 17 [must] - 不標步驟的任務只限三類
- 不標 🔴、🟢、🔵、📏 的任務只能是這三類:工具鏈設定、原樣複製 spec package 的規格檔、CI 設定,而且只放在 Setup
- 其餘會改到程式或測試的任務,都要是某個案例的紅燈、綠燈,某一節的重構,或某個量測案例的量測;排不進去的,在 plan.md 登記待決問題,問要不要在 testplan 補案例
- 前置功能整片還不存在時(例如故事 5 先做,故事 1~4 的進房、開始都還沒有),由第一個需要它的案例的綠燈任務只做出讓這個案例通過的最小版本,不另開不標步驟的任務
- 為什麼:沒有步驟標記的任務,implement 不會照 tdd 的規則做,也沒有紅燈證明它需要;一旦開了例外,共用的程式、順手的改動都會往這裡塞,測試逼不出來的程式碼就混進去了

## good example

# Rule 18 [must] - 共用模組歸給一個端點節
- 一個檔會被同一個故事兩個以上的端點節用到時,由第一個用到它的案例所在的節負責建立;建立它的任務寫出這個檔
- 其他節用到它的任務,描述裡寫出這個檔與「依賴 T<建立它的任務編號>」,讓 implement〈同一個檔的任務不同時做〉認得出來,把這幾節排成依序做
