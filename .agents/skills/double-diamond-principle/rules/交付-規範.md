# Rule 1 [must] - 完整實作前先小規模測試
- 在投入完整實作前,以最便宜的方式(spike、測試切片、單項效能量測)驗證最不確定的關鍵點
- 拿來判斷的測試或檢查器本身也必須先驗證:先餵入已知為壞的輸入,確認檢查器確實會報錯失敗,方能採信其「通過」的結果
- 為什麼:過早投入完整實作會造成高昂重工成本;未經驗證的檢查器容易產生假綠燈盲點

## good example
- **小規模驗證效能並先測測試器**:用 3000 筆資料量測小切片,且確認量測器對慢程式確實報警
```markdown
Deliver 動作:
1. 先寫小規模 benchmark 腳本,測試原程式在 3000 筆確實為 12 秒(確認量測器有效)。
2. 針對「單次讀取」做 10 行 spike 切片實測,耗時降為 0.3 秒,成功驗證關鍵不確定點。
```

## bad example
- **跳過小規模驗證直接重構**:直接把整個系統改寫完才跑測試,中途失敗全部報銷
```markdown
Deliver 動作:不先測瓶頸或相容性,一口氣修改五個檔案重構整個輸出模組,結果跑下去才發現架構不符。
```

# Rule 2 [must] - 依測試結果淘汰與改進
- 依小規模測試之客觀數據或結果淘汰行不通的方案,並明確記下淘汰原因
- 選定行得通的方案並依測試結果調整細節後再完成實作,附上前後對照之量測數字或驗證證據
- 很小的修改可省略 spike,但仍需以 brief 定義之成功準則進行驗收
- 為什麼:淘汰記錄能防止未來重複嘗試失敗路徑;量測證據是成果驗收的客觀基礎

## good example
- **以實測淘汰快取並附前後數字**:列出快取方案被淘汰的數據與理由
```markdown
淘汰方案:快取方案在新增一筆資料後需額外處理清空邏輯,複雜度高且耗時 0.4 秒;單次讀取已達 0.3 秒且無過期問題。淘汰快取方案。
實測證據:spend list 執行時間由 12.1 秒降至 0.28 秒,輸出內容 100% 一致,所有測試通過。
```

## bad example
- **憑個人直覺挑選且未留淘汰依據**:未有任何數據即說某方案不好,無量測證據
```markdown
覺得快取比較難寫所以不採用,實作完後只說「程式改好了現在變很快」,沒有任何數據。
```

# Rule 3 [must] - 實作中學到新認知時回頭修正
- 若在實作或測試過程中學到的新事實動搖了先前的假設或問題定義,不可默默偏離既有 brief 或硬做下去
- 必須回到對應的 Phase(Define 或 Discover)更新 brief 與規格,並清楚向使用者說明回頭修正的原因與依據
- 為什麼:Double Diamond 是非線性迭代流程,及早回頭修正能防止把錯的規格做完

## good example
- **發現資料不符主動回頭修正**:實作中發現欄位與原 brief 不符,回溯 Define 更新 brief
```markdown
實作中發現:歷史資料中金額包含負數(退款),原 brief 僅定義正數累計。
回頭動作:回溯至 Phase 2 更新 brief 的成功準則與限制,明確將負數納入計算,並於回報中特別說明此項回溯。
```

## bad example
- **默默自行硬改或忽視矛盾**:發現問題但硬著頭皮做完,導致交付成果與 brief 嚴重脫節
```markdown
實作中發現歷史資料有負數,自己默默忽略或私自把負數濾掉,不更新 brief 也不告知使用者。
```
