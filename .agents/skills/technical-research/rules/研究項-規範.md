# Rule 1 [must] - 選型的研究項寫出要對照的同類產品
- 研究項是在幾個方案之間挑一個(前端做法、後端框架、資料怎麼存、怎麼部署)時,列出 1 到 3 個解決同一件事的現有產品,開源或可以自架的優先,並寫出要對照它們的哪一點
- 只查一個技術事實、不用在方案之間挑的研究項(某個 API 的限制、某個工具的參數),不用列
- 為什麼:只比技術本身,容易選出同類產品沒有人這樣做的組合;等使用者問「別人怎麼做」才回頭補查,已經寫好的方案要整段重來

## good example
- 「前端做法」要在幾個方案之間挑,**列出兩個做同一件事的自架產品與要對照的點**
```
R8. 前端:伺服器端渲染、Markdown 與 Mermaid、XSS 防護(FR-003、FR-011、使用者指定)
  同類產品:Pinchflat、YouTubeTLDR —— 對照它們用 SPA 框架還是伺服器端渲染
```

## bad example
- 同一個研究項,但**只列了要比的技術**;research.md 寫完才發現同類產品都沒用 SPA,方案得重新比
```
R8. 前端:伺服器端渲染、Markdown 與 Mermaid、XSS 防護(FR-003、FR-011、使用者指定)
  候選:React SPA、Vue SPA、伺服器端渲染 + htmx
```

## good example
- 邊界:「取得 YouTube 字幕」只查 yt-dlp 能不能取到字幕、要哪些參數,**不用在方案之間挑,不列同類產品**
```
R1. 取得 YouTube 字幕(FR-002、NFR-001、SC-001)
```

## bad example
- 邊界:同一個研究項,**也硬列了同類產品**;要查的是一個工具的行為,別的產品怎麼做不會改變答案,只多了一次查證
```
R1. 取得 YouTube 字幕(FR-002、NFR-001、SC-001)
  同類產品:Pinchflat、Whishper —— 對照它們怎麼取字幕
```

# Rule 2 [must] - spec 對既有資料或外部服務的假設先查一筆真實的再列
- spec.md 的假設涉及既有資料(每份都有某個欄位、某種格式)或外部服務(會回某個東西、有某個限制)時,列研究項之前先查一筆真實資料、打一次真實請求,把看到的結果和來處寫進研究項的描述
- 讀程式只能知道 App 送了什麼、讀了什麼,不能當作資料或服務本身的事實;資料和服務都要各看一次實物
- 查不了(沒有存取權、會計費、資料還不存在)時,研究項寫明「假設未查」與原因
- 為什麼:研究項是照假設列的,假設錯了,列出來的就是錯的問題;先從程式或印象推斷「服務沒有這個功能」,整個方向會跟著走歪,而真相常常只差一次請求就看得到

## good example
- spec 假設每份逐字稿都有時間點;**看一份真實筆記、打一次服務**,才知道沒有時間點是 App 沒要,研究項因此問對問題
```
假設:每份逐字稿每段開頭都有 [mm:ss]
查資料:data/notes/m-07.md → 外部辨識的筆記沒有時間點
查服務:POST /v1/audio/transcriptions,response_format=verbose_json → 200,有 segments[].start
R2. 外部辨識改要逐句時間(FR-002):服務有,目前 App 只要 json
```

## bad example
- 同一個假設,**只讀程式就下結論**;程式送 `json`、只讀 `text`,於是把「服務沒有時間碼」當事實,研究項問成要自己估時間
```
假設:每份逐字稿每段開頭都有 [mm:ss]
讀 remote_asr.py:只讀 text → 外部服務沒有時間碼
R2. 沒有時間碼時怎麼估算每段時間(FR-002)
```

## good example
- 邊界:外部服務要計費又沒有測試金鑰,**真的查不了,照實寫明**,研究項不把假設當事實
```
假設:付款服務的退款 webhook 會帶原訂單編號
查服務:沒有測試金鑰,實際請求會扣款 → 假設未查
R5. 退款 webhook 的欄位(FR-012):假設未查,先查文件,上線前以測試金鑰驗
```

## bad example
- 邊界:同一個假設,**因為查不了就不提**;研究項看起來像已知事實,下游照它做
```
假設:付款服務的退款 webhook 會帶原訂單編號
R5. 用 webhook 的原訂單編號對應退款(FR-012)
```

## good example
- 邊界:假設是使用者定的產品行為,**不涉及既有資料或外部服務,沒有實物可看**,不必查
```
假設:使用者一次只校正一份筆記
R3. 校正工作的佇列模型(FR-001)
```

## bad example
- 邊界:同一個假設,**也去翻資料庫**;資料庫裡沒有這個行為,查了也回答不了
```
假設:使用者一次只校正一份筆記
查資料:SELECT * FROM jobs LIMIT 1
R3. 校正工作的佇列模型(FR-001)
```
