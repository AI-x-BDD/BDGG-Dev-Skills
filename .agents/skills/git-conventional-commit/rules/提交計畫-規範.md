# Rule 1 [must] - 一筆 commit 只裝一件事
- 這批變更裡性質不同、彼此不需要對方就能成立的事,各自一筆;典型的組合:新功能 / 無關的 bug 修正 / 順手做的 refactor / 排版調整 / 相依套件升級 / 文件
- 為什麼:header 只寫得下一個 type,其餘的變更會從 changelog 與版號計算裡消失;日後要 revert 其中一件,也得連另一件一起退掉

## good example
- 工作目錄混了四件互不相依的事,**四件各一筆**
```
工作目錄
  todo/cli.py、todo/store.py、tests/test_delete.py   新增 delete 指令
  todo/dates.py、tests/test_dates.py                 修正 +N 到期日差一天
  README.md                                          補安裝說明
  pyproject.toml                                     ruff 0.4 → 0.6

提交計畫
  1. feat: add delete command
  2. fix: correct off-by-one in +N due dates
  3. docs: add install instructions
  4. build: bump ruff to 0.6
```

## bad example
- 同一個工作目錄,但**四件事裝進同一筆**;header 只寫了新功能,修正、文件與升版在 changelog 裡都看不到
```
提交計畫
  1. feat: add delete command and other updates
```

## good example
- 邊界:兩件事改在同一個檔,但**落在不同的 hunk、彼此不需要對方就能成立**,仍然各自一筆
```
工作目錄
  todo/store.py  第 7–10 行   load 遇到空檔案會當掉的修正
  todo/store.py  第 13–15 行  新增 clear 指令

提交計畫
  1. fix: return empty list when the data file is empty
  2. feat: add clear command
```

## bad example
- 邊界:同一個情況,因為「都改在 `store.py`」就併成一筆;**是幾筆看的是有幾件事,不是有幾個檔**
```
提交計畫
  1. feat: add clear command and fix empty file crash
```

# Rule 2 [must] - 測試跟著它驗證的變更走
- 測試放進它所驗證的那一筆 `feat` 或 `fix`;只有單純補測試(被測的程式這次沒有改)才獨立成 `test`
- 為什麼:測試與它驗證的變更分在兩筆,前一筆單獨取出時不是沒有測試保護,就是測試先進來而跑不過

## good example
- `test_delete.py` **和 delete 指令同一筆**,`test_dates.py` 和日期的修正同一筆
```
1. feat: add delete command              todo/cli.py、todo/store.py、tests/test_delete.py
2. fix: correct off-by-one in +N dates   todo/dates.py、tests/test_dates.py
```

## bad example
- 同一批變更,但**兩個測試檔另外收成一筆 `test`**;前兩筆單獨取出時都沒有測試驗證
```
1. feat: add delete command              todo/cli.py、todo/store.py
2. fix: correct off-by-one in +N dates   todo/dates.py
3. test: add tests                       tests/test_delete.py、tests/test_dates.py
```

## good example
- 邊界:這次替**沒有改動的 `list` 指令**補了測試;沒有對應的 `feat` 或 `fix` 可以跟,獨立成 `test`
```
1. feat: add delete command              todo/cli.py、todo/store.py、tests/test_delete.py
2. test: cover list command              tests/test_list.py
```

## bad example
- 邊界:同一個情況,把 `test_list.py` 順手塞進 delete 那一筆;看起來也是「測試跟著功能」,但**它驗證的不是這一筆的變更**
```
1. feat: add delete command              todo/cli.py、todo/store.py、tests/test_delete.py、tests/test_list.py
```

# Rule 3 [must] - 同一種性質、同一個目的的修改是一筆
- 同一種性質、同一個目的的幾處修改不再往下拆;判斷的依據是有幾種性質不同的事,不是改了幾個地方
- 為什麼:拆得比事情還細,歷史裡每一筆都不完整,要 revert 這件事得找齊好幾筆

## good example
- README 改了三個地方,**都是在修文件,一筆 `docs`**
```
README.md
  修一個錯字
  補一段安裝說明
  改一句介紹

提交計畫
  1. docs: fix typo and expand install instructions
```

## bad example
- 同樣三處修改,但**一處一筆**;三筆的性質與目的都一樣
```
提交計畫
  1. docs: fix typo
  2. docs: add install instructions
  3. docs: reword introduction
```

## good example
- 邊界:description 要用「and」才寫得完,但**兩處修改性質相同、目的相同**,仍然是一筆
```
1. docs: fix typo and expand install instructions
```

## bad example
- 邊界:同一筆,因為 description 出現了「and」就拆成兩筆;**「and」連的是同一件事的兩處,不是兩件事**
```
1. docs: fix typo
2. docs: expand install instructions
```

# Rule 4 [must] - 交纏在同一行或同一段的變更是一筆
- 同一行同時改了兩樣東西、或兩處修改互相依賴才跑得動時,不拆
- description 寫主要的那件事,其餘的寫進 body
- 為什麼:硬拆開來,其中一筆單獨取出時跑不動,或得靠〈不為了拆而寫出中間版本〉禁止的做法才湊得出來

## good example
- 選項改名與預設值搬家**落在同一行**,一筆,次要的那件寫進 body
```
- parser.add_argument("--file", default="todo.json")
+ parser.add_argument("--data-file", default=default_data_path())

提交計畫
  1. feat(cli)!: rename --file to --data-file
     body:預設的資料檔位置同時改到使用者資料目錄
```

## bad example
- 同一行,但**拆成改名與搬家兩筆**;第一筆需要一個「只改名、預設值不動」的版本,使用者從來沒寫過那一行
```
提交計畫
  1. feat(cli)!: rename --file to --data-file
  2. feat(cli)!: move default data file to user data dir
```

## good example
- 邊界:兩處修改在不同的檔,但**函式改了簽名、呼叫端跟著改,少了任何一邊都跑不動**,仍然是一筆
```
todo/store.py   def save(items, path)  →  def save(path, items)
todo/cli.py     store.save(items, path) →  store.save(path, items)

提交計畫
  1. refactor: put path first in store.save
```

## bad example
- 邊界:同一個情況,因為「在不同的檔」就拆成兩筆;**第一筆單獨取出時,呼叫端傳的參數順序是錯的**
```
提交計畫
  1. refactor: put path first in store.save   todo/store.py
  2. refactor: update save callers            todo/cli.py
```

# Rule 5 [must] - 不為了拆而寫出中間版本
- 拆開之後得由你動手寫出一個「中間版本」的檔案內容,就不要拆
- 只是把原本寫好的內容少放幾行不算:刪掉 patch 裡不屬於這一筆的行、設定檔先不放後面那一筆才需要的幾項
- 為什麼:那個版本使用者沒寫過、沒人跑過,把它放進歷史等於提交一段沒驗證過的程式

## good example
- 使用者把 `load()` 整個重寫並順便加了快取,兩者寫在同一段;**不另外寫一個沒有快取的版本,一筆**
```
提交計畫
  1. perf: cache parsed data file in load
     body:重寫 load() 的讀檔流程,並以檔案的 mtime 當快取的鍵
```

## bad example
- 同一段修改,但**為了拆成兩筆,自己寫了一個「重寫過、還沒有快取」的 `load()`**;那個版本只存在於這一筆 commit 裡
```
提交計畫
  1. refactor: rewrite load        ← 檔案內容是為了這一筆另外寫的
  2. perf: cache parsed data file
```

## good example
- 邊界:兩個測試緊鄰寫在同一個 hunk;**把 patch 裡屬於 `test_clear` 的那幾行刪掉再 stage,每一行仍是使用者原本寫的**,所以可以拆
```
tests/test_store.py 的 hunk
  +    def test_load_empty(self): ...   ← 留在 fix 那一筆
  +    def test_clear(self): ...        ← 從 patch 刪掉,留給 feat 那一筆
```

## bad example
- 邊界:同一個 hunk,為了讓第一筆跑得過,**另外補了一行使用者沒寫過的 stub**;只多一行,但那已經是中間版本
```
tests/test_store.py 的 hunk
  +    def test_load_empty(self): ...
  +    def test_clear(self): ...
todo/store.py
  +def clear(path): pass               ← 為了第一筆另外寫的
```

# Rule 6 [should] - 拿不準時偏向少拆
- 拿不準該不該再往下拆時偏向少拆,並在回報裡說明
- 為什麼:使用者想再細分很容易,要把拆錯的歷史合回來比較麻煩

## good example
- 一段修改看起來像重構,又像順便修了邊界條件,分不清楚;**收成一筆,回報裡交代**
```
提交計畫
  1. fix: handle empty input in parse_due

回報:parse_due 的改寫同時整理了分支的寫法,分不出哪幾行只是整理,所以收在同一筆。
```

## bad example
- 同一段修改,但**憑猜測硬拆成兩筆**;哪幾行屬於哪一筆是猜的,拆錯了要改寫歷史才合得回來
```
提交計畫
  1. refactor: simplify parse_due branches
  2. fix: handle empty input in parse_due
```

## good example
- 邊界:README 的修改與程式的修正**性質明顯不同,不是「拿不準」**,照〈一筆 commit 只裝一件事〉拆
```
提交計畫
  1. fix: handle empty input in parse_due
  2. docs: document the +N syntax
```

## bad example
- 邊界:同一批變更,拿「偏向少拆」當理由併成一筆;**這條 Rule 只管分不清楚的情況**,分得清楚的仍然要拆
```
提交計畫
  1. fix: handle empty input in parse_due and update README
```

# Rule 7 [must] - 每一筆都能獨立通過建置與測試
- 拆完的每一筆單獨取出時,建置與測試都要通過
- 沒有通過,多半代表這一筆用到了還沒 stage 的東西:把它一起帶進來、調換提交的順序,或承認這兩件事其實分不開
- 為什麼:日後 `git bisect` 或 revert 單一 commit 時,會落在壞掉的狀態

## good example
- fix 用到了 feat 那一筆才加進來的 `parse_offset()`,單獨取出時沒過;**調換順序,讓它排在 feat 之後**
```
原本的計畫
  1. fix: correct off-by-one in +N dates   ← 單獨取出:NameError: parse_offset
  2. feat: accept +Nw for weeks

調整後
  1. feat: accept +Nw for weeks
  2. fix: correct off-by-one in +N dates
```

## bad example
- 同一個結果,但**照原本的順序提交**,理由是兩筆都提交完之後測試會過;第一筆單獨取出時是壞的
```
提交計畫
  1. fix: correct off-by-one in +N dates   ← 單獨取出:NameError: parse_offset
  2. feat: accept +Nw for weeks
```

## good example
- 邊界:調換順序之後還是沒過,兩筆互相用到對方的東西;**承認分不開,併成一筆**
```
調換後
  1. feat: accept +Nw for weeks            ← 單獨取出:測試用到修正後的日期算法
  2. fix: correct off-by-one in +N dates

調整後
  1. feat: accept +Nw for weeks
     body:同時修正 +N 少算一天的問題,新的週數換算建立在修正後的算法上
```

## bad example
- 邊界:同一個情況,把那個會失敗的測試先標成 skip 讓第一筆通過;看起來每一筆都過了,但**通過的原因是測試被關掉**
```
1. feat: accept +Nw for weeks              ← 加了 @unittest.skip 才通過
2. fix: correct off-by-one in +N dates     ← 再把 skip 拿掉
```

# Rule 8 [must] - 提交在使用者指示或 repo 既有的 branch
- 要提交在哪一條 branch,依使用者的指示或 repo 既有的整合方式;不要因為要 commit 就另外開 branch
- 為什麼:這支 skill 只管怎麼切、訊息怎麼寫;多開的 branch 使用者沒有要求,還得另外合回來

## good example
- 使用者在 `main` 上說「幫我 commit」,repo 的歷史都是直接提交在 `main`;**就提交在 `main`**
```
$ git branch --show-current
main

提交計畫
  branch:main
  1. feat: add delete command
```

## bad example
- 同一個情況,但**自己開了一條 feature branch**;使用者回來發現 `main` 上什麼都沒有
```
$ git switch -c feature/delete-command

提交計畫
  branch:feature/delete-command
  1. feat: add delete command
```

## good example
- 邊界:repo 的 `CONTRIBUTING.md` 寫明 `main` 受保護、一律走 merge request;**開 branch 是照 repo 既有的整合方式**
```
CONTRIBUTING.md:所有變更一律開 branch 並發 merge request,main 不接受直接 push。

提交計畫
  branch:feat/delete-command
```

## bad example
- 邊界:repo 沒有這種規定,歷史也都直接提交在 `main`,只因為「直接提交到 main 不太好」就開了 branch;**那是自己的習慣,不是 repo 的整合方式**
```
$ git log --oneline --merges | wc -l
0

提交計畫
  branch:feat/delete-command
```

# Rule 9 [must] - 已經共用的 commit 不自行改寫
- 要修改的 commit(用錯 type、訊息要改寫)還沒有 push 到共用分支:用 `git commit --amend` 或 `git rebase -i` 改掉
- 已經 push 到共用分支或已經發布的 commit,先問過使用者再動,不自行改寫
- 為什麼:改寫已經共用的歷史,其他人手上的 clone 會對不上,得靠 force push 才推得上去

## good example
- 剛提交的那一筆 type 用錯了,**還沒 push,直接 amend**
```
$ git status -sb
## main...origin/main [ahead 1]

$ git commit --amend -F <訊息檔>
```

## bad example
- 同一個錯誤,但那一筆**已經在 `origin/main` 上**,仍然直接 amend 再 force push
```
$ git status -sb
## main...origin/main

$ git commit --amend -F <訊息檔>
$ git push --force
```

## good example
- 邊界:那一筆 push 到了一條 feature branch,看不出有沒有其他人拉過;**不確定算不算共用,先問使用者**
```
$ git status -sb
## feat/delete-command...origin/feat/delete-command

問使用者:a1b2c3d 的 type 應該是 feat,但它已經 push 到 origin/feat/delete-command。要改寫並 force push 嗎?
```

## bad example
- 邊界:同一個情況,認定「feature branch 只有自己在用」就直接改寫;**有沒有人拉過是猜的**
```
$ git commit --amend -F <訊息檔>
$ git push --force-with-lease
```
