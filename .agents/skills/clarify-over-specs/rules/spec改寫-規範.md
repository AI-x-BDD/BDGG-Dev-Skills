# Rule 1 [must] - 決策寫進它改變的章節
- 每一項已確認的決策,依下表寫進它改變的章節;只寫進釐清紀錄不算寫回

| 決策改變的是 | 寫進 |
|---|---|
| 系統要做什麼 | 所屬故事的功能需求,或跨兩個以上故事時的全域功能需求 |
| 做到什麼程度 | 非功能需求;能量的門檻同時寫進成功標準 |
| 例外情況下的反應 | 邊界情況 |
| 資料的屬性、唯一性、關係 | 關鍵實體 |
| 範圍內外、預設 | 假設 |

- 為什麼:下游的 technical-research 與 system-analysis 只讀正文;答案只留在釐清紀錄,下游照舊的模糊寫法去做,這一場等於白問

## good example
- 「搜尋要快」問到了 1 秒;**改寫了 FR,新增 NFR 與 SC,釐清紀錄也有一筆**
```
問答:搜尋相簿名稱,結果要在多久內出現? → 答:1 秒內

改寫後
- **FR-009**:使用者可以用相簿名稱搜尋。
- **NFR-002**:搜尋結果必須在 1 秒內出現(門檻見 SC-008)。
- **SC-008**:相簿達 500 本時,輸入名稱到看見搜尋結果不超過 1 秒。

### 2026-10-19 釐清
- 問:搜尋相簿名稱,結果要在多久內出現? → 答:1 秒內
```

## bad example
- 同一個答案,但**只追加到釐清紀錄**;FR-009 還是寫著「搜尋要快」
```
- **FR-009**:使用者可以用相簿名稱搜尋,搜尋要快。

### 2026-10-19 釐清
- 問:搜尋相簿名稱,結果要在多久內出現? → 答:1 秒內
```

# Rule 2 [must] - clarify 交還的假設只寫進「假設」
- clarify 交還的「假設」是沒有問使用者、採用通行預設的事,只寫進 spec.md 的「假設」,不寫成功能需求、非功能需求或邊界情況
- 為什麼:寫進需求的條目,下游會當成使用者拍板過的事去實作與驗收;放在「假設」,讀的人才知道這一條沒有問過,不對可以推翻

## good example
- clarify 交還一條假設;**只寫進「假設」**
```
clarify 的假設:匯入、重新掃描與自動分類同一時間只跑一項

spec.md「假設」
- 匯入、重新掃描與自動分類同一時間只跑一項,再啟動第二項時提示已有工作在進行。
```

## bad example
- 同一條假設,但**寫成邊界情況**;看起來像使用者決定過的需求
```
clarify 的假設:匯入、重新掃描與自動分類同一時間只跑一項

spec.md「邊界情況」
- 匯入、重新掃描與自動分類同一時間只能進行一個,另一個要再啟動時,系統應擋下並提示。
```

# Rule 3 [must] - 被推翻的舊說法直接取代
- 決策和正文原有的說法衝突時,改寫原有的那一句,不在旁邊另外加一句新的
- 為什麼:兩句並存,讀的人分不出哪一句才算數,下游可能照舊的那一句實作

## good example
- 決策是「多人共用」;**原本的那一條假設被改寫**,只剩一條
```
改寫前:- 只有一位使用者,不需要帳號、權限與分享;多人與分享不在第一版範圍內。
改寫後:- 家中成員共用同一個照片庫,每個人有自己的帳號;相簿分享不在第一版範圍內。
```

## bad example
- 同一個決策,但**舊的假設留著、在後面另加一條**;兩條假設互相矛盾
```
- 只有一位使用者,不需要帳號、權限與分享;多人與分享不在第一版範圍內。
- 家中成員共用同一個照片庫,每個人有自己的帳號。
```

# Rule 4 [must] - 釐清紀錄的舊答案註明修訂
- 釐清紀錄裡被這一場推翻的那一筆,在原答案後註明「(後經某日釐清修訂為…)」,不刪也不改原答案
- 為什麼:舊答案刪掉或直接改掉,之後就查不到需求為什麼變了,也分不出是使用者改了主意還是當初記錯

## good example
- **舊答案留著,後面註明修訂**
```
- 問:使用者範圍為何? → 答:只有一人使用,不需要帳號(後經 2026-10-19 釐清修訂為家中成員共用、各有帳號)
```

## bad example
- 同一筆,但**直接把舊答案改成新的**;看不出這個需求曾經是一個人用
```
- 問:使用者範圍為何? → 答:家中成員共用、各有帳號
```

# Rule 5 [must] - 新增條目後依出現順序重編
- 新增或刪除 FR、NFR、SC 之後,三種編號各自依在檔案裡出現的順序重新連號,內文引用跟著改成新編號
- 為什麼:spec.md 的結構檢查要求依出現順序全檔連號,插在中間的新條目不重編就過不了;引用沒跟著改,NFR 會指到另一條 FR

## good example
- 在故事 1 的 FR-007 後面新增一條;**後面的 FR 全部往後移,引用跟著改**
```
新增:故事 1 的 FR-008「相簿可以改名」

重編
- 原 FR-008 → FR-009
- 原 FR-009 → FR-010
引用:NFR-002 裡的「FR-009」改成「FR-010」
```

## bad example
- 同一條新增,但**為了不動既有的編號,接在最後編成 FR-015**;它出現在故事 1 裡,結構檢查會判不過連號
```
新增:故事 1 的 FR-015「相簿可以改名」(放在 FR-007 之後)
```

# Rule 6 [must] - 編號有變動就記下對照
- 重編之後,每一個編號有變動的條目都記下舊編號到新編號的對照,交給澄清報告
- 為什麼:同一個資料夾已經有 research.md、plan.md 或 tasks.md 時,它們引用的是舊編號;沒有對照表,下游的錨點會悄悄指到別條

## good example
- 重編了兩條,**兩條都記下對照**
```
編號對照:FR-008→FR-009、FR-009→FR-010
```

## bad example
- 同一次重編,但**只寫「後面的 FR 往後移了」**;tasks.md 裡的 ⚙ FR-009 該改成哪一條,得自己去比對
```
編號對照:FR-008 之後的 FR 都往後移一號
```

# Rule 7 [should] - 同一個東西全文用同一個詞
- 決策定下的名稱,或發現同一個東西有兩種叫法時,全文統一成一個,舊名稱只在第一次出現處標「(原稱 X)」
- 為什麼:同一個東西兩種叫法,下游會當成兩個實體,資料庫多一張表、API 多一組端點

## good example
- 「相簿」和「資料夾」指的是同一個東西;**全文統一成相簿,只在第一次出現處標原稱**
```
- **相簿(Album)**(原稱「虛擬資料夾」):一組照片的命名集合。
- **FR-006**:使用者必須能將一張或多張照片加入相簿。
```

## bad example
- 同一份 spec,但**兩種叫法都留著**;關鍵實體叫相簿,FR 叫虛擬資料夾
```
- **相簿(Album)**:一組照片的命名集合。
- **FR-006**:使用者必須能將一張或多張照片加入虛擬資料夾。
```

## good example
- 邊界:「照片資料夾」和「相簿」都有「資料夾」的意思,但**照片資料夾是伺服器上放原檔的地方,是另一個東西**,不統一
```
- **FR-001**:系統必須讓使用者選擇伺服器上的照片資料夾,把其中的照片匯入照片庫。
- **FR-006**:使用者必須能將一張或多張照片加入相簿。
```

## bad example
- 邊界:同一份 spec,看到兩個詞都有「資料夾」就**統一成相簿**;FR-001 變成從相簿匯入照片,意思整個錯了
```
- **FR-001**:系統必須讓使用者選擇伺服器上的相簿(原稱「照片資料夾」),把其中的照片匯入照片庫。
```
