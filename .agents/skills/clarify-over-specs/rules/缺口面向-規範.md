# Rule 1 [must] - 每個面向都要判定並對到寫回的章節
- 逐一判定下表每個面向在 spec.md 裡是清楚、部分還是缺少,一個都不跳過;判定為部分或缺少的,列成缺口,並記下答案要寫回哪個章節

| 面向 | 看什麼 | 答案寫回的章節 |
|---|---|---|
| 使用者故事與驗收情境 | 角色、目標、每個故事都有可以照著測的驗收情境 | 使用者故事、驗收情境 |
| 功能行為 | 系統要做的事、範圍內外的界線 | 功能需求 |
| 品質門檻 | 效能、容量、可用性有沒有數字 | 非功能需求、成功標準 |
| 邊界與失敗 | 空資料、錯誤輸入、同時操作、中斷之後怎麼辦 | 邊界情況 |
| 外部依賴失敗 | 用到的外部服務或檔案來源出問題時系統怎麼反應 | 邊界情況、功能需求 |
| 資料 | 實體、屬性、唯一性、狀態的變化 | 關鍵實體 |
| 權限與隱私 | 誰能看、誰能改、哪些資料要保護 | 功能需求、非功能需求 |
| 可觀測性 | 使用者或維護的人要看得到哪些紀錄與進度 | 功能需求、非功能需求 |
| 術語一致 | 同一個東西有沒有用了不同的名稱 | 全文 |
| 成功標準可量測 | 每條成功標準都有門檻與量法 | 成功標準 |
| 假設與範圍 | 預設與「不在第一版」有沒有寫明 | 假設 |

- 為什麼:只靠讀的時候想到什麼就問什麼,模板沒有欄位的面向(外部服務掛掉、誰看得到)最容易整片漏掉;缺口沒記下寫回的章節,問到的答案就只會留在釐清紀錄,下游只讀正文,照舊的模糊寫法去做

## good example
- **十一個面向都判定了**,每個缺口都記下要寫回的章節
```
spec:照片相簿整理

| 面向 | 狀態 | 缺口 | 寫回 |
|---|---|---|---|
| 使用者故事與驗收情境 | 清楚 | | |
| 功能行為 | 清楚 | | |
| 品質門檻 | 部分 | 匯入時的進度要多久更新一次沒有寫 | 非功能需求 |
| 邊界與失敗 | 清楚 | | |
| 外部依賴失敗 | 缺少 | 照片資料夾所在的磁碟離線時,匯入與瀏覽要怎麼反應 | 邊界情況 |
| 資料 | 清楚 | | |
| 權限與隱私 | 清楚 | | |
| 可觀測性 | 清楚 | | |
| 術語一致 | 清楚 | | |
| 成功標準可量測 | 清楚 | | |
| 假設與範圍 | 清楚 | | |
```

## bad example
- 同一份 spec,但**只列了讀到時想到的兩個面向**,外部依賴失敗沒有被判定,也沒有記下寫回的章節
```
spec:照片相簿整理

缺口
- 匯入進度要多久更新一次
- 相簿封面怎麼選
```

# Rule 2 [must] - 沒有門檻的形容詞與待定事項算缺口
- 正文裡沒有數字或可檢查條件的形容詞(快速、流暢、友善、穩定、安全),以及殘留的待定、TBD、之後再說,都判定為部分,列成缺口
- 形容詞旁邊已經指到有門檻的 SC 或 NFR 的,算清楚
- 為什麼:「要快」寫進規格,驗收的人和實作的人各自想像一個數字,做完才發現對不上;待定事項沒有被問,下游會自己替它決定

## good example
- 「搜尋要快」沒有門檻,**列成缺口**
```
FR-009:使用者可以用相簿名稱搜尋,搜尋要快。

缺口:品質門檻,部分,「搜尋要快」沒有門檻 → 寫回 非功能需求、成功標準
```

## bad example
- 同一句,但**因為已經寫了「要快」就判定為清楚**
```
FR-009:使用者可以用相簿名稱搜尋,搜尋要快。

品質門檻:清楚
```

## good example
- 邊界:「流暢」也是形容詞,但**同一句已經指到有門檻的 SC-003**,算清楚
```
NFR-001:照片庫達上萬張時,打開相簿、瀏覽與捲動必須維持流暢(門檻見 SC-003)。

品質門檻:清楚
```

## bad example
- 邊界:同一句,只因為出現「流暢」就**列成缺口**;SC-003 已經寫了 2 秒,使用者被問一題已經回答過的事
```
NFR-001:照片庫達上萬張時,打開相簿、瀏覽與捲動必須維持流暢(門檻見 SC-003)。

缺口:品質門檻,部分,「流暢」沒有門檻
```

# Rule 3 [must] - 技術選型與實作方法不列成缺口
- 缺口的答案是選哪一種技術、框架、資料庫、部署方式,或怎麼實作的,不列成缺口,記進「交給技術研究」
- 只有在不先決定就寫不出功能行為時,才列成缺口,而且問的是使用者看得到的行為,不是技術名稱
- 為什麼:這支 Skill 的下一步是 technical-research,技術選型在那裡會有實測與查證;在這裡問,使用者只能憑印象選,規格也被寫死了一個還沒研究過的技術

## good example
- 「資料庫要用哪一種」是技術選型;**記進交給技術研究,不出題**
```
spec 的假設:照片庫資料存放在伺服器端(資料庫待定)

交給技術研究:照片庫的資料要用哪一種資料庫存放
```

## bad example
- 同一句,但**列成缺口去問使用者**
```
spec 的假設:照片庫資料存放在伺服器端(資料庫待定)

缺口:假設與範圍,部分,資料庫要用 SQLite 還是 PostgreSQL → 寫回 假設
```

## good example
- 邊界:「要不要離線使用」聽起來像技術問題,但**它決定使用者沒有網路時看不看得到相簿**,是功能行為,列成缺口,問的是看得到的行為
```
缺口:功能行為,缺少,家裡網路斷掉時,已經匯入的相簿還要能打開嗎 → 寫回 功能需求
```

## bad example
- 邊界:同一個缺口,但**問成技術名稱**;使用者得懂 Service Worker 才答得出來
```
缺口:功能行為,缺少,要不要用 Service Worker 做離線快取 → 寫回 功能需求
```
