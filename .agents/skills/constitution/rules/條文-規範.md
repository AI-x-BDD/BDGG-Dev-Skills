# Rule 1 [must] - 只寫這次要約束的產出物
- 只替使用者這次講到的產出物列條文;使用者沒講到的產出物不預先建檔,也不補「順便也該有」的條文
- 使用者的話涵蓋好幾種產出物時(例如「REST 和 WebSocket 都要」),每一種都算講到
- 為什麼:憲法是一條一條長出來的,多寫的那幾條沒有人要求過,之後每支 Skill 都得照著對照;使用者不知道它們從哪裡來,也就不敢刪

## good example
- 使用者只講了 REST 的成功回應;**清單只有 `api-plan/openapi.md` 的一條**
```
使用者:我們的 API 成功回應都要包成 {data, meta},meta 要有 requestId

條文清單
  constitution/api-plan/openapi.md  Rule 1 [must] 成功回應一律包成 {data, meta}
```

## bad example
- 同一句話,但**順便替 AsyncAPI 與 DBML 也列了條文**;使用者沒提推送訊息,也沒提資料表
```
使用者:我們的 API 成功回應都要包成 {data, meta},meta 要有 requestId

條文清單
  constitution/api-plan/openapi.md   Rule 1 [must] 成功回應一律包成 {data, meta}
  constitution/api-plan/asyncapi.md  Rule 1 [must] 推送訊息一律包成 {data, meta}
  constitution/data-plan/schema.md   Rule 1 [must] 每張表都有 created_at 與 updated_at
```

## good example
- 邊界:使用者**親口講了 REST 和 WebSocket**,AsyncAPI 也是這次講到的產出物,所以列進來
```
使用者:REST 回應和 WebSocket 推送的訊息都要包成 {data, meta}

條文清單
  constitution/_shared/回應包裝.md  applies_to [api-plan/openapi, api-plan/asyncapi]
    Rule 1 [must] 回應與推送一律包成 {data, meta}
```

## bad example
- 邊界:使用者只講了 REST,覺得「一致比較好」就**把 AsyncAPI 也算進來**;看起來是同一件事,但推送訊息要不要包裝,使用者沒有決定過
```
使用者:REST 回應都要包成 {data, meta}

條文清單
  constitution/_shared/回應包裝.md  applies_to [api-plan/openapi, api-plan/asyncapi]
    Rule 1 [must] 回應與推送一律包成 {data, meta}
```

# Rule 2 [must] - Skill 已經要求的不寫成條文
- 條文只寫 Skill 的規範與樣板之外多加的要求;Skill 已經要求的,不寫成條文,列進「不寫成條文的事」並寫出是哪一支 Skill 的哪一條〈Rule 名稱〉已經要求
- 為什麼:同一個要求在 Skill 與憲法各寫一次,Skill 改版換了寫法時,憲法還留著舊的說法,兩份互相打架

## good example
- 要求帶 `requestId` 是在 Skill 的 `code`、`message` 之外**多加一個欄位**,條文只寫多加的這一點
```
使用者:錯誤回應要帶 requestId

條文清單
  constitution/api-plan/openapi.md  Rule 2 [must] 錯誤回應帶 requestId
    加嚴的地方:Error 多一個必填的 requestId
```

## bad example
- 同一句話,但條文**把 Skill 已經要求的 `x-error-codes` 也寫了一次**;Skill 改版換掉這個欄位時,憲法還留著舊的說法
```
使用者:錯誤回應要帶 requestId

條文清單
  constitution/api-plan/openapi.md  Rule 2 [must] 錯誤回應帶 requestId 與 x-error-codes
    每個失敗回應都要有 x-error-codes,Error 的必填欄位是 code、message、requestId
```

## good example
- 邊界:使用者講得像一條新要求,但**api-plan 的契約-規範已經要求每個條件都有具名的錯誤**,所以不寫成條文
```
使用者:伺服器檢查的每個條件都要有自己的錯誤碼

不寫成條文的事
  每個條件都有錯誤碼:api-plan/rules/契約-規範.md〈伺服器把關的條件都有具名的錯誤〉已經要求
```

## bad example
- 邊界:同一句話,因為使用者特別講了就**寫成條文**;內容和 Skill 的那一條一模一樣,只是多了一份要一起維護的說法
```
使用者:伺服器檢查的每個條件都要有自己的錯誤碼

條文清單
  constitution/api-plan/openapi.md  Rule 2 [must] 每個伺服器把關的條件都有具名的錯誤碼
```

# Rule 3 [must] - 和 Skill 規範衝突的條文點名取代的 Rule
- 要求和 Skill 的某一條 Rule 衝突、等於要翻掉它時,寫成條文,並在條文的 desc 加一行 `- 取代:<skill>/rules/<規範檔>〈Rule 名稱〉`;一條條文翻掉幾條 Rule 就寫幾行
- Skill 沒有規定的地方再多加要求,是加嚴,不寫取代
- 為什麼:沒有點名的衝突,Skill 寫產出物時只能在兩條規則之間自己選邊,檢查腳本也照樣用被翻掉的那一條判不過;點名之後,Skill 知道哪一條改照憲法,腳本也知道哪一項檢查要讓位

## good example
- problem+json **要拿掉 Skill 規定的 `x-error-codes`**,寫成條文並點名取代那一條
```
使用者:錯誤回應不要 x-error-codes,改用 problem+json

條文清單
  constitution/api-plan/openapi.md  Rule 3 [must] 錯誤回應改用 problem+json
    取代:api-plan/rules/契約-規範.md〈伺服器把關的條件都有具名的錯誤〉
```

## bad example
- 同一句話,寫成了條文,但**沒有點名取代哪一條**;api-plan 照樣依契約-規範寫出 `x-error-codes`,`check_api.py` 也照樣要求它
```
使用者:錯誤回應不要 x-error-codes,改用 problem+json

條文清單
  constitution/api-plan/openapi.md  Rule 3 [must] 錯誤回應改用 problem+json,不寫 x-error-codes
```

## good example
- 邊界:錯誤碼聽起來是 Skill 管的,但 **Skill 只要求錯誤碼具名,沒有規定大小寫**,多加規定是加嚴,不寫取代
```
使用者:錯誤碼一律大寫加底線

條文清單
  constitution/api-plan/openapi.md  Rule 2 [must] 錯誤碼一律大寫加底線
    加嚴的地方:Error 的 code enum 每個值符合 ^[A-Z][A-Z0-9_]*$
```

## bad example
- 邊界:同一句話,因為碰到 Skill 管的錯誤碼就**點名取代〈伺服器把關的條件都有具名的錯誤〉**;那一條的檢查被關掉,錯誤碼不具名也不會有人發現
```
使用者:錯誤碼一律大寫加底線

條文清單
  constitution/api-plan/openapi.md  Rule 2 [must] 錯誤碼一律大寫加底線
    取代:api-plan/rules/契約-規範.md〈伺服器把關的條件都有具名的錯誤〉
```

# Rule 4 [must] - 流程契約與機密不寫成取代
- 要翻掉的對象在 constitution 的 `scripts/check_constitution.py` 裡 `LOCKED` 列的範圍裡,或是 Skill 樣板的固定內容、檢查腳本的流程契約檢查(解析、`x-requirements`、需求覆蓋、編號)時,不寫成條文,列進「不寫成條文的事」,寫出它為什麼不可取代
- 不在這些範圍裡的 Rule,即使聽起來很重要,也照〈和 Skill 規範衝突的條文點名取代的 Rule〉寫成取代
- 為什麼:spec、research、plan、tasks 的編號與錨點被下游 Skill 的腳本讀取,被翻掉之後整條流程會讀不到它要的結構;機密的規則被翻掉,密碼就會進到 repo 裡

## good example
- FR 編號是 spec 樣板的固定內容,**被 system-analysis、tasks 的腳本讀取**,不寫成條文
```
使用者:spec 的 FR 編號改成 REQ-001

不寫成條文的事
  FR 改成 REQ:specify 的規範與 spec 樣板不可取代;FR 編號被 check_plan、list_elements、check_tasks 讀取
```

## bad example
- 同一句話,**寫成取代 specify 規範的條文**;spec.md 改用 REQ 之後,system-analysis 對不到任何需求出處
```
使用者:spec 的 FR 編號改成 REQ-001

條文清單
  constitution/specify/spec.md  Rule 1 [must] 需求編號用 REQ-001
    取代:specify/rules/需求歸屬-規範.md〈FR 寫系統做什麼,NFR 寫做到什麼程度〉
```

## good example
- 邊界:原型的審美設定聽起來是 Skill 的硬規定,但**〈審美設定只寫在 :root 變數〉不在不可取代的範圍**,照樣寫成取代
```
使用者:原型直接寫顏色就好,不用 :root 變數

條文清單
  constitution/uiux-plan/style.md  Rule 1 [must] 顏色直接寫在用到的地方
    取代:uiux-plan/rules/原型-規範.md〈審美設定只寫在 :root 變數〉
```

## bad example
- 邊界:同一句話,覺得是 Skill 的硬規定就**當成流程契約拒寫**;使用者要的風格寫不進憲法
```
使用者:原型直接寫顏色就好,不用 :root 變數

不寫成條文的事
  不用 :root 變數:原型-規範不可取代
```

# Rule 5 [must] - 管兩種以上產出物的條文放 `_shared/`
- 只管一種產出物的條文放 `constitution/<skill>/<產出物>.md`
- 管兩種以上產出物的條文放 `constitution/_shared/<主題>.md`,檔頭的 `applies_to` 列出它管的每一種產出物;同一條約束不在兩個檔各寫一次
- 為什麼:同一條約束寫在兩處,改的時候只改到一處,兩個產出物就照著不一樣的規定產出;只管一種的放進 `_shared/`,打開那個產出物的檔卻看不到它

## good example
- 時間格式同時管 API 與資料庫;**寫一份放進 `_shared/`,`applies_to` 列出兩種產出物**
```
使用者:時間一律帶時區,API 和資料庫都要

條文清單
  constitution/_shared/時間格式.md  applies_to [api-plan/openapi, data-plan/schema]
    Rule 1 [must] 時間點一律帶時區,名稱以 at 結尾
```

## bad example
- 同一句話,但**在兩個產出物的檔各寫一條**;之後只改了其中一條,API 與資料庫的時間格式就對不上
```
使用者:時間一律帶時區,API 和資料庫都要

條文清單
  constitution/api-plan/openapi.md  Rule 3 [must] 時間欄位用 date-time,帶時區
  constitution/data-plan/schema.md  Rule 2 [must] 時間欄位用 timestamptz
```

## good example
- 邊界:條文的「為什麼」提到了資料庫,但**它要求的只有 OpenAPI 裡的欄位**,只管一種產出物,所以放 `api-plan/openapi.md`
```
使用者:列表 API 的總數放在 meta.total,因為資料庫那邊是另外用 count 查的

條文清單
  constitution/api-plan/openapi.md  Rule 3 [must] 列表回應的總數放在 meta.total
```

## bad example
- 邊界:同一句話,因為提到資料庫就**放進 `_shared/`**,`applies_to` 卻只有一種產出物;打開 `api-plan/openapi.md` 看不到這條
```
使用者:列表 API 的總數放在 meta.total,因為資料庫那邊是另外用 count 查的

條文清單
  constitution/_shared/分頁.md  applies_to [api-plan/openapi]
    Rule 1 [must] 列表回應的總數放在 meta.total
```

# Rule 6 [must] - 只看產出物就判得了對錯
- 條文寫的是產出物裡看得到的東西:欄位、格式、命名、段落與它們的內容
- 不寫「好用」「清楚」「足夠」這類每個人判得不一樣的字眼;使用者的要求只講得出這類字眼時,不列成條文,把它當成缺口交給 clarify 問到具體的樣子
- 為什麼:Skill 寫完產出物要逐條對照條文;判不了對錯的條文,對照的人只能自己猜,猜出來的過與不過每次都不一樣

## good example
- 條文寫出**欄位放在哪裡**,打開 OpenAPI 就看得出有沒有照做
```
條文清單
  constitution/api-plan/openapi.md  Rule 1 [must] 列表回應的分頁資訊放在 meta
    要求:meta 有必填的 total 與 page,data 只放項目本身
```

## bad example
- 同一個要求,但**只寫「好用、清楚」**;同一份 OpenAPI,這次判過、下次可能判不過
```
條文清單
  constitution/api-plan/openapi.md  Rule 1 [must] API 回應要好用
    要求:回應結構清楚,前端容易使用
```

## good example
- 邊界:「這個情境是不是失敗情境」要讀懂句意才判得了,但**只看 spec.md 的驗收情境就判得出來**,不必猜作者的意思
```
條文清單
  constitution/specify/spec.md  Rule 1 [must] 每個使用者故事至少有一個失敗的驗收情境
    要求:至少一個情境的「則」寫的是系統拒絕、提示錯誤或維持原狀
```

## bad example
- 邊界:同一個方向,但寫成「**足夠的**邊界情況」;每個故事要幾個才算足夠,只看 spec.md 判不出來
```
條文清單
  constitution/specify/spec.md  Rule 1 [must] 驗收情境涵蓋足夠的邊界情況
```

# Rule 7 [must] - 流程、測試策略與團隊流程不寫進憲法
- 步驟順序、要不要問使用者、測試覆蓋率與測試方法、PR 審查與合併關卡,都不寫成條文,列進「不寫成條文的事」
- 測試策略類的,說明之後由 test-plan、test-tdd 這類 Skill 處理;流程類的,說明那是 Skill 本身的事
- 要求的對象是某個產出物裡的內容時,即使聽起來和測試或品質有關,仍然寫成條文
- 為什麼:憲法只約束產出物,不能改 SDD 的流程;把測試策略與團隊流程寫進來,就沒有任何一支 Skill 的產出物對照得到它,條文只是掛著

## good example
- 覆蓋率與 PR 審查**都不是任何產出物裡看得到的東西**,列進不寫成條文的事
```
使用者:每個功能的測試覆蓋率要 80% 以上,PR 也要有人審

不寫成條文的事
  測試覆蓋率 80%:測試策略,之後由 test-plan、test-tdd 處理
  PR 要有人審:團隊流程,不是任何產出物的內容
```

## bad example
- 同一句話,但**掛到 tasks.md 底下寫成條文**;tasks 交出的任務清單裡沒有覆蓋率可以對照
```
使用者:每個功能的測試覆蓋率要 80% 以上,PR 也要有人審

條文清單
  constitution/tasks/tasks.md  Rule 1 [must] 測試覆蓋率 80% 以上,PR 經過審查
```

## good example
- 邊界:「可量測」聽起來像測試策略,但**要求的是 spec.md 裡 NFR 的寫法**,是產出物的內容,所以寫成條文
```
使用者:spec 裡的每條 NFR 都要寫出可量測的數字

條文清單
  constitution/specify/spec.md  Rule 2 [must] 每條 NFR 寫出可量測的數字與單位
```

## bad example
- 邊界:同一句話,因為聽起來和測試有關就**列進不寫成條文的事**;spec.md 的 NFR 照樣可以寫成「要很快」
```
使用者:spec 裡的每條 NFR 都要寫出可量測的數字

不寫成條文的事
  NFR 要可量測:測試策略,之後由 test-plan、test-tdd 處理
```
