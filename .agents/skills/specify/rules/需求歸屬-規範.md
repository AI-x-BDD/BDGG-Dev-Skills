# Rule 1 [must] - 只屬於一個故事的需求放在那個故事底下
- 一條 FR 或 NFR,只有一個使用者故事會用到它,就寫在那個故事的「功能需求」或「非功能需求」底下,不放進全域需求
- 為什麼:需求散在全域,讀的人得自己對回是哪個故事要的;只做 P1 的時候,也分不出哪幾條需求是這一次要完成的

## good example
- 「自動分類只分未加入相簿的照片」**只有故事 2 會用到**,寫在故事 2 底下
```
### 使用者故事 2 - 依規則自動分類到相簿(優先順序:P2)
...
**功能需求**:

- **FR-008**:系統必須提供自動分類功能,只針對尚未加入任何相簿的照片,依拍攝日期按月產生相簿建議(例如「2026 年 10 月」),並在使用者確認後才套用。
```

## bad example
- 同一條需求,但**放在全域需求**;它只跟故事 2 有關,只做故事 1 的人也得讀過它才知道不用做
```
## 全域需求 *(必填)*

### 功能需求

- **FR-008**:系統必須提供自動分類功能,只針對尚未加入任何相簿的照片,依拍攝日期按月產生相簿建議(例如「2026 年 10 月」),並在使用者確認後才套用。
```

## good example
- 邊界:「匯入照片」是三個故事都要先做的事,但**驗收它的是故事 1 的獨立測試**,其他故事只是前提,所以寫在故事 1 底下
```
### 使用者故事 1 - 建立相簿並把照片放進去(優先順序:P1)
...
- **FR-001**:系統必須讓使用者在瀏覽器中選擇家中伺服器上的照片資料夾,把其中的照片匯入照片庫。
```

## bad example
- 邊界:同一條,因為「每個故事都要先匯入」就**放進全域**;故事 2、3 的驗收情境裡沒有任何一項在驗它,全域需求變成放前提的地方
```
## 全域需求 *(必填)*

### 功能需求

- **FR-014**(適用:使用者故事 1、2、3):系統必須讓使用者在瀏覽器中選擇家中伺服器上的照片資料夾,把其中的照片匯入照片庫。
```

# Rule 2 [must] - 全域需求只放跨越兩個以上故事的需求並標出適用的故事
- 全域需求裡的每一條,都要有兩個以上的使用者故事會用到它
- 每一條寫成 `(適用:使用者故事 <序號>、<序號>)`,列出用到它的每一個故事
- 為什麼:沒有標出適用的故事,讀的人看不出它為什麼在全域,也沒辦法檢查是不是真的跨故事;只適用一個故事的需求混進來,全域需求就又變回散落的清單

## good example
- 「不動原檔」在加入相簿(故事 1)、套用自動分類(故事 2)、刪除相簿(故事 3)**都要守**,放在全域並列出三個故事
```
- **FR-015**(適用:使用者故事 1、2、3):相簿為虛擬分組;加入或移出相簿、套用自動分類、刪除相簿或從照片庫移除照片,都只影響照片庫中的紀錄,系統不得移動、改名、修改或刪除任何照片原檔。
```

## bad example
- 同一條需求放在全域,但**沒有標出適用的故事**;讀的人看不出它為什麼不在任何一個故事底下
```
- **FR-015**:相簿為虛擬分組;加入或移出相簿、套用自動分類、刪除相簿或從照片庫移除照片,都只影響照片庫中的紀錄,系統不得移動、改名、修改或刪除任何照片原檔。
```

## good example
- 邊界:進度與取消只適用匯入(故事 1)與自動分類(故事 2),**兩個故事就算跨故事**,列出這兩個
```
- **NFR-003**(適用:使用者故事 1、2):超過 1 秒的操作(匯入、重新掃描、自動分類)必須顯示進度,且必須可中途取消;取消後已完成的部分保留。
```

## bad example
- 邊界:同一條,為了看起來一致就**標成全部三個故事**;故事 3 沒有任何超過 1 秒的操作,驗收故事 3 的人會去找一個不存在的進度條
```
- **NFR-003**(適用:使用者故事 1、2、3):超過 1 秒的操作(匯入、重新掃描、自動分類)必須顯示進度,且必須可中途取消;取消後已完成的部分保留。
```

# Rule 3 [must] - 一條需求只管一件事
- 一句需求涵蓋了不同故事各自要的行為時,拆成多條,各自歸到它的故事
- 為什麼:一條需求跨了兩個故事的不同部分,放在哪一邊都不對;放進全域,它其實不是每個故事都要的,放進其中一個故事,另一個故事就少了一條

## good example
- 「建立相簿」屬於故事 1、「重新命名、刪除相簿」屬於故事 3,**拆成三條各自歸位**
```
### 使用者故事 1
- **FR-005**:系統必須讓使用者建立相簿。

### 使用者故事 3
- **FR-011**:系統必須讓使用者重新命名相簿。
- **FR-012**:系統必須讓使用者刪除相簿,且刪除前必須有明確的確認步驟。
```

## bad example
- 同樣的內容寫成一條,**放在故事 1 底下**;故事 3 的驗收情境在驗改名與刪除,底下卻沒有對應的需求
```
### 使用者故事 1
- **FR-005**:系統必須讓使用者建立、重新命名與刪除相簿。
```

## good example
- 邊界:「名稱唯一」同時管建立(故事 1)、改名(故事 3)與自動分類的同名判斷(故事 2),但**三個故事守的是同一個比對規則**,所以是一件事,留成一條放在全域
```
- **FR-014**(適用:使用者故事 1、2、3):相簿名稱必須唯一;建立、重新命名或自動分類產生建議時,名稱經去除前後空白並忽略英文大小寫後與既有相簿相同者,視為同名。建立或重新命名遇到同名時,系統必須阻止該操作並提示使用者改名。
```

## bad example
- 邊界:同一個比對規則,因為牽涉三個故事就**拆成三條**;三份「去除前後空白、忽略大小寫」日後只要改一份,三個故事對「同名」的判斷就不一致
```
### 使用者故事 1
- **FR-005**:建立相簿時,名稱去除前後空白並忽略英文大小寫後與既有相簿相同者,必須阻止並提示改名。

### 使用者故事 2
- **FR-009**:建議名稱去除前後空白並忽略英文大小寫後與既有相簿相同者,預覽必須標示「將併入既有相簿」。

### 使用者故事 3
- **FR-011**:重新命名時,名稱去除前後空白並忽略英文大小寫後與既有相簿相同者,必須阻止並提示改名。
```

# Rule 4 [must] - FR 寫系統做什麼,NFR 寫做到什麼程度
- FR 寫系統提供的行為:使用者能做什麼、系統對什麼輸入做出什麼反應
- NFR 寫這些行為要達到的品質:效能、存取範圍、介面語言與操作方式、資料保存、畫面狀態
- 為什麼:兩種混在一起,驗收的人分不出這一條是要測「有沒有這個功能」還是「功能做到什麼程度」;品質要求寫成 FR,也常常因為沒有對應的使用者動作而被漏測

## good example
- 「打開相簿流暢」是在講**打開相簿這個行為要做到什麼程度**,寫成 NFR
```
**非功能需求**:

- **NFR-001**:照片庫達上萬張時,打開相簿、瀏覽與捲動必須維持流暢(門檻見 SC-003)。
```

## bad example
- 同一條,但**寫在功能需求底下**;它沒有新的使用者動作,驗收的人會以為打開相簿的 FR 已經涵蓋了
```
**功能需求**:

- **FR-008**:照片庫達上萬張時,打開相簿、瀏覽與捲動必須維持流暢(門檻見 SC-003)。
```

## good example
- 邊界:「刪除前要確認」聽起來像是安全性的品質要求,但**它是使用者看得到、會操作的一個步驟**,所以是 FR
```
**功能需求**:

- **FR-012**:系統必須讓使用者刪除相簿,且刪除前必須有明確的確認步驟。
```

## bad example
- 邊界:同一個要求,因為和「安全」有關就**拆成 NFR**;確認對話框是要被點的行為,放在 NFR 驗收時只會被當成品質去評,不會有人去點它
```
**非功能需求**:

- **NFR-002**:刪除相簿必須安全,不得誤刪。
```
