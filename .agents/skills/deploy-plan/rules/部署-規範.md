# Rule 1 [must] - 機密只寫成 ${變數},值不進任何檔
- 密碼、token、金鑰、連線字串裡的帳密,在 compose.yaml 一律寫成 `${變數名稱}`;`.env.example` 只列變數名稱,等號後面留空
- Dockerfile 與反向代理設定也不寫機密的值
- 為什麼:部署檔會進版本控制、會被複製到別的機器;值一旦寫進去,就跟著每一次 commit 與每一份複本外流,而且收不回來

## good example
- 資料庫密碼與金流金鑰**都寫成 `${…}`**,`.env.example` 只有名稱
```
compose.yaml
    environment:
      NODE_ENV: production
      DATABASE_URL: ${DATABASE_URL}
      PAYMENT_HASH_KEY: ${PAYMENT_HASH_KEY}

.env.example
DATABASE_URL=
PAYMENT_HASH_KEY=
```

## bad example
- 同一個服務,但**把開發時用的值直接寫進去**;compose.yaml 一 commit,金鑰就在版本紀錄裡
```
compose.yaml
    environment:
      NODE_ENV: production
      DATABASE_URL: postgres://shop:s3cret@db:5432/shop
      PAYMENT_HASH_KEY: 5294y06JbISpM5x9
```

## good example
- 邊界:`.env.example` 是「範例」,看起來填一個假的值比較好懂;但**它跟著 repo 走,有值就會被人直接拿去用**,所以只列名稱
```
.env.example
DB_PASSWORD=
PAYMENT_HASH_KEY=
```

## bad example
- 邊界:同一份檔,**填了看起來像假的值**;部署的人沒改就上線,正式環境的資料庫密碼就是 `changeme`
```
.env.example
DB_PASSWORD=changeme
PAYMENT_HASH_KEY=xxxxxxxxxxxxxxxx
```

# Rule 2 [must] - 不寫特定環境的主機、IP 與網域
- 部署檔不寫某一台機器或某一個環境才有的東西:主機名稱、IP、內部網域、主機上的絕對路徑
- 隨環境而變的值寫成 `${變數名稱}`,或用不依賴主機名稱的寫法(例如反向代理的 `server_name _;`)
- 為什麼:部署檔要能搬到另一台機器、另一個環境直接用;寫死某台機器的 IP 或內網網域,換個地方就連不上,還把內部的網路配置一起公開了

## good example
- 對外網域與憑證路徑**不寫死**,反向代理接受任何主機名稱,憑證從相對路徑掛進來
```
proxy.conf
server {
    listen 443 ssl;
    server_name _;
    ssl_certificate     /etc/nginx/certs/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/privkey.pem;
}

compose.yaml
    volumes:
      - ./certs:/etc/nginx/certs:ro
```

## bad example
- 同一份設定,但**寫死了某台主機的網域、IP 與絕對路徑**;換一台機器就要逐行改,內網的配置也跟著公開
```
proxy.conf
server {
    listen 443 ssl;
    server_name shop.home.example.internal;
    ssl_certificate     /mnt/user/appdata/certs/fullchain.pem;
    ssl_certificate_key /mnt/user/appdata/certs/privkey.pem;
}

compose.yaml
    extra_hosts:
      - "db.internal:192.168.10.20"
```

## good example
- 邊界:`db`、`api` 也是主機名稱;但**它們是 compose 自己的服務名稱**,在任何環境都一樣,可以寫
```
    environment:
      DATABASE_URL: ${DATABASE_URL}
    depends_on:
      db:
        condition: service_healthy
```

## bad example
- 邊界:同樣是「連到資料庫」,但**寫的是外部資料庫主機的 IP**;它不是 compose 的服務,換環境就連不上
```
    environment:
      DB_HOST: 10.0.0.15
```

# Rule 3 [must] - port 與路徑照前幾步規格檔的原文
- 理由欄點名的前幾步規格檔已經定下的 port、base path、WebSocket 路徑與健康檢查路徑,在 compose.yaml 與反向代理設定照原文使用,不改、不另加前綴
- 照原文用會和需求或這次的部署衝突時,不自行改寫,把衝突列進交出時的待決問題
- 為什麼:前端與後端已經照規格檔的路徑寫完了;反向代理換了一個前綴,每一個請求都會落到 404,而且兩邊的程式都看不出錯

## good example
- OpenAPI 的 servers 是 `/api/v1`、AsyncAPI 的 pathname 是 `/ws`;**反向代理照這兩個路徑轉發**
```
proxy.conf
location /api/v1/ {
    proxy_pass http://api:8080;
}
location /ws {
    proxy_pass http://api:8080;
}
```

## bad example
- 同一份設定,但**把路徑改成自己的慣例**;前端照規格連 `/ws`,反向代理只認 `/socket`
```
proxy.conf
location /api/ {
    proxy_pass http://api:8080/api/v1/;
}
location /socket {
    proxy_pass http://api:8080/ws;
}
```

## good example
- 邊界:規格檔沒有寫容器內的 port,看起來可以照慣例挑一個;**規格檔沒定的才自己定**,而且全部檔案用同一個值
```
compose.yaml
    environment:
      PORT: 8080
    expose:
      - "8080"

proxy.conf
    proxy_pass http://api:8080;
```

## bad example
- 邊界:同樣是自己定的 port,但**每個檔案各寫一個**;環境變數是 3000,反向代理連的是 8080
```
compose.yaml
    environment:
      PORT: 3000
    expose:
      - "8080"

proxy.conf
    proxy_pass http://api:8080;
```

# Rule 4 [must] - 長連線寫明 Upgrade 與閒置逾時
- 前幾步規格檔有 WebSocket 或 SSE 時,反向代理設定要寫出這兩件事:轉發升級的 header(`Upgrade`、`Connection`),以及比心跳間隔長的閒置逾時
- 為什麼:反向代理預設不轉發 Upgrade,WebSocket 根本連不上;預設的閒置逾時通常是 60 秒,比心跳長的安靜時段一到,連線就被切斷,畫面上看起來是隨機斷線

## good example
- AsyncAPI 的心跳是 15 秒;**轉發 Upgrade,閒置逾時設成心跳的好幾倍**
```
location /ws {
    proxy_pass http://api:8080;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 120s;
    proxy_send_timeout 120s;
}
```

## bad example
- 同一個路徑,但**當成一般的 HTTP 轉發**;沒有 Upgrade header,WebSocket 握手直接失敗
```
location /ws {
    proxy_pass http://api:8080;
}
```

## good example
- 邊界:SSE 不需要 Upgrade,但**它同樣是長時間不關的連線**;要關掉緩衝,並把閒置逾時拉長
```
location /api/v1/events {
    proxy_pass http://api:8080;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_read_timeout 3600s;
}
```

## bad example
- 邊界:同一個 SSE 路徑,因為不是 WebSocket 就**照一般請求轉發**;nginx 把事件緩衝起來一次送,60 秒後還會把連線切斷
```
location /api/v1/events {
    proxy_pass http://api:8080;
}
```

# Rule 5 [must] - 憲法的條文和本 Skill 的規範都要照做
- 寫compose.yaml 與附檔時,`constitution_rules.py` 交回的每一條條文都照做;本 Skill 的規範沒有被條文點名取代的,也照樣照做
- 條文和本 Skill 的規範要求的是不同的事時,兩邊同時成立,不因為有了憲法就跳過本 Skill 的規範
- 為什麼:憲法是這個專案多加的要求,Skill 的規範是這份產出物能被下游讀懂的基本盤;只照其中一邊,交出的compose.yaml 與附檔不是違反憲法,就是讓下游的 Skill 讀不懂

## good example
- 憲法要 healthcheck,Skill 要機密寫成 `${變數}`;**兩邊都照做**
```
憲法:constitution/deploy-plan/compose.md〈每個服務都有 healthcheck〉
Skill:rules/部署-規範.md〈機密只寫成 ${變數},值不進任何檔〉

db:
  environment:
    POSTGRES_PASSWORD: ${DB_PASSWORD}
  healthcheck:
    test: ["CMD", "pg_isready"]
```

## bad example
- 同一個服務,healthcheck 有寫,但**密碼寫成了值**;只照了憲法,機密進了 repo
```
db:
  environment:
    POSTGRES_PASSWORD: s3cret
  healthcheck:
    test: ["CMD", "pg_isready"]
```

# Rule 6 [must] - 只有 waive 列的 Rule 改照條文做
- `constitution_rules.py` 交回的 waive 列的 Rule 不照做,改照點名取代它的那一條條文;waive 沒有列的 Rule,即使和它在同一個規範檔,也照樣照做
- 檢查腳本有 `--waive` 參數時,把 waive 的每一項原樣交給它
- 為什麼:waive 是使用者寫憲法時確認過要翻掉的;照樣照被取代的 Rule 做,交出的compose.yaml 與附檔就違反憲法;把整個規範檔都當成被取代,沒有被翻掉的規定就沒有人守

## good example
- waive 列了〈長連線寫明 Upgrade 與閒置逾時〉;**改照條文不寫反向代理設定**
```
憲法:constitution/deploy-plan/compose.md〈反向代理由維運統一管理,不寫進部署檔〉
waive:部署-規範〈長連線寫明 Upgrade 與閒置逾時〉

deploy/:compose.yaml、Dockerfile、.env.example(沒有 nginx.conf)
```

## bad example
- 同一個 waive,但**照樣寫了 nginx.conf 的 Upgrade 設定**;違反了憲法
```
deploy/:compose.yaml、Dockerfile、.env.example、nginx.conf
```

## good example
- 邊界:waive 只列了長連線那一條;**同一個規範檔的〈不寫特定環境的主機、IP 與網域〉照樣照做**
```
api:
  environment:
    PUBLIC_URL: ${PUBLIC_URL}
```

## bad example
- 邊界:同一個 waive,**把整個部署-規範都當成被取代**,寫進了特定環境的網域
```
api:
  environment:
    PUBLIC_URL: https://shop.example.com
```

# Rule 7 [must] - 沒有點名取代的衝突照本 Skill 的 Rule 做並交給使用者決定
- 條文和本 Skill 的某條 Rule 衝突、卻沒有用 `- 取代:` 點名它時,不自己選邊:compose.yaml 與附檔照本 Skill 的 Rule 寫,把衝突的條文與 Rule 列進交出時的待決問題,由使用者決定要改憲法還是改產出物
- 為什麼:沒有點名的衝突,使用者沒有決定過要翻掉哪一條;AI 自己選了憲法,等於替使用者改了 Skill 的規範,選了 Skill 又沒說,使用者以為憲法有被照做

## good example
- 條文要密碼直接寫進 compose,但沒有也不能點名取代;**照 Skill 寫成 `${變數}`,把衝突列進待決問題**
```
憲法:constitution/deploy-plan/compose.md〈本機開發的密碼直接寫在 compose〉(沒有取代)
Skill:rules/部署-規範.md〈機密只寫成 ${變數},值不進任何檔〉

POSTGRES_PASSWORD: ${DB_PASSWORD}
待決問題:憲法〈本機開發的密碼直接寫在 compose〉和機密規範衝突,機密不可取代,先照 Skill 寫;請你決定要不要改憲法
```

## bad example
- 同一個衝突,**AI 自己選了憲法**,密碼寫成了值;待決問題也沒提
```
POSTGRES_PASSWORD: devpass
待決問題:(沒有提到衝突)
```
