# Rule 1 [must] - 非互動執行必用 codex exec
- 在 subshell、腳本或 automated agent 工具中調用時，必須使用 `codex exec` 子指令，禁止裸調用 `codex`
- 為什麼:裸調用 `codex` 會啟動互動式 TUI，在非互動的終端或 headless 環境中會因缺乏 TTY 終端而立即失敗或卡住

## good example
- 使用非互動子指令 `codex exec`
```bash
codex exec -s workspace-write -C /project -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
```

## bad example
- 裸調用 `codex`，在非互動環境觸發 TUI
```bash
codex "請幫我重構 OrderService"
```

# Rule 2 [must] - 以檔案或 stdin 傳遞 prompt
- 傳遞給 `codex exec` 的提示詞必須存成暫存檔並以 stdin 重導向傳入（如 `- < /path/to/prompt.md`），禁止在 shell 命令列以字串參數直接傳入多行 prompt
- 為什麼:多行字串在 shell 命令列容易遭遇雙引號、單引號、變數展開 `$VAR` 或特殊字元截斷，導致語法錯誤使命令執行失敗

## good example
- 將 prompt 存為檔案後透過 stdin 導向傳給 `codex exec`
```bash
codex exec -s workspace-write -C /project -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
```

## bad example
- 在命令列以多行字串直接作為 prompt 參數傳入
```bash
codex exec -s workspace-write -C /project -o /tmp/task/codex.out "重構函式：process_tax\n請注意變數與引號" 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
```

# Rule 3 [must] - 沙盒依任務要碰到的東西選,不帶審批或略過沙盒的旗標
- 調用 `codex exec` 時依任務要碰到的東西選沙盒與旗標,依下表

| 任務要碰到的東西 | 例子 | 旗標 |
|---|---|---|
| 只讀、不連網 | 審查 diff、分析 | `-s read-only` |
| 要改工作區的檔 | 重構、修 bug | `-s workspace-write` |
| 要連網 | 在 GitLab 留審查結果、approve | `-s workspace-write -c sandbox_workspace_write.network_access=true -c shell_environment_policy.ignore_default_excludes=true` |
| 要提交 | 在本機 clone 或 git worktree 以作者身分提交修正 | `-s workspace-write --add-dir <git-dir> --add-dir <git-common-dir>` |

- 要提交時,`<git-dir>` 與 `<git-common-dir>` 在 `-C` 指到的目錄跑 `git rev-parse --path-format=absolute --git-dir` 與 `--git-common-dir` 取得,兩個都加;一般 clone 兩者都是 `<repo>/.git`,重複加無妨;git worktree 裡兩者不同,`<worktree>/.git` 是一個檔案,不能拿它當 `--add-dir`
- 要連網的任務若用到名稱含 KEY/SECRET/TOKEN 的環境變數(例如 `GITLAB_BOT_TOKEN`),一定要帶 `-c shell_environment_policy.ignore_default_excludes=true`;Codex 預設會把這類變數濾掉,不帶就傳不進沙盒
- 沙盒裡 `~/.cache/uv` 是唯讀的;任務要用 `uv run` 時,把 `UV_CACHE_DIR` 指到工作區內的目錄,並用 `--add-dir` 加上它
- 要連網又要提交時,兩組旗標都帶
- `-C` 指到的不是 git 目錄時,加 `--skip-git-repo-check`;不加 codex 會直接 exit 1
- 不帶 `--approve-for-me`,也不用 `--dangerously-bypass-approvals-and-sandbox`
- 為什麼:沙盒給得比任務需要的寬,Codex 就能改它不該改的檔;給得比任務需要的窄,任務就做不完 —— 連不到 GitLab、環境變數傳不進去、`uv` 建不了暫存檔,Codex 照樣交出一份看似完成的輸出(實測 2026-10-20/21 以 bot-codex 審查 GitLab MR;2026-10-21 apps/agent-dispatch 四輪 Codex 審查帶 `network_access` 與 `ignore_default_excludes` 成功核准)。`-s` 與 `--approve-for-me` 互斥,同時帶上 codex 會直接以 exit 2 結束、什麼都沒做(實測);略過沙盒之後 Codex 可以改工作目錄以外的檔,任務並不需要。只指定沙盒時 `codex exec` 就跑得完(實測,當時環境的 `approvals_reviewer` 設為 `auto_review`)。`-s workspace-write` 會把 `.git` 設成唯讀,要提交的任務改得了檔卻建不了 `index.lock`,Codex 只回報修改留在工作目錄(實測 2026-10-22 對照:同一個指示,不加旗標時 `fatal: Unable to create '<repo>/.git/index.lock': Read-only file system`,加上 `--add-dir <repo>/.git` 就提交成功)。git worktree 的 index 與 HEAD 在 `<git-dir>`(主 repo 的 `.git/worktrees/<名>`),物件與 refs 在 `<git-common-dir>`(主 repo 的 `.git`),少開任何一個都提交不了,而且四種失敗 codex 都是 exit 0(實測 2026-10-22,codex-cli 0.163.0,同一個「追加一行並提交」的指示:不加旗標與只加 `<git-common-dir>` 都是 `.git/worktrees/<名>/index.lock: Read-only file system`;只加 `<git-dir>` 是 `unable to create temporary file: Read-only file system`,物件寫不進去;加 `<worktree>/.git` 時 bubblewrap 啟動沙盒就 panic,Codex 什麼都沒改;兩個都加才提交成功,一般 clone 帶兩個相同路徑也提交成功)

## good example
- 任務要改 `pricing.py`;**只用 `-s workspace-write` 指定沙盒**
```bash
codex exec -s workspace-write -C /project -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
```

## bad example
- 同一個任務,但**同時帶了 `-s workspace-write` 與 `--approve-for-me`**;codex 回 `the argument '--sandbox <SANDBOX_MODE>' cannot be used with '--approve-for-me'`,exit 2
```bash
codex exec -s workspace-write --approve-for-me -C /project -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
```

## good example
- 審查 MR 並在 GitLab approve,審查時要跑 `uv run pytest`;**帶齊連網、環境變數、`UV_CACHE_DIR` 與 `--add-dir`**,token 只以變數引用傳入
```bash
GITLAB_BOT_TOKEN="$GITLAB_PAT_CODEX" UV_CACHE_DIR=/project/.uv-cache \
codex exec -s workspace-write \
  -c sandbox_workspace_write.network_access=true \
  -c shell_environment_policy.ignore_default_excludes=true \
  --add-dir /project/.uv-cache \
  -C /project -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
```

## bad example
- 同一個審查任務,但**只用 `-s read-only`**;Codex 連不到 GitLab、`uv` 建不了鎖定暫存檔,pytest 沒跑,也沒有 approve(實測 2026-10-21)
```bash
GITLAB_BOT_TOKEN="$GITLAB_PAT_CODEX" UV_CACHE_DIR=/project/.uv-cache \
codex exec -s read-only -C /project -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
```

## good example
- 邊界:任務是審查一份 diff,結果只寫進 `-o` 的輸出檔、不在 GitLab 留結果;**不連網也不改檔,仍用 `-s read-only`**
```bash
codex exec -s read-only -C /project -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
```

## bad example
- 邊界:同一個只讀審查,想著審查任務都要連網就**用了 `-s workspace-write` 加 `network_access=true`**;審查者因此能改檔、能連網,任務兩樣都不需要
```bash
codex exec -s workspace-write -c sandbox_workspace_write.network_access=true -C /project -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
```

## good example
- 任務要修正並以作者身分提交;**`-s workspace-write` 再加 `<git-dir>` 與 `<git-common-dir>`**(一般 clone 兩者都是 `/project/.git`),Codex 提交成功,工作目錄乾淨
```bash
GIT_DIR_ABS=$(git -C /project rev-parse --path-format=absolute --git-dir)
GIT_COMMON_ABS=$(git -C /project rev-parse --path-format=absolute --git-common-dir)
codex exec -s workspace-write --add-dir "$GIT_DIR_ABS" --add-dir "$GIT_COMMON_ABS" -C /project -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
```

## bad example
- 同一個要提交的任務,但**只帶 `-s workspace-write`**;Codex 改了檔,commit 卻因 `.git/index.lock: Read-only file system` 失敗,exit 0、沒有新提交
```bash
codex exec -s workspace-write -C /project -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
```

## good example
- 邊界:同一個要提交的任務,但 `-C` 指到 git worktree `/wt/fix-a`(`/wt/fix-a/.git` 是檔案,內容是 `gitdir: /project/.git/worktrees/fix-a`);**照同一組 `rev-parse` 取兩個目錄**,拿到的是 `/project/.git/worktrees/fix-a` 與 `/project/.git`,Codex 提交成功
```bash
GIT_DIR_ABS=$(git -C /wt/fix-a rev-parse --path-format=absolute --git-dir)
GIT_COMMON_ABS=$(git -C /wt/fix-a rev-parse --path-format=absolute --git-common-dir)
codex exec -s workspace-write --add-dir "$GIT_DIR_ABS" --add-dir "$GIT_COMMON_ABS" -C /wt/fix-a -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
```

## bad example
- 邊界:同一個 worktree,照一般 clone 的寫法**加 `--add-dir /wt/fix-a/.git`**;它是檔案不是目錄,bubblewrap 建沙盒時 panic(`Can't mkdir parents for /wt/fix-a/.git/.git: Not a directory`),Codex 什麼都沒改,exit 仍是 0
```bash
codex exec -s workspace-write --add-dir /wt/fix-a/.git -C /wt/fix-a -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
```

# Rule 4 [must] - 指定輸出檔與工作目錄
- 調用 `codex exec` 時必須使用 `-C <dir>` 指定目標工作根目錄，並使用 `-o <file>` 指定輸出檔案路徑以完整捕獲最後產出訊息
- 為什麼:未指定 `-C` 會導致 Codex 在未預期的目錄執行而找不到檔案或寫錯路徑；未指定 `-o` 會使執行結果混在標準輸出的日誌中難以乾淨提取

## good example
- 同時指定工作目錄 `-C` 與輸出檔 `-o`
```bash
codex exec -s workspace-write -C /home/user/repo -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
```

## bad example
- 缺少 `-C` 與 `-o`，目錄依賴當前環境且無法單獨取得最後訊息
```bash
codex exec -s workspace-write - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
```

# Rule 5 [must] - 調用前確認 git baseline
- 在執行 `codex exec` 前，必須先執行 `git status --porcelain` 確認或記錄當前工作區狀態，確保無未預期的未追蹤或未提交改動
- 為什麼:調用前工作區若有未提交的髒檔案，調用完成後無法透過 `git diff` 清楚辨別哪些變更是 Codex 產生的，導致驗收無依據

## good example
- 調用前先檢查工作區並確認乾淨基準
```bash
git status --porcelain
codex exec -s workspace-write -C /project -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
git diff
```

## bad example
- 調用前未檢查 git 狀態即直接執行，無法分辨變更來源
```bash
codex exec -s workspace-write -C /project -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
git diff
```

# Rule 6 [must] - stderr 與結束碼各寫成紀錄檔
- stderr 重導向到 `codex.err`,指令最後接 `; echo $? > codex.exit` 把結束碼寫進 `codex.exit`;兩個檔和 `-o` 的輸出檔、任務指示檔放在同一個資料夾
- 為什麼:用量用完時 codex 不會寫出 `-o` 的輸出檔,原因與可以重試的時間只寫在 stderr;`codex.exit` 出現才代表 codex 真的結束了,也才分得出輸出檔是還沒寫、還是不會寫了

## good example
- stderr 與結束碼**各寫進和輸出檔、指示檔同一個資料夾的 `codex.err`、`codex.exit`**
```bash
codex exec -s workspace-write -C /project -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
```

## bad example
- 同一次調用,但**stderr 沒有存檔、也沒有寫結束碼**;輸出檔沒出現時看不出是用量用完、參數錯了,還是 codex 還在跑
```bash
codex exec -s workspace-write -C /project -o /tmp/task/codex.out - < /tmp/task/task_prompt.md
```

## good example
- 邊界:codex 的 stderr 很長,多半是執行過程的紀錄,看起來不值得存;**仍然寫進 `codex.err`**
```bash
codex exec -s workspace-write -C /project -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /tmp/task/codex.err; echo $? > /tmp/task/codex.exit
```

## bad example
- 邊界:同一次調用,嫌 stderr 太吵就**用 `2> /dev/null` 丟掉**;用量用完的那一行 `You’ve hit your usage limit … try again at …` 只寫在 stderr
```bash
codex exec -s workspace-write -C /project -o /tmp/task/codex.out - < /tmp/task/task_prompt.md 2> /dev/null; echo $? > /tmp/task/codex.exit
```

# Rule 7 [must] - 安全相關的審查寫成「兩個解讀是否一致」的中性問題
- 任務指示檔要 Codex 審查和安全有關的程式(白名單、過濾、驗證)時,把問題寫成「A 與 B 兩個實作或解讀是否一致,列出兩者解讀不同的輸入」;不寫「繞過」「攻擊」「繞開限制」這類字眼
- 為什麼:任務檔寫成找辦法繞過,Codex 會以安全理由拒答整個任務,輸出是拒絕審查的文字而不是審查結果,exit 仍是 0,容易被當成審查通過。2026-10-23 審 bdgg-dev-skills !6 的 `check_allowlist.py`,任務檔寫「審查 allowlist 能否被繞過」被整個拒絕;改寫成「審查 tokenizer 與 bash 分詞的一致性,列出兩者解讀不同的輸入」後正常完成

## good example
- 同一個審查,寫成兩個解讀是否一致的中性問題
```text
審查 check_allowlist.py 的 tokenizer 與 bash 分詞的一致性,列出兩者解讀不同的輸入,並說明每個輸入各被怎麼解讀。
```

## bad example
- 同一個審查寫成「能否被繞過」;Codex 以安全理由拒答,交出的是拒絕審查的回覆,不是審查結果
```text
審查 check_allowlist.py 的 allowlist 能否被繞過。
```
