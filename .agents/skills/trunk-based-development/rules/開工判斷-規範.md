# Rule 1 [must] - trunk 以 remote 的預設 branch 為準
- 使用 `git ls-remote --symref origin HEAD` 詢問 remote 預設 branch 作為 trunk
- 為什麼:本機的 `refs/remotes/origin/HEAD` 只有在 clone 出來的 repo 存在,`git init` 後才 add remote 的 repo 不存在;照本機的捷徑判斷,在這種 repo 會找不到 trunk

## good example
- **直接問 remote**,得到 trunk 是 `main`
```bash
$ git ls-remote --symref origin HEAD
ref: refs/heads/main	HEAD
# trunk 是 main
```

## bad example
- 同一個 repo(`git init` 之後才 `git remote add`),但**讀本機的 `origin/HEAD`**;它不存在,trunk 判不出來
```bash
$ git checkout origin/HEAD
error: pathspec 'origin/HEAD' did not match any file(s) known to git
```

# Rule 2 [must] - remote 還是空的時以本機目前的 branch 為 trunk
- 若 remote 尚無輸出則以目前本機 branch 為 trunk
- 為什麼:remote 還沒有任何 branch 時問不到預設 branch;憑習慣猜一個名字,之後的同步與推送會對到一條不存在的 branch

## good example
- remote 還是空的(第一次 push 之前),`ls-remote` 沒有任何輸出;**以目前本機的 branch 為 trunk**
```bash
$ git ls-remote --symref origin HEAD
$ git branch --show-current
main
# trunk 是 main
```

## bad example
- 同一個空的 remote,沒有輸出就**照習慣當成 `master`**;本機這一條是 `main`,之後的同步對到一條不存在的 branch
```bash
$ git ls-remote --symref origin HEAD
$ git pull --rebase origin master
fatal: couldn't find remote ref master
```

# Rule 3 [must] - 完整建置指令對齊 CI 設定檔
- 提交前必須跑的完整建置指令(編譯 + 單元測試 + 整合測試)必須對齊 CI 設定檔
- 為什麼:本機建置若與 CI 不一致,無法守住「不弄壞建置」的承諾

## good example
- CI 設定檔跑的是 `make test`;**本機跑同一道**
```
.github/workflows/ci.yml   run: make test
本機提交前                 make test
```

## bad example
- 同一份 CI 設定檔,但本機**只挑單元測試跑**;整合測試沒有跑到,語意衝突要等 CI 才看得到
```
.github/workflows/ci.yml   run: make test
本機提交前                 pytest tests/unit/
```

## good example
- 邊界:CI 設定檔有 lint 與 test 兩道;**本機兩道都跑**
```
.github/workflows/ci.yml   run: make lint
                           run: make test
本機提交前                 make lint && make test
```

## bad example
- 邊界:同一份 CI 設定檔,本機只跑 `make test`;測試全過、看起來已經對齊,但 **lint 那一道沒有跑**,推上去 CI 照樣會紅
```
.github/workflows/ci.yml   run: make lint
                           run: make test
本機提交前                 make test
```

# Rule 4 [must] - 找不到自動化測試時告知使用者
- 若找不到任何自動化測試,必須主動告知使用者此為前提缺失
- 為什麼:沒有測試就無法證明這次的變更沒有弄壞建置;不講,使用者會把回報裡的「建置通過」當成有測試守著

## good example
- repo 裡沒有任何測試;**主動告訴使用者**
```
找過:tests/、Makefile、pyproject.toml、.github/workflows/,沒有任何自動化測試
告知:這個 repo 找不到任何自動化測試。這是主幹式開發的前提缺失:沒有測試,我沒辦法證明這次的變更沒有弄壞建置。
```

## bad example
- 同一個 repo,但**什麼都沒說**;回報裡的「建置通過」其實只代表程式編得過
```
找過:tests/、Makefile、pyproject.toml、.github/workflows/,沒有任何自動化測試
告知:(沒有)
整合回報的建置證據:python -m compileall 通過
```

## good example
- 邊界:repo 有 `make lint`、CI 也會跑它,但沒有任何測試;**lint 不是測試,仍然告知**
```
找過:Makefile 只有 lint 目標(ruff check),CI 設定檔只跑 make lint,沒有 tests/
告知:這個 repo 找不到任何自動化測試,只有 lint。這是主幹式開發的前提缺失:沒有測試,我沒辦法證明這次的變更沒有弄壞建置。
```

## bad example
- 邊界:同一個 repo,因為 **`make lint` 會過就當成有自動化檢查在守著**,沒有告知;lint 過了只代表寫法合規,不代表行為沒有壞
```
找過:Makefile 只有 lint 目標(ruff check),CI 設定檔只跑 make lint,沒有 tests/
告知:(沒有)
整合回報的建置證據:make lint 通過
```

# Rule 5 [must] - 一次變更在數小時內做得完
- 每次變更的大小控制在動手後數小時內(上限一至兩天)即可完成並送出
- 一張需求卡不等於一次整合,可拆成多筆 commit 流進 trunk
- 為什麼:變更過大會產生開長期 branch 慢慢做的壓力,累積的變更越多,距離整合越遠,合併風險呈指數增加

## good example
- 「todo 統計」估三天;**拆成五次整合**,每一次半天到一天
```
需求:todo 統計,估 3 天
切法
  1. todo count 只印 total             約半天,整合
  2. todo count 加上 completed         約半天,整合
  3. todo count 加上 pending           約半天,整合
  4. todo count --json                 約半天,整合
  5. todo count --tag <tag>            約一天,整合
```

## bad example
- 同一個需求,但**整個做完才送一次**;這三天裡 trunk 上別人的變更都沒有帶進來
```
需求:todo 統計,估 3 天
切法
  1. 五項全部做完                      3 天,整合一次
```

## good example
- 邊界:一張需求卡估兩天半,超過上限;**同一張卡拆成兩次整合**,每一次都在兩天以內
```
需求卡 #42:匯出 CSV,估 2.5 天
切法
  1. todo export 匯出全部項目          1.5 天,整合
  2. todo export --since <日期>        1 天,整合
```

## bad example
- 邊界:同一張卡,只比上限多半天,又**因為只有一張卡就當成一次整合**
```
需求卡 #42:匯出 CSV,估 2.5 天
切法
  1. 整張卡做完                        2.5 天,整合一次
```

# Rule 6 [must] - 變更切成貫穿各層的垂直切片
- 變更切成貫穿各層、可單獨上線的薄垂直切片(thin vertical slice)
- 為什麼:只做完其中一層的變更單獨上線沒有人用得到;要等其他層做完才算完成,實際整合的仍然是一大塊

## good example
- 第一片就**貫穿 store、CLI 與測試**,送進 trunk 之後 `todo count` 已經可以用
```
第一片:todo count 只印 total
  todo/store.py       count_total()
  todo/cli.py         count 子指令,印出 total
  tests/test_cli.py   test_count_prints_total
```

## bad example
- 同一個功能,但第一筆**只做 store 這一層**;沒有指令會呼叫它,單獨上線沒有人用得到
```
第一筆:store 層的三個統計函式
  todo/store.py       count_total()、count_completed()、count_pending()
```

## good example
- 邊界:這一片很薄,只多印一個數字;但**三層都動到了,而且單獨上線就能用**
```
第二片:todo count 加上 completed
  todo/store.py       count_completed()
  todo/cli.py         count 多印一行 completed
  tests/test_cli.py   test_count_prints_completed
```

## bad example
- 邊界:同一片,store 與 CLI 都動了、看起來貫穿了各層,但 **store 的函式還沒有實作**,上線之後 `todo count` 會直接出錯
```
第二片:todo count 加上 completed
  todo/store.py       count_completed() 只有 raise NotImplementedError
  todo/cli.py         count 多印一行 completed
```

# Rule 7 [must] - 大規模改名與目錄調整單獨先送
- 大規模改名或目錄調整單獨先送鋪路 commit(facilitating commit)
- 為什麼:改名與搬目錄會波及所有人;和功能混在同一筆,後面的變更跟著變大,隊友同步時也分不出哪些行是功能、哪些只是改名

## good example
- `store.load` 改名會動到 30 個檔;**先單獨送一筆鋪路 commit**,功能那一筆只剩 3 個檔
```
1. refactor: rename store.load to load_items     30 個檔,只有改名
2. feat: add todo count                          3 個檔
```

## bad example
- 同樣的改名與功能,但**混在同一筆**;33 個檔裡哪幾個是功能,得自己找
```
1. feat: add todo count                          33 個檔,改名與功能混在一起
```

## good example
- 邊界:改名只碰到這次功能本來就要改的檔,**不算大規模,跟功能同一筆送**
```
1. feat: add todo count                          3 個檔,其中 2 個順手把區域變數 n 改成 total
```

## bad example
- 邊界:同一個功能,改的是被 12 個檔引用的函式名稱;檔數不到上一組的一半、看起來不大,但**已經波及這次功能以外的檔**,仍然混在同一筆
```
1. feat: add todo count                          15 個檔,其中 12 個只是跟著改名
```

# Rule 8 [must] - 整合風格選擇
- 依團隊規模與 repo 既有慣例選擇直接進 trunk 或走短期 feature branch
- 很小的團隊(含單人)、建置快且無 PR 強制規範時,直接 commit/push 到 trunk
- 需要 code review、有 branch protection 或人數較多時,走壽命不超過兩天的短期 branch
- 為什麼:兩種風格各有代價,選錯就只剩代價:直接進 trunk 時壞掉的 commit 會直接影響隊友,人多或需要 review 的 repo 承受不起;短期 branch 的 review 一慢就拖垮節奏,不需要 review 的小 repo 白白多等

## good example
- `main` 有 branch protection、歷史上都是 PR 合併;**走短期 branch**
```
開工狀態:5 人團隊;main 有 branch protection(要求 PR 與 1 個 review);最近 20 筆都是 PR 合併
整合風格:短期 branch
```

## bad example
- 同一個 repo,但**選了直接進 trunk**;推送會被 branch protection 擋下
```
開工狀態:5 人團隊;main 有 branch protection(要求 PR 與 1 個 review);最近 20 筆都是 PR 合併
整合風格:直接進 trunk
```

## good example
- 邊界:只有一個人在開發,但 `main` 有 branch protection;**repo 的規範要求 PR,仍然走短期 branch**
```
開工狀態:單人專案;main 有 branch protection(要求 PR 與 CI 通過)
整合風格:短期 branch
```

## bad example
- 邊界:同一個 repo,因為**只有自己一個人就選直接進 trunk**;「很小的團隊」符合了,「無 PR 強制規範」卻不符合
```
開工狀態:單人專案;main 有 branch protection(要求 PR 與 CI 通過)
整合風格:直接進 trunk
```
