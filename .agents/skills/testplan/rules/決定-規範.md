# Rule 1 [must] - 寫回決定前對照 spec、規格檔、先前的決定與前幾次迭代的實跑護欄,矛盾就帶著原文再問
- 每一個決定寫回 plan.md 之前,對照四處:spec.md 的需求與假設、規格檔(contracts、原型、部署檔)、plan.md 裡已經決定的待決問題,以及 spec.md 註明建立在前一次迭代之上時,前面每一次迭代 testplan.md 的實跑共同護欄
- 決定和其中任何一處矛盾時,不寫回;回到提問的那一步,把矛盾的兩邊原文(這個決定與被它抵觸的那一句,寫出檔名與位置)一起列出,再問一次要照哪一邊、要不要改哪一份
- 不論決定是誰給的(使用者本人或代為回答的人),都照同樣的方式處理
- 為什麼:決定寫進 plan.md 之後,下游照它排任務、寫程式;和 spec 或合約矛盾的決定一旦寫進去,兩份文件各說各話,做事的人只能自己挑一邊。colab-gpu-bridge 第一次迭代的 plan.md 有 17 列改判或推翻先前的做法,沒有一列回頭確認過矛盾。第三次迭代(003)的 testplan 把 G-01 決定成對桌機 127.0.0.1:11434 的 Ollama 送 GET,而 001 testplan 的實跑共同護欄 P6 寫「桌機的 11434 是使用者自己的 Ollama,不送任何請求」;只對照三處時這一句不在範圍內,決定照樣寫回,到 analyze 追原始碼才被攔下

## good example
- 使用者對 Q12 回「不補 `latest`,直接用輸入的名稱查」,但合約 `ui.openapi.yaml` 寫了沒寫版本時補成 `latest`;**不寫回,帶著兩邊原文再問一次**
```
Q12 的回答和合約矛盾,請再決定一次:
- 你的決定:不補 latest,直接用輸入的名稱查
- 合約 contracts/ui.openapi.yaml § paths./api/downloads/estimate.post:「name 沒有 `:` 時補成 `<name>:latest`」
要照決定改合約(轉交 api-plan),還是照合約補 latest?
```

## bad example
- 同一個回答,**照樣寫回 plan.md**;tasks 照決定排任務,合約照舊寫補 `latest`,implement 時兩邊對不上,只能由做事的人自己挑
```
| Q12 | testplan | 沒寫版本時要不要補 latest… | — | 不補,直接用輸入的名稱查 |
```

## good example
- 003 的 spec.md 註明建立在 002 之上;對 Q8 的回答是「G-01 對桌機 Ollama 唯讀實跑」,003 的 spec、規格檔與 plan.md 都沒提 11434,但 001 testplan 的實跑共同護欄 P6 不准;**對照到前面迭代的護欄,不寫回,帶著兩邊原文再問**
```
Q8 的回答和前一次迭代的實跑護欄矛盾,請再決定一次:
- 你的決定:(a)G-01,真的 RemoteOllama 對桌機 127.0.0.1:11434 的 Ollama 只送 GET /api/tags、GET /api/ps
- ../001-session-model-catalog/testplan.md § 實跑案例的共同護欄 P6:「桌機的 11434 是使用者自己的 Ollama,不送任何請求」
要在 003 放寬 P6,還是 G-01 不碰 11434(例如測試自己在別的 port 起臨時的 ollama serve)?
```

## bad example
- 同一個回答,只對照 003 自己的三處,**沒有讀前面迭代的 testplan.md,照樣寫回 plan.md**;到 analyze 追原始碼才發現 `RecordingTransport` 的 `check_port(11434)` 會擋下,只能回頭新增 Q27 取代 Q8
```
| Q8 | testplan | E7 的 httpx.MockTransport 與 E2 的 FakeRemoteOllama 指到哪個實跑… | — | (a)G-01 對桌機 Ollama 唯讀實跑,Colab 上的寫未驗證 |
```

## good example
- 邊界:決定只是在合約允許的範圍內選一種做法(合約寫「錯誤訊息用繁體中文」,決定選了哪一句文案);**不算矛盾,直接寫回**
```
| Q13 | testplan | LIBRARY_TIMEOUT 的訊息要不要附退路… | — | (a) 附「從精選清單挑選或直接輸入名稱」 |
```

## bad example
- 邊界:同一個決定,因為「和合約的文字不完全一樣」就**當成矛盾再問一次**;合約沒有規定文案,使用者被問了一題不需要問的問題
```
Q13 的回答和合約矛盾,請再決定一次:合約只寫「繁體中文」,沒有寫這句文案
```

# Rule 2 [must] - 改判先前的決定時新增一列,不覆寫原列
- 新的決定,或使用者這次的請求本身,推翻或修改 plan.md 已經決定的某一題時(例如某題決定「這一輪不補」,這次請求就是要補),不改那一題的「決定」欄;在表尾新增一題,「問題」欄開頭寫「取代 Q<原編號>:」並寫出改判的理由
- 被取代的那一題,「決定」欄原文保留,在後面加上「(已被 Q<新編號> 取代)」
- 為什麼:覆寫之後,看不出原本決定了什麼、為什麼改;任務描述、commit 訊息與完成報告引用的還是舊的決定,沒有人知道它已經不成立

## good example
- Q19 原本決定 (a),實作時發現要改成 (b);**新增 Q26 寫明取代 Q19 與理由,Q19 原文保留並註明被取代**
```
| Q19 | tasks | 已滿足的案例怎麼排紅燈… | — | (a) 對照組紅燈(已被 Q26 取代) |
| Q26 | implement T058a | 取代 Q19:T001b 已讓 _get 接住例外,改成… | — | (b) … |
```

## bad example
- 同一次改判,**直接把 Q19 的決定欄改成 (b)**;已經照 (a) 排好的 20 個任務還寫著 (a) 的做法,沒有人知道 Q19 改過
```
| Q19 | tasks | 已滿足的案例怎麼排紅燈… | — | (b) … |
```

## good example
- 邊界:原本的決定欄寫「待決」,現在才第一次決定;**直接填寫,不算改判**
```
| Q21 | tasks | 綠燈要寫多寬… | — | (a) 每個綠燈只寫剛好讓自己案例通過的程式碼 |
```

## bad example
- 邊界:同一題第一次決定,卻**新增一列「取代 Q21」**;表裡多了一題沒有意義的取代,`check_plan` 還要追一條不存在的改判
```
| Q21 | tasks | 綠燈要寫多寬… | — | 待決(已被 Q27 取代) |
| Q27 | tasks | 取代 Q21:第一次決定… | — | (a) … |
```
