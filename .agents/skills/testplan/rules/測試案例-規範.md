# Rule 1 [must] - 要抓的錯寫成一種具體的錯誤實作
- 「要抓的錯」寫出一種寫錯的程式會怎麼做:哪個元件在什麼情況下做了什麼不該做的事,或沒做什麼該做的事
- 一個案例要抓不只一種錯時,用「或」串起來,每一種都要具體
- 為什麼:接手寫測試的人只讀計劃;他是照「要抓的錯」挑斷言、確認紅燈是為了對的理由失敗。只寫「功能壞掉」,他挑不出哪一個斷言能分辨對錯,寫出來的測試換成錯誤的實作照樣會綠

## good example
- **寫出錯誤實作做了什麼**:聊天會重置計時,接手的人知道要斷言逾時發生的時間點
```
| BE-11 | `/ws` › 送 `chat` → `/ws` › 出手限時到期 | … | 在 T 一半時 Bob 送 `chat`,之後 Alice 不出手 | 則1:… | 聊天把出手計時重置或延後 | FR-027 |
```

## bad example
- 同一個案例,但**只寫了出問題的範圍**;接手的人只會斷言「最後是逾時」,聊天重置計時的實作也會通過
```
| BE-11 | `/ws` › 送 `chat` → `/ws` › 出手限時到期 | … | 在 T 一半時 Bob 送 `chat`,之後 Alice 不出手 | 則1:… | 計時有問題 | FR-027 |
```

## good example
- 邊界:這個案例要抓兩種錯,**用「或」串起來,兩種都各自具體**
```
| BE-25 | `/ws` › 送 `guess` | Alice 猜 `5678` 猜中 | Bob 補猜 `9012` | 則1:… | 房主猜中就立刻結束,不給挑戰者補猜;或補猜沒中仍判平手 | FR-013 |
```

## bad example
- 邊界:同一個案例,看起來也講了錯在哪,但**只是把需求反過來說**;沒有說是哪一種實作會犯錯,接手的人挑不出斷言
```
| BE-25 | `/ws` › 送 `guess` | Alice 猜 `5678` 猜中 | Bob 補猜 `9012` | 則1:… | 勝負判定不符合 FR-013 | FR-013 |
```

# Rule 2 [must] - 換成要抓的錯,至少有一條則會不過
- 寫完一個案例,把「要抓的錯」那種實作代進去走一遍:「則」裡至少要有一條會不過
- 和時間有關的則寫成量化的界線(在幾秒到幾秒之間、幾秒內、經過幾秒仍沒有),不寫「附近」「很快」「正常」
- 為什麼:則沒有鑑別力時,紅燈只證明功能還沒寫,綠燈卻證明不了要抓的錯不存在;「附近」這種字,接手的人會整句略過,斷言就只剩下最後的結果

## good example
- 限時 0.6 秒,0.3 秒時聊天;計時被重置的話 0.9 秒才逾時,**則1 的界線會讓它不過**
```
| BE-11 | … | 對局中,輪到 Alice,出手限時 0.6 秒 | 0.3 秒時 Bob 送 `chat`,之後 Alice 不出手 | 則1:Alice 在開局後 0.6 到 0.8 秒之間收到 `match_ended{reason:"timeout"}` | 聊天把出手計時重置或延後 | FR-027 |
```

## bad example
- 同一個案例,但**則沒有時間界線**;計時被重置的實作 0.9 秒時一樣逾時,這條則照樣通過
```
| BE-11 | … | 對局中,輪到 Alice,出手限時 0.6 秒 | 0.3 秒時 Bob 送 `chat`,之後 Alice 不出手 | 則1:仍在原本的 T 附近收到 `match_ended`,原因為逾時 | 聊天把出手計時重置或延後 | FR-027 |
```

## good example
- 邊界:要抓的錯是「沒推播給對手」,只看送的人那一側抓不到;**則2 斷言對手那一側,代進去會不過**
```
| FE-09 | 對局畫面 › 「送出猜測」 | 對局開始 | Alice 猜 `5612` | 則1:Alice 的猜測紀錄出現「房主:5612 → 2A0B」<br>則2:Bob 的猜測紀錄出現「房主:5612 → 2A0B」 | 對手畫面沒有即時更新猜測紀錄 | FR-012 |
```

## bad example
- 邊界:同一個案例,則寫得具體、也量得出來,但**只斷言送的人那一側**;沒推播給對手的實作,Alice 畫面照樣出現這一列
```
| FE-09 | 對局畫面 › 「送出猜測」 | 對局開始 | Alice 猜 `5612` | 則1:Alice 的猜測紀錄出現「房主:5612 → 2A0B」 | 對手畫面沒有即時更新猜測紀錄 | FR-012 |
```

# Rule 3 [must] - 一條則只斷言一件可以觀察的事
- 一條則只有一個觀察對象:一個收件者收到的一則訊息、一個回傳值,或一個人畫面上的一個元素
- 同一件事要對兩個人、兩個方向或前後兩個時間點成立,就拆成兩條則
- 為什麼:接手寫測試的人是一條一條把則寫成斷言的;一格裡塞了好幾件事,他常只寫出前面那一件,後面的斷言就沒有了,也沒有人對得出少了哪一條

## good example
- 「仍能聊」與「寬限照舊判負」**拆成兩條**,少寫哪一條一眼就對得出來
```
| BE-12 | `/ws` › 連線關閉 → `/ws` › 送 `chat` | 對局中,Bob 斷線、寬限 1 秒 | Alice 送 `chat{text:"在嗎"}` | 則1:Alice 收到自己的 `chat_message{text:"在嗎"}`<br>則2:Bob 斷線後 1 到 1.3 秒之間 Alice 收到 `match_ended{reason:"disconnect"}` | 對手斷線時拒收聊天,或聊天讓寬限計時重來 | FR-027 |
```

## bad example
- 同一個案例,但**兩件事擠在一句**;接手的人寫完前半就停了,寬限到期判負的斷言沒有出現在測試裡
```
| BE-12 | `/ws` › 連線關閉 → `/ws` › 送 `chat` | 對局中,Bob 斷線、寬限 1 秒 | Alice 送 `chat{text:"在嗎"}` | 則1:Alice 收到自己的 `chat_message`,沒有 `error`;Bob 的寬限計時照舊,到期仍判負 | 對手斷線時拒收聊天,或聊天讓寬限計時重來 | FR-027 |
```

## good example
- 邊界:同一則訊息裡的兩個欄位,**是同一個觀察對象**,可以留在同一條則
```
則1:Alice 收到 `room_state`,`you=host`、`status=waiting`
```

## bad example
- 邊界:同樣只有一句,但**觀察對象是兩個人**;要對 Carol 與 Dave 各自成立,就要拆成兩條
```
則1:Carol、Dave 的 `room_state.chat` 是空陣列
```

# Rule 4 [must] - 需求依適用的故事數歸到故事或全域測試區
- spec 寫在某個使用者故事底下、或「適用」只列一個故事的需求,它的案例放在那個故事的節,需求覆蓋表的歸屬寫「故事 N」
- 「適用」列了兩個以上故事的需求,歸屬寫「全域」,放進全域測試區的涵蓋彙整;範疇內的故事裡已經有案例涵蓋它的,在彙整的「故事裡涵蓋它的案例」列出,沒辦法歸到單一故事的,在全域案例寫成 `G-` 案例
- 為什麼:跨故事的需求塞進其中一個故事,其他故事做完時沒有人會再驗它;每個故事都各寫一次,同一件事又會被測好幾遍、門檻還各寫各的

## good example
- NFR-007 只適用故事 5,**放在故事 5**;NFR-005 適用故事 1~5,**歸到全域**,故事 5 裡涵蓋它的案例在彙整列出
```
| NFR-007 訊息只送同房 | 故事 5 | US5-BE-18 | — | US5-AJ-13 | — | 🔴🟢 |
| NFR-005 即時推送 | 全域 | US5-BE-01 | — | US5-AJ-01 | G-01 | 🔴🟢、📏 量測 |

### 3.1 全域 NFR 的涵蓋彙整
| NFR-005 即時推送 | 1、2、3、4、5 | US5-BE-01、US5-AJ-01 | G-01 |
```

## bad example
- 同一份 spec,但 **NFR-005 被當成故事 5 的需求**;故事 1~4 的推送延遲沒有任何地方會再驗
```
| NFR-005 即時推送 | 故事 5 | US5-BE-01 | — | US5-AJ-01 | — | 🔴🟢 |
```

## good example
- 邊界:NFR-001 寫在故事 2 底下,但故事 5 的 US5-BE-13 順帶驗到它;**歸屬仍是故事 2**,故事 5 的案例只在需求欄列出 NFR-001
```
| US5-BE-13 | `/ws` › 送 `chat` | … | Alice 送 `chat{text:"我的答案是 1234"}` | 則1:… | … | 邊界情況、NFR-001 |
```

## bad example
- 邊界:同一個案例,因為兩個故事都碰到 NFR-001 就**把它改歸全域**;spec 只把它寫在故事 2,彙整表多出一條沒有人宣告過的全域需求
```
| NFR-001 答案不外流 | 全域 | US5-BE-13 | — | — | — | 🔴🟢 |
```

# Rule 5 [must] - 要後端回應才看得到的畫面行為放跨端點驗收
- 前端行為要等後端回應才看得到的(收到訊息、狀態更新、重連回補),案例放在故事的「跨端點驗收」節,ID 寫 `US<k>-AJ-<兩位數>`,接真的後端
- 前端的端點節只放不靠後端就看得到的行為(例如輸入框的字數限制提示);不用假後端或照合約回放訊息的替身來測需要後端的行為
- 前端端點節沒有這類行為時,那一節寫明沒有案例
- 為什麼:替身照合約寫,合約或後端任一邊錯了,替身和前端一起錯,測試全綠、一接上真的後端就壞;前端端點節的案例要和後端平行開發,真正需要後端的行為放在端點節都完成後的跨端點驗收,紅燈與綠燈才都是接真東西跑出來的

## good example
- 「對手送出訊息後我的聊天室出現泡泡」要後端轉送,**放在跨端點驗收**
```
### 2.3 跨端點驗收
| US5-AJ-03 | 對局畫面 › 「送出訊息」 | 對局進行中 | Bob 送出「加油」 | 則1:Alice 的對局畫面聊天室出現 Bob·挑戰者·加油 的泡泡 | … | FR-023 |
```

## bad example
- 同一個行為,但**放在 E1 前端節,用回放 `chat_message` 的假後端來測**;後端轉送漏給送出者的錯,這個案例永遠抓不到
```
### 2.2 E1 前端
| US5-FE-03 | 對局畫面 › 「送出訊息」 | 假後端回放 `chat_message{sender:"challenger"}` | Bob 送出「加油」 | 則1:Alice 的聊天室出現泡泡 | … | FR-023 |
```

## good example
- 邊界:「首頁的暱稱只有空白時進入房間不可按」只要打開首頁就看得到,不需要後端回應;**它可以留在 E1 前端節**
```
### 2.2 E1 前端
| US1-FE-01 | 首頁 › 「進入房間」 | 首頁已打開 | 「暱稱」輸入框只有空白字元 | 則1:「進入房間」不可按 | 只判斷空字串、沒去除空白 | FR-001 |
```

## bad example
- 邊界:「訊息輸入框只有空白時送出訊息不可按」看起來也只是一個輸入框,但房間畫面要進房才出現,**進房要靠後端,卻仍留在 E1 前端節**,只能靠假後端把房間畫面撐出來
```
### 2.2 E1 前端
| US5-FE-01 | 房間畫面 › 「送出訊息」 | 假後端回 `room_state{status:"setup"}` | 「訊息」輸入框只有空白字元 | 則1:「送出訊息」不可按 | … | FR-024 |
```

# Rule 6 [must] - 每條 NFR 都有標明驗證方式的案例
- 每條 NFR 至少有一個非功能案例或全域案例涵蓋;案例的「驗證方式」填 `🔴🟢 行為測試`、`📏 量測` 或 `📏 人工` 其中一種
- 能以一次執行的斷言判定對錯的,寫成 🔴🟢 行為測試;要在負載或一段時間下量出數字的寫 📏 量測,要真人、真裝置或正式環境才驗得到的寫 📏 人工
- 為什麼:NFR 沒有驗證方式,`/tasks` 不知道要排 /tdd 紅綠還是 📏 量測任務,最後只會被標成不在範疇;寫得出斷言的 NFR 被標成 📏,就少了紅燈證據

## good example
- NFR-006 要 50 房同時對局才量得到,**標 📏 量測**
```
| G-01 | 效能(延遲與承載) | 📏 量測 | `/ws` › 送 `guess` | 50 間房同時在對局 | 每間房每 2 秒送一次 `guess`,持續 5 分鐘 | 則1:從送出 `guess` 到雙方都收到 `guess_result`,p95 ≤ 1 秒 | 廣播時逐一 `await` 每條連線 | NFR-006、SC-003 |
```

## bad example
- 同一條 NFR,但**驗證方式沒填**;排任務的人不知道要寫負載腳本還是 /tdd 紅綠
```
| G-01 | 效能(延遲與承載) | | `/ws` › 送 `guess` | 50 間房同時在對局 | 每間房每 2 秒送一次 `guess`,持續 5 分鐘 | 則1:從送出 `guess` 到雙方都收到 `guess_result`,p95 ≤ 1 秒 | 廣播時逐一 `await` 每條連線 | NFR-006、SC-003 |
```

## good example
- 邊界:NFR-008 純文字顯示看起來是「品質」,但**一次送出、一個斷言就判得出對錯**,所以是 🔴🟢 行為測試
```
| US5-AJ-07 | 安全(XSS) | 🔴🟢 行為測試 | 房間畫面 › 「送出訊息」 | 雙方在房間畫面 | Alice 送出 `<b>粗</b><script>window.__x=1</script>` | 則1:Bob 的聊天室泡泡原樣顯示這串文字<br>則2:Bob 的 `window.__x` 未被設定 | 用 `dangerouslySetInnerHTML` 畫訊息 | NFR-008 |
```

## bad example
- 邊界:同一個案例,因為是 NFR 就**一律標成 📏 人工**;一個寫得出斷言的安全行為被排成人工檢查,沒有紅燈證據
```
| US5-AJ-07 | 安全(XSS) | 📏 人工 | 房間畫面 › 「送出訊息」 | 雙方在房間畫面 | 人工送出含 HTML 的訊息 | 則1:看起來沒有被解析 | 用 `dangerouslySetInnerHTML` 畫訊息 | NFR-008 |
```

# Rule 7 [must] - 📏 案例的則寫出指標與門檻
- 驗證方式是 📏 量測或 📏 人工的案例,每一條「則」寫出要量的指標與通過門檻(例如 p95 ≤ 1 秒、0 條、1 分鐘內),門檻取自 spec 的 NFR 或 SC
- 為什麼:📏 任務做完交出的是一個數字;則沒有門檻,量出來的數字沒有人能判斷是過還是沒過,完成報告只能寫「已量測」

## good example
- **指標與門檻都寫出來**,門檻取自 SC-003
```
| G-01 | 效能(延遲與承載) | 📏 量測 | `/ws` › 送 `guess` | 50 間房同時在對局 | 每間房每 2 秒送一次 `guess`,持續 5 分鐘 | 則1:從送出 `guess` 到雙方都收到 `guess_result`,p95 ≤ 1 秒<br>則2:5 分鐘內沒有連線被伺服器中斷 | 廣播時逐一 `await` 每條連線 | NFR-006、SC-003 |
```

## bad example
- 同一個案例,但**則只寫了感受**;量到 p95 1.4 秒時,沒有人能判斷算不算過
```
| G-01 | 效能(延遲與承載) | 📏 量測 | `/ws` › 送 `guess` | 50 間房同時在對局 | 每間房每 2 秒送一次 `guess`,持續 5 分鐘 | 則1:推送很快、不卡 | 廣播時逐一 `await` 每條連線 | NFR-006、SC-003 |
```

## good example
- 邊界:人工驗證也一樣;**門檻寫成計時的上限**,取自 SC-001
```
| G-04 | 易用性 | 📏 人工 | 首頁 › 「進入房間」 → 房間畫面 › 「開始」 | 兩位沒玩過的人 | 不看說明,從打開網址到對局開始 | 則1:兩人都在 1 分鐘內開始對局 | 房號或答案的格式提示不清楚,使用者反覆被拒 | SC-001 |
```

## bad example
- 邊界:同一個人工案例,因為「人工本來就是主觀的」就**只寫了感想**;找了兩個人試完,判斷不出 SC-001 過了沒有
```
| G-04 | 易用性 | 📏 人工 | 首頁 › 「進入房間」 → 房間畫面 › 「開始」 | 兩位沒玩過的人 | 不看說明,從打開網址到對局開始 | 則1:兩人覺得很好上手 | 房號或答案的格式提示不清楚,使用者反覆被拒 | SC-001 |
```

# Rule 8 [must] - 📏 案例寫出副作用與護欄
- 驗證方式是 📏 量測或 📏 人工的案例,「副作用與護欄」欄寫出會寫到哪裡、呼叫哪些服務,以及防止碰到正式資料的具體做法:用哪個暫存 volume 或資料庫、哪些指令不用、服務位址與金鑰從哪裡帶入
- 會碰到正式資料或共用服務的案例,在提出測試計劃時列為要使用者同意的項目,寫出呼叫量與占用
- 🔴🟢 行為測試的案例這一欄寫 —
- 為什麼:實跑要越真實越好,也就越容易碰到真的東西;護欄沒寫具體做法,實跑的人會照平常的指令做,compose 的 project name 和正式服務相同時,照常 `up` 就會對正式資料庫跑 migration

## good example
- 接 asr-gateway 的正確率案例;**寫出只寫哪個暫存 volume、呼叫量、位址與金鑰怎麼帶入,以及服務不通時怎麼辦**
```
| ID | 品質屬性 | 驗證方式 | … | 則 | 要抓的錯 | 需求 | 副作用與護欄 | 判定者與樣本 |
```
