# Rule 1 [must] - 只講格式名稱不算講明參考範例
- 使用者給了參考 artifact 的檔案路徑、網址或貼上的全文,才算講明要參考哪一份 artifact
- 只講格式或出處的名稱(例如「GitHub 常見的 PR 描述」「spec-kit 的 spec」)不算講明,要問使用者實物
- 為什麼:沒有實物,寫進範例的內容只能由 AI 照印象自擬;之後的客製化、抽樣板與後設規則都建立在這份自擬的範例上,做出來的 Skill 產出的是 AI 以為的格式,不是使用者手上那一份

## good example
- 使用者**給了檔案路徑**,算講明,不用再問
```
使用者:我想做一支 skill 叫 spec-writer,放在 tmp/verify/spec-writer/,參考 .claude/skills/specify/templates/spec.template.example.md
判斷:給了參考 artifact 的檔案路徑 → 已講明
```

## bad example
- 使用者**只講了格式名稱**,卻被判成已講明;範例由 AI 照常見寫法自擬
```
使用者:我想做一支 skill 叫 pr-description,參考 GitHub 常見的 PR 描述格式
判斷:講了要參考的格式 → 已講明,自己寫一份 GitHub 常見的 PR 描述當範例
```

## good example
- 邊界:格式名稱之外還列了三個標題,但**只有標題沒有內文**,仍然不算講明,要問實物
```
使用者:參考 GitHub 常見的 PR 描述格式(## Summary / ## Changes / ## Test plan)
判斷:只有格式名稱與標題,沒有檔案路徑、網址或全文 → 未講明,問實物
```

## bad example
- 邊界:同一句,因為**列出了標題就當成給了實物**;每一段底下寫什麼、寫多長,都還是 AI 自擬
```
使用者:參考 GitHub 常見的 PR 描述格式(## Summary / ## Changes / ## Test plan)
判斷:標題都給了 → 已講明,照三個標題自己補上內文當範例
```
