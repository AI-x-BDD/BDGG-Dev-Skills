# Rule 1 [must] - 每個驗收情境都看得到
- spec 裡這個介面涉及的每一個驗收情境,正常的流程在原型裡照著點、照著等就走得到;錯誤、空的、載入中與不常見的事件(斷線、逾時)在狀態總覽各有一格
- 一個畫面有幾種 `data-state`,狀態總覽就有幾格 `頁面.html?state=狀態代號` 的 iframe
- 為什麼:原型是拿來讓人看介面、提意見的;只做了順利的那一條路,錯誤訊息怎麼寫、空的時候放什麼,要等實作完才第一次被看到,那時改的成本最高

## good example
- 「購物車是空的」與「庫存不足」兩個驗收情境,**在狀態總覽各有一格**
```html
<figure>
  <iframe src="cart.html?state=empty" title="購物車:空的" loading="lazy"></iframe>
  <figcaption>空的:FR-006 移除最後一件商品之後</figcaption>
</figure>
<figure>
  <iframe src="cart.html?state=error" title="購物車:庫存不足" loading="lazy"></iframe>
  <figcaption>庫存不足:FR-007 結帳時數量超過庫存</figcaption>
</figure>
```

## bad example
- 同一個畫面,但**狀態總覽只放了有商品的那一格**;空購物車與庫存不足的畫面沒有人看過
```html
<figure>
  <iframe src="cart.html?state=normal" title="購物車:有商品" loading="lazy"></iframe>
  <figcaption>有商品:FR-004、FR-005 改數量與合計</figcaption>
</figure>
```

## good example
- 邊界:「結帳時庫存不足」在狀態總覽已經有一格;但**它是照著流程就會碰到的情境,假資料也安排了一件超過庫存的商品**,在原型裡照著點也走得到
```js
cart: [
  { productId: "p-soap-02", name: "山茶花手工皂 3 入組(無香精,敏感肌適用)", price: 420, quantity: 4 },
],
products: [
  { id: "p-soap-02", name: "山茶花手工皂 3 入組(無香精,敏感肌適用)", price: 420, stock: 3, category: "洗沐" },
],
```

## bad example
- 邊界:同一個情境,狀態總覽有那一格,但**假資料的數量都在庫存以內**;照著流程點永遠看不到錯誤是在哪一步冒出來的
```js
cart: [
  { productId: "p-soap-02", name: "山茶花手工皂 3 入組(無香精,敏感肌適用)", price: 420, quantity: 1 },
],
```

# Rule 2 [must] - 審美設定只寫在 :root 變數
- 顏色、字體、圓角、間距與陰影只在 `style.css` 的 `:root` 定義一次,其他地方一律寫成 `var(--變數)`
- HTML 裡不寫 `style` 屬性與 `<style>` 區塊
- 為什麼:使用者看完原型最常提的是「顏色再暖一點」「字大一點」;散落在各處的色碼要一個一個找,改漏一處就出現兩種主色

## good example
- 按鈕的顏色、圓角、間距**全部用變數**
```css
.btn-primary {
  padding: var(--space-sm) var(--space-lg);
  color: var(--color-primary-text);
  background: var(--color-primary);
  border-radius: var(--radius-sm);
}
```

## bad example
- 同一個按鈕,但**直接寫了色碼與像素**;要把主色從磚紅換成墨綠,得在每個選擇器裡找 `#b5532f`
```css
.btn-primary {
  padding: 10px 28px;
  color: #fff;
  background: #b5532f;
  border-radius: 6px;
}
```

## good example
- 邊界:`font-size: 13px` 與 `width: 72px` 不是變數;但**它們是版面的尺寸,不是顏色、字體、圓角、間距與陰影**,可以直接寫
```css
.thumb {
  width: 72px;
  height: 72px;
  border-radius: var(--radius-sm);
  background: var(--color-line);
}
```

## bad example
- 邊界:同一個縮圖,尺寸照樣直接寫,但**順手把底色與圓角也寫死**;它們屬於審美設定,改主題時會被漏掉
```css
.thumb {
  width: 72px;
  height: 72px;
  border-radius: 6px;
  background: #e6dfd5;
}
```

# Rule 3 [must] - 假資料要像真的
- 假資料用這個產品實際會出現的內容:真實的名稱與說法、長短不一的文字、會碰到邊界的數值(庫存 0、最長的名稱、最大的數量)
- 不用「商品 1」「測試」「Lorem ipsum」這類佔位字
- 畫面上有圖片的資料,假資料也帶圖片:用依 id 固定的佔位照片網址(例如 `https://picsum.photos/seed/<id>/240/240`),載不到時退回灰色方塊
- 為什麼:版面是被真實內容撐壞的;名字都一樣短、數字都剛剛好,原型看起來很整齊,上線第一天就遇到換行、截斷與售完沒有畫面

## good example
- 名稱有長有短,**有一件庫存 0、有一件名稱特別長**
```js
products: [
  { id: "p-tea-01", name: "阿里山高山烏龍茶 150g", price: 680, stock: 24, category: "茶葉" },
  { id: "p-soap-02", name: "山茶花手工皂 3 入組(無香精,敏感肌適用)", price: 420, stock: 3, category: "洗沐" },
  { id: "p-cup-03", name: "鶯歌柴燒對杯", price: 1280, stock: 0, category: "器皿" },
],
```

## bad example
- 同一份資料,但**全是佔位字與整齊的數字**;看不出長名稱會不會撐破卡片,也沒有售完的商品可以看
```js
products: [
  { id: "p1", name: "商品 1", price: 100, stock: 10, category: "分類 A" },
  { id: "p2", name: "商品 2", price: 200, stock: 10, category: "分類 A" },
  { id: "p3", name: "商品 3", price: 300, stock: 10, category: "分類 B" },
],
```

## good example
- 邊界:訂單編號 `ORD-7K2M9QXA` 看起來是亂打的;但**它照 API 規格的格式 `ORD-` + 8 碼英數**,是像真的資料
```js
orders: [
  { orderId: "ORD-7K2M9QXA", status: "paid", total: 1780, createdAt: "2026-10-18T14:32:00+08:00" },
],
```

## bad example
- 邊界:同一筆訂單,編號用了好記的 `ORD-1`;看起來比較清楚,但**長度與格式都和真的不一樣**,訂單列表的欄寬就是照錯的長度排的
```js
orders: [
  { orderId: "ORD-1", status: "paid", total: 1780, createdAt: "2026-10-18T14:32:00+08:00" },
],
```

## good example
- 商品卡片會放縮圖;**假資料每一筆都帶 `image`,網址用商品 id 當 seed**,每次打開都是同一張
```js
products: [
  { id: "p-tea-01", name: "阿里山高山烏龍茶 150g", price: 680, stock: 24, category: "茶葉", image: "https://picsum.photos/seed/p-tea-01/240/240" },
],
```

## bad example
- 同一份資料,但**沒有圖片欄位**;畫面上的縮圖只是一塊灰色,看不出照片放進去之後卡片會不會太擠
```js
products: [
  { id: "p-tea-01", name: "阿里山高山烏龍茶 150g", price: 680, stock: 24, category: "茶葉" },
],
```

# Rule 4 [must] - 不連任何真的後端
- 原型的資料全部來自 `mock.js`;伺服器的回應、延遲、其他使用者的動作用 `Proto.later` 模擬
- 不呼叫 `fetch`、`XMLHttpRequest`、`WebSocket`、`EventSource`;從 CDN 載入樣式或函式庫可以
- 為什麼:原型要在後端還沒做好、沒有網路的時候也點得開;一連真的後端,打開就是一片錯誤,看的人分不出是畫面的問題還是服務沒開

## good example
- 結帳時的「確認庫存」**用 `Proto.later` 模擬伺服器的延遲與回應**
```js
document.getElementById("checkout").addEventListener("click", () => {
  Proto.showState("loading");
  Proto.later(800, () => {
    const short = cart.find((item) => item.quantity > products.find((p) => p.id === item.productId).stock);
    if (short) return Proto.showState("error");
    location.href = "checkout.html";
  });
});
```

## bad example
- 同一個按鈕,但**真的去呼叫 API**;後端還沒開,按下去只會在 console 看到連線失敗
```js
document.getElementById("checkout").addEventListener("click", async () => {
  const res = await fetch("/api/v1/checkout", { method: "POST" });
  if (!res.ok) return Proto.showState("error");
  location.href = "checkout.html";
});
```

## good example
- 邊界:「付款完成時賣家收到通知」是另一個人的動作,看起來要開 WebSocket 才演得出來;**用 `Proto.later` 在幾秒後把通知加進畫面,一樣看得到**
```js
Proto.later(3000, () => {
  document.getElementById("toast").textContent = "訂單 ORD-7K2M9QXA 已付款,請準備出貨";
  document.getElementById("toast").hidden = false;
});
```

## bad example
- 邊界:同一個通知,因為「推送本來就是 WebSocket」就**在原型裡開連線**;沒有伺服器時,這個畫面永遠等不到通知
```js
const ws = new WebSocket("wss://shop.example.com/ws");
ws.onmessage = (event) => {
  document.getElementById("toast").textContent = JSON.parse(event.data).message;
  document.getElementById("toast").hidden = false;
};
```

# Rule 5 [must] - 動作改到的數字在每個畫面都跟著變
- 加入、刪除、送出這類動作改到的資料,其他畫面上看得到的數字(導覽列的件數、未讀數、合計)都從 `Proto.load` 重新算,不寫死
- 寫入一律經過 `Proto.save`,它會順便更新導覽列的徽章
- 為什麼:原型最常被拿來點的是一整條流程;在這一頁加了東西,下一頁的數字沒變,看的人會以為功能壞了,真正要討論的畫面反而沒人看

## good example
- 導覽列的購物車件數**從購物車的假資料算出來**,在任何一頁加入或刪除都會跟著變
```js
badge() {
  const el = document.getElementById("cart-count");
  if (!el) return;
  const count = Proto.load("cart").reduce((sum, item) => sum + item.quantity, 0);
  el.textContent = count;
  el.hidden = count === 0;
},
```

## bad example
- 同一個徽章,但**件數寫死在 HTML**;商品頁加了兩件,導覽列永遠顯示 2
```html
<a href="cart.html">購物車 <span class="badge">2</span></a>
```

## good example
- 邊界:結帳成功後要清空購物車,看起來直接刪掉 localStorage 最乾淨;**仍然經過 `Proto.save`**,徽章才會跟著歸零
```js
Proto.save("cart", []);
location.href = "orders.html";
```

## bad example
- 邊界:同一個清空,**直接呼叫 `localStorage.removeItem`**;資料清掉了,但這一頁的徽章沒有重算,還顯示剛才的件數
```js
localStorage.removeItem("proto:cart");
location.href = "orders.html";
```

# Rule 6 [must] - 原型頁不放測試用的控制
- 原型頁只呈現實際的運作邏輯:不放切換狀態的按鈕、「模擬某件事」的按鈕與快轉倒數;這些看法一律放在狀態總覽
- 其他使用者的動作照真實的節奏用 `Proto.later` 自動發生;不常見的事件(斷線、逾時)不在原型裡隨機發生,只在狀態總覽看
- 為什麼:看原型的人是在想像真的使用者怎麼用;畫面上混著測試按鈕,他分不出哪些是產品的功能,也會把注意力放在按按鈕而不是走流程

## good example
- 對局畫面上**只有玩家真的會按的東西**;其他玩家的猜測幾秒後自動出現
```js
Proto.later(2500, () => {
  addGuess({ seat: 2, target: 3, digits: "1357", result: "1A1B" });
  nextTurn();
});
```

## bad example
- 同一個畫面,但**上面多了一排模擬按鈕**;看的人以為「模擬:有人斷線」是產品的功能
```html
<button type="button" id="sim-guess">模擬:這一手猜中</button>
<button type="button" id="sim-drop">模擬:有人斷線</button>
<button type="button" id="sim-fast">快轉倒數(剩 3 秒)</button>
```

## good example
- 邊界:「60 秒逾時跳過」是正常流程的一部分,看起來應該在原型裡演;但**它要等滿 60 秒才看得到**,所以照真實的節奏留在原型裡,另外在狀態總覽放一格逾時的樣子
```html
<figure>
  <iframe src="game.html?state=timeout" title="對局:逾時跳過" loading="lazy"></iframe>
  <figcaption>逾時跳過:FR-015 60 秒內沒猜就換下一位</figcaption>
</figure>
```

## bad example
- 邊界:同一個逾時,為了讓人不用等,**把回合倒數改成 5 秒**;流程是走得到了,但看原型的人會以為一回合只有 5 秒
```js
const TURN_SECONDS = 5;
```

# Rule 7 [must] - 憲法的條文和本 Skill 的規範都要照做
- 寫原型時,`constitution_rules.py` 交回的每一條條文都照做;本 Skill 的規範沒有被條文點名取代的,也照樣照做
- 條文和本 Skill 的規範要求的是不同的事時,兩邊同時成立,不因為有了憲法就跳過本 Skill 的規範
- 為什麼:憲法是這個專案多加的要求,Skill 的規範是這份產出物能被下游讀懂的基本盤;只照其中一邊,交出的原型不是違反憲法,就是讓下游的 Skill 讀不懂

## good example
- 憲法要右上角顯示登入者,Skill 要假資料像真的;**兩邊都照做**
```
憲法:constitution/ui-plan/page.md〈每個畫面右上角顯示登入者名稱〉
Skill:rules/原型-規範.md〈假資料要像真的〉

<header><span class="user">王小明</span></header>
```

## bad example
- 同一個畫面,右上角有名稱,但**假資料是 `User Name`**;只照了憲法,Skill 的規範沒有人守
```
<header><span class="user">User Name</span></header>
```

# Rule 8 [must] - 只有 waive 列的 Rule 改照條文做
- `constitution_rules.py` 交回的 waive 列的 Rule 不照做,改照點名取代它的那一條條文;waive 沒有列的 Rule,即使和它在同一個規範檔,也照樣照做
- 檢查腳本有 `--waive` 參數時,把 waive 的每一項原樣交給它
- 為什麼:waive 是使用者寫憲法時確認過要翻掉的;照樣照被取代的 Rule 做,交出的原型就違反憲法;把整個規範檔都當成被取代,沒有被翻掉的規定就沒有人守

## good example
- waive 列了〈審美設定只寫在 :root 變數〉;**改照條文直接寫顏色,檢查時交給 `--waive`**
```
憲法:constitution/ui-plan/style.md〈顏色直接寫在用到的地方〉
waive:原型-規範〈審美設定只寫在 :root 變數〉

.btn-primary { background: #2563eb; }
uv run scripts/check_prototype.py --prototype … --waive "原型-規範〈審美設定只寫在 :root 變數〉"
```

## bad example
- 同一個 waive,但**照樣把顏色寫成 :root 變數**;違反了憲法
```
:root { --primary: #2563eb; }
.btn-primary { background: var(--primary); }
```

## good example
- 邊界:waive 只列了審美那一條;**同一個規範檔的〈不連任何真的後端〉照樣照做**
```
.btn-primary { background: #2563eb; }
fetch 一律換成 Proto.load()
```

## bad example
- 邊界:同一個 waive,**把整個原型-規範都當成被取代**,畫面直接 fetch 真的 API
```
.btn-primary { background: #2563eb; }
fetch('/api/cart')
```

# Rule 9 [must] - 沒有點名取代的衝突照本 Skill 的 Rule 做並交給使用者決定
- 條文和本 Skill 的某條 Rule 衝突、卻沒有用 `- 取代:` 點名它時,不自己選邊:原型照本 Skill 的 Rule 寫,把衝突的條文與 Rule 列進交出時的待決問題,由使用者決定要改憲法還是改產出物
- 為什麼:沒有點名的衝突,使用者沒有決定過要翻掉哪一條;AI 自己選了憲法,等於替使用者改了 Skill 的規範,選了 Skill 又沒說,使用者以為憲法有被照做

## good example
- 條文要加切換狀態的按鈕,但沒有點名取代;**照 Skill 不加,把衝突列進待決問題**
```
憲法:constitution/ui-plan/page.md〈每個畫面加一個切換狀態的除錯按鈕〉(沒有取代)
Skill:rules/原型-規範.md〈原型頁不放測試用的控制〉

page.html:沒有除錯按鈕;狀態從 states.html 看
待決問題:憲法〈每個畫面加一個切換狀態的除錯按鈕〉和原型-規範衝突,先照 Skill 不加;要不要在憲法點名取代,請你決定
```

## bad example
- 同一個衝突,**AI 自己選了憲法**,加了除錯按鈕;`check_prototype.py` 判不過,待決問題也沒提
```
page.html:<button onclick="Proto.setState('error')">切到錯誤</button>
待決問題:(沒有提到衝突)
```
