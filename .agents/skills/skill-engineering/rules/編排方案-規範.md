# Rule 1 [must] - 方案先設計必要的 SOP 主幹
- 依確認過的預期與診斷，用 skill-form-sop 的規範設計草案；提案階段只讀規範，不執行它的寫檔步驟。
- 檢查每一步對成果的必要性，再判斷需要哪些部件；新建時目標檔不存在屬正常，實作時由 form-sop 建立。
- 為什麼：先替既有每一步加部件，會把不必要或錯誤的流程一起固定下來。

## good example
- 重複詢問的原因已確認，先改流程責任。
草案讓入口取得必要資訊、下游接收已確認內容，缺資料才回問；再決定交接判斷需要哪些規則。

## bad example
- 同一診斷保留所有詢問，再補限制。
原有三次 Ask 全部留下，分別加上「不要重複詢問」規則，沒有決定資訊由誰取得與傳遞。

# Rule 2 [must] - 部件依職責選用
- engineering 負責預期成果、根因、整體編排與驗收；Forms 負責部件成形，Derivers 負責單一步驟轉換。
- 對必要步驟依下表選用；原句已足夠清楚就保留，不為了湊齊目錄建立部件。

| 職責 | 編排方式 |
|---|---|
| 順序、分支、步驟責任 | form-sop |
| 步驟的判斷要求 | derive-rule → form-rule → form-sop |
| 步驟產出的固定格式 | derive-template → form-template → form-sop |
| 明確輸入輸出的確定性處理 | derive-script → form-script → form-sop |
| 既有部件改寫、合併、刪減內容 | 對應 Form；引用有變再交 form-sop |

- 同一步可用多種部件，但各自承擔不同職責；同一要求指定一個主要維護位置，其他部件只保留必要引用或驗證。
- 為什麼：用樣板代替判斷、用規則代替可執行處理，會把責任放到難以維護的位置。

## good example
- 同一報告的三種責任分開處理。
腳本計算數字，Rule 指導如何解讀差異，樣板固定報告欄位；Rule 不另抄一份欄位排列。

## bad example
- 同一報告的格式存在兩個主要維護位置。
樣板已固定所有欄位，Rule 又逐字列出同樣的欄位與順序，改格式必須同步改兩份。

# Rule 3 [must] - 每項重構操作對應成果或根因
- 方案列出保留、改寫、搬移、合併、刪除與新增的必要操作；每項包含目標位置、理由、前後行為、負責的 Form／Deriver 與驗收依據，不必列沒有用到的操作種類。
- 允許整段重寫或跨 Skill 調整；範圍由因果關係決定，不以最小 diff 或最大改動量為目標。
- 刪減時說明原職責已不需要或由誰完整接手，檢查相關使用端；引用與分支也在同一方案內修復。
- 為什麼：根本性改善需要移除造成問題的機制，也需要避免因刪除而丟失仍有用的行為。

## good example
- 邊界：抽樣板與清理被列成兩個明確操作。
derive-template 抽出報告格式；form-rule 刪掉已由樣板承接的欄位順序要求，保留資料判讀要求；驗收格式一致且判讀仍正確。

## bad example
- 邊界：同一次抽樣板只增加部件。
新增樣板後保留重複的欄位順序要求，理由只有「少改比較安全」，沒有評估兩份格式日後如何維護。

# Rule 4 [must] - 具體方案的確認可以傳遞
- 方案確認涵蓋具體目標、轉換內容、輸入輸出或格式、刪改範圍與驗收方式；委派時把相關內容和使用者確認一併交給子 Skill。
- 方案未確認，不實作；使用者沉默不算確認。同一份仍有效的具體方案已確認時沿用，新證據改變根因、預期或範圍時，原確認不涵蓋該差異。
- 子 Skill 的結果仍在該範圍內，就沿用確認；新決定改變成果、範圍或對外行為時，回到方案確認。根因或預期改變時，先回到診斷或預期確認。
- 為什麼：只傳一句「使用者同意了」不足以判定授權範圍，完整方案則不需要在每層重新詢問。

## good example
- 已確認的具體樣板操作直接執行。
傳入目標步驟、骨架與範例路徑、固定欄位、填位符號、改寫後步驟及該方案的確認；derive-template 核對一致後寫入。

## bad example
- 同一委派只傳籠統授權。
「使用者同意優化，直接抽樣板。」沒有格式或目標步驟，卻要求子 Skill 略過所有確認。

# Rule 5 [must] - 整體清理由 engineering 排入操作順序
- Deriver 的一次局部操作仍遵守其邊界；跨部件刪減、搬移與清理另交對應 Forms，整檔移除由 engineering 依已確認清單執行，無此操作就略過。
- 先讓替代職責就位，再移除舊內容並修復使用端；不刪除與本次因果範圍無關的部件。
- 每次 SOP 改動後，依最新檔案與步驟職責重新定位下一個目標；原 Phase／Step 位址只作對照，不能照舊編號盲改。
- 為什麼：局部工具容易忽略其他使用端；重排步驟後舊位址也可能指到完全不同的工作。

## good example
- 同一份清單隨 SOP 重排重新定位。
原 Phase 2 Step 3「產生報告」變成 Step 2；委派前讀回確認職責與新位址，抽出樣板，再刪掉方案指定的重複 Rule。

## bad example
- 同一份清單沿用舊位址。
SOP 重排後仍叫 Deriver 改 Step 3，實際改到「等待確認」，並要求它順手清理所有 Rule File。
