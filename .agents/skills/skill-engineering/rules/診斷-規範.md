# Rule 1 [must] - 診斷以可觀察的預期與落差開始
- 寫出使用者在什麼情境下預期得到什麼、實際得到什麼，以及可觀察的差異；從已有對話擷取，只詢問影響判斷的缺口。
- 為什麼：沒有成功的樣子，後續只能依個人偏好調整文件，無法判定是否解決問題。

## good example
- 同一份回饋被轉成可以驗收的差異。
使用者說「需求都給了還一直問」。預期：資料齊全時直接提出方案；實際：入口確認後，下游又問相同需求。驗收：完整資料不重問，缺少影響決策的資料仍會詢問。

## bad example
- 同一份回饋只被換成抽象目標。
使用者說「需求都給了還一直問」。診斷寫「需要更智慧、更精簡」，沒有指出哪個提問重複，也沒有成功條件。

# Rule 2 [must] - 根因沿實際相關路徑追溯
- 從造成不滿意結果的入口追蹤相關 Skills 的呼叫與交接，定位到 SOP 步驟、Rule 名稱、樣板內容、腳本行為或缺失的交接資料。
- 逐個關鍵位置重演「收到的輸入 → 適用的指令 → 決定或處理 → 輸出」，找出偏差如何產生與傳遞；追到足以解釋落差即可。
- 為什麼：最後產出錯誤的 Skill 可能只是接到錯誤輸入，改它會掩蓋上游原因。

## good example
- 同一次重複提問沿交接追到原因。
入口已取得欄位與格式，但只把「抽樣板」交給 derive-template；下游收不到格式，所以詢問。診斷指向入口的委派步驟遺漏資料，並列出上下游輸入差異。

## bad example
- 同一次重複提問直接歸咎最後詢問的 Skill。
看到 derive-template 提問，就判定它的提問規則多餘；沒有讀入口如何委派。

# Rule 3 [must] - 根因結論區分證據與假說
- 對每個原因標示實際紀錄、文字推演或待驗證假說，附具體位置與因果解釋；缺少紀錄時不可聲稱重現過。
- 說明有哪些證據支持或反駁原因，以及改變該因素後預期哪個偏差會消失；不強求唯一根因，也不把「缺規則」當預設答案。
- 為什麼：推演可能忽略執行時未載入、未遵循指令或工具失敗，直接加規則不一定有效。

## good example
- 邊界：只有檔案時保留證據限制。
「文字推演：Phase 1 Step 4 無條件 Ask，可能造成已確認後仍重問。沒有該次執行紀錄，尚不能排除入口漏傳資訊；需以完整交接案例確認。」

## bad example
- 邊界：同樣只有檔案，卻宣稱知道當時行為。
「已重現：Phase 1 Step 4 就是唯一根因。」實際沒有執行或紀錄佐證。

# Rule 4 [must] - 診斷確認先於解法編排
- 提出預期、現況、落差、原因位置、因果解釋、證據限制與驗收案例後，等待使用者確認；有關鍵未知就先取得資料並修訂診斷。
- 使用者可明確接受帶有證據限制的假說作為下一步依據；沿用已確認診斷時指出對應內容，不把籠統的修改授權視為診斷確認。
- 診斷確認與改寫方案確認是兩個獨立閘門；診斷未確認，不提出編排方案、不改目標檔案。使用者沉默不算確認。
- 此時不混入具體部件操作或寫檔提案，讓使用者能獨立判斷問題是否理解正確。
- 為什麼：把原因與解法綁成一次同意，容易在尚未理解預期時就開始堆疊機制。

## good example
- 診斷提出後確實停在閘門。
「預期是完整需求不重問；紀錄顯示確認資訊在入口委派時遺失。你是否同意這個診斷？」等待回答後才設計交接方式。

## bad example
- 同一個診斷未確認就接著設計。
「根因是入口漏傳確認資訊，所以我已決定新增兩條規則並刪掉下游 Ask。」使用者還沒有同意原因。
