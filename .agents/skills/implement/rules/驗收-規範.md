# Rule 1 [must] - ⚙ 的每個錨點都指出程式碼的位置
- 驗收一個任務時,⚙ 列的每一個錨點都要對照規格檔裡那一段,寫出程式碼裡做出它的位置(檔名與函式、行號或選擇器)
- 少一個錨點找不到位置,這個任務就不過
- 為什麼:⚙ 是這個任務的完成範圍;只說「照合約做了」,沒有人知道 `Player` 的四個欄位是不是都在,少了一個要到前端畫面空白才發現

## good example
- T040 的 ⚙ 有 `Room`、`Player` 兩個錨點;**兩個都對照合約,寫出程式碼裡的位置**
```
T040 ⚙ 對照
  components.schemas.Room → backend/src/views/room-view.ts toRoomView():status、hostSeat、players(依座位號排序)
  components.schemas.Player → backend/src/views/room-view.ts toPlayerView():seat、nickname、isHost、connection,不含 token
```

## bad example
- 同一個任務,**只寫一句總結**;`Player` 有沒有漏欄位、有沒有多帶 token,看不出來
```
T040 ⚙ 對照:Room、Player 都照合約做了
```

## good example
- 邊界:T041 的 ⚙ 是原型的 6 個選擇器與狀態;**原型的錨點對照的是 DOM 與狀態切換,一樣逐一寫出位置**
```
T041 ⚙ 對照
  #match-form → frontend/src/pages/nickname.js render() 的 <form id="match-form">
  [data-state="nickname-long"] → nickname.js onSubmit():超過 12 個字時 setState("nickname-long")
  ……(其餘 4 個狀態各一列)
```

## bad example
- 邊界:同一個任務,覺得畫面「看起來跟原型一樣」就**只附一張截圖**;截圖只拍到 `normal` 狀態,`loading` 與 `error` 兩個狀態有沒有做,看不出來
```
T041 ⚙ 對照:畫面與原型一致(附截圖 nickname.png)
```

# Rule 2 [must] - 測試由主 agent 自己重跑
- 驗收時,和這個任務有關的測試由主 agent 自己執行,看到綠燈才算數;subagent 回報的「測試通過」只當線索
- 寫出執行的指令與結果(通過幾個、失敗幾個)
- 為什麼:subagent 可能只跑了自己那一支測試,也可能跑在還沒存檔的版本上;主 agent 勾的 `[X]` 要對得起自己看到的結果

## good example
- E2 subagent 回報 T029–T040 全部通過;**主 agent 自己跑一次 `npm test`**
```
$ npm test -- backend/test/
  tests 48 / pass 48 / fail 0
```

## bad example
- 同一份回報,**直接照抄 subagent 的結果**;subagent 只跑了 `backend/test/domain/`,`rooms/` 底下有 2 個測試其實是紅的
```
T029–T040 測試:subagent 回報全部通過
```

## good example
- 邊界:T009 是複製部署檔,沒有測試;**改成執行能證明它做完的指令**
```
$ docker compose -f deploy/compose.yaml config --quiet
  exit 0
$ diff -r specs/001-bulls-cows-online/deploy deploy
  (無差異)
```

## bad example
- 邊界:同一個任務,因為「沒有測試可以跑」就**直接算過**;複製時漏了 `.env.example`,要到部署時才發現
```
T009:沒有測試,直接勾選
```

# Rule 3 [must] - 測試任務附紅燈的證據
- 測試任務驗收時,要看到它在實作之前跑出的紅燈,而且是實作規範〈測試的紅燈要是斷言失敗〉要的斷言失敗
- 拿不出紅燈的訊息,或訊息是載入錯誤、例外,這個測試任務不過
- 為什麼:只看到最後的綠燈,分不出這個測試是真的在檢查,還是不管實作寫什麼都會綠

## good example
- T010 附上**實作前的斷言失敗訊息**與實作後的綠燈
```
T010 紅燈(T013 之前):AssertionError: validateDigits("1234") 預期 null,實際 "DIGITS_FORMAT_INVALID"
T010 綠燈(T013 之後):7 / 7 pass
```

## bad example
- 同一個測試,**只有最後的綠燈**;沒有人知道它在 T013 之前是不是紅的
```
T010:7 / 7 pass
```

## good example
- 邊界:subagent 回報的紅燈訊息是 `AssertionError`;**主 agent 看過訊息的內容確實是那個斷言,才採用**
```
T029 紅燈(subagent 回報):AssertionError: normalizeNickname("   ") 預期 "NICKNAME_EMPTY",實際 undefined
判定:斷言失敗,採用
```

## bad example
- 邊界:subagent 回報「先跑過,是紅的」,**沒有附訊息就採用**;那次其實是 `Cannot find module`
```
T029 紅燈:subagent 回報已確認失敗
判定:採用
```

# Rule 4 [must] - 驗不了的項目標未驗證
- 手動才能確認的行為、這台機器缺環境跑不了的指令、量不到數字的 SC,一律標「未驗證」並寫明原因與要怎麼驗
- 標了未驗證的項目不算通過;它所在的任務可以勾選,但要在 Checkpoint 報告與完成報告裡列出來
- 為什麼:驗不了卻寫成通過,使用者會以為它驗過了;到上線時才發現的落差,就是這個 skill 要擋的 bug

## good example
- T089 要重測 R5「手機切飛航模式後 30 秒內被判斷線」;**agent 沒有實機可以切飛航模式,標未驗證並寫出步驟**
```
未驗證:T089 R5 手機飛航模式斷線偵測
  原因:要用實體手機切換飛航模式
  怎麼驗:手機連上部署環境進房,切飛航模式,另一個分頁在 30 秒內看到「斷線中」
```

## bad example
- 同一個項目,因為 T021 的心跳測試是綠的,就**寫成已驗證**;單元測試是在本機直接關掉連線,行動網路斷線時 TCP 不會送出 close,這正是 R5 要驗的情況
```
已驗證:T089 R5(T021 心跳測試全綠)
```

## good example
- 邊界:SC-003 要 100 間房、400 位玩家時 SC-002 仍成立,`scripts/load-test.ts` 量得到;**量到了就寫數字,不標未驗證**
```
SC-003:100 間房、400 位玩家,推送延遲 p95 120 毫秒,最大房間 4 人(scripts/load-test.ts)
```

## bad example
- 邊界:同一條 SC 量得到,卻因為「效能數字跟機器有關」就**標未驗證**;使用者拿不到任何數字,也不知道它其實量得到
```
SC-003:未驗證(效能與機器有關)
```
