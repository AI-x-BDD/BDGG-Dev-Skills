# Rule 1 [must] - 只問會改變結果的缺口
- 一個缺口的答案會讓呼叫者接下來的產出(規格、設計、程式)寫得不一樣,才列成要問的題目
- 答案不會改變任何產出,或業界有通行的合理預設的,不問,把採用的預設寫進澄清結果的「假設」
- 為什麼:題目一多,使用者會隨便選來打發,真正決定結果的那幾題反而沒有被好好想過;該問的沒問,AI 就自己替使用者補完了需求,交出去的東西看起來完整,卻不是他要的

## good example
- 「誰看得到同一份清單」的答案**決定了有沒有帳號與共享的需求**,所以問;品項欄位有通行的預設,寫進假設
```
需求:幫我做一個家人共用的購物清單 App

要問:誰看得到同一份清單?(決定要不要帳號、要不要邀請家人加入)
假設:品項只有名稱與數量兩個欄位,不含圖片與價格。
```

## bad example
- 同一份需求,但**把有通行預設的品項欄位也列成題目**;使用者得多回答一題,答案也不會讓規格寫得不一樣
```
需求:幫我做一個家人共用的購物清單 App

要問:誰看得到同一份清單?(決定要不要帳號、要不要邀請家人加入)
要問:品項要有哪些欄位?
```

## good example
- 邊界:「勾掉的品項要不要留著」聽起來是小細節,但**答案會多出一個「買過的紀錄」功能**,所以要問
```
需求:幫我做一個家人共用的購物清單 App

要問:勾掉的品項是直接消失,還是留著當作買過的紀錄?
```

## bad example
- 邊界:同一個缺口,覺得是小細節就**自己決定、也沒寫進假設**;交出去的規格沒有買過的紀錄,使用者要到實際用了才發現勾掉的東西找不回來
```
需求:幫我做一個家人共用的購物清單 App

(沒有列成題目,也沒有寫進假設)
```

# Rule 2 [must] - 呼叫者指定的面向先問
- 呼叫者指定了提問面向時,那些面向的缺口排在最前面;一輪排不下的其餘缺口留到下一輪
- 為什麼:呼叫者指定的面向就是它轉交過來的原因,排在後面,整場 5 題用完了它還沒拿到答案,只能自己補完

## good example
- specify 轉交時指定「先問資料同步與權限」;**本輪前兩題就是這兩個面向**
```
呼叫者:specify,指定先問資料同步與權限

本輪
  Q1 家人同時改同一份清單時,要即時同步嗎?
  Q2 誰看得到同一份清單?
  Q3 勾掉的品項是直接消失,還是留著當作買過的紀錄?
下一輪
  Q4 清單可以自訂名稱嗎?
```

## bad example
- 同樣四題,只是**照自己想到的順序排**;指定的同步擠到下一輪,呼叫者這一輪拿不到它最需要的答案
```
呼叫者:specify,指定先問資料同步與權限

本輪
  Q1 勾掉的品項是直接消失,還是留著當作買過的紀錄?
  Q2 清單可以自訂名稱嗎?
  Q3 誰看得到同一份清單?
下一輪
  Q4 家人同時改同一份清單時,要即時同步嗎?
```

# Rule 3 [must] - 其餘的缺口依影響範圍排序
- 呼叫者沒有指定的缺口,依答案會改變多少產出排序,改變越多的越前面
- 為什麼:影響小的排在前面,題數上限會先花在不重要的地方,真正決定結果的缺口留到最後被砍掉,或使用者只回了前幾題就沒有答案

## good example
- 「誰看得到同一份清單」決定帳號、邀請與權限,**改變的產出最多,排在最前面**;介面配色只改一個設定
```
呼叫者:沒有

本輪
  Q1 誰看得到同一份清單?
  Q2 勾掉的品項是直接消失,還是留著當作買過的紀錄?
  Q3 介面要不要支援深色模式?
```

## bad example
- 同樣三題,但**配色排在最前面**;使用者只回了第一題,決定帳號與權限的那一題還沒有答案
```
呼叫者:沒有

本輪
  Q1 介面要不要支援深色模式?
  Q2 勾掉的品項是直接消失,還是留著當作買過的紀錄?
  Q3 誰看得到同一份清單?
```

## good example
- 邊界:「離線能不能用」和「清單能不能自訂名稱」都只是一句話,但**離線決定了資料存在哪裡與同步方式**,改變的產出比多一個名稱欄位多,所以排在前面
```
呼叫者:沒有

本輪
  Q1 誰看得到同一份清單?
  Q2 沒有網路時還要能新增與勾選嗎?
  Q3 清單可以自訂名稱嗎?
```

## bad example
- 邊界:同樣三題,只是**把只影響一個欄位的題目排到前面**;兩題看起來一樣小,實際上離線那一題會改掉架構
```
呼叫者:沒有

本輪
  Q1 誰看得到同一份清單?
  Q2 清單可以自訂名稱嗎?
  Q3 沒有網路時還要能新增與勾選嗎?
```
