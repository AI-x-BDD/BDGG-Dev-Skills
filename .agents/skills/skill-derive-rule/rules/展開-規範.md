# Rule 1 [must] - 一次展開只動一步與一個 Rule File
- 展開前後的差異只有兩處:指定那一步的那一行,以及那一步的 Rule File,樣子如下

```
首次展開(那一步還沒有點名 Rule File)
  before  <M>. <動詞> <動作描述>
          rules/ 底下沒有這一步的 Rule File
  after   <M>. <動詞> 依 `rules/<檔名>` <動作描述>
          rules/<檔名>   ← 新開

再次展開(那一步已經點名 Rule File)
  before  <M>. <動詞> 依 `rules/<檔名>` <動作描述>
          rules/<檔名>   ← 已有的 Rule
  after   <M>. <動詞> 依 `rules/<檔名>` <動作描述>   ← 這一行不變
          rules/<檔名>   ← 多了這次的 Rule
```

- 目標 skill 的其他步驟、其他 Rule File 都不動;要展開另一步,就再跑一次
- 為什麼:規則是流程跑過之後才一步一步補上的,一次只動一步,補上之後流程哪裡變了,才對得回是哪一步的 Rule 造成的

## good example
- 使用者指定 Phase 1 Step 2;**前後只差那一行與一個新檔**,Step 1、Step 3 一字未動
```
before
  ## Phase 1: 提出類別圖
  1. Read 這次開發會動到的現有程式碼。
  2. Think 設計這次開發的類別組織。
  3. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發。

after
  ## Phase 1: 提出類別圖
  1. Read 這次開發會動到的現有程式碼。
  2. Think 依 `rules/類別圖-規範.md` 設計這次開發的類別組織。
  3. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發。

  rules/
  └── 類別圖-規範.md   ← 新開
```

## bad example
- 同一次展開,但**順手把 Step 3 也展開了**;使用者只指定了 Step 2,這一次就動了兩步與兩個檔
```
before
  ## Phase 1: 提出類別圖
  1. Read 這次開發會動到的現有程式碼。
  2. Think 設計這次開發的類別組織。
  3. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發。

after
  ## Phase 1: 提出類別圖
  1. Read 這次開發會動到的現有程式碼。
  2. Think 依 `rules/類別圖-規範.md` 設計這次開發的類別組織。
  3. Ask 依 `rules/確認-規範.md` 用 Mermaid 提出設計,問使用者是否可以進入開發。

  rules/
  ├── 類別圖-規範.md   ← 新開
  └── 確認-規範.md     ← 也新開
```

# Rule 2 [must] - Rule 只來自使用者說要把關的事
- 使用者說要把關的每一件事各寫成 Rule,使用者沒提的要求不寫進 Rule File
- 每條 Rule 的名稱、強度、為什麼與 example 由 agent 補上
- 展開時想到其他值得把關的事,只在回覆裡提,由使用者決定要不要再展開一次
- 為什麼:agent 推測出來的規則沒有人實際遇過,寫進去之後,那一步每次執行卻都要載入並對照它

## good example
- 使用者講了一件事,**Rule File 就只多一條**;想到的另一件事留在回覆裡
```
使用者:Phase 1 Step 2 要把關:類別圖不超過七個類別。

rules/類別圖-規範.md
  # Rule 1 [must] - 類別圖不超過七個類別

回覆:另外想到「相依方向」也可以把關,這次沒有寫進去,需要的話再展開一次。
```

## bad example
- 同一句話,但 **Rule File 多了兩條使用者沒提過的 Rule**,之後每次設計類別組織都要對照它們
```
使用者:Phase 1 Step 2 要把關:類別圖不超過七個類別。

rules/類別圖-規範.md
  # Rule 1 [must] - 類別圖不超過七個類別
  # Rule 2 [must] - 每個類別只有一個職責
  # Rule 3 [must] - 相依方向由外層指向內層
```

## good example
- 邊界:名稱、強度、為什麼都是 agent 補的,但**要求本身還是使用者那一句**
```
# Rule 1 [must] - 類別圖不超過七個類別
- 一張類別圖最多七個類別
- 為什麼:超過七個,看圖的人就看不懂類別之間的關係
```

## bad example
- 邊界:同樣只有一條 Rule,看起來沒有多加,但 **desc 多了一個使用者沒提過的要求**
```
# Rule 1 [must] - 類別圖不超過七個類別
- 一張類別圖最多七個類別
- 每個類別最多五個方法
- 為什麼:超過七個,看圖的人就看不懂類別之間的關係
```

# Rule 3 [should] - 新開或疊加看那一步有沒有點名 Rule File
- 指定那一步的行內已經有「依 `rules/<檔名>`」,這次的 Rule 就接在那個檔的最後;沒有,才新開一個 Rule File
- 為什麼:同一步要讀的 Rule 拆成兩個檔,沒有任何一次執行能少讀,只是多一個檔要點名、要維護

## good example
- 那一步已經點名 `類別圖-規範.md`,**這次的 Rule 接在同一個檔的最後**,SOP 那一行不變
```
使用者:Phase 1 Step 2 還要把關「每條關係都標出方向」。

before
  2. Think 依 `rules/類別圖-規範.md` 設計這次開發的類別組織。

  rules/類別圖-規範.md
    # Rule 1 [must] - 類別圖不超過七個類別

after
  2. Think 依 `rules/類別圖-規範.md` 設計這次開發的類別組織。

  rules/類別圖-規範.md
    # Rule 1 [must] - 類別圖不超過七個類別
    # Rule 2 [must] - 每條關係都標出方向   ← 這次疊加
```

## bad example
- 同一次展開,但**替這條 Rule 另開一個檔**;同一步現在要點名、要讀兩個檔
```
使用者:Phase 1 Step 2 還要把關「每條關係都標出方向」。

before
  2. Think 依 `rules/類別圖-規範.md` 設計這次開發的類別組織。

  rules/類別圖-規範.md
    # Rule 1 [must] - 類別圖不超過七個類別

after
  2. Think 依 `rules/類別圖-規範.md` 與 `rules/類別圖-關係-規範.md` 設計這次開發的類別組織。

  rules/類別圖-規範.md
    # Rule 1 [must] - 類別圖不超過七個類別

  rules/類別圖-關係-規範.md   ← 新開
    # Rule 1 [must] - 每條關係都標出方向
```

# Rule 4 [must] - 新開的 Rule File 以那一步的產出物命名
- 檔名以那一步做完留下的產出物開頭,不是以這次寫進去的 Rule 的主題開頭
- 為什麼:之後疊加進同一個檔的,會是那一步的其他把關;檔名綁在第一條 Rule 的主題上,第二條就放不進去

## good example
- 邊界:這次只有「不超過七個類別」一條 Rule,但**檔名取的是那一步的產出物「類別圖」**,之後關係、命名的 Rule 都放得進來
```
2. Think 依 `rules/類別圖-規範.md` 設計這次開發的類別組織。

rules/
└── 類別圖-規範.md
    # Rule 1 [must] - 類別圖不超過七個類別
```

## bad example
- 邊界:同一次展開,檔名取自這次那一條 Rule,看起來更精確,但**下一條「每條關係都標出方向」就放不進這個檔**
```
2. Think 依 `rules/類別數量-規範.md` 設計這次開發的類別組織。

rules/
└── 類別數量-規範.md
    # Rule 1 [must] - 類別圖不超過七個類別
```

# Rule 5 [must] - 指定那一步只多出 Rule File 的指標
- 〈一次展開只動一步與一個 Rule File〉的首次展開,只在那一步的動詞後面接上「依 `rules/<檔名>`」;編號、動詞與原本的動作描述照原樣
- Rule 的內容留在 Rule File,不寫進步驟
- 為什麼:使用者同意的是替這一步加把關,不是改這一步做的事;編號或動詞一變,別處的「跳至 Phase N Step M」也會跟著指錯

## good example
- 前後**只差「依 `rules/類別圖-規範.md`」這一段**,原本那一句一字未動
```
before  2. Think 設計這次開發的類別組織。
after   2. Think 依 `rules/類別圖-規範.md` 設計這次開發的類別組織。
```

## bad example
- 同一次展開,但**把 Rule 的內容也寫進了步驟**,動作描述不再是原本那一句
```
before  2. Think 設計這次開發的類別組織。
after   2. Think 依 `rules/類別圖-規範.md` 設計不超過七個類別的類別組織。
```

# Rule 6 [must] - 沿用已確認的具體轉換
- 使用者先前直接確認，或上游傳入可追溯的已確認方案，且內容涵蓋目標步驟、要把關的要求、Rule File、規則內容與改寫後的步驟時，核對本次轉換一致後跳過重複確認。
- 確認只涵蓋原有的局部操作範圍；缺少資訊、新增要求或轉換結果超出方案時，提出該差異並等待確認。「同意優化」不等於已確認具體轉換。
- 上游需刪減其他部件時，由上游另外編排；沿用確認不擴大本 Deriver 的修改邊界。
- 為什麼:完整方案已經讓使用者做過相同決定，重問只增加往返；缺少具體內容則無法判定是否仍在已確認範圍內。

## good example
- 同一項具體轉換已有確認，核對後直接執行。
使用者已確認「新增一條「圖中最多七個類別」到指定 Rule File」，上游附上完整操作資料與確認紀錄；本次產出符合該方案，進入 Phase 2，不再詢問同一件事。

## bad example
- 同一項具體轉換已有確認，卻再次要求相同決定。
使用者已確認「新增一條「圖中最多七個類別」到指定 Rule File」，上游也附上完整操作資料與確認紀錄；本次產出沒有差異，仍停在 Phase 1 Step 4 問一次是否可以寫入。

## good example
- 邊界：確認內容不足時只詢問缺口。
使用者只說「同意優化」，沒有目標步驟、要把關的要求、Rule File、規則內容與改寫後的步驟；先補齊資訊、提出具體轉換並等待確認。

## bad example
- 邊界：同樣只有籠統同意，卻跳過確認。
使用者只說「同意優化」，agent 自己決定目標步驟、要把關的要求、Rule File、規則內容與改寫後的步驟，直接進入 Phase 2。

# Rule 7 [must] - 產出不符預期的直接請求不展開
- 使用者是因為目標 skill 跑出來的產出不符預期而直接要求加規則,又沒有上游傳入的已確認方案時,不展開:不動任何檔,在回覆裡說明要先用 skill-engineering 找出根因
- 上游傳入已確認的方案時,照〈沿用已確認的具體轉換〉承接
- 為什麼:使用者指出的那一步是他看到問題的地方,不一定是問題的來源;直接在那裡加規則,真正寫錯、多出來或放錯位置的文字會原封不動留著

## good example
- 使用者講的是**哪裡的產出不對**,不是要加什麼把關;不動任何檔,只在回覆裡指出該走哪一條路
```
使用者:Phase 1 Step 2 畫出來的類別圖常常太大,超過七個類別就看不懂,加一條規則。

rules/ 不新增也不修改任何檔

回覆:這是因為產出不符預期而要求的修改,請先用 skill-engineering 找出根因;加規則是不是對的修法,要看根因落在哪一步。
```

## bad example
- 同一句話,但**直接展開成一條 Rule**;若類別圖太大是因為另一條 Rule 要求畫出完整的相依鏈,那一條還在,只是多了一條擋不住它的規則
```
使用者:Phase 1 Step 2 畫出來的類別圖常常太大,超過七個類別就看不懂,加一條規則。

rules/類別圖-規範.md
  # Rule 1 [must] - 類別圖不超過七個類別
```

## good example
- 邊界:使用者講的是**要加的把關**,沒有說哪一次的產出不對;不是因為產出不符預期而來的修改,照常展開
```
使用者:Phase 1 Step 2 要把關:類別圖不超過七個類別。

rules/類別圖-規範.md
  # Rule 1 [must] - 類別圖不超過七個類別
```

## bad example
- 邊界:同一句話,因為「七個類別」聽起來像是嫌圖太大就拒絕;**使用者沒有說任何一次的產出不對**,沒有根因可以找
```
使用者:Phase 1 Step 2 要把關:類別圖不超過七個類別。

rules/ 不新增也不修改任何檔

回覆:這是因為產出不符預期而要求的修改,請先用 skill-engineering 找出根因。
```

## good example
- 邊界:起因一樣是類別圖太大,但這次是**上游帶著使用者確認過的方案轉交來的**,根因已經找過了,照方案承接
```
上游:skill-engineering 轉交,使用者已確認的方案是「在 rules/類別圖-規範.md 加〈類別圖不超過七個類別〉」。

rules/類別圖-規範.md
  # Rule 1 [must] - 類別圖不超過七個類別
```

## bad example
- 邊界:同一次轉交,因為起因是產出不符預期就拒絕;**已經確認過的方案被擋回去**,上游只能再轉交一次
```
上游:skill-engineering 轉交,使用者已確認的方案是「在 rules/類別圖-規範.md 加〈類別圖不超過七個類別〉」。

rules/ 不新增也不修改任何檔

回覆:這是因為產出不符預期而要求的修改,請先用 skill-engineering 找出根因。
```
