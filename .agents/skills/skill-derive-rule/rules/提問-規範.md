# Rule 1 [must] - 提問時列出每一步與它已有的 Rule File
- 問之前先用一張表列出目標 skill 的每一步:步驟位址、那一行的原文、那一行點名的 Rule File(沒有就寫「沒有」)
- 為什麼:只問「要展開哪一步」,使用者答不出來;看到每一步的原文與現有的把關,才指得出要哪一步、缺什麼

## good example
- **先列出五步的原文與各自的 Rule File,再問**;使用者一眼看得出 Phase 2 Step 2 是唯一會改檔卻沒有把關的步驟
```
| 步驟 | 原文 | 點名的 Rule File |
|---|---|---|
| Phase 1 Step 1 | Read 這次開發會動到的現有程式碼。 | 沒有 |
| Phase 1 Step 2 | Think 依 `rules/類別圖-規範.md` 設計這次開發的類別組織。 | 類別圖-規範.md |
| Phase 1 Step 3 | Ask 依 `rules/確認-規範.md` 用 Mermaid `classDiagram` 提出這份設計,問使用者是否可以進入開發;若使用者要修改 → 跳至 Phase 1 Step 2。 | 確認-規範.md |
| Phase 2 Step 1 | Think 依 `rules/實作-規範.md` 排出類別的開發順序。 | 實作-規範.md |
| Phase 2 Step 2 | Write 照這個順序逐一實作類別圖裡的類別;若必須偏離類別圖 → 跳至 Phase 1 Step 2。 | 沒有 |

要展開哪一步?這一步要把關什麼?
```

## bad example
- 同一次提問,但**只丟出問題**;使用者得自己去翻 SKILL.md 和 `rules/`,才知道有哪幾步、哪幾步已經有把關
```
要展開哪一步(Phase N Step M)?這一步要把關什麼?
```

# Rule 2 [must] - 提到的候選標明依據
- 提問時若提到可以把關的候選,每一個都標明依據是下表哪一種

| 依據 | 意思 |
|---|---|
| 實際遇到 | 跑流程時發生過 |
| 文字上看得到 | 讀 SOP 或 Rule File 就看得出的缺口 |
| 推測 | 還沒發生,文字上也看不出,只是想到 |

- 為什麼:三種混在一起,使用者會把推測當成已經發生的問題來加規則

## good example
- 兩個候選**各自標了依據**;使用者看得出第一個有憑據、第二個只是想到
```
- Phase 2 Step 2「什麼算偏離類別圖」——文字上看得到:行尾寫「若必須偏離類別圖」,但沒有任何 Rule 定義什麼算偏離。
- Phase 1 Step 1「現有程式碼要讀到多廣」——推測:這支 skill 還沒跑過,只是想到。
```

## bad example
- 同樣兩個候選,但**沒有標依據**;兩個看起來一樣值得加
```
- Phase 2 Step 2 可以加「什麼算偏離類別圖」。
- Phase 1 Step 1 可以加「現有程式碼要讀到多廣」。
```

## good example
- 邊界:這個缺口還沒有實際發生過,但**讀 SOP 就指得出是哪一行**,所以標「文字上看得到」
```
- Phase 2 Step 2「什麼算偏離類別圖」——文字上看得到:行尾寫「若必須偏離類別圖」,但沒有任何 Rule 定義什麼算偏離。
```

## bad example
- 邊界:同一個候選,因為覺得「實作時一定會分不清」就**標成實際遇到**;這支 skill 還沒有人跑過
```
- Phase 2 Step 2「什麼算偏離類別圖」——實際遇到:實作時分不清什麼算偏離。
```
