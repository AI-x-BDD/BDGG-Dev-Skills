# Rule 1 [must] - 做到一半無法上線的內容不合進 trunk
- 嚴禁把做到一半無法上線的內容中途合進 trunk
- 為什麼:trunk 要隨時可以發布;合進一段還不能上線的內容,下一次發布就會把它帶出去

## good example
- `todo count` 的 handler 與測試**都完成了才進 trunk**
```python
def count(args):
    print(store.count_total(args.file))
```

## bad example
- 同一個指令,但 **handler 還沒寫完就進了 trunk**;使用者執行 `todo count` 會直接看到例外
```python
def count(args):
    raise NotImplementedError("count 還沒做完")
```

## good example
- 邊界:功能同樣還沒做完,但**指令包在預設關閉的 flag 後面**;使用者碰不到它,trunk 仍然可以發布
```python
if feature_flags.is_enabled("todo_count"):   # 預設關
    subparsers.add_parser("count")
```

## bad example
- 邊界:同一個沒做完的指令,沒有包 flag,只在說明文字裡**寫了「尚未完成」**;看起來有交代,但使用者照樣執行得到
```python
subparsers.add_parser("count", help="(尚未完成,請勿使用)")
```

# Rule 2 [must] - 兩天內做不完的變更包在 feature flag 後面
- 無法在兩天內全部完成的長變更,必須包在 feature flag 開關後面,使程式碼仍可持續整合進 trunk
- 為什麼:沒有 flag,做到一半的程式碼進不了 trunk,只能留在分支上;留得越久離 trunk 越遠,合回時的衝突越大,和別人的變更不相容也要到做完才會發現

## good example
- 把儲存換成 SQLite 估五天;**包在 `use_sqlite` 後面**,每天把做完的部分整合進 trunk
```
變更:把儲存從 JSON 換成 SQLite,估 5 天
做法:新實作包在 flag use_sqlite 後面,每天把當天完成的部分整合進 trunk
```

## bad example
- 同一個變更,但**開一條 branch 做五天**,做完才合回 trunk
```
變更:把儲存從 JSON 換成 SQLite,估 5 天
做法:開 feature/sqlite,五天後全部做完再合回 trunk
```

## good example
- 邊界:估一天半,兩天內做得完;**不需要 flag**,切成兩次整合就進得了 trunk
```
變更:替 todo 加上到期提醒,估 1.5 天
做法:不包 flag,切成兩次整合,兩天內全部進 trunk
```

## bad example
- 邊界:同一個變更估成兩天半,而且切不成可以單獨上線的小片;只比界線多半天,覺得趕一下就好而**沒有包 flag**,做完之前沒有東西進得了 trunk
```
變更:替 todo 加上到期提醒,估 2.5 天,切不成可以單獨上線的小片
做法:不包 flag,做到第三天才第一次整合
```

# Rule 3 [must] - 未完成功能的 flag 在 production 保持關閉
- 包住未完成功能的 flag 在 production 保持關閉
- 為什麼:flag 一開,做到一半的功能就在 production 生效,使用者會直接用到還沒完成的東西

## good example
- `SqliteStore` 還沒做完;**production 的設定是關**
```
config/production.toml   use_sqlite = false   # SqliteStore 還沒做完
```

## bad example
- 同一個 flag,但 **production 的設定是開**
```
config/production.toml   use_sqlite = true    # SqliteStore 還沒做完
```

## good example
- 邊界:flag 在開發環境是開的,看起來沒有關;但**只有開發環境的設定打開它**,production 用的預設值仍然是關
```
config/default.toml      use_sqlite = false
config/development.toml  use_sqlite = true    # 只有開發環境打開來測
```

## bad example
- 邊界:同一個 flag,為了方便測試**把預設值改成開**;production 沒有另外覆寫,未完成的實作直接生效
```
config/default.toml      use_sqlite = true    # 為了方便測試改成預設開
```

# Rule 4 [should] - flag 在啟動或注入處切換實作
- 盡量透過抽象層在啟動或注入處依 flag 切換實作,避免在商業邏輯各處散落 if/else
- 為什麼:散落的 flag 判斷難以維護;移除 flag 的時候,得把每一處判斷都找出來

## good example
- **啟動時依 flag 選一次實作**,其他地方只認得 `store`
```python
store = SqliteStore() if feature_flags.is_enabled("use_sqlite") else JsonStore()
```

## bad example
- 同一個 flag,但**判斷散在每個指令裡**
```python
def add(args):
    if feature_flags.is_enabled("use_sqlite"):
        sqlite_insert(args)
    else:
        json_append(args)

def list_items(args):
    if feature_flags.is_enabled("use_sqlite"):
        rows = sqlite_select()
    else:
        rows = json_load()
```

## good example
- 邊界:這個 flag 只決定到期日的顯示方式,而且只有一個函式在格式化到期日;**單一判斷寫在那一處,有正當理由不另建抽象層**
```python
def format_due(item):
    if feature_flags.is_enabled("relative_due"):
        return humanize(item.due)
    return item.due.isoformat()
```

## bad example
- 邊界:同一個顯示用的 flag,但 `list`、`show`、`export` 各自格式化到期日;每一處看起來都只是一行,**同一個判斷卻寫了三次**
```python
def list_items(args):
    due = humanize(item.due) if feature_flags.is_enabled("relative_due") else item.due.isoformat()

def show(args):
    due = humanize(item.due) if feature_flags.is_enabled("relative_due") else item.due.isoformat()

def export(args):
    due = humanize(item.due) if feature_flags.is_enabled("relative_due") else item.due.isoformat()
```

# Rule 5 [must] - 被 flag 包住的程式碼在開與關兩種狀態都有測試
- 被 flag 包住的程式碼,測試在 flag 開與關兩種狀態下都要跑
- 為什麼:在 production 關著的程式碼沒有人會執行到;沒有測試守著,它在 trunk 上壞了也不會有人發現,要到打開 flag 的那一天才出事

## good example
- 同一個測試**在開與關兩種狀態各跑一次**,`SqliteStore` 與 `JsonStore` 都被建置守著
```python
@pytest.mark.parametrize("use_sqlite", [True, False])
def test_add_then_list(use_sqlite, tmp_path):
    store = make_store(use_sqlite, tmp_path)
    store.add("買牛奶")
    assert [item.title for item in store.list()] == ["買牛奶"]
```

## bad example
- 同一個測試,但**只在 flag 關的狀態跑**;`SqliteStore` 在 trunk 上沒有任何測試
```python
def test_add_then_list(tmp_path):
    store = make_store(False, tmp_path)
    store.add("買牛奶")
    assert [item.title for item in store.list()] == ["買牛奶"]
```

## good example
- 邊界:`SqliteStore` 另外有直接測它的單元測試;**經過 flag 選實作的那一條路,開與關仍然各跑一次**
```python
def test_sqlite_store_add(tmp_path):
    store = SqliteStore(tmp_path / "todo.db")
    store.add("買牛奶")
    assert [item.title for item in store.list()] == ["買牛奶"]

@pytest.mark.parametrize("use_sqlite", [True, False])
def test_add_then_list(use_sqlite, tmp_path):
    store = make_store(use_sqlite, tmp_path)
    store.add("買牛奶")
    assert [item.title for item in store.list()] == ["買牛奶"]
```

## bad example
- 邊界:同樣有直接測 `SqliteStore` 的單元測試,看起來新實作已經測過;但**經過 flag 的那一條路只在關的狀態跑**,打開 flag 之後接不接得起來沒有測試守著
```python
def test_sqlite_store_add(tmp_path):
    store = SqliteStore(tmp_path / "todo.db")
    store.add("買牛奶")
    assert [item.title for item in store.list()] == ["買牛奶"]

def test_add_then_list(tmp_path):
    store = make_store(False, tmp_path)
    store.add("買牛奶")
    assert [item.title for item in store.list()] == ["買牛奶"]
```

# Rule 6 [must] - 建立 flag 的當下訂出移除日期
- flag 是技術債,建立 flag 的當下必須訂定檢查並移除的具體日期(例如記錄於 README 或設定中)
- 為什麼:若無明確移除計畫,flag 會成為永久技術債

## good example
- 加上 `use_sqlite` 的同一筆 commit 裡,**README 記下哪一天回來檢查並移除**
```markdown
<!-- README.md -->
- Feature flag `use_sqlite`:2026-11-05 檢查,移除 JsonStore 與這個 flag。
```

## bad example
- 同一個 flag,但**沒有任何地方記它何時移除**
```markdown
<!-- README.md -->
- Feature flag `use_sqlite`:切換儲存實作。
```

## good example
- 邊界:沒有寫在 README,而是寫在設定檔的註解裡;**有具體的日期**,記在哪裡不影響
```toml
use_sqlite = false   # 2026-11-05 檢查並移除
```

## bad example
- 邊界:同一行註解,一樣交代了要移除,但**寫的是條件、不是日期**;「穩定」沒有人會去判定,這一行不會有到期的一天
```toml
use_sqlite = false   # 上線穩定後移除
```

# Rule 7 [must] - 多日的底層替換照 Branch by Abstraction 的五個步驟做
- 耗時多日的底層替換必須依五步驟逐步整合:1. 在被取代代碼外建立抽象層並改由使用端依賴,提交;2. 為抽象層寫新實作,提交;3. 切換開關至新實作,提交;4. 移除舊實作;5. 移除過渡抽象層
- 為什麼:大型替換直接在分支上一次重寫容易卡住數週且無法發布;抽象分支法讓遷移過程可隨時暫停且 trunk 不受破壞

## good example
- 把 `JsonStorage` 換成 `SqliteStorage`,**五個步驟各自整合進 trunk**
```
1. 建立 Storage 介面,JsonStorage 實作它,使用端改成依賴 Storage
2. 新增 SqliteStorage 與它的單元測試(預設不啟用)
3. 把預設實作切到 SqliteStorage
4. 移除 JsonStorage
5. 移除 Storage 介面,使用端直接依賴 SqliteStorage
```

## bad example
- 同一個替換,但**一筆 commit 改完**;做到一半時 trunk 沒有任何一個可以發布的狀態
```
1. 刪除 JsonStorage,把所有呼叫處改寫成 SqliteStorage
```

## good example
- 邊界:使用端只有 `add` 與 `list` 兩處,看起來不值得多一層;**仍然先建抽象層**,後面四步才有地方切換
```
1. 建立 Storage 介面,JsonStorage 實作它,add 與 list 改成依賴 Storage
2. 新增 SqliteStorage 與它的單元測試(預設不啟用)
3. 把預設實作切到 SqliteStorage
4. 移除 JsonStorage
5. 移除 Storage 介面,add 與 list 直接依賴 SqliteStorage
```

## bad example
- 邊界:同一個替換,因為只有兩處就**跳過建抽象層**;其餘的步驟都還在、每一筆也都過建置,但新舊實作的選擇散在使用端,沒有一筆 commit 可以一次切換
```
1. 新增 SqliteStorage 與它的單元測試(預設不啟用)
2. add 與 list 各加一個 if use_sqlite 判斷,切到 SqliteStorage
3. 移除 JsonStorage,刪掉兩處的 else 分支
```

# Rule 8 [must] - 替換過程的每一筆 commit 都通過完整建置
- 每一筆 commit 都必須通過本機完整建置,確保 trunk 隨時 release ready
- 每個步驟可以拆成多筆 commit,拆出來的每一筆同樣適用
- 為什麼:推上共用 repo 的任何一筆 commit 都不能危及上線能力;每一筆都過建置,遷移才可以在任何一筆之後暫停

## good example
- 第 2 步分成兩筆,**每一筆都通過完整建置**
```
a1f3c20  新增 SqliteStorage 的 add 與 list,連同單元測試      make test:通過
b27c9e4  新增 SqliteStorage 的 delete,連同單元測試           make test:通過
```

## bad example
- 同樣兩筆,但**第一筆是編不過的半成品**,打算靠下一筆補上
```
a1f3c20  新增 SqliteStorage 的 add 與 list(delete 還沒實作)  make test:失敗
b27c9e4  補上 SqliteStorage 的 delete                         make test:通過
```

## good example
- 邊界:兩筆一起推;**推之前各自取出來跑過建置**
```
a1f3c20  make test:通過(在這一筆上跑)
b27c9e4  make test:通過(在這一筆上跑)
git push origin main        # 兩筆一起推
```

## bad example
- 邊界:同樣兩筆一起推,**只在最後一筆上跑過建置**;最後的狀態是綠的,但 `a1f3c20` 單獨取出來過不過沒有人知道
```
a1f3c20  (沒有跑)
b27c9e4  make test:通過
git push origin main        # 兩筆一起推
```

# Rule 9 [should] - production 的 bug 先在 trunk 修好再 cherry-pick
- production 的 bug 先在 trunk(main)重現並修好(附測試、CI 通過),再 cherry-pick 到對應的 release branch
- 不直接在 release branch 上修復
- 為什麼:方向若反過來,極易漏掉將修正帶回 trunk,導致下一個大版本發生 regression

## good example
- **在 trunk 修好**並通過測試,再把那一筆 cherry-pick 到 `release/1.0`
```bash
git switch main
# 在 trunk 重現並修復 bug,附測試,提交為 abc1234,CI 通過
git push origin main
git switch release/1.0
git cherry-pick abc1234
git push origin release/1.0
```

## bad example
- 同一個 bug,但**直接在 `release/1.0` 上修**;main 沒有這一筆修正
```bash
git switch release/1.0
# 修復 bug,提交為 def5678
git push origin release/1.0
# main 沒有動
```

## good example
- 邊界:這段程式在 trunk 上已經整個改寫,bug **在 trunk 重現不出來**;有正當理由在 release branch 上修,並向使用者說明
```bash
git switch main
# 照同樣的步驟重現:這段在 trunk 上已經改寫,bug 不存在
git switch release/1.0
# 修復 bug,提交為 def5678
git push origin release/1.0
# 向使用者說明:這筆修正只在 release/1.0,因為 trunk 上重現不出來;下一版有 regression 的風險
```

## bad example
- 邊界:同一個 bug,在 trunk 上其實重現得出來,只是**趕著出 hotfix 就先在 release branch 上修**;「晚點再補回 trunk」正是會被忘掉的那一步
```bash
git switch release/1.0
# 趕時間,先在這裡修復並提交為 def5678
git push origin release/1.0
# 打算晚點再把修正補回 main
```

# Rule 10 [must] - release branch 不合回 trunk
- 嚴禁將 release branch 合回 trunk
- 為什麼:release branch 上會有只屬於那個版本的 commit(例如版號);整條合回 trunk,這些變更會跟著進到下一版

## good example
- `release/1.0` 不再使用;**打 tag 之後刪除,不合回 main**
```bash
git tag v1.0.3 release/1.0
git push origin v1.0.3
git push origin --delete release/1.0
```

## bad example
- 同一條 `release/1.0`,同樣打 tag 之後刪除,但**刪除之前先合回了 main**
```bash
git switch main
git merge release/1.0
git push origin main
git tag v1.0.3 release/1.0
git push origin v1.0.3
git push origin --delete release/1.0
```

## good example
- 邊界:`release/1.0` 上有一筆 main 還沒有的修正要帶回來;**只把那一筆 cherry-pick 回 main**
```bash
git switch main
git cherry-pick def5678
```

## bad example
- 邊界:同樣要帶回那一筆,但**合回整條 branch**;只是為了一筆修正,`release/1.0` 上的版號 commit 也一起進了 main
```bash
git switch main
git merge release/1.0
```
