# Rule 1 [must] - 短期分支限制
- 短期分支壽命不得超過一至兩天,且僅供單人(或一組 pair)開發使用
- 合併方向僅允許兩種:將 trunk 合進分支追上 HEAD,以及結束時合回 trunk;合回後必須立刻刪除本機與 remote 分支
- 嚴禁把做到一半無法上線的內容中途合進 trunk、嚴禁合到別人的短期分支或合到 release 分支
- 為什麼:分支會拉開開發者之間的距離;開了分支卻沒有在同一段工作內合回並刪除,變更會離 trunk 越來越遠而造成 merge hell

## good example
- 開出短期分支實作一小步,通過驗證後立刻合回 main 並刪除分支
```bash
git switch -c feat/add-counter
# 實作與本機建置完成
git switch main && git merge --ff-only feat/add-counter && git push origin main
git branch -d feat/add-counter && git push origin --delete feat/add-counter
```

## bad example
- 開出長期分支積累多日,甚至兩人以上共同在該分支開發或合進 release 分支
```bash
git switch -c feature/v2-system
# 在此分支上累積 14 天提交,並讓隊友也 checkout 此分支協作
```

# Rule 2 [must] - Feature Flag 抽象隔絕與設定移除日期
- 無法在兩天內全部完成的長變更,必須包在 feature flag 開關後面,使程式碼仍可持續整合進 trunk 並在 production 保持關閉
- 盡量透過抽象層在啟動或注入處依 flag 切換實作,避免在商業邏輯各處散落 if/else
- flag 是技術債,建立 flag 的當下必須訂定檢查並移除的具體日期(例如記錄於 README 或設定中)
- 為什麼:未完成的功能留在分支上會脫離主幹整合;散落的 flag 判斷難以維護,且若無明確移除計畫會成為永久技術債

## good example
- 用抽象層切換儲存實作,並於 README 標註移除旗標的檢視日期
```python
# 依 flag 注入儲存實作
store = SqliteStore() if feature_flags.is_enabled("use_sqlite") else JsonStore()
```
```markdown
<!-- README.md -->
- Feature flag `use_sqlite`: 預計上線後於 2026-11-05 檢查並移除舊實作與 flag。
```

## bad example
- 在程式碼各處直接穿插 if/else 且未註記移除日期
```python
if os.getenv("ENABLE_SQLITE") == "true":
    ...
# 未設定任何過期或移除計畫,且測試未覆蓋開與關兩種情境
```

# Rule 3 [must] - Branch by Abstraction 逐步替換
- 耗時多日的底層替換必須依五步驟逐步整合:1. 在被取代代碼外建立抽象層並改由使用端依賴,提交;2. 為抽象層寫新實作,提交;3. 切換開關至新實作,提交;4. 移除舊實作;5. 移除過渡抽象層
- 每個步驟拆成多筆獨立 commit,每一筆 commit 都必須通過本機完整建置,確保 trunk 隨時 release ready
- 為什麼:大型替換直接在分支上一次重寫容易卡住數週且無法發布;抽象分支法讓遷移過程可隨時暫停且 trunk 不受破壞

## good example
- 逐步建立抽象層、注入新實作並分批整合進 trunk
```markdown
1. commit 1: 建立 Storage 抽象介面,JsonStorage 實作介面,使用端依賴 Storage
2. commit 2: 新增 SqliteStorage 實作與其單元測試(預設不啟用)
3. commit 3: 切換預設實作為 SqliteStorage
4. commit 4: 移除 JsonStorage
```

## bad example
- 在一次 commit 裡暴力替換所有使用端的實作,造成 trunk 無法中途發布
```markdown
直接刪除 JsonStorage,在同一筆提交中重寫所有調用處為 SqliteStorage,
中途若遇緊急 hotfix 無法隨時發布 trunk。
```

# Rule 4 [must] - Production Bug 先在 Trunk 修復
- production 的 bug 一律先在 trunk(main)重現並修好(附測試、CI 通過),再 cherry-pick 到對應的 release branch
- 嚴禁直接在 release branch 上修復再合回 trunk,嚴禁將 release branch 合回 trunk
- 為什麼:方向若反過來,極易漏掉將修正帶回 trunk,導致下一個大版本發生 regression

## good example
- 在 trunk 修復並通過測試後,cherry-pick 該 commit 至 release/1.0
```bash
git switch main
# 在 trunk 重現並修復 bug,提交為 commit abc1234
git push origin main
git switch release/1.0
git cherry-pick abc1234
git push origin release/1.0
```

## bad example
- 在 release/1.0 上直接修復並執行 `git merge release/1.0` 回 trunk
```bash
git switch release/1.0
# 修復 bug 並 commit
git switch main
git merge release/1.0   # 違反規範: 嚴禁將 release 分支 merge 回 trunk
```
