# Rule 1 [must] - 主幹與完整建置指令判斷
- 使用 `git ls-remote --symref origin HEAD` 詢問 remote 預設 branch 作為 trunk;若 remote 尚無輸出則以目前本機 branch 為 trunk
- 提交前必須跑的完整建置指令(編譯 + 單元測試 + 整合測試)必須對齊 CI 設定檔;若找不到任何自動化測試,必須主動告知使用者此為前提缺失
- 為什麼:本機的 `refs/remotes/origin/HEAD` 只有在 clone 出來的 repo 存在,`git init` 後才 add remote 的 repo 不存在;且本機建置若與 CI 不一致,無法守住「不弄壞建置」的承諾

## good example
- 用 `ls-remote` 查 trunk,並從 CI 設定檔對齊完整測試指令
```bash
git ls-remote --symref origin HEAD
# 輸出: ref: refs/heads/main  HEAD
# 對照 .github/workflows/ci.yml 確認建置指令為 `make test`
```

## bad example
- 依賴本機 `origin/HEAD` 捷徑,並隨意挑選部分測試當作完整建置
```bash
git checkout origin/HEAD
# 報錯: error: pathspec 'origin/HEAD' did not match any file(s) known to git
pytest tests/unit/
# 漏跑整合測試,語意衝突無法提前抓出
```

# Rule 2 [must] - 變更切成薄垂直切片
- 每次變更的大小控制在動手後數小時內(上限一至兩天)即可完成並送出
- 變更切成貫穿各層、可單獨上線的薄垂直切片(thin vertical slice);大規模改名或目錄調整單獨先送鋪路 commit(facilitating commit)
- 一張需求卡不等於一次整合,可拆成多筆 commit 流進 trunk
- 為什麼:變更過大會產生開長期 branch 慢慢做的壓力,累積的變更越多,距離整合越遠,合併風險呈指數增加

## good example
- 將大型功能拆解成鋪路 commit 與垂直切片分別整合進 trunk
```markdown
1. facilitating commit: 先送出 store.load 改名為 load_items 的鋪路重構
2. feature slice 1: 先送出計算 total 與 completed 的 count 邏輯與測試
3. feature slice 2: 補上 pending 統計與 CLI 格式化輸出
```

## bad example
- 將整個需求積累在未提交的工作目錄或本機多日後才一次整合
```markdown
將需求的所有改動、重構、資料庫轉換一次性在一個超大 commit 送出,
中途累積數十個檔案變更且未持續與 trunk 整合。
```

# Rule 3 [must] - 整合風格選擇
- 依團隊規模與 repo 既有慣例選擇直接進 trunk 或走短期 feature branch
- 很小的團隊(含單人)、建置快且無 PR 強制規範時,直接 commit/push 到 trunk
- 需要 code review、有 branch protection 或人數較多時,走壽命不超過兩天的短期 branch
- 為什麼:直接進 trunk 最能維持小 commit 流動,但壞掉會直接影響隊友;短期 branch trunk 最穩,但 review 過慢會拖垮節奏

## good example
- 評估 repo 特性後選擇適合的整合路徑
```markdown
- Repo 規範: main 分支有 branch protection,要求 PR 通過 review
- 決策: 切出短期 branch `feat/todo-count`,實作後開 PR 整合,合回後立刻刪除 branch
```

## bad example
- 在要求 PR 的專案強推 trunk,或在單人快速迭代專案開啟活了一星期的長期分支
```markdown
明明是單人個人工具專案,卻開了 `feature/v2-rewrite` 分支並在上面連續開發兩週未整合回 trunk。
```
