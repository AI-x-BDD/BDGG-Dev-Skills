# Rule 1 [must] - 端點是需求連得到的獨立系統
- 每個端點都要對得到 spec 的需求出處(FR、NFR、SC 或 Assumptions 的編號)
- 同一個行程裡的模組不另列端點,例如後端程式裡的純函式、後端記憶體裡的狀態;它們的介面屬於所在的那個端點
- 只出現在 techstack、沒有需求用到的工具也不列,例如 CI、linter、測試框架
- 為什麼:每個端點之後都要占一個分析步驟;列進沒有需求的端點,會多出一步沒有東西可以分析,把行程裡的模組拆成端點,同一份介面會被分析兩次

## good example
- 照片相簿應用程式;**每一列都對得到需求出處**,`domain/` 的純函式和 GitLab CI 沒有列
```
| E2 | 後端(Fastify) | REST API:資源、操作、錯誤碼、長時間工作的進度與取消 | FR-001–FR-011、FR-013、FR-017 |
| E3 | 資料庫(MySQL) | 資料表、關聯、唯一性與狀態約束 | FR-004、FR-009、FR-010、FR-016、Key Entities |
```

## bad example
- 同一個應用程式,但**把後端行程裡的純函式和 techstack 裡的 CI 也列成端點**;兩列都對不到需求出處
```
| E2 | 後端(Fastify) | REST API:資源、操作、錯誤碼、長時間工作的進度與取消 | FR-001–FR-011、FR-013、FR-017 |
| E3 | 資料庫(MySQL) | 資料表、關聯、唯一性與狀態約束 | FR-004、FR-009、FR-010、FR-016、Key Entities |
| E8 | 領域邏輯(`domain/`) | 純函式:normalizeAlbumName、buildSuggestions | 無 |
| E9 | GitLab CI | pipeline 階段 | 無 |
```

## good example
- 邊界:縮圖寫在 `DATA_DIR`,看起來像後端的內部細節;但**檔案系統是後端行程以外的系統,需求也講明不能動原檔**,所以列成端點
```
| E4 | 檔案系統 | 照片原檔(`PHOTO_ROOT` 唯讀)與縮圖(`DATA_DIR`)的路徑與讀寫規約 | FR-001、FR-005、FR-017、SC-006 |
```

## bad example
- 邊界:同一個情況,因為讀寫檔案的程式寫在後端裡,就**把檔案系統併進後端**;原檔唯讀這條約束沒有一個步驟專門分析
```
| E2 | 後端(Fastify) | REST API 與照片檔案的讀寫 | FR-001–FR-011、FR-013、FR-017、SC-006 |
```

# Rule 2 [must] - 外部系統各自成一個端點
- 需求裡出現的第三方服務、硬體、手機、雲端服務,各列一個端點,不併進後端
- 名稱寫出它是哪一種外部系統,有指名的產品就一起寫,例如「第三方金流(如綠界 ECPay)」
- 為什麼:外部系統的介面是對方定好的,排分析波段時要排在最前面;併進後端,它就和後端排在同一步,依賴它的介面看不出要等它

## good example
- 相簿沖印要用第三方金流付款;**金流商自己列一個端點**,介面寫的是金流商提供的那一套 API
```
| E2 | 後端(Fastify) | REST API:資源、操作、錯誤碼、長時間工作的進度與取消 | FR-001–FR-011、FR-013、FR-017 |
| E7 | 第三方金流(如綠界 ECPay) | 金流商 API:建立交易、付款頁導轉、付款結果通知(webhook)、簽章驗證、查單 | FR-018 |
```

## bad example
- 同一個需求,但**金流被寫進後端的介面裡**;盤點表看不出有一個介面是別人定好、我們只能照著接的
```
| E2 | 後端(Fastify) | REST API:資源、操作、錯誤碼、付款與金流回呼 | FR-001–FR-011、FR-013、FR-017、FR-018 |
```

## good example
- 邊界:影像處理工具是後端用子行程呼叫的命令列程式,不是網路上的服務;但**它是別人寫好、參數與失敗方式都由它決定的外部程式**,所以仍然列一個端點
```
| E5 | 影像處理工具(libheif CLI、sharp) | 外部程序呼叫:輸入格式、參數、輸出、逾時與失敗原因 | FR-011、SC-002、Assumptions(JPEG/PNG/HEIC) |
```

## bad example
- 邊界:同一個工具,因為它跑在同一台機器、由後端呼叫,就**併進後端**;逾時與失敗原因要由誰分析,盤點表上看不出來
```
| E2 | 後端(Fastify) | REST API 與縮圖產生 | FR-001–FR-011、FR-013、FR-017 |
```

# Rule 3 [must] - 介面只寫要分析的項目,不寫分析結果
- 介面欄寫這個介面之後要分析哪些項目,例如「資料表、關聯、唯一性與狀態約束」
- 不寫要分析完才知道的東西:表的數量、操作的數量、欄位名稱、函式名稱、錯誤碼的值
- 為什麼:plan.md 這時還沒有做任何分析;先寫出來的數字與名稱沒有分析過,卻會被之後分析那個介面的步驟當成定案照抄

## good example
- **只列出要分析的項目**,幾張表、叫什麼名字留給分析資料庫的那一步
```
| E3 | 資料庫(MySQL) | 資料表、關聯、唯一性與狀態約束 | FR-004、FR-009、FR-010、FR-016、Key Entities |
```

## bad example
- 同一個端點,但**介面欄先寫了表數與表名**;這些是分析完資料庫才知道的
```
| E3 | 資料庫(MySQL) | 8 張表:photos、albums、album_photos、folders、jobs、suggestions、suggestion_items、print_orders | FR-004、FR-009、FR-010、FR-016、Key Entities |
```

## good example
- 邊界:「付款結果通知(webhook)」看起來很具體,但**它是金流商本來就提供的介面項目,不是我們分析出來的結果**,可以寫
```
| E7 | 第三方金流(如綠界 ECPay) | 金流商 API:建立交易、付款頁導轉、付款結果通知(webhook)、簽章驗證、查單 | FR-018 |
```

## bad example
- 邊界:同一個端點,也只寫了金流商提供的東西,但**連回呼路徑與參數名稱都定了**;那是分析金流介面那一步才要決定的
```
| E7 | 第三方金流(如綠界 ECPay) | 金流商 API:`POST /payment/callback`,參數 `MerchantTradeNo`、`RtnCode`、`CheckMacValue` | FR-018 |
```
