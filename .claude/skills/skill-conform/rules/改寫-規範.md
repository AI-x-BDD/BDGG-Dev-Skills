# Rule 1 [must] - 改寫要讓那條 Rule 管的事成立
- 決定寫法之前,先讀檢查清單那一項指到的那條 Rule 的原文:它在所屬 form skill 的 `rules/` 底下,檔名寫在檢查結果那一項的 `source`
- 要改成的寫法符合那條 Rule 的要求;原本那一行在做的事留著,只換成那條 Rule 規定的寫法
- 條件動作(「若…則…」)拆成獨立的步驟,並在行尾寫成那條 Rule 規定的分支;不改成「…時…」這類敘述句,也不收進括號
- 為什麼:檢查腳本只認得出寫法,認不出條件還在、只是換了說法;這樣改過的一行重新檢查會過,流程視覺圖上卻少了一條分支,使用者會以為它已經符合規範

## good example
- 條件動作**拆成獨立的步驟**,行尾改成固定寫法;重新檢查會過,流程視覺圖上也看得到這條分支
```
原本    3. Write 建立出貨單;若有缺貨的商品則通知客服。
要改成  3. Write 建立出貨單;若商品都有庫存 → 結束。
        4. Write 通知客服有哪些商品缺貨。
```

## bad example
- 同一行,但**只把「;若…則…」換成敘述句**;重新檢查一樣會過,「缺貨才通知」這個條件卻從流程視覺圖上消失了
```
原本    3. Write 建立出貨單;若有缺貨的商品則通知客服。
要改成  3. Write 建立出貨單,有缺貨的商品時通知客服。
```

## good example
- 邊界:這個條件管的只是指令的一個參數,沒有另一件事可以拆成步驟;**改成一律加上,並在改寫提案寫明行為變了**
```
原本          2. Write 從 trunk 拉取最新變更;若有未提交變更則加 `--autostash`。
要改成        2. Write 以 `--autostash` 從 trunk 拉取最新變更。
流程有沒有變  變了:`--autostash` 改成一律加,工作目錄乾淨時沒有作用
```

## bad example
- 邊界:同一行,把條件收進括號;看起來只是補充說明,但**條件還在、檢查腳本認不出來**,改寫提案也沒有說行為有沒有變
```
原本          2. Write 從 trunk 拉取最新變更;若有未提交變更則加 `--autostash`。
要改成        2. Write 從 trunk 拉取最新變更(有未提交變更時加 `--autostash`)。
流程有沒有變  沒有變
```
