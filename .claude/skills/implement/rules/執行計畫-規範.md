# Rule 1 [must] - 範圍的終點延到 Checkpoint
- 使用者給的範圍落在某個 phase 的中間時,把範圍延到那個 phase 的最後一個任務,終點就是那個 phase 的 Checkpoint
- 計畫裡寫明使用者給的範圍、延到哪個 Checkpoint,以及因此多做的任務(`plan_scope.py` 的 `extended`)
- 為什麼:Checkpoint 是 tasks.md 唯一寫好「怎樣算做完」的地方;停在 phase 中間,沒有指令可以跑、覆蓋表也還有空格,做完的那一半沒辦法驗收

## good example
- 使用者說「做到 T020」;**延到 Phase 2 的 Checkpoint,並寫明多做了 T021–T027**
```
範圍:做到 T020 → 延到 Phase 2 Foundational 的 Checkpoint(T027)
延入的任務:T021–T027(T020 在 Phase 2 中間;Phase 2 的 Checkpoint 要 `npm test` 全綠、`/ws` 能升級)
```

## bad example
- 同一個範圍,**照字面停在 T020**;T021 的 `connection.ts` 還沒寫,Checkpoint 的「`/ws` 能升級」跑不了,這一段沒辦法驗收
```
範圍:T001–T020
```

## good example
- 邊界:使用者說「做到 US1」,範圍本來就**剛好結束在 Phase 3 的 Checkpoint**;不必延,計畫裡寫明沒有延入的任務
```
範圍:做到 US1 → 結束在 Phase 3 US1 的 Checkpoint(T045)
延入的任務:無
```

## bad example
- 邊界:同一個範圍,覺得「做到 MVP」應該連 Polish 的部署檢查一起做,**自己把 Phase 6 也延進來**;延到 Checkpoint 是為了讓範圍可以驗收,不是替使用者加範圍
```
範圍:做到 US1 → 延到 Phase 6 Polish 的 Checkpoint(T089)
延入的任務:T046–T089
```

# Rule 2 [must] - 前面沒做完的任務排在最前面
- 範圍第一個 phase 之前,還有沒勾選的任務(`plan_scope.py` 的 `pending_before`)時,把它們排在計畫最前面,並寫明是因為後面的 phase 依賴它們
- 只補 tasks.md「Phase Dependencies」寫明擋住範圍的 phase;沒有擋住的不補
- 為什麼:Foundational 擋住所有使用者故事;跳過它直接做 US2,用到的 `protocol.ts`、`push.ts` 都還不存在,subagent 會各自補一份,之後就是兩套實作

## good example
- 使用者說「做 US2」,Phase 1–3 都還沒勾;**計畫先列出 Phase 1–3,並寫明原因**
```
範圍:做 US2(Phase 4)
前面沒做完:Phase 1 Setup、Phase 2 Foundational、Phase 3 US1 共 45 個任務,排在 Phase 4 之前
原因:Foundational 擋住所有故事;US2 的「開始遊戲」要 US1 的房間與配對(tasks.md User Story Dependencies)
```

## bad example
- 同一個範圍,**直接從 Phase 4 開始**;T049 的 `game-start.test.ts` 要先有人進房,US1 的 `rooms/registry.ts` 與 `matchmaking.ts` 都還不存在
```
範圍:做 US2(Phase 4):T046–T067
```

## good example
- 邊界:使用者說「做 Polish」,US3 還沒做;但 Phase Dependencies 寫 Polish 只依賴「想交付的故事」,**沒有擋住的 US3 不補,寫明這一點**
```
範圍:做 Polish(Phase 6)
前面沒做完:Phase 5 US3 共 16 個任務;Polish 只依賴想交付的故事,不補,請使用者確認 US3 要不要一起交付
```

## bad example
- 邊界:同一個範圍,看到 `pending_before` 有 16 個任務就**全部排進來**;使用者只想先修效能與文件,拿到的是多做一整個故事
```
範圍:做 Polish(Phase 6)
前面沒做完:T068–T083,排在 Phase 6 之前
```

# Rule 3 [must] - 只問範圍內還沒決定的待決問題
- 計畫裡要使用者決定的,只有範圍內任務的 📎 指到、而且 plan.md 待決問題表「決定」欄是 — 或空白的那幾題(`plan_scope.py` 的 `open_questions`)
- 已經決定的題目不重問;範圍外任務指到的題目留到做那個範圍時再問
- 為什麼:待決問題表動輒二十幾題,一次全攤開,使用者分不出哪幾題現在不回答就不能開工,已經答過的也會被翻案

## good example
- 範圍是 Phase 1–2,只有 T010 指到的 **Q30 還沒決定,計畫只問這一題**
```
要先決定的待決問題(1 題)
Q30(T010、T013):`validateDigits()` 收到全形數字時怎麼處理:(a)回 DIGITS_FORMAT_INVALID(tasks 先採用)(b)先轉成半形再檢查
```

## bad example
- 同一個範圍,**把整張待決問題表貼出來請使用者確認**;Q1–Q29 早就決定了,真正擋住開工的 Q30 被淹沒在第 30 列
```
要先決定的待決問題(30 題)
Q1:等待中有人離開後座位怎麼排 ……(已決定:(b))
Q2:其他人看不看得到斷線玩家剩多少保留時間 ……(已決定:(b))
……
Q30:`validateDigits()` 收到全形數字時怎麼處理 ……
```

## good example
- 邊界:範圍內沒有任何還沒決定的題目;**計畫裡寫明「沒有」**,不另外挑幾題來問
```
要先決定的待決問題:沒有(範圍內任務指到的 Q12、Q29 都已決定)
```

## bad example
- 邊界:同一個情況,覺得 Q8 的決定「可能還要再想想」就**拿出來重問**;使用者已經在 tasks 階段答過,重問等於請他翻案
```
要先決定的待決問題(1 題)
Q8:等待中的房間有人斷線,要不要也保留座位 60 秒(已決定 (a),要不要改?)
```

# Rule 4 [must] - 主 agent 與 subagent 依 phase 種類分工
- Setup、Foundational、Polish 的每個任務,以及每個使用者故事的「跨端點驗收」任務,由主 agent 依編號順序做
- 使用者故事底下的每一個端點節(`### E<序號> …`)交給一個 subagent,同一個 phase 的端點節可以平行
- 為什麼:Setup 與 Foundational 的檔被後面每個故事共用,平行做最容易互相覆蓋;使用者故事已經依端點切好目錄,這時才平行,衝突最少

## good example
- US1 的計畫:**跨端點驗收由主 agent 先做,E2、E1、E3 各交給一個 subagent**
```
Phase 3 US1
  主 agent:T028(跨端點驗收,先寫、確認失敗)
  subagent E2 後端(backend/):T029–T040
  subagent E1 前端(frontend/):T041–T044
  subagent E3 部署(deploy/):T045
  平行:E2、E1、E3
```

## bad example
- 同一個 phase,**跨端點驗收也交給 E2 的 subagent**;它寫的 e2e 測試只照自己的後端去寫,前端的那一半沒有人驗
```
Phase 3 US1
  subagent E2 後端(backend/):T028–T040
  subagent E1 前端(frontend/):T041–T044
  subagent E3 部署(deploy/):T045
```

## good example
- 邊界:Foundational 有 10 個標了 `[P]` 的任務,看起來可以平行;但**它不是使用者故事,仍然由主 agent 依序做**
```
Phase 2 Foundational
  主 agent:T010 → T011 → … → T027(依序)
```

## bad example
- 邊界:同一個 phase,看到 `[P]` 就**拆成三個 subagent 平行**;T015 的 `protocol.ts` 被 T018、T019 同時 import,三個 subagent 各自猜型別長什麼樣子
```
Phase 2 Foundational
  subagent A:T010、T013
  subagent B:T011、T014
  subagent C:T012、T015、T018
```

# Rule 5 [must] - 同一個檔的任務不同時做
- `plan_scope.py` 的 `shared_files` 列出描述裡提到同一個檔的任務;先看描述判斷哪幾個任務真的會改它,只是提到的不算
- 會改到同一個檔的任務照編號依序做,計畫裡寫出這條順序
- 這些任務落在同一個 phase 的不同端點節時,那幾個端點節不平行,後面的等前面的做完
- 為什麼:兩個 agent 同時改同一個檔,後寫的會蓋掉先寫的;覆蓋的那一段測試照樣可能是綠的,要到很後面才發現少了一個功能

## good example
- `shared_files` 列出 `backend/src/rooms/game.ts` 被 T056–T060、T075 提到;**計畫寫出會改它的任務的順序,全部留在同一個 subagent**
```
同一個檔的任務
  backend/src/rooms/game.ts:T056 → T057 → T058 → T059(Phase 4,E2 subagent 依序)→ T075(Phase 5)
```

## bad example
- 同一個檔,**計畫沒有寫順序**,把 T057 與 T058 分給兩個 agent 平行;兩個任務同時改 `game.ts`,後寫的蓋掉先寫的
```
同一個檔的任務
  (沒有列 backend/src/rooms/game.ts)
平行:T057、T058
```

## good example
- 邊界:T060 也提到 `game.ts`,但它改的是 `views/player-view.ts`,描述只是說「`game.ts` 只能透過這裡產生推送內容」;**只是提到、不會改,不排進 `game.ts` 的順序**
```
同一個檔的任務
  backend/src/rooms/game.ts:T056 → T057 → T058 → T059 → T075
  (T060 只提到 game.ts,不改它)
```

## bad example
- 邊界:同一份 `shared_files`,**照單全收**,把 T060 也排進 `game.ts` 的依序鏈;T060 原本可以和 T059 平行,被白白拉成依序
```
同一個檔的任務
  backend/src/rooms/game.ts:T056 → T057 → T058 → T059 → T060 → T075
```

## good example
- 邊界:`deploy/compose.yaml` 被 T009(Phase 1)與 T083(Phase 5)改到;**兩者在不同 phase,phase 本來就依序,計畫照樣寫出這條順序**
```
同一個檔的任務
  deploy/compose.yaml:T009(Phase 1)→ T083(Phase 5)
```

## bad example
- 邊界:同一個檔,因為不同 phase 就**不寫進計畫**;之後使用者把範圍改成只做 Phase 5,T009 還沒做,沒有人知道 T083 要改的檔還不存在
```
同一個檔的任務
  (沒有列 deploy/compose.yaml)
```

# Rule 6 [should] - 描述裡寫的依賴排進順序
- 任務描述裡寫的「依賴 T0xx」「讓 T0xx 通過」,排在計畫裡:被依賴的任務在前;「讓 T0xx 通過」的實作任務排在那個測試任務之後
- 每一條都照原文寫進那個任務後面的括號,照編號排本來就滿足的也寫
- 為什麼:這些依賴只寫在描述文字裡,腳本抓不到;照編號排通常剛好對,但 `[P]` 任務被分到不同 agent 時,文字裡的依賴就是唯一的線索

## good example
- T018 寫「依賴 T015;讓 T012 通過」;**計畫把它排在 T015 與 T012 之後**
```
Phase 2 Foundational(主 agent 依序)
  T012(測試)→ T015(protocol.ts)→ T018(validate.ts,依賴 T015;讓 T012 通過)
```

## bad example
- 同一組任務,只看到 T018 沒有 `[P]` 就**排在最前面**;它要 import 的 `protocol.ts` 還不存在
```
Phase 2 Foundational(主 agent 依序)
  T018 → T012 → T015
```

## good example
- 邊界:T035 寫「讓 T029 通過」,兩個都在 E2 subagent 裡,編號順序本來就是 T029 在前;**照編號排就滿足,依賴仍然照原文寫在括號裡,留在 E2 的順序中**
```
subagent E2 後端:T029 → … → T035(讓 T029 通過)→ …
```

## bad example
- 邊界:同樣兩個任務,為了「把依賴寫清楚」**把 T035 拉出來另開一行**,寫成和 E2 平行;反而讓它和 T029 分到不同的 agent
```
subagent E2 後端:T029 → …
另外:T035(讓 T029 通過),可與 E2 平行
```
