# Rule 1 [must] - 只做任務寫到的檔與 ⚙ 列的元素
- 一個任務只改它描述裡寫的檔,做出它 ⚙ 列的介面元素;tasks.md 沒有任何任務寫到的檔不碰
- 做的時候發現別的檔也該改,寫進交回的內容,不順手改
- 為什麼:⚙ 是這個任務的完成範圍,驗收只對照這幾個元素;順手改的那一段沒有任務負責驗收,也沒有測試在看,壞了要到很後面才有人發現

## good example
- T035 只做 `nickname.ts`;**發現 `router.ts` 還沒接 `match.start`,寫進交回的內容,不動它**
```
T035 實作 backend/src/domain/nickname.ts
  改的檔:backend/src/domain/nickname.ts
  交回:router.ts 目前還沒接 match.start,是 T040 的範圍
```

## bad example
- 同一個任務,**順手在 `router.ts` 接上 `match.start`**;T040 之後照自己的描述再接一次,`router.ts` 出現兩個處理 `match.start` 的分支
```
T035 實作 backend/src/domain/nickname.ts
  改的檔:backend/src/domain/nickname.ts、backend/src/ws/router.ts
```

## good example
- 邊界:T040 的描述寫了「在 `backend/src/ws/router.ts` 接上 `match.start`、`room.leave`」;`router.ts` 不是它開頭的那個檔,但**描述寫到了,所以是它的範圍**
```
T040 實作 backend/src/views/room-view.ts
  改的檔:backend/src/views/room-view.ts、backend/src/ws/router.ts
```

## bad example
- 邊界:同一個任務,只看開頭的檔名就**不碰 `router.ts`**;`match.start` 沒有人接上,T034 永遠跑不綠
```
T040 實作 backend/src/views/room-view.ts
  改的檔:backend/src/views/room-view.ts
  交回:router.ts 不在範圍內,沒有接
```

# Rule 2 [must] - 測試的紅燈要是斷言失敗
- 測試任務寫完要跑一次,看到的失敗必須是斷言失敗:測試載入了、呼叫了被測的函式、拿到的值和預期不同
- 被測的模組還不存在時,先建立只有簽名、回傳錯誤值的空殼,讓測試載入得了;空殼不算實作任務做完
- 為什麼:`import` 失敗、檔案不存在、語法錯誤也是紅燈,但那種紅燈在實作寫出來之前就決定了結果,測試裡的斷言一條都沒跑過,寫錯了也不會有人發現

## good example
- T010 寫完時 `digits.ts` 還不存在;**先建空殼,跑出來是斷言失敗**
```
T010 撰寫 shared/test/digits.test.ts
  空殼:shared/src/digits.ts 匯出 validateDigits(s) { return "DIGITS_FORMAT_INVALID" }
  紅燈:7 個案例中 2 個失敗
    AssertionError: validateDigits("1234") 預期 null,實際 "DIGITS_FORMAT_INVALID"
```

## bad example
- 同一個測試,**沒有空殼就跑**;失敗訊息是找不到模組,7 個斷言一個都沒有執行
```
T010 撰寫 shared/test/digits.test.ts
  紅燈:Error [ERR_MODULE_NOT_FOUND]: Cannot find module 'shared/src/digits.ts'
```

## good example
- 邊界:空殼讓 7 個案例中 5 個意外通過(剛好都該回 `DIGITS_FORMAT_INVALID`);**仍然有斷言失敗,而且失敗的是該失敗的那 2 個**,這是對的紅燈
```
紅燈:7 個案例中 2 個失敗("1234"、"0123" 預期 null)
```

## bad example
- 邊界:空殼寫成直接呼叫 `throw new Error("TODO")`;每個案例都失敗,看起來很紅,但**失敗的原因是例外,不是回傳值和預期不同**,斷言其實沒有比對過任何值
```
紅燈:7 個案例全部失敗
  Error: TODO
```

# Rule 3 [must] - 規格有問題只停受影響的任務
- 規格之間互相矛盾、⚙ 的錨點照規格做不出來、📎 寫得不夠決定做法時,停下那個任務與依賴它的任務,其他任務照計畫繼續
- 把問題整理成一題待決問題:問題、可選的做法、受影響的任務;主 agent 登記到 plan.md 待決問題表,「提出的步驟」寫 `implement T<編號>`,「決定」欄寫 —;subagent 把這題寫進交回的內容,由主 agent 登記
- 為什麼:自己挑一個做法繼續做,程式碼和規格就不一致,而且沒有人知道;整批停下來,平行的 agent 又會全部卡在一個與它們無關的問題上

## good example
- T013 發現合約 `Digits` 的 pattern 和 FR-009 說的不一樣;**只停 T013 與依賴它的 T010 驗收,登記成一題,其他任務繼續**
```
停下:T013(與它要讓通過的 T010)
登記 plan.md 待決問題
| Q30 | implement T013 | 合約 `Digits` 的 pattern 允許 5 位數,FR-009 要 4 位數:(a)照 FR-009 改成 4 位(b)照合約 | — | — |
繼續:T014–T027
```

## bad example
- 同一個問題,**自己選了照 FR-009 做完**,沒有登記;合約仍然允許 5 位數,前端照合約做的檢查和後端對不上
```
T013 完成:照 FR-009 只收 4 位數(合約寫的是 5 位數,以 spec 為準)
```

## good example
- 邊界:📎 指到的 Q12 已經決定要「拆開」兩種錯誤碼,描述也寫了要分得出格式錯與重複;**規格寫得夠清楚,照做,不登記**
```
T013 照 Q12(a):格式錯回 DIGITS_FORMAT_INVALID,重複回 DIGITS_REPEATED
```

## bad example
- 邊界:同一個任務,覺得「也許該問一下錯誤碼要不要合併」就**停下來登記一題**;Q12 早就決定了,這等於替使用者翻案,還讓 T013 白白停住
```
停下:T013
登記:| Q30 | implement T013 | 錯誤碼要不要合併成一個 | — | — |
```

# Rule 4 [must] - 不改規格檔
- spec package 裡的規格檔(spec.md、research.md、techstack.md、`contracts/`、`prototype/`、`deploy/`)實作時一律不改;tasks.md 只由主 agent 勾選,plan.md 只由主 agent 寫待決問題表
- 要改規格才做得下去時,照〈規格有問題只停受影響的任務〉登記
- 為什麼:規格是驗收對照的標準;為了讓實作通過而改規格,驗收就變成拿自己對照自己,原本要抓的落差永遠不會出現

## good example
- T009 要把 spec package 的 `deploy/` 複製到 repo 根目錄;**改的是複製出去的那一份,spec package 裡的原檔不動**
```
T009 改的檔:deploy/compose.yaml(repo 根目錄)
spec package 的 specs/001-bulls-cows-online/deploy/compose.yaml:未修改
```

## bad example
- 同一個任務,`compose.yaml` 的 healthcheck 跑不起來,就**直接改 spec package 裡的原檔**讓它通過;之後的驗收拿改過的那一份對照,永遠是綠的
```
T009 改的檔:deploy/compose.yaml、specs/001-bulls-cows-online/deploy/compose.yaml
```

## good example
- 邊界:spec package 的 `prototype/` 是畫面的規格;T041 照它做前端,**`prototype/index.html` 有錯字也不改**,寫進交回的內容
```
T041 交回:prototype/index.html 的 #match-form 標題有錯字「暱稱」寫成「匿稱」,前端照正確的字做,原型未修改
```

## bad example
- 邊界:同一個錯字,覺得「只是錯字、不影響行為」就**順手改了原型**;這次確實無害,但規格檔被實作改過一次,之後再出現差異,沒有人分得出是規格本來就這樣,還是實作改的
```
T041 改的檔:frontend/src/pages/nickname.js、prototype/index.html
```

# Rule 5 [must] - 非平行任務失敗就停下這個 phase
- 沒有標 `[P]` 的任務失敗、修不好時,停下這個 phase 剩下的任務,回報失敗的原因
- 標了 `[P]` 的任務失敗時,不依賴它的任務照樣繼續,失敗的那個列進回報
- 為什麼:沒有標 `[P]` 的任務是後面任務的前提;它沒做好就繼續,後面的任務會繞過它各自補一份,錯誤一路擴散到下一個 phase

## good example
- T021(沒有 `[P]`)的心跳測試一直逾時;**停下 T022–T027,回報原因**
```
失敗:T021 backend/src/ws/connection.ts,心跳測試在 15 秒後逾時
停下:T022–T027(T022 依賴 T021)
```

## bad example
- 同一個失敗,**跳過 T021 繼續做 T022**;`router.ts` 沒有連線層可以接,自己另寫了一個簡化版的 upgrade 處理
```
失敗:T021
繼續:T022(router.ts 內自行處理 upgrade)、T023–T027
```

## good example
- 邊界:T014(`[P]`)的 `score.ts` 有一個案例算錯;**它只被 T011 依賴,T015–T027 照樣繼續**,T014 列進回報
```
失敗:T014 shared/src/score.ts,score("1234", "4321") 回 { a: 0, b: 3 }
繼續:T015–T027
```

## bad example
- 邊界:同一個失敗,因為「有任務失敗」就**整個 phase 停下來**;T015–T027 跟分數計算無關,卻全部等著一個 `[P]` 任務
```
失敗:T014
停下:T015–T027
```

# Rule 6 [must] - 失敗任務的半成品要還原或列出
- 任務失敗停下時,它已經改過的檔要還原成開始前的樣子;沒辦法還原的(例如改到一半、其他任務也改過),在回報裡逐一列出檔名與改到哪裡
- 為什麼:半成品留在工作目錄,下一個 commit 會把它一起帶進去,看起來像做完的程式碼,其實沒有通過任何驗收

## good example
- T021 失敗;**`connection.ts` 是它新建的,刪掉還原**,`server.ts` 是 T020 做的、它只加了一行,把那一行拿掉
```
還原:backend/src/ws/connection.ts(刪除,T021 新建)、backend/src/server.ts(移除 T021 加的 upgrade 那一行)
```

## bad example
- 同一個失敗,**檔案原封不動留著**;下一組 commit 把寫到一半的 `connection.ts` 一起提交,`npm run typecheck` 在下一個 phase 才爆出來
```
失敗:T021
(未處理已修改的檔)
```

## good example
- 邊界:T058 失敗時,`game.ts` 裡還有同一組已經驗收、但還沒 commit 的 T056、T057 改動,**沒辦法整個檔還原;只拿掉 T058 加的那一段,並列出來**
```
沒有整檔還原:backend/src/rooms/game.ts,保留 T056、T057 的改動(已驗收,等這一組 commit),移除 T058 加的 guess.submit 處理(第 120–164 行)
```

## bad example
- 邊界:同一個情況,**用 `git checkout` 把整個檔還原到上一個 commit**;T056、T057 已經驗收過的改動也一起被丟掉
```
還原:git checkout backend/src/rooms/game.ts
```
