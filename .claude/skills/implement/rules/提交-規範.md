# Rule 1 [must] - 一組驗收過的任務 commit 一次
- 一組是一個端點節的任務,或主 agent 依序做的一個測試任務與讓它通過的實作任務;這一組全部勾成 `[X]` 之後才 commit
- 只 commit 這一組任務改的檔與勾選後的 tasks.md;footer 用 `Refs:` 列出這一組的任務編號
- 為什麼:commit 是出錯時能退回的位置;每個 commit 都是驗收過的一組,退回去就是一個能跑的狀態,而 `Refs:` 讓人從 `git log` 對回 tasks.md 是哪幾個任務

## good example
- T010 與讓它通過的 T013 都驗收過;**一起 commit,`Refs:` 列出兩個任務**
```
feat(shared): 新增祕密數字的格式檢查

validateDigits() 分得出格式錯與數字重複,錯誤碼照 Q12 拆開。

Refs: T010, T013
```

## bad example
- 同一組任務,**T013 還沒驗收就和 T010 一起 commit**,也沒有寫是哪幾個任務;T013 之後驗收不過,這個 commit 退回去也不是能跑的狀態
```
feat(shared): 新增 digits
```

## good example
- 邊界:E2 subagent 一次交回 T029–T040,其中 T040 停下等待決問題;**它要讓通過的 T034 也先不勾,其餘 10 個勾選並 commit,T034、T040 改的檔不放進這次 commit**
```
feat(backend): 實作暱稱、座位與自動配對

Refs: T029, T030, T031, T032, T033, T035, T036, T037, T038, T039
```

## bad example
- 邊界:同一個情況,為了「一個端點節一個 commit」就**連 T034 的測試與 T040 的半成品一起 commit**;`Refs:` 沒有它們,但一支紅的測試與改到一半的 `room-view.ts` 已經進了歷史,這個 commit 跑 `npm test` 是紅的
```
feat(backend): 實作暱稱、座位與自動配對

Refs: T029, T030, T031, T032, T033, T035, T036, T037, T038, T039
(staged:backend/test/contract/us1-messages.test.ts、backend/src/views/room-view.ts 也在內)
```

# Rule 2 [must] - ignore 檔只補缺的 pattern
- 第一次 commit 之前,依 techstack.md 的語言與工具,確認 `.gitignore` 有該忽略的 pattern(例如 Node 的 `node_modules/`、`dist/`、`coverage/`、`.env`);`deploy/` 有 Dockerfile 時也確認 `.dockerignore`
- 檔已經存在時,只在檔尾附加缺的 pattern,既有的每一行都不改、不刪
- tasks.md 有任務負責建立這個 ignore 檔時,交給那個任務做,這裡不先建
- 為什麼:沒有 ignore 檔,第一個 commit 就會把 `node_modules/` 與建置產物帶進歷史;改掉使用者既有的 pattern,原本被忽略的檔會突然出現在 `git status`

## good example
- repo 原本沒有 `.gitignore`,tasks.md 也沒有任務負責;**依 techstack 的 Node、Vite、Playwright 建立**
```
.gitignore(新建)
node_modules/
dist/
coverage/
playwright-report/
test-results/
.env
```

## bad example
- 同一個 repo,**沒有建 `.gitignore` 就 commit**;第一個 commit 有 4 萬個 `node_modules/` 底下的檔
```
$ git commit
  41,233 files changed
```

## good example
- 邊界:`.gitignore` 已經有使用者寫的 `*.local`、`.idea/`;**只在檔尾加上缺的 `dist/`、`coverage/`**
```
.gitignore(檔尾附加)
# implement:依 techstack 補上
dist/
coverage/
```

## bad example
- 邊界:同一個檔,覺得 `.idea/` 不屬於這個專案就**刪掉並整份重排**;使用者的 IDE 設定開始出現在 `git status`
```
.gitignore(整份改寫)
node_modules/
dist/
coverage/
```

# Rule 3 [must] - 任務寫到的檔都不能被忽略
- 補完 ignore 檔之後,用 `git check-ignore` 檢查這一組任務改的檔與 tasks.md 寫到要提交的檔,一個都不能被忽略
- 被忽略的,在 ignore 檔加上 `!<路徑>` 例外,再檢查一次
- 為什麼:被忽略的檔 `git add` 不會報錯,只是安靜地不進 commit;常見的 `.env*` 會把 `deploy/.env.example` 一起擋掉,別人 clone 下來就少了部署要的範本

## good example
- `.gitignore` 有 `.env*`;**檢查到 T009 的 `deploy/.env.example` 被忽略,加上例外後再檢查**
```
$ git check-ignore -v deploy/.env.example
  .gitignore:6:.env*	deploy/.env.example
.gitignore 附加:!.env.example
$ git check-ignore deploy/.env.example
  (無輸出,exit 1:沒有被忽略)
```

## bad example
- 同一個 repo,**沒有檢查就 commit**;`git add deploy/` 沒有報錯,但 `.env.example` 沒進 commit
```
$ git add deploy/ && git commit
$ git show --stat HEAD
  deploy/compose.yaml | 48 +
  deploy/Dockerfile   | 22 +
  deploy/proxy.conf   | 31 +
```

## good example
- 邊界:`frontend/dist/` 被 `dist/` 忽略,T004 的描述也提到它;但 **T004 只是設定建置產物放在那裡,沒有寫要提交它**,忽略是對的
```
$ git check-ignore frontend/dist
  frontend/dist   ← 建置產物,本來就不提交
```

## bad example
- 邊界:同一個檔,看到「任務提到的路徑被忽略」就**加上 `!frontend/dist/`**;建置產物從此每次都進 commit
```
.gitignore 附加:!frontend/dist/
```

# Rule 4 [should] - 不屬於任何任務的新檔不 commit
- `git status` 裡出現這一組任務沒有寫到的新檔時,先判斷它是什麼:建置產物、快取、測試報告就加進 ignore 檔;判斷不出來的,列進回報,不 commit
- 為什麼:這些檔沒有任務負責,也沒有驗收過;一起 commit,歷史裡就多了說不出來由的檔,之後也沒有人敢刪
- 允許例外:工具自己產生、必須跟著提交的檔(例如 `package-lock.json`)照常 commit

## good example
- 跑完 e2e 之後多了 `test-results/` 與 `playwright-report/`;**是測試報告,加進 `.gitignore`**
```
.gitignore 附加:test-results/、playwright-report/
```

## bad example
- 同一組檔,**用 `git add -A` 一起提交**;每次跑測試都產生一批新的報告 commit
```
$ git add -A && git commit
  test-results/.last-run.json | 4 +
  playwright-report/index.html | 2,113 +
```

## good example
- 邊界:`npm install` 產生了 `package-lock.json`,沒有任務寫到它;但 **它是鎖定依賴版本、必須提交的檔**,照常 commit
```
$ git add package-lock.json
```

## bad example
- 邊界:同一個檔,因為「沒有任務寫到」就**加進 `.gitignore`**;別台機器裝到的版本和這台不一樣
```
.gitignore 附加:package-lock.json
```

# Rule 5 [must] - 寫回決定的 plan.md 單獨 commit
- Checkpoint 把使用者的決定寫回 plan.md 待決問題表之後,只把 plan.md commit 一次,不和任務的程式碼放在同一個 commit
- 訊息寫出這次決定了哪幾題;footer 用 `Refs:` 列出那幾題的 Q 編號與受影響的任務編號
- spec package 的其他檔(spec.md、contracts/ 等)不跟著 commit,是否納入版控由使用者決定
- 為什麼:待決問題要等使用者在 Checkpoint 拍板才算定案;不 commit,換一台機器或 `git checkout` 之後,沒有人知道程式為什麼照這個做法寫,和程式碼放在同一個 commit,又分不出哪一段是決定、哪一段是實作

## good example
- Phase 1 的 Checkpoint 決定了 Q30;**寫回之後只 commit plan.md**,`Refs:` 對得到題號與任務
```
docs(plan): 決定 Q30,ESLint 改用 typescript-eslint 檢查 TypeScript

Refs: Q30, T007
(staged:specs/001-bulls-cows-online/plan.md)
```

## bad example
- 同一個決定,**寫回 plan.md 之後沒有 commit**;之後補做的 T007 把 TypeScript 降到 6.0,歷史裡看不到是誰、因為哪一題決定的
```
$ git status --short
 M specs/001-bulls-cows-online/plan.md
```

## good example
- 邊界:Phase 1 Step 6 時使用者決定了 Q26,當時已寫回 plan.md 但還沒有 commit;**到第一個 Checkpoint 寫回 Q30 時,兩題一起進這次的 commit**
```
docs(plan): 決定 Q26、Q30

Refs: Q26, Q30, T007, T010
```

## bad example
- 邊界:同一個時間點,**把 plan.md 和 T007 補做的程式碼放進同一個 commit**;`git log` 只看得到「加入 ESLint 設定」,看不出 TypeScript 降版是一個待決問題的決定
```
build: 加入 ESLint 與 Prettier 設定

Refs: T007
(staged:eslint.config.js、package.json、specs/001-bulls-cows-online/plan.md)
```
