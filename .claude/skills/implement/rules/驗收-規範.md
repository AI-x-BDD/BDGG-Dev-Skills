# Rule 1 [must] - ⚙ 的每個錨點都指出程式碼的位置
- 驗收一個任務時,⚙ 列的每一個錨點都要對照規格檔裡那一段,寫出程式碼裡做出它的位置(檔名與函式、行號或選擇器)
- 少一個錨點找不到位置,這個任務就不過
- 為什麼:⚙ 是這個任務的完成範圍;只說「照合約做了」,沒有人知道 `Player` 的四個欄位是不是都在,少了一個要到前端畫面空白才發現

## good example
- T040 的 ⚙ 有 `Room`、`Player` 兩個錨點;**兩個都對照合約,寫出程式碼裡的位置**
```
T040 ⚙ 對照
  components.schemas.Room → backend/src/views/room-view.ts toRoomView():status、hostSeat、players(依座位號排序)
  components.schemas.Player → backend/src/views/room-view.ts toPlayerView():seat、nickname、isHost、connection,不含 token
```

## bad example
- 同一個任務,**只寫一句總結**;`Player` 有沒有漏欄位、有沒有多帶 token,看不出來
```
T040 ⚙ 對照:Room、Player 都照合約做了
```

## good example
- 邊界:T041 的 ⚙ 是原型的 6 個選擇器與狀態;**原型的錨點對照的是 DOM 與狀態切換,一樣逐一寫出位置**
```
T041 ⚙ 對照
  #match-form → frontend/src/pages/nickname.js render() 的 <form id="match-form">
  [data-state="nickname-long"] → nickname.js onSubmit():超過 12 個字時 setState("nickname-long")
  ……(其餘 4 個狀態各一列)
```

## bad example
- 邊界:同一個任務,覺得畫面「看起來跟原型一樣」就**只附一張截圖**;截圖只拍到 `normal` 狀態,`loading` 與 `error` 兩個狀態有沒有做,看不出來
```
T041 ⚙ 對照:畫面與原型一致(附截圖 nickname.png)
```

# Rule 2 [must] - 測試由主 agent 自己重跑
- 驗收時,和這個任務有關的測試由主 agent 自己執行,看到綠燈才算數;subagent 回報的「測試通過」只當線索
- 寫出執行的指令與結果(通過幾個、失敗幾個)
- 為什麼:subagent 可能只跑了自己那一支測試,也可能跑在還沒存檔的版本上;主 agent 勾的 `[X]` 要對得起自己看到的結果

## good example
- E2 subagent 回報 T029–T040 全部通過;**主 agent 自己跑一次 `npm test`**
```
$ npm test -- backend/test/
  tests 48 / pass 48 / fail 0
```

## bad example
- 同一份回報,**直接照抄 subagent 的結果**;subagent 只跑了 `backend/test/domain/`,`rooms/` 底下有 2 個測試其實是紅的
```
T029–T040 測試:subagent 回報全部通過
```

## good example
- 邊界:T009 是複製部署檔,沒有測試;**改成執行能證明它做完的指令**
```
$ docker compose -f deploy/compose.yaml config --quiet
  exit 0
$ diff -r specs/001-bulls-cows-online/deploy deploy
  (無差異)
```

## bad example
- 邊界:同一個任務,因為「沒有測試可以跑」就**直接算過**;複製時漏了 `.env.example`,要到部署時才發現
```
T009:沒有測試,直接勾選
```

# Rule 3 [must] - 🔴 任務附紅燈的證據
- 🔴 `/tdd 紅燈` 任務驗收時,要看到它在 🟢 之前跑出的紅燈,而且是 `~/.claude/skills/tdd/rules/紅燈-規範.md`〈測試的紅燈要是斷言失敗〉要的斷言失敗
- 拿不出紅燈的訊息,或訊息是載入錯誤、例外,這個 🔴 任務不過
- 為什麼:只看到最後的綠燈,分不出這個測試是真的在檢查,還是不管實作寫什麼都會綠

## good example
- T101a 附上**🟢 之前的斷言失敗訊息**,T101b 附上轉綠的結果
```
T101a 紅燈(T101b 之前):AssertionError: Bob 預期收到 chat_message{text:"你好"},實際沒有收到
T101b 綠燈:backend/tests 42 / 42 pass
```

## bad example
- 同一組任務,**只有最後的綠燈**;沒有人知道 US5-BE-01 的測試在 T101b 之前是不是紅的
```
T101a、T101b:42 / 42 pass
```

## good example
- 邊界:subagent 回報的紅燈訊息是 `AssertionError`;**主 agent 看過訊息的內容確實是那個斷言,才採用**
```
T102a 紅燈(subagent 回報):AssertionError: chat_message.sender 預期 "challenger",實際 "host"
判定:斷言失敗,採用
```

## bad example
- 邊界:subagent 回報「先跑過,是紅的」,**沒有附訊息就採用**;那次其實是 `ModuleNotFoundError`
```
T102a 紅燈:subagent 回報已確認失敗
判定:採用
```

# Rule 4 [must] - 驗不了的項目標未驗證
- 手動才能確認的行為、這台機器缺環境跑不了的指令、量不到數字的 SC,一律標「未驗證」並寫明原因與要怎麼驗
- 標了未驗證的項目不算通過;它所在的任務可以勾選,但要在 Checkpoint 報告與完成報告裡列出來
- 為什麼:驗不了卻寫成通過,使用者會以為它驗過了;到上線時才發現的落差,就是這個 skill 要擋的 bug

## good example
- T089 要重測 R5「手機切飛航模式後 30 秒內被判斷線」;**agent 沒有實機可以切飛航模式,標未驗證並寫出步驟**
```
未驗證:T089 R5 手機飛航模式斷線偵測
  原因:要用實體手機切換飛航模式
  怎麼驗:手機連上部署環境進房,切飛航模式,另一個分頁在 30 秒內看到「斷線中」
```

## bad example
- 同一個項目,因為 T021 的心跳測試是綠的,就**寫成已驗證**;單元測試是在本機直接關掉連線,行動網路斷線時 TCP 不會送出 close,這正是 R5 要驗的情況
```
已驗證:T089 R5(T021 心跳測試全綠)
```

## good example
- 邊界:SC-003 要 100 間房、400 位玩家時 SC-002 仍成立,`scripts/load-test.ts` 量得到;**量到了就寫數字,不標未驗證**
```
SC-003:100 間房、400 位玩家,推送延遲 p95 120 毫秒,最大房間 4 人(scripts/load-test.ts)
```

## bad example
- 邊界:同一條 SC 量得到,卻因為「效能數字跟機器有關」就**標未驗證**;使用者拿不到任何數字,也不知道它其實量得到
```
SC-003:未驗證(效能與機器有關)
```

# Rule 5 [must] - 描述寫到的每一項都對到做出它的位置
- 勾選一個任務之前,把描述寫到的每一個檔、函式、欄位與行為逐項列出,各寫出做出它的位置;⚙ 錨點照〈⚙ 的每個錨點都指出程式碼的位置〉另外對照
- 有一項沒做,這個任務就不過、不勾;在報告裡寫出沒做的是哪一項
- 要部署、實機或人工才驗得了的項目,照〈驗不了的項目標未驗證〉處理,不算沒做;程式裡該有、卻還沒寫的,不能改標未驗證
- 為什麼:⚙ 只列規格檔裡的元素,描述裡「判定依據記下排序」「session 檔被清」這類行為常常不在 ⚙ 裡;只對 ⚙ 與測試,這些沒做的部分會跟著勾成 `[X]`,`check_phase.py` 與 CI 只看勾選,之後沒有人會再發現它沒做

## good example
- T294 的 ⚙ 只有 ai-quota 的 `paths./mcp.post`,描述還寫了三個檔與「判定依據記下排序與用到的快照時間」;**逐項列出,找到判定依據沒有記排序,不勾**
```
T294 描述逐項對照
  quota.py 回傳各家剩餘比例與 stale → src/agent_dispatch/quota.py QuotaJudgement.remaining_pct
  審查排序純函式 → src/agent_dispatch/domain/review.py rank_by_remaining()
  dispatcher 審查選家時帶入 → services/dispatcher.py _prepare_review() 呼叫 select_reviewers(rank=True)
  判定依據記下排序與用到的快照時間 → 找不到:evidence 只寫了選到的家
判定:T294 不過,不勾;沒做的是「判定依據記下排序與快照時間」
```

## bad example
- 同一個任務,**只對了 ⚙ 與測試就勾選**;⚙ 沒有列判定依據,測試也沒有測它,T294 被勾成 `[X]`,判定依據沒有記排序這件事直到審查才被發現
```
T294 ⚙ 對照
  paths./mcp.post → src/agent_dispatch/quota.py fetch_snapshot()
T293 測試:12 / 12 pass
判定:T294 勾選
```

## good example
- 邊界:T296 的描述最後寫「live 驗收(在 agent-flow-test 開純文件 MR)須合併部署後再做」;**這一項要部署之後才驗得了,標未驗證,程式的部分逐項都對到了,可以勾**
```
T296 描述逐項對照
  domain/low_risk.py 判定純函式 → src/agent_dispatch/domain/low_risk.py is_low_risk()
  判門之後套用、傳進 pick_agy_model → services/dispatcher.py _prepare_review()
  低風險每 5 張抽 1 張加派 codex → services/dispatcher.py _low_risk_sample()
未驗證:live 驗收(要合併部署後在 agent-flow-test 開純文件 MR)
判定:T296 勾選,未驗證列進 Checkpoint 報告
```

## bad example
- 邊界:同一個任務,「低風險每 5 張抽 1 張加派 codex」在程式裡還沒寫,卻**以「要開 5 張 MR 才驗得了」和 live 驗收一起標成未驗證就勾選**;抽樣是程式裡該寫卻沒寫的,不是驗不了
```
T296 描述逐項對照
  domain/low_risk.py 判定純函式 → src/agent_dispatch/domain/low_risk.py is_low_risk()
  判門之後套用、傳進 pick_agy_model → services/dispatcher.py _prepare_review()
未驗證:低風險每 5 張抽 1 張加派 codex(要開 5 張 MR);live 驗收
判定:T296 勾選
```

# Rule 6 [must] - 🔵 任務附重構前後的測試結果
- 🔵 `/tdd 重構` 任務驗收時,要看到重構前與重構後兩次全部測試的結果,兩次都全綠、通過的測試一樣多
- 重構任務改到的檔裡不能有測試檔的斷言;改到斷言,這個 🔵 任務不過
- 為什麼:重構只能動結構;只看重構後的綠燈,分不出是行為沒變,還是測試被改成配合新的行為

## good example
- T119 附上**前後兩次的測試結果,改的檔只有 `src/`**
```
T119 重構前:backend/tests 42 / 42 pass
T119 重構後:backend/tests 42 / 42 pass
改的檔:backend/src/guess_number/business/game_service.py、backend/src/guess_number/presentation/websocket.py
```

## bad example
- 同一個任務,**只有重構後的綠燈,而且改了 `test_chat.py` 的斷言**;沒有人知道是不是行為變了、測試跟著改
```
T119:42 / 42 pass
改的檔:backend/src/guess_number/business/game_service.py、backend/tests/test_chat.py
```

## good example
- 邊界:T119 把 `tests/helpers.py` 裡重複的連線建立抽成一個函式,改到的是測試的輔助程式、不是斷言;**前後兩次一樣全綠,採用**
```
T119 重構前:42 / 42 pass;重構後:42 / 42 pass
改的檔:backend/tests/helpers.py(抽出 connect_pair(),斷言沒變)
```

## bad example
- 邊界:同一個改動,因為「改到 `tests/` 底下」就**判不過**;沒有看改的是不是斷言
```
T119:改到 backend/tests/helpers.py → 不過
```

# Rule 7 [must] - 📏 任務附量到的數字與門檻
- 📏 量測任務驗收時,要看到量到的數字、testplan 案例寫的門檻,以及兩者比較的結果;人工量測寫出誰在什麼環境量到什麼
- 量到的數字沒過門檻,任務照樣可以勾選,但要列進 Checkpoint 報告;量不到的照〈驗不了的項目標未驗證〉處理
- 為什麼:📏 任務沒有紅綠可以看,只寫「已量測」等於沒有證據;不寫門檻,使用者看不出數字是好是壞

## good example
- T141 附上**數字、門檻與比較結果**
```
T141 G-01:guess_result p95 0.42 秒、chat_message p95 0.38 秒(門檻 ≤ 1 秒,過);中斷連線 0 條(門檻 0,過)
```

## bad example
- 同一個任務,**只寫跑過了**;沒有數字,也沒有和門檻比
```
T141 G-01:負載測試已執行,看起來正常
```

## good example
- 邊界:T141 量到 `guess_result` p95 1.3 秒,**沒過門檻;照樣勾選,但列進 Checkpoint 報告**
```
T141 G-01:guess_result p95 1.3 秒(門檻 ≤ 1 秒,沒過)→ 列進 Checkpoint 報告
```

## bad example
- 邊界:同一個結果,因為沒過門檻就**把任務標成失敗、停下這一節**;量測任務做的是量,量完了就是做完,沒過門檻是要使用者決定的事
```
T141 失敗:p95 1.3 秒超過門檻
停下:T142、T143
```
