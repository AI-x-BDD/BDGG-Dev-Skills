# Rule 1 [must] - SOP 照固定骨架寫
- 骨架是 `# SOP` → `## Phase N: <Phase 標題>` → 編號步驟,格式如下

```
# SOP
## Phase 1: <Phase 標題>
1. <動詞> <動作描述>
2. <動詞> <動作描述>;若 <條件> → 跳至 Phase N Step M。
3. ...
## Phase 2: <Phase 標題>
```

- `<動作描述>` 裡的核心動作用 `**` 包起來,寫法見〈核心動作用粗體標出〉與〈粗體照固定寫法〉
- 為什麼:固定的三層讓每一步都有「Phase N Step M」這個位址,分支與回頭才有地方可以指

## good example
- **三層都在**:`# SOP`、`## Phase N:`、編號步驟,每一步都能用「Phase N Step M」指到
```
# SOP
## Phase 1: 提出類別圖
1. Read 這次開發會動到的現有程式碼。
2. Think 設計這次開發的類別組織。
## Phase 2: 按圖實作類別
1. Write 依類別圖逐一實作類別。
```

## bad example
- 同一份流程,但**少了 Phase 這一層**,步驟也不是編號,沒辦法指到某一步
```
# 流程
- Read 這次開發會動到的現有程式碼。
- Think 設計這次開發的類別組織。
- Write 依類別圖逐一實作類別。
```

# Rule 2 [should] - Phase 依產出分組
- 一組動作做完留下一個可以檢查的產出,一組就是一個 Phase
- 為什麼:每個 Phase 結束都有東西可以檢查,流程走偏時在 Phase 交界就能發現

## good example
- Phase 1 做完留下**使用者確認過的類別圖**,Phase 2 做完留下**實作好的類別**,各有一個可以檢查的產出
```
## Phase 1: 提出類別圖
1. Read 這次開發會動到的現有程式碼。
2. Think 設計這次開發的類別組織。
3. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發。
## Phase 2: 按圖實作類別
1. Think 排出開發順序。
2. Write 依這個順序逐一實作類別。
```

## bad example
- 同樣五步,但**兩個產出擠在一個 Phase**,類別圖有沒有確認過,中途沒有地方可以檢查
```
## Phase 1: 完成開發
1. Read 這次開發會動到的現有程式碼。
2. Think 設計這次開發的類別組織。
3. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發。
4. Think 排出開發順序。
5. Write 依這個順序逐一實作類別。
```

## good example
- 邊界:「排出開發順序」是一個決定,但**做完沒有留下可以檢查的東西**,所以留在實作的 Phase 裡當第一步
```
## Phase 2: 按圖實作類別
1. Think 排出開發順序。
2. Write 依這個順序逐一實作類別。
```

## bad example
- 邊界:同樣兩步,但把這個決定**獨立成一個 Phase**;它結束時手上沒有任何可以檢查的產出
```
## Phase 2: 排出開發順序
1. Think 排出開發順序。
## Phase 3: 按圖實作類別
1. Write 依這個順序逐一實作類別。
```

# Rule 3 [must] - Phase 標題是「動詞 + 受詞」
- 受詞就是這個 Phase 的產出
- 為什麼:只讀標題就要知道這個 Phase 做完會留下什麼

## good example
- 受詞是「類別圖」「類別」,**看標題就知道這個 Phase 做完會留下什麼**
```
## Phase 1: 提出類別圖
## Phase 2: 按圖實作類別
```

## bad example
- 同樣兩個 Phase,但**標題只有名詞**,看不出做完會留下什麼
```
## Phase 1: 設計階段
## Phase 2: 開發階段
```

# Rule 4 [must] - 步驟以動詞表的動詞開頭
- 每一步的第一個詞必須是下表的動詞之一

| 動詞 | 意思 | 流程上的效果 |
|---|---|---|
| Read | 讀檔、讀指令輸出 | 只觀察,不改變任何東西 |
| Write | 寫檔、改檔 | 留下檔案變更 |
| Think | 判斷、分組、決定 | 不碰檔案 |
| Ask | 問使用者並等回答 | 流程在這裡暫停 |
| Delegate | 把職責轉交給 script、其他 skill 或 subagent | 職責移出本 skill |

- 為什麼:動詞決定這一步對流程的效果,用了表外的詞,就看不出這一步會不會改東西、會不會暫停

## good example
- 兩步的第一個詞**都查得到動詞表**,知道第 1 步只觀察、第 2 步不碰檔案
```
1. Read 這次開發會動到的現有程式碼。
2. Think 設計這次開發的類別組織。
```

## bad example
- 同樣兩步,但**「分析」「設計」不在動詞表**,看不出哪一步只觀察、哪一步會改東西
```
1. 分析這次開發會動到的現有程式碼。
2. 設計這次開發的類別組織。
```

# Rule 5 [must] - 一步只做一件事
- 要兩個動詞才講得完,就拆成兩步
- 為什麼:開頭的動詞只有一個,第二件事會被它蓋住,只讀動詞的人看不到

## good example
- **設計與提問拆成兩步**,各有自己的動詞
```
2. Think 設計這次開發的類別組織。
3. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發。
```

## bad example
- 同一段流程,但**設計與提問塞在同一步**,開頭的 Think 蓋住了後面的提問
```
2. Think 設計這次開發的類別組織,並用 Mermaid 提出設計問使用者是否可以進入開發。
```

## good example
- 邊界:同一個動詞作用在兩個對象,**仍然是一件事**
```
1. Read 這次開發會動到的現有程式碼與測試。
```

## bad example
- 邊界:只多了半句,但「挑出」是判斷,**已經是第二件事**,要拆成 Read 與 Think 兩步
```
1. Read 這次開發會動到的現有程式碼,挑出要改的類別。
```

## good example
- 邊界:「依 `rules/…`」只是指向細節的指標,**這一步做的事仍然只有 Write**
```
2. Write 依 `rules/SOP-格式規範.md` 把使用者要的流程寫成目標 skill 的 `# SOP`。
```

## bad example
- 邊界:同樣提到 Rule File,但多了「整理出重點」這個判斷,**已經是第二件事**
```
2. Write 依 `rules/SOP-格式規範.md` 整理出重點,再把使用者要的流程寫成目標 skill 的 `# SOP`。
```

# Rule 6 [must] - 一步只有一行
- 一行放不下的細節放到 SOP 以外的 section、`rules/` 或 `templates/`,步驟裡只留指過去的名稱
- 為什麼:細節掛在步驟底下,流程就被淹沒,SOP 沒辦法一眼掃完

## good example
- 設計時要守的細節放在 `# 設計原則` section,**步驟裡只留名稱**
```
2. Think 依〈設計原則〉設計這次開發的類別組織。
```

## bad example
- 同一步,但**細節直接掛在步驟底下**,步驟不再是一行
```
2. Think 設計這次開發的類別組織。
   - 每個類別只有一個職責
   - 相依方向由外層指向內層
   - 不超過七個類別
```

# Rule 7 [must] - 分支與回頭只寫在行尾
- 寫法固定為 `;若 <條件> → 跳至 Phase N Step M。`;流程走到這一步就該停時,寫成 `;若 <條件> → 結束。`
- 不用巢狀清單表達分支
- 天然冪等步驟不設跳轉（避免防禦性旁路）：若下一步驟在條件未滿足時自然無動作（例如處理 0 筆資料、不產生額外修改），應平鋪作為主線順序執行，不應加設前置 bypass 跳轉。跳轉僅用於「回退修正 (Rework Loop)」、「業務分流 (Routing)」與「提前終止 (Early Exit)」
- 正向條件優先：條件應描述積極發生的異常或分流狀態（例如 `若有 must 不過`、`若使用者要修改`），避免用「若沒有...」等否定句引導 bypass
- 為什麼:巢狀的分支沒有編號可以指,主線也不再是一直線;該停卻只能寫「跳至」,執行的人會被帶到一個用不到的步驟再做一次;替天然冪等步驟設跳轉會切斷主線,並在流程圖上製造不必要的負向判斷菱形節點

## good example
- 回頭**寫在行尾**,而且指明跳到哪一步
```
3. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發;若使用者要修改 → 跳至 Phase 1 Step 2。
```

## bad example
- 同一步,但**分支寫成巢狀清單**,「回到上面」也沒有指明是哪一步
```
3. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發。
   - 可以:繼續下一步
   - 要修改:回到上面重新設計
```

## good example
- 邊界:這次開發不會動到任何類別時流程就該停,**行尾寫成「→ 結束」**
```
1. Read 這次開發會動到的現有程式碼;若這次開發不會新增或修改任何類別 → 結束。
```

## bad example
- 邊界:同一步,為了套用「跳至」而**指到最後一步**;沒有類別可以實作,那一步卻照樣被執行
```
1. Read 這次開發會動到的現有程式碼;若這次開發不會新增或修改任何類別 → 跳至 Phase 2 Step 2。
```

## good example
- 邊界:下一步驟自然是冪等操作（例如替用得到的步驟加上指標,若無指標需要加上則不變動任何檔案）,**不設跳轉,平鋪順序執行**
```
2. Write 依 `rules/SOP-格式規範.md` 把使用者要的流程寫成目標 skill 的 `# SOP`。
3. Write 依 `rules/SOP-按需載入-格式規範.md` 替用得到的步驟寫上指標。
```

## bad example
- 邊界:同一步,但替天然冪等的下一步驟**加設了防禦性跳轉**;主線被打斷,流程圖上也會多出多餘的負向判斷菱形節點
```
2. Write 依 `rules/SOP-格式規範.md` 把使用者要的流程寫成目標 skill 的 `# SOP`;若沒有步驟用得到 `rules/`、`templates/` 或 `scripts/` 底下的檔 → 跳至 Phase 1 Step 4。
3. Write 依 `rules/SOP-按需載入-格式規範.md` 替用得到的步驟寫上指標。
```

# Rule 8 [must] - 只讀標題與動詞就能複述流程
- 只讀 Phase 標題與每一步的動詞,就能複述整個流程
- 所以每一步的動詞要對得上它在〈步驟以動詞表的動詞開頭〉表裡的效果
- 為什麼:SOP 是拿來快速掌握流程的,要讀完每一行才看得懂,就跟沒有結構一樣

## good example
- 只讀標題與動詞是「提出類別圖:Read → Think → Ask」,**看得出流程在第 3 步停下來等使用者**
```
## Phase 1: 提出類別圖
1. Read 這次開發會動到的現有程式碼。
2. Think 設計這次開發的類別組織。
3. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發。
```

## bad example
- 同樣三步,但第 3 步其實在等使用者,動詞卻寫 Think;只讀動詞是「Read → Think → Think」,**看不出流程會暫停**
```
## Phase 1: 提出類別圖
1. Read 這次開發會動到的現有程式碼。
2. Think 設計這次開發的類別組織。
3. Think 用 Mermaid 提出設計,等使用者說可以再進入開發。
```

# Rule 9 [must] - SOP 走最短可執行路徑
- 拿掉某一步之後流程仍然做得完、產出也不變,那一步就不該存在
- 為什麼:每多一步,執行的人就多一個要判斷「這裡要做什麼」的地方,真正必要的步驟也更容易被淹沒

## good example
- 三步**每一步拿掉,類別圖就提不出來**
```
## Phase 1: 提出類別圖
1. Read 這次開發會動到的現有程式碼。
2. Think 設計這次開發的類別組織。
3. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發。
```

## bad example
- 同一段流程多了兩步;**拿掉「確認需求」「整理內容」,類別圖還是一樣提得出來**
```
## Phase 1: 提出類別圖
1. Think 確認使用者的需求。
2. Read 這次開發會動到的現有程式碼。
3. Think 整理剛才讀到的內容。
4. Think 設計這次開發的類別組織。
5. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發。
```

## good example
- 邊界:「讀回檔案」拿掉之後流程一樣走得完,但**把關紀錄對照的會變成草稿而不是檔案,產出變了**,所以這一步要留
```
## Phase 2: 列出把關紀錄
1. Read 剛寫進目標 skill 的 `# SOP`。
2. Think 依 `rules/把關紀錄-格式規範.md` 列出把關紀錄。
```

## bad example
- 邊界:為了更短把讀回那一步也拿掉;流程還是做得完,但**產出已經不一樣**
```
## Phase 2: 列出把關紀錄
1. Think 依 `rules/把關紀錄-格式規範.md` 列出把關紀錄。
```

# Rule 10 [should] - 核心動作用粗體標出
- 每一步的動作描述裡,用 `**` 把這一步的核心動作包起來;流程視覺圖的節點與時序圖的訊息只顯示動詞與這一段
- 核心動作是原句裡連續的一段字,單獨接在動詞後面讀,也看得出這一步在做什麼
- 粗體只是加在原句上的記號,不為了標它而刪改句子裡其他的字;原句裡標不出這樣的一段時可以不標,圖上會顯示整句
- 為什麼:圖上放不下整句,交給腳本去截只會留下句子的前半,而這一步真正在做的事常常在句尾;由寫的人標出來,圖上顯示的才是重點,給執行的人看的句子也不必為了畫圖而刪短

## good example
- 兩步各標出**單獨讀也看得懂的那一段**;圖上是「2. Think:設計這次開發的類別組織」「3. Ask:提出設計」
```
2. Think **設計這次開發的類別組織**。
3. Ask 用 Mermaid **提出設計**,問使用者是否可以進入開發;若使用者要修改 → 跳至 Phase 1 Step 2。
```

## bad example
- 同樣兩步,但**標的是修飾的字**;圖上變成「2. Think:這次開發」「3. Ask:用 Mermaid」,看不出這兩步在做什麼
```
2. Think 設計**這次開發**的類別組織。
3. Ask **用 Mermaid** 提出設計,問使用者是否可以進入開發;若使用者要修改 → 跳至 Phase 1 Step 2。
```

## good example
- 邊界:句子的前半在交代要交出去的東西,**要對方做的事在句尾**,標的是句尾那一段
```
2. Delegate 把類別圖與這次的需求交給不帶這場對話脈絡的 subagent,**審查類別圖漏掉的相依**。
```

## bad example
- 邊界:同一步,標了最先出現的那一段;它是連續的字、也不長,但**單獨讀只知道有東西要交出去**,不知道要對方做什麼
```
2. Delegate **把類別圖與這次的需求**交給不帶這場對話脈絡的 subagent,審查類別圖漏掉的相依。
```

## good example
- 邊界:要讀的三樣東西並列,標哪一段都會漏掉另外兩樣;**不標**,圖上顯示整句
```
1. Read 這次開發會動到的現有程式碼、測試與上一次確認過的類別圖。
```

## bad example
- 邊界:同一步,為了標得出短短的一段而**把另外兩樣從句子裡刪掉**;圖變短了,執行的人也不會再去讀測試與上一次確認過的類別圖
```
1. Read **這次開發會動到的現有程式碼**。
```

# Rule 11 [must] - 粗體照固定寫法
- 〈核心動作用粗體標出〉的粗體,一步最多一段,寫在動作描述裡,不寫在行尾的條件裡
- 一段不超過 36 個半形字寬:全形字算 2,反引號不算
- 資源的指標與 `uv run` 指令放在粗體外面
- 粗體以標點、引號或反引號開頭時,它的前面是空白或標點;以這些字結尾時,它的後面是空白或標點
- 為什麼:圖上的標籤是腳本照這一段取出來的,多於一段不知道該取哪一段,太長則節點放不下;開頭或結尾是標點、外側又緊接著文字時,Markdown 不會把它當成粗體,讀 SOP 的人看到的是字面上的 `**`

## good example
- 這一步**只標了一段,而且在動作描述裡**
```
3. Ask 用 Mermaid **提出設計**,問使用者是否可以進入開發;若使用者要修改 → 跳至 Phase 1 Step 2。
```

## bad example
- 同一步,但**行尾的條件也標了一段**;一步有兩段粗體,腳本不知道圖上該顯示哪一段
```
3. Ask 用 Mermaid **提出設計**,問使用者是否可以進入開發;若**使用者要修改** → 跳至 Phase 1 Step 2。
```

## good example
- 指標**留在粗體外面**,圖上的標籤是「2. Think:設計這次開發的類別組織」
```
2. Think 依 `rules/類別圖-規範.md` **設計這次開發的類別組織**。
```

## bad example
- 同一步,但**把指標也包進粗體**;圖上的標籤多了一串路徑,寬度也超過 36 個半形字
```
2. Think **依 `rules/類別圖-規範.md` 設計這次開發的類別組織**。
```

## good example
- 邊界:粗體以反引號結尾,**後面接了一個空白**,Markdown 照樣把它當成粗體
```
3. Write 把確認過的類別圖**存成 `class-diagram.mmd`** 放到專案根目錄。
```
