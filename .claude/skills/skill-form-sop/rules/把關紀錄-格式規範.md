# Rule 1 [must] - 把關紀錄逐條列出判定
- SOP 規範的每條 Rule 在紀錄裡各佔一列,格式如下

```
| Rule | 強度 | 判定 | 依據 |
|---|---|---|---|
| <SOP 規範的 Rule 名稱> | <must 或 should> | <過 或 不過> | <看了 SOP 的哪裡、看到什麼> |
```

- 為什麼:只寫一句「都過」,使用者無從知道是不是每一條都真的看過,漏看的那一條也不會留下痕跡

## good example
- **10 條 Rule 各有一列**,每一列都有自己的判定與依據,少看哪一條一眼就看得出來
```
| Rule | 強度 | 判定 | 依據 |
|---|---|---|---|
| SOP 照固定骨架寫 | must | 過 | `# SOP` 底下是 Phase 1、Phase 2,兩個 Phase 都是編號步驟 |
| Phase 依產出分組 | should | 過 | Phase 1 留下確認過的類別圖,Phase 2 留下實作好的類別 |
| Phase 標題是「動詞 + 受詞」 | must | 過 | Phase 1「提出類別圖」、Phase 2「按圖實作類別」 |
| 步驟以動詞表的動詞開頭 | must | 過 | Phase 1 Step 1–3 是 Read、Think、Ask;Phase 2 Step 1–2 是 Think、Write |
| 一步只做一件事 | must | 過 | Phase 1 Step 1–3、Phase 2 Step 1–2 都只有開頭那一個動作 |
| 一步只有一行 | must | 過 | 五步都是一行,底下沒有掛細節 |
| 分支與回頭只寫在行尾 | must | 過 | Phase 1 Step 3、Phase 2 Step 2 的回頭都寫成「;若 … → 跳至 Phase 1 Step 2。」 |
| 只讀標題與動詞就能複述流程 | must | 過 | 讀出來是「提出類別圖:Read → Think → Ask;按圖實作類別:Think → Write」 |
| Rule File 只在用到它的那一步點名 | must | 過 | Phase 1 Step 1–3、Phase 2 Step 1–2 都沒有用到 Rule File,沒有路徑需要點名 |
| SOP 走最短可執行路徑 | must | 過 | 拿掉 Phase 1 任何一步就提不出類別圖;拿掉 Phase 2 Step 1 實作順序沒有依據,拿掉 Step 2 沒有產出 |
```

## bad example
- 同一份 SOP、同樣的結論,但**只有一句話**;哪幾條看過、各自看了哪裡,完全查不到
```
逐條對照 SOP 規範,10 條都過。
```

# Rule 2 [must] - 對照寫進檔案後的 SOP
- 列把關紀錄之前先把目標 skill 的 SKILL.md 讀回來,對照的是檔案裡的 `# SOP`
- 為什麼:腦中的草稿和實際寫進檔案的內容可能不一樣,而使用者拿到的是檔案

## good example
- 寫完之後**把檔案讀回來才對照**,所以看得到檔案裡沒被換掉的舊步驟
```
1. 把新的 `# SOP` 寫進 SKILL.md,但實際上只換掉了 Phase 1。
2. 讀回 SKILL.md,看到 Phase 2 Step 1 還是舊的「分析相依關係,排出開發順序。」
3. 把關紀錄:〈步驟以動詞表的動詞開頭〉不過,Phase 2 Step 1 開頭是「分析」。
```

## bad example
- 同一個情況,但**對照的是剛才寫的草稿**;草稿裡沒有問題,檔案裡的舊步驟沒有人看到
```
1. 把新的 `# SOP` 寫進 SKILL.md,但實際上只換掉了 Phase 1。
2. 把關紀錄:依剛才寫的草稿,〈步驟以動詞表的動詞開頭〉過,五步都以動詞表的動詞開頭。
```

# Rule 3 [must] - 每個判定指到 SOP 的位置
- 〈把關紀錄逐條列出判定〉的依據欄寫出看的是哪裡(Phase N Step M 或 Phase N 的標題),以及在那裡看到什麼
- 為什麼:沒有位置的判定沒辦法複查;判定為不過時,回頭改的人也不知道要改哪一行

## good example
- 依據**指到 Phase 1 Step 1,並寫出那裡的詞**,要複查或要改都找得到
```
| 步驟以動詞表的動詞開頭 | must | 不過 | Phase 1 Step 1 開頭是「分析」,不在動詞表 |
```

## bad example
- 同一個判定,但依據**只把規則反過來講一次**,沒說是哪一步
```
| 步驟以動詞表的動詞開頭 | must | 不過 | 有步驟沒有用動詞表的動詞開頭 |
```

## good example
- 邊界:這條 Rule 管的是整份 SOP,沒有單一步驟可以指,但依據仍然**寫出實際讀出來的結果**
```
| 只讀標題與動詞就能複述流程 | must | 過 | 讀出來是「提出類別圖:Read → Think → Ask;按圖實作類別:Think → Write」 |
```

## bad example
- 邊界:同一個判定,因為「是整體的規則」就**只寫感想**,沒辦法複查到底讀出了什麼
```
| 只讀標題與動詞就能複述流程 | must | 過 | 整體流程清楚易懂 |
```

# Rule 4 [must] - 不過的處理依強度決定
- 強度寫在 SOP 規範每條 Rule 的標題裡,判定為不過時依下表處理

| 強度 | 判定為不過時 |
|---|---|
| must | 回頭改 SOP,不能放行 |
| should | 可以放行,但依據欄要寫出放行的理由 |

- 為什麼:沒有這張表,每條不過看起來一樣重,把關的人不是全部擋下,就是自己挑著放行

## good example
- **should 的不過附了放行理由,must 的不過讓整份回頭改**
```
| Phase 依產出分組 | should | 不過 | Phase 1「確認工作區乾淨」做完沒有產出;放行理由:不乾淨就整個流程都不做,需要一個獨立的關卡 |
| 一步只做一件事 | must | 不過 | Phase 2 Step 1「Think 設計類別組織並詢問使用者」有設計與提問兩件事 |

結論:有 must 不過,回頭改 Phase 2 Step 1。
```

## bad example
- 同樣兩列,但 **should 的不過沒有理由,must 的不過被一起放行**
```
| Phase 依產出分組 | should | 不過 | Phase 1「確認工作區乾淨」做完沒有產出 |
| 一步只做一件事 | must | 不過 | Phase 2 Step 1「Think 設計類別組織並詢問使用者」有設計與提問兩件事 |

結論:只有兩條不過,整體可以接受,放行。
```

## good example
- 邊界:放行理由說明了**這個情況為什麼和那條 Rule 要防的事不衝突**
```
| Phase 依產出分組 | should | 不過 | Phase 1「確認工作區乾淨」做完沒有產出;放行理由:不乾淨就整個流程都不做,需要一個獨立的關卡 |
```

## bad example
- 邊界:同一列也寫了理由,但**理由只是不想改**,換成任何一條 Rule 都能套用
```
| Phase 依產出分組 | should | 不過 | Phase 1「確認工作區乾淨」做完沒有產出;放行理由:這樣分比較順 |
```
