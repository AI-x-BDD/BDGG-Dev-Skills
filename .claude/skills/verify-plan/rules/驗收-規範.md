# Rule 1 [must] - 每個替身都對應一次不用它的實跑
- 自動測試用假工具、假服務或假的前端函式庫碰到的行為,要有一項用真的元件走完同一條路徑
- 真的元件拿不到時,照實寫「無法實跑」與原因,通過條件列進待驗證,不寫成已驗證
- 為什麼:替身是照作者對工具的理解寫的,理解錯了測試照樣全綠;訂閱 bug 靠假 yt-dlp 過關,舊工作頁點不進去也要到真瀏覽器才現形

## good example
- 測試用假 yt-dlp,**另有一項讓真的 yt-dlp 讀真的頻道**
```
| V2 | SC-003 | yt-dlp | tests/fixtures/fake_ytdlp | 真的 yt-dlp 讀一個公開頻道 |
```

## bad example
- 同一項,**實跑還是用假工具**,只是換到容器裡跑;對工具的誤解一樣驗不出來
```
| V2 | SC-003 | yt-dlp | tests/fixtures/fake_ytdlp | 容器裡跑 pytest,用 fake_ytdlp |
```

## good example
- 邊界:純函式沒有外部元件,**替身欄寫「無」**,實跑只要照 SC 的條件量
```
| V3 | SC-001 | 替換規則 | 無 | 用沒調過規則的影片跑,逐筆判定 |
```

## bad example
- 邊界:同一個純函式,**硬要開瀏覽器走一次**當驗收;正確率要看逐筆結果,瀏覽器什麼都沒多驗到
```
| V3 | SC-001 | 替換規則 | 無 | 用 Playwright 打開工作頁確認有清單 |
```

# Rule 2 [must] - 含畫面的故事有真瀏覽器的走查
- 使用者故事有畫面操作時,要有一項用真瀏覽器照驗收情境點過,通過條件寫出看到什麼
- 為什麼:路由回 200、片段含文字,不代表使用者點得到;導頁、事件順序與前端函式庫的行為只有瀏覽器看得到

## good example
- **照情境點按鈕,寫出畫面應有的結果**
```
| V5 | 故事 2 | 瀏覽器、htmx | tests 的 htmx 替身 | Playwright 撤銷一處 | 清單標「已撤銷」、逐字稿只差那一處 |
```

## bad example
- 同一個故事,**只用 HTTP 打路由**;htmx 怎麼處理回應沒有人看到
```
| V5 | 故事 2 | 瀏覽器、htmx | tests 的 htmx 替身 | curl POST undo | 回 200 |
```

# Rule 3 [must] - 寫出副作用與護欄
- 每項寫出會寫到哪裡、呼叫哪些服務,以及防止碰到正式資料的做法;會動到正式資料或共用服務的,交給使用者同意
- 為什麼:驗收要越真實越好,也就越容易碰到真的東西;compose 的 project name 相同時,照常 `up` 就會對正式資料庫跑 migration

## good example
- **寫出暫存 volume 與不用的指令**
```
副作用與護欄:只寫 volume wln005-verify;用 docker run --rm,不用 compose up,不掛正式 volume
```

## bad example
- 同一項,**只寫「小心不要動到正式資料」**;沒有說怎麼做,實跑的人還是會照常 `up`
```
副作用與護欄:小心不要動到正式資料
```

# Rule 4 [must] - 寫出判定者與樣本來源
- 要人判斷結果的項目寫出判定者;判定者是 AI 時標明使用者尚未複核;樣本寫出是否用來調整過規則
- 為什麼:AI 逐筆判定的 96% 和使用者複核過的 96% 不是同一件事,報告裡分不出來,使用者會以為已經有人看過

## good example
- **判定者與樣本來源都寫明**
```
樣本:plan-1(未用於調整);判定者:Claude,使用者尚未複核
```

## bad example
- 同一項,**只寫數字來源是人工判定**;看不出是誰判的,也看不出樣本有沒有調過規則
```
樣本:三支影片;判定者:人工
```
