# Rule 1 [must] - 欄位對應前幾步規格檔的原文
- 理由欄點名的前幾步規格檔(OpenAPI、AsyncAPI)裡已經定下的資源、欄位、enum 值與格式,在 DBML 裡沿用同一個名稱與值;只做命名慣例的轉換(camelCase 轉 snake_case),不另取名字
- 規格檔的欄位對不上要存的資料、或照原文會和需求衝突時,不自行改名,把衝突列進交出時的待決問題
- 為什麼:API 回應的欄位是從這些表讀出來的;兩邊各取一套名字與 enum 值,實作的人得自己寫一層對照,對錯的那一次就是把 `paid` 當成 `completed` 回給買家

## good example
- API 規格的 `Order.status` 是 `pending`、`paid`、`cancelled`;**enum 照原值,欄位只從 camelCase 轉成 snake_case**
```
Enum order_status {
  pending [note: '已建立,等待付款']
  paid [note: '金流通知驗簽通過']
  cancelled [note: '付款連結 15 分鐘內未付款']
}

Table orders {
  id varchar(12) [pk, note: '對外的 orderId,格式 ORD- + 8 碼英數']
  shipping_address_id varchar(32) [not null]
  Note: '需求: FR-007、FR-008、FR-011'
}
```

## bad example
- 同一張表,但**另取了 enum 值與欄位名**;API 回的是 `paid`,資料庫存的是 `completed`,中間得多一層對照
```
Enum order_status {
  waiting [note: '等待付款']
  completed [note: '已付款']
  expired [note: '逾時']
}

Table orders {
  order_no varchar(12) [pk]
  ship_to varchar(32) [not null]
  Note: '需求: FR-007、FR-008、FR-011'
}
```

## good example
- 邊界:金流的 `MerchantTradeNo` 不是 camelCase,看起來可以照原樣保留;但**這條 Rule 允許的只有命名慣例的轉換**,轉成 `merchant_trade_no`,並在 note 註明對應的原文
```
Table payments {
  merchant_trade_no varchar(20) [pk, note: '照 S1 的 MerchantTradeNo']
  Note: '需求: FR-009、NFR-003'
}
```

## bad example
- 邊界:同一個欄位,轉換時**順手換成自己覺得比較清楚的名字**;之後要對照 S1 的通知參數,找不到 `trade_ref` 是哪一個
```
Table payments {
  trade_ref varchar(20) [pk]
  Note: '需求: FR-009、NFR-003'
}
```

# Rule 2 [must] - 需求的約束寫成 DBML 語法
- 需求裡的唯一性、必填、狀態的可選值、相依刪除的行為,寫成 DBML 本身的 `pk`、`unique`、`not null`、`Enum`、`indexes`、`Ref` 的 `delete:`,不只寫在 note 裡
- DBML 表達不了的約束(數值範圍、跨欄位的條件)寫在那個欄位的 note
- 為什麼:只寫在 note 的約束轉成 SQL 時不會變成任何限制,資料庫照樣收下重複或不合法的資料;寫成語法,轉出來的 SQL 就會擋下它

## good example
- 「一張訂單只有一筆付款」**寫成 `unique` 與一對一的 `Ref`**
```
Table payments {
  merchant_trade_no varchar(20) [pk, note: '照 S1 的 MerchantTradeNo']
  order_id varchar(12) [not null, unique]
  Note: '需求: FR-009、NFR-003'
}

Ref: payments.order_id - orders.id [delete: restrict]
```

## bad example
- 同一個約束,但**只寫在 note**;轉成 SQL 之後,同一張訂單照樣可以寫進兩筆付款
```
Table payments {
  merchant_trade_no varchar(20) [pk, note: '照 S1 的 MerchantTradeNo']
  order_id varchar(12) [not null, note: '一張訂單只能有一筆付款']
  Note: '需求: FR-009、NFR-003'
}

Ref: payments.order_id > orders.id
```

## good example
- 邊界:「數量 1 到 99」DBML 沒有對應的語法;**寫在欄位的 note**,型別與 `not null` 仍然用語法
```
Table cart_items {
  quantity integer [not null, note: '1–99,對外回 INVALID_QUANTITY']
  Note: '需求: FR-004、FR-005、FR-006'
}
```

## bad example
- 邊界:同一個欄位,因為範圍只能寫在 note,就**連必填也只寫在 note**;`not null` 明明有語法可以表達
```
Table cart_items {
  quantity integer [note: '必填,1–99']
  Note: '需求: FR-004、FR-005、FR-006'
}
```

# Rule 3 [must] - 只寫要持久化的資料
- 只為重新啟動之後還要存在的資料建表;快取、連線狀態、只活在一次請求或一條連線裡的資料不建表
- 需求說「不保留」的資料不建表
- 為什麼:多建的表沒有人會寫入或清掉,實作的人卻會以為要維護它;把連線狀態存進資料庫,每一次斷線重連都多一次寫入,還要處理行程掛掉時留下的殘值

## good example
- 購物車要在訪客關掉瀏覽器後還在,**建表**;「誰正在看這個商品」只是畫面上的即時人數,**不建表**
```
Table carts {
  id varchar(32) [pk]
  anonymous_token varchar(64) [unique]
  updated_at timestamptz [not null]
  Note: '需求: FR-004、FR-005'
}
```

## bad example
- 同一個需求,但**把即時人數也建成一張表**;每個訪客進出商品頁都要寫一次,行程重啟後表裡還留著早就離開的人
```
Table product_viewers {
  product_id varchar(32) [not null]
  session_id varchar(64) [not null]
  joined_at timestamptz [not null]
  Note: '需求: FR-003'
}
```

## good example
- 邊界:WebSocket 的訂閱是連線狀態,看起來不該建表;但**需求要求斷線後重連還能補收漏掉的付款通知**,通知本身要持久化,所以為通知建表,連線本身仍然不建
```
Table order_notifications {
  id varchar(32) [pk]
  order_id varchar(12) [not null]
  sent_at timestamptz [note: '尚未送達為 null']
  Note: '需求: FR-010'
}
```

## bad example
- 邊界:同一個需求,為了補收通知**把每條連線也建成一張表**;要補收的是通知,連線在行程重啟之後已經不存在
```
Table ws_connections {
  connection_id varchar(64) [pk]
  buyer_id varchar(32) [not null]
  connected_at timestamptz [not null]
  Note: '需求: FR-010'
}
```
