# Rule 1 [must] - 一次展開只動一步與一個 Rule File
- 展開前後的差異只有兩處:指定那一步的那一行,以及那一步的 Rule File,樣子如下

```
首次展開(那一步還沒有點名 Rule File)
  before  <M>. <動詞> <動作描述>
          rules/ 底下沒有這一步的 Rule File
  after   <M>. <動詞> 依 `rules/<檔名>` <動作描述>
          rules/<檔名>   ← 新開

再次展開(那一步已經點名 Rule File)
  before  <M>. <動詞> 依 `rules/<檔名>` <動作描述>
          rules/<檔名>   ← 已有的 Rule
  after   <M>. <動詞> 依 `rules/<檔名>` <動作描述>   ← 這一行不變
          rules/<檔名>   ← 多了這次的 Rule
```

- 目標 skill 的其他步驟、其他 Rule File 都不動;要展開另一步,就再跑一次
- 為什麼:規則是流程跑過之後才一步一步補上的,一次只動一步,補上之後流程哪裡變了,才對得回是哪一步的 Rule 造成的

## good example
- 使用者指定 Phase 1 Step 2;**前後只差那一行與一個新檔**,Step 1、Step 3 一字未動
```
before
  ## Phase 1: 提出類別圖
  1. Read 這次開發會動到的現有程式碼。
  2. Think 設計這次開發的類別組織。
  3. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發。

after
  ## Phase 1: 提出類別圖
  1. Read 這次開發會動到的現有程式碼。
  2. Think 依 `rules/類別圖-規範.md` 設計這次開發的類別組織。
  3. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發。

  rules/
  └── 類別圖-規範.md   ← 新開
```

## bad example
- 同一次展開,但**順手把 Step 3 也展開了**;使用者只指定了 Step 2,這一次就動了兩步與兩個檔
```
before
  ## Phase 1: 提出類別圖
  1. Read 這次開發會動到的現有程式碼。
  2. Think 設計這次開發的類別組織。
  3. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發。

after
  ## Phase 1: 提出類別圖
  1. Read 這次開發會動到的現有程式碼。
  2. Think 依 `rules/類別圖-規範.md` 設計這次開發的類別組織。
  3. Ask 依 `rules/確認-規範.md` 用 Mermaid 提出設計,問使用者是否可以進入開發。

  rules/
  ├── 類別圖-規範.md   ← 新開
  └── 確認-規範.md     ← 也新開
```

# Rule 2 [must] - Rule 只來自使用者說要把關的事
- 使用者說要把關的每一件事各寫成 Rule,使用者沒提的要求不寫進 Rule File
- 每條 Rule 的名稱、強度、為什麼與 example 由 agent 補上
- 展開時想到其他值得把關的事,只在回覆裡提,由使用者決定要不要再展開一次
- 為什麼:agent 推測出來的規則沒有人實際遇過,寫進去之後,那一步每次執行卻都要載入並對照它

## good example
- 使用者講了一件事,**Rule File 就只多一條**;想到的另一件事留在回覆裡
```
使用者:Phase 1 Step 2 畫出來的類別圖常常太大,超過七個類別就看不懂。

rules/類別圖-規範.md
  # Rule 1 [must] - 類別圖不超過七個類別

回覆:另外想到「相依方向」也可以把關,這次沒有寫進去,需要的話再展開一次。
```

## bad example
- 同一句話,但 **Rule File 多了兩條使用者沒提過的 Rule**,之後每次設計類別組織都要對照它們
```
使用者:Phase 1 Step 2 畫出來的類別圖常常太大,超過七個類別就看不懂。

rules/類別圖-規範.md
  # Rule 1 [must] - 類別圖不超過七個類別
  # Rule 2 [must] - 每個類別只有一個職責
  # Rule 3 [must] - 相依方向由外層指向內層
```

## good example
- 邊界:名稱、強度、為什麼都是 agent 補的,但**要求本身還是使用者那一句**
```
# Rule 1 [must] - 類別圖不超過七個類別
- 一張類別圖最多七個類別
- 為什麼:超過七個,看圖的人就看不懂類別之間的關係
```

## bad example
- 邊界:同樣只有一條 Rule,看起來沒有多加,但 **desc 多了一個使用者沒提過的要求**
```
# Rule 1 [must] - 類別圖不超過七個類別
- 一張類別圖最多七個類別
- 每個類別最多五個方法
- 為什麼:超過七個,看圖的人就看不懂類別之間的關係
```

# Rule 3 [should] - 新開或疊加看那一步有沒有點名 Rule File
- 指定那一步的行內已經有「依 `rules/<檔名>`」,這次的 Rule 就接在那個檔的最後;沒有,才新開一個 Rule File
- 為什麼:同一步要讀的 Rule 拆成兩個檔,沒有任何一次執行能少讀,只是多一個檔要點名、要維護

## good example
- 那一步已經點名 `類別圖-規範.md`,**這次的 Rule 接在同一個檔的最後**,SOP 那一行不變
```
使用者:Phase 1 Step 2 還要把關「每條關係都標出方向」。

before
  2. Think 依 `rules/類別圖-規範.md` 設計這次開發的類別組織。

  rules/類別圖-規範.md
    # Rule 1 [must] - 類別圖不超過七個類別

after
  2. Think 依 `rules/類別圖-規範.md` 設計這次開發的類別組織。

  rules/類別圖-規範.md
    # Rule 1 [must] - 類別圖不超過七個類別
    # Rule 2 [must] - 每條關係都標出方向   ← 這次疊加
```

## bad example
- 同一次展開,但**替這條 Rule 另開一個檔**;同一步現在要點名、要讀兩個檔
```
使用者:Phase 1 Step 2 還要把關「每條關係都標出方向」。

before
  2. Think 依 `rules/類別圖-規範.md` 設計這次開發的類別組織。

  rules/類別圖-規範.md
    # Rule 1 [must] - 類別圖不超過七個類別

after
  2. Think 依 `rules/類別圖-規範.md` 與 `rules/類別圖-關係-規範.md` 設計這次開發的類別組織。

  rules/類別圖-規範.md
    # Rule 1 [must] - 類別圖不超過七個類別

  rules/類別圖-關係-規範.md   ← 新開
    # Rule 1 [must] - 每條關係都標出方向
```

# Rule 4 [must] - 新開的 Rule File 以那一步的產出物命名
- 檔名以那一步做完留下的產出物開頭,不是以這次寫進去的 Rule 的主題開頭
- 為什麼:之後疊加進同一個檔的,會是那一步的其他把關;檔名綁在第一條 Rule 的主題上,第二條就放不進去

## good example
- 邊界:這次只有「不超過七個類別」一條 Rule,但**檔名取的是那一步的產出物「類別圖」**,之後關係、命名的 Rule 都放得進來
```
2. Think 依 `rules/類別圖-規範.md` 設計這次開發的類別組織。

rules/
└── 類別圖-規範.md
    # Rule 1 [must] - 類別圖不超過七個類別
```

## bad example
- 邊界:同一次展開,檔名取自這次那一條 Rule,看起來更精確,但**下一條「每條關係都標出方向」就放不進這個檔**
```
2. Think 依 `rules/類別數量-規範.md` 設計這次開發的類別組織。

rules/
└── 類別數量-規範.md
    # Rule 1 [must] - 類別圖不超過七個類別
```

# Rule 5 [must] - 指定那一步只多出 Rule File 的指標
- 〈一次展開只動一步與一個 Rule File〉的首次展開,只在那一步的動詞後面接上「依 `rules/<檔名>`」;編號、動詞與原本的動作描述照原樣
- Rule 的內容留在 Rule File,不寫進步驟
- 為什麼:使用者同意的是替這一步加把關,不是改這一步做的事;編號或動詞一變,別處的「跳至 Phase N Step M」也會跟著指錯

## good example
- 前後**只差「依 `rules/類別圖-規範.md`」這一段**,原本那一句一字未動
```
before  2. Think 設計這次開發的類別組織。
after   2. Think 依 `rules/類別圖-規範.md` 設計這次開發的類別組織。
```

## bad example
- 同一次展開,但**把 Rule 的內容也寫進了步驟**,動作描述不再是原本那一句
```
before  2. Think 設計這次開發的類別組織。
after   2. Think 依 `rules/類別圖-規範.md` 設計不超過七個類別的類別組織。
```
