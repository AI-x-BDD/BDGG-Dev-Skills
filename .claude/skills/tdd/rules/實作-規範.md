# Rule 1 [must] - 只寫讓目前這個測試通過所需的程式碼
- 這一輪的程式碼只為了讓剛寫的那個測試從紅燈變綠燈
- 不預先做之後的測試才會要求的行為,也不加需求沒提、自己推測出來的功能
- 為什麼:沒有測試逼出來的程式碼沒有任何紅燈證明它需要、也沒有測試保護它;下一輪學到的事常常讓預先寫的那段變成錯的或多餘的

## good example
- 測試要求「沒按運算子就按 `=` 時保留畫面上的數字」;**只補上沒有運算元時的那一個分支**
```python
elif button_id == "=":
    if self._operand is not None:
        self._display = str(add(self._operand, int(self._display)))
    self._starting_new_entry = True
```

## bad example
- 同一個測試,但**順手加了減法與乘法**;沒有任何測試要求它們,也沒有紅燈證明它們算得對
```python
elif button_id == "=":
    if self._operand is None:
        pass
    elif self._operator == "-":
        self._display = str(self._operand - int(self._display))
    elif self._operator == "*":
        self._display = str(self._operand * int(self._display))
    else:
        self._display = str(add(self._operand, int(self._display)))
    self._starting_new_entry = True
```

## good example
- 邊界:測試只用了一位數;**多位數本來就由既有的 `_enter_digit` 處理,不需要為它寫任何東西**,這一輪就只有那一個分支
```python
elif button_id == "=":
    if self._operand is not None:
        self._display = str(add(self._operand, int(self._display)))
    self._starting_new_entry = True
```

## bad example
- 邊界:同一個測試,因為「連按兩次 `=` 等一下也會測」就**先把重複上一次運算的邏輯寫進去**;那是下一個測試才會要求的行為,現在沒有紅燈證明它對
```python
elif button_id == "=":
    if self._operand is not None:
        self._last_addend = int(self._display)
        self._display = str(add(self._operand, self._last_addend))
    elif self._last_addend is not None:
        self._display = str(add(int(self._display), self._last_addend))
    self._starting_new_entry = True
```

# Rule 2 [must] - 這個循環裡不重構
- 紅燈到綠燈的循環只改讓測試通過所需的地方,不改名、不搬移、不抽函式、不整理和這個測試無關的程式碼
- 看到值得重構的地方記下來,留給審查階段(`code-review`)
- 為什麼:重構和修正混在同一輪,綠燈時分不出是哪一個改動讓它通過;測試失敗時,也分不出是修正錯了還是重構弄壞了

## good example
- 修好 `=` 的分支,**`_enter_digit` 的寫法看不順眼也只記下來**
```
這一輪的改動  Calculator.press 的 "=" 分支多一個 if
記下來留給 code-review  `_enter_digit` 的兩個條件可以合併
```

## bad example
- 同一輪,**順手把 `_enter_digit` 改寫、又把 `_operand` 改名**;改完全部通過,但說不出是哪一個改動修好了 bug
```
這一輪的改動  Calculator.press 的 "=" 分支多一個 if
              `_enter_digit` 改寫成一行
              `_operand` 改名為 `_pending_value`
```

## good example
- 邊界:讓測試通過非得改到 `press` 的 `=` 分支,**那幾行是修正本身,不算重構**
```
這一輪的改動  Calculator.press 的 "=" 分支:沒有運算元時不呼叫 add
```

## bad example
- 邊界:同一個分支,改的時候**把整個 `press` 的 if/elif 換成一張按鍵對應表**;行為一樣、看起來更乾淨,但那是重構,不是讓這個測試通過所需的
```
這一輪的改動  Calculator.press 改成 self._handlers[button_id]() 查表
              新增 _on_plus、_on_equals、_on_digit 三個方法
```

# Rule 3 [should] - 外部依賴從參數注入並各給一個函式
- 碰到外部依賴(HTTP API、付款、寄信)時,從參數傳進來,不在函式裡自己建立
- 每個外部操作各給一個專用的函式,不寫成一個帶網址或選項的通用 fetch
- 為什麼:自己建立的 client 測試換不掉,只能真的打外部服務;通用 fetch 的假物件得在裡面判斷是哪一個網址,測試設定變成另一段要除錯的邏輯
- 既有程式已經用某種方式取得依賴、而且測試換得掉它時,照既有的方式寫,不為了這條在這一輪改掉它

## good example
- 匯率 client **從參數傳進來**,而且只有 `get_rate` 這一個專用操作
```python
class RatesClient:
    def get_rate(self, currency: str) -> float:
        return httpx.get(f"{RATES_URL}/rates/{currency}").json()["rate"]

def convert(amount: float, currency: str, rates_client: RatesClient) -> float:
    return amount * rates_client.get_rate(currency)
```

## bad example
- 同一個功能,但 **client 在函式裡自己建立**;測試換不掉它,每跑一次都真的打外部 API
```python
def convert(amount: float, currency: str) -> float:
    client = RatesClient()
    return amount * client.get_rate(currency)
```

## good example
- 邊界:client 有兩個外部操作;**各自一個函式**,假物件各回一種形狀就好
```python
class RatesClient:
    def get_rate(self, currency: str) -> float:
        return httpx.get(f"{RATES_URL}/rates/{currency}").json()["rate"]

    def list_currencies(self) -> list[str]:
        return httpx.get(f"{RATES_URL}/currencies").json()
```

## bad example
- 邊界:同樣是注入進來的 client,但**只給一個通用的 `fetch(path)`**;測試的假物件得在裡面判斷 path 才知道要回什麼
```python
class RatesClient:
    def fetch(self, path: str) -> dict:
        return httpx.get(f"{RATES_URL}{path}").json()

def convert(amount: float, currency: str, rates_client: RatesClient) -> float:
    return amount * rates_client.fetch(f"/rates/{currency}")["rate"]
```
