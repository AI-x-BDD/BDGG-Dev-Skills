# Rule 1 [must] - 只在使用者確認過的接縫寫測試
- 測試呼叫的介面,必須是 Phase 1 使用者確認過的接縫之一;呼叫方指定了 `testplan.md` 的案例時,是 testplan「接縫的取捨」表列出的接縫之一(使用者在 testplan 已確認過)
- 確認過的接縫底下可以寫很多個測試;要在清單以外的介面寫測試,先回頭請使用者確認那個接縫
- 為什麼:接縫是和使用者約定好的測試範圍;自己多開一個接縫,測試的工夫就落到使用者沒同意的地方,而且那個接縫可能正是他刻意不想綁死的介面

## good example
- 確認過的接縫是 `Calculator.press` 後讀 `Calculator.display`;**測試只透過這兩個介面操作與觀察**
```python
# 確認過的接縫:Calculator.press(button_id) 後讀 Calculator.display
def test_pressing_equals_without_operator_keeps_the_entered_number():
    # Arrange
    calc = Calculator()
    calc.press("7")

    # Act
    calc.press("=")

    # Assert
    assert calc.display == "7"
```

## bad example
- 同一個修正,但**測試直接呼叫 `add`**;`add` 不在確認過的清單裡
```python
# 確認過的接縫:Calculator.press(button_id) 後讀 Calculator.display
def test_add_returns_the_entered_number_when_no_operand():
    # Arrange
    entered = 7

    # Act
    result = add(0, entered)

    # Assert
    assert result == 7
```

## good example
- 邊界:這個測試驗的是另一個情況(連按兩次 `=`),但**用的仍是確認過的那個接縫**,不需要再問
```python
# 確認過的接縫:Calculator.press(button_id) 後讀 Calculator.display
def test_pressing_equals_twice_without_operator_keeps_the_entered_number():
    # Arrange
    calc = Calculator()
    calc.press("7")

    # Act
    calc.press("=")
    calc.press("=")

    # Assert
    assert calc.display == "7"
```

## bad example
- 邊界:同一個情況,改從 `add` 這個也是公開的函式去驗;**公開不等於確認過**,使用者沒同意在 `add` 上綁測試
```python
# 確認過的接縫:Calculator.press(button_id) 後讀 Calculator.display
def test_add_twice_with_no_operand_keeps_the_entered_number():
    # Arrange
    entered = 7

    # Act
    result = add(0, add(0, entered))

    # Assert
    assert result == 7
```

# Rule 2 [must] - 一次只寫一個測試
- 這一輪只新增一個測試,走完紅燈到綠燈之後,依這一輪學到的事決定下一個測試要測什麼
- 不先把預想中的測試一次寫完再去實作(水平切片)
- 為什麼:一次寫完的測試驗的是想像中的行為,綁住的是還沒寫出來的實作的形狀;每輪只寫一個,下一個測試才能回應實作時真正學到的事

## good example
- **每一輪只多一個測試**;第二個測試是第一輪綠燈之後才發現需要的
```
第 1 輪  新增 test_pressing_equals_without_operator_keeps_the_entered_number
         紅燈:TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'
         綠燈:1 passed
         學到:沒有運算元時 `=` 要保留畫面上的數字
第 2 輪  新增 test_pressing_equals_twice_without_operator_keeps_the_entered_number
```

## bad example
- 同一個修正,但**第 1 輪就把預想的三個測試全部寫好**,才開始改程式
```
第 1 輪  新增 test_pressing_equals_without_operator_keeps_the_entered_number
         新增 test_pressing_equals_twice_without_operator_keeps_the_entered_number
         新增 test_pressing_equals_on_fresh_calculator_shows_zero
         紅燈:3 failed
```

## good example
- 邊界:寫第一個測試時就想到第二個情況;**先把它記成待辦,等這一輪綠燈再寫**
```
第 1 輪  新增 test_pressing_equals_without_operator_keeps_the_entered_number
         待辦(還沒寫):連按兩次 `=`
         紅燈:TypeError ...
```

## bad example
- 邊界:同一個想法,因為「反正等一下也要寫」就**趁第一個還在紅燈時先寫進去**;第二個測試沒有機會回應第一輪學到的事
```
第 1 輪  新增 test_pressing_equals_without_operator_keeps_the_entered_number
         新增 test_pressing_equals_twice_without_operator_keeps_the_entered_number
         紅燈:2 failed
```

# Rule 3 [must] - 透過公開介面驗證行為
- 測試只透過公開介面操作與觀察:不 mock 內部協作者、不測 private 方法、不斷言呼叫次數或順序、不繞過介面去查資料庫
- 為什麼:綁在實作細節上的測試,重構時行為沒變也會壞;測試要讀起來像規格,實作整個換掉它都還成立

## good example
- 存進去的使用者**透過公開的 `get_user` 取回來驗**
```python
def test_created_user_can_be_retrieved():
    # Arrange
    user = create_user(name="Alice")

    # Act
    retrieved = get_user(user.id)

    # Assert
    assert retrieved.name == "Alice"
```

## bad example
- 同一個測試,但**繞過介面直接查資料庫**;改了表結構,行為沒變,這個測試就壞了
```python
def test_created_user_can_be_retrieved():
    # Arrange
    create_user(name="Alice")

    # Act
    row = db.execute("SELECT * FROM users WHERE name = ?", ("Alice",)).fetchone()

    # Assert
    assert row is not None
```

## good example
- 邊界:要驗的是按數字鍵的效果,實作剛好在 private 的 `_enter_digit` 裡;**仍然從 `press` 按、從 `display` 看**
```python
def test_digits_pressed_in_order_build_up_the_number():
    # Arrange
    calc = Calculator()

    # Act
    calc.press("1")
    calc.press("2")

    # Assert
    assert calc.display == "12"
```

## bad example
- 邊界:同一個測試,因為邏輯就在 `_enter_digit` 裡就**直接呼叫它、再讀 private 的 `_display`**;把 `_enter_digit` 合併回 `press`,行為沒變,這個測試就壞了
```python
def test_digits_pressed_in_order_build_up_the_number():
    # Arrange
    calc = Calculator()

    # Act
    calc._enter_digit("1")
    calc._enter_digit("2")

    # Assert
    assert calc._display == "12"
```

# Rule 4 [must] - 測試名稱寫做到什麼
- 測試名稱寫它驗證的行為(做到什麼),不寫它怎麼做(呼叫了誰、走了哪個分支、改了哪個欄位)
- 為什麼:名稱是紅燈時第一個被讀到的東西;寫成怎麼做,實作一換名稱就說錯了,讀的人也看不出壞掉的是哪一個能力

## good example
- 名稱**說的是使用者看得到的能力**:建立的使用者取得回來
```python
def test_created_user_can_be_retrieved():
    # Arrange
    user = create_user(name="Alice")

    # Act
    retrieved = get_user(user.id)

    # Assert
    assert retrieved.name == "Alice"
```

## bad example
- 同一個測試,內容一字未改,但**名稱寫的是內部呼叫了誰**;把 repository 換掉,名稱就說錯了
```python
def test_create_user_calls_repository_save():
    # Arrange
    user = create_user(name="Alice")

    # Act
    retrieved = get_user(user.id)

    # Assert
    assert retrieved.name == "Alice"
```

## good example
- 邊界:名稱裡有 `equals`、`operator` 這些介面上的按鍵,**它們是使用者操作的東西,不是實作**
```python
def test_pressing_equals_without_operator_keeps_the_entered_number():
    # Arrange
    calc = Calculator()
    calc.press("7")

    # Act
    calc.press("=")

    # Assert
    assert calc.display == "7"
```

## bad example
- 邊界:同一個測試,名稱也提到 `=`,但**講的是 operand 為 None 時跳過 `add`**;這是修法,不是行為,改成別的修法名稱就不成立
```python
def test_equals_skips_add_when_operand_is_none():
    # Arrange
    calc = Calculator()
    calc.press("7")

    # Act
    calc.press("=")

    # Assert
    assert calc.display == "7"
```

# Rule 5 [must] - 預期值來自獨立來源
- 斷言裡的預期值取自已知的字面值、手算的例子或規格,不用和程式一樣的算法在測試裡重算
- 為什麼:用同一套算法重算的預期值,程式算錯它也跟著錯,這個測試照定義永遠會過,抓不到任何錯

## good example
- 預期值是**手算好的字面值** `15`
```python
def test_order_total_is_sum_of_line_item_prices():
    # Arrange
    items = [LineItem(price=10), LineItem(price=5)]

    # Act
    total = order_total(items)

    # Assert
    assert total == 15
```

## bad example
- 同一個測試,但**預期值用和程式一樣的加總重算**;`order_total` 算錯,`expected` 也一起錯
```python
def test_order_total_is_sum_of_line_item_prices():
    # Arrange
    items = [LineItem(price=10), LineItem(price=5)]
    expected = sum(item.price for item in items)

    # Act
    total = order_total(items)

    # Assert
    assert total == expected
```

## good example
- 邊界:預期值有運算,但**算式是規格裡寫死的數字**(10 元打九折),不是重走程式的算法
```python
def test_member_discount_takes_ten_percent_off():
    # Arrange
    product = Product(price=100)

    # Act
    price = price_for_member(product)

    # Assert
    assert price == 90  # 規格:會員九折,100 → 90
```

## bad example
- 邊界:同一個測試,寫成 `price * 0.9`,看起來和規格一樣;但**這正是程式裡的那行算式**,程式改成 `* 0.8`、測試若照抄也一起改,它就抓不到
```python
def test_member_discount_takes_ten_percent_off():
    # Arrange
    product = Product(price=100)

    # Act
    price = price_for_member(product)

    # Assert
    assert price == product.price * 0.9
```

# Rule 6 [must] - 只在系統邊界 mock
- 可以 mock 的只有系統邊界:外部 API(付款、寄信、匯率)、時間與亂數;資料庫與檔案系統必要時才 mock,能用測試用的資料庫或暫存目錄就不 mock
- 自己的類別、模組與內部協作者不 mock
- 為什麼:mock 自己的模組,測的就變成「有沒有照預想的方式呼叫」,模組內部一改測試就壞;邊界以外的東西不受控制、又慢又不穩,才值得換成假的

## good example
- 匯率來自外部 HTTP API,**只把注入的匯率 client 換成假的**,`convert` 自己的計算照真的跑
```python
class FakeRatesClient:
    def get_rate(self, currency: str) -> float:
        return {"JPY": 0.2}[currency]

def test_convert_uses_the_rate_for_the_target_currency():
    # Arrange
    rates_client = FakeRatesClient()

    # Act
    converted = convert(100, "JPY", rates_client=rates_client)

    # Assert
    assert converted == 20
```

## bad example
- 同一個功能,但**連自己的 `round_money` 也 patch 掉了**;`round_money` 改了實作,這個測試照樣過,改壞了也抓不到
```python
def test_convert_uses_the_rate_for_the_target_currency(mocker):
    # Arrange
    mocker.patch("tdd_test.money.round_money", side_effect=lambda x: x)
    rates_client = FakeRatesClient()

    # Act
    converted = convert(100, "JPY", rates_client=rates_client)

    # Assert
    assert converted == 20
```

## good example
- 邊界:「今天是不是週末」來自系統時鐘,**時間是邊界**,換成固定的時鐘
```python
def test_weekend_orders_ship_on_monday():
    # Arrange
    saturday = FixedClock(date(2026, 11, 7))

    # Act
    shipped_on = shipping_date(clock=saturday)

    # Assert
    assert shipped_on == date(2026, 11, 9)
```

## bad example
- 邊界:同一個情況,改成 patch 自己的 `is_weekend`;它看起來也和時間有關,但**它是自己的函式,不是邊界**,裡面的判斷寫錯也不會被抓到
```python
def test_weekend_orders_ship_on_monday(mocker):
    # Arrange
    mocker.patch("tdd_test.shipping.is_weekend", return_value=True)

    # Act
    shipped_on = shipping_date()

    # Assert
    assert shipped_on == date(2026, 11, 9)
```

# Rule 7 [should] - 一個測試只有一個邏輯斷言
- 一個測試只驗一個行為;為了描述同一個結果可以有多行 `assert`
- 舊程式還沒有其他測試、一個流程要先整段鎖住時,可以暫時在一個測試裡驗多個結果,之後再拆
- 為什麼:一個測試驗好幾個行為,紅燈時看名稱不知道是哪一個壞了,前一個斷言失敗也會蓋住後面的

## good example
- 這個測試**只驗「連續加法的結果」這一件事**
```python
def test_adding_two_numbers_shows_their_sum():
    # Arrange
    calc = Calculator()

    # Act
    for button in ["1", "2", "+", "3", "="]:
        calc.press(button)

    # Assert
    assert calc.display == "15"
```

## bad example
- 同一個測試,**順便驗了另一個行為**(按完 `=` 再按數字會重新開始);紅燈時從名稱看不出是哪一個壞了
```python
def test_adding_two_numbers_shows_their_sum():
    # Arrange
    calc = Calculator()

    # Act
    for button in ["1", "2", "+", "3", "="]:
        calc.press(button)
    shown_after_equals = calc.display
    calc.press("4")

    # Assert
    assert shown_after_equals == "15"
    assert calc.display == "4"
```

## good example
- 邊界:兩行 `assert`,但**都在描述同一筆取回來的使用者**,仍然是一個邏輯斷言
```python
def test_created_user_can_be_retrieved():
    # Arrange
    user = create_user(name="Alice", email="alice@example.com")

    # Act
    retrieved = get_user(user.id)

    # Assert
    assert retrieved.name == "Alice"
    assert retrieved.email == "alice@example.com"
```

## bad example
- 邊界:同樣是兩行 `assert`,但第二行**驗的是另一個行為**(同名不能再建一次);它應該是另一個測試
```python
def test_created_user_can_be_retrieved():
    # Arrange
    user = create_user(name="Alice", email="alice@example.com")

    # Act
    retrieved = get_user(user.id)

    # Assert
    assert retrieved.name == "Alice"
    with pytest.raises(DuplicateUser):
        create_user(name="Alice", email="alice@example.com")
```

# Rule 8 [should] - 測試名稱用專案的領域用語
- 測試名稱用專案 `GLOSSARY.md` 與公開介面裡的詞,不另造同義詞
- 專案沒有 `GLOSSARY.md` 時,用公開介面與需求裡已經在用的詞
- 為什麼:名稱和領域用語對不上,讀測試的人得自己翻譯;同一個概念有兩種叫法,找測試的時候也搜不到

## good example
- `GLOSSARY.md` 把付款完成叫 checkout、把購物車叫 cart;**測試名稱照用這兩個詞**
```python
def test_user_can_checkout_with_valid_cart():
    # Arrange
    cart = Cart()
    cart.add(Product(price=10))

    # Act
    result = checkout(cart, payment_method=FakeCard())

    # Assert
    assert result.status == "confirmed"
```

## bad example
- 同一個測試,但**名稱改叫 purchase 與 basket**;搜 checkout 找不到它
```python
def test_user_can_purchase_with_valid_basket():
    # Arrange
    cart = Cart()
    cart.add(Product(price=10))

    # Act
    result = checkout(cart, payment_method=FakeCard())

    # Assert
    assert result.status == "confirmed"
```

## good example
- 邊界:專案沒有 `GLOSSARY.md`;**名稱用公開介面上的 `display` 與按鍵的說法**
```python
def test_pressing_equals_without_operator_keeps_the_entered_number():
    # Arrange
    calc = Calculator()
    calc.press("7")

    # Act
    calc.press("=")

    # Assert
    assert calc.display == "7"
```

## bad example
- 邊界:同一個測試,因為沒有 `GLOSSARY.md` 就**用了自己習慣的 screen、submit**;介面上沒有這兩個詞,讀的人得自己對回 `display` 與 `=`
```python
def test_submit_without_operator_keeps_screen_value():
    # Arrange
    calc = Calculator()
    calc.press("7")

    # Act
    calc.press("=")

    # Assert
    assert calc.display == "7"
```
