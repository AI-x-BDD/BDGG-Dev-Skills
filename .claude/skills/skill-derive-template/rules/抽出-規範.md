# Rule 1 [must] - 約束生成內容格式的步驟才抽樣板
- 使用者要固定的是那一步生成的內容長什麼樣子(有哪些段落、什麼順序、哪些字固定)時,才抽成樣板
- 使用者要的是需要判斷的要求(該不該、多少、選哪一種)時,不抽樣板,在回覆裡說明這屬於 Rule File,由使用者決定要不要改用 skill-derive-rule
- 為什麼:樣板只能被複製與填空,表達不了「什麼情況下該怎麼選」;把判斷硬寫成樣板,執行的人只會照抄樣板上的那一種情況

## good example
- 使用者要的是「不超過七個」這個判斷,**所以不抽樣板,只在回覆裡指出該走哪一條路**
```
使用者:Phase 1 Step 3 提出的類別圖常常太大,超過七個類別就看不懂。

templates/ 不新增任何檔案

回覆:「不超過七個類別」是需要判斷的要求,樣板表達不了,屬於 Rule File;需要的話請改用 skill-derive-rule 展開這一步。
```

## bad example
- 同一句話,但**抽成了樣板,骨架裡放了七個類別區塊**;執行的人每次都會把七個填滿
```
使用者:Phase 1 Step 3 提出的類別圖常常太大,超過七個類別就看不懂。

templates/class-diagram.mmd
  classDiagram
      class {{第一個類別}}
      class {{第二個類別}}
      ...
      class {{第七個類別}}
```

## good example
- 邊界:這句話聽起來像一條規定,但**它固定的是每個類別框裡多出哪一行**,是內容的樣子,所以抽樣板
```
使用者:Phase 1 Step 3 提出的類別圖,每個類別框的第一行都要標出是新增、修改還是既有。

templates/class-diagram.mmd
  classDiagram
      class {{類別名稱}} {
          <<{{新增、修改或既有}}>>
      }
```

## bad example
- 邊界:同一句話,因為聽起來像規定就**沒有抽**;但這一行每個類別都要有、不需要判斷該不該寫,複製骨架就做得到
```
使用者:Phase 1 Step 3 提出的類別圖,每個類別框的第一行都要標出是新增、修改還是既有。

templates/ 不新增任何檔案

回覆:「標出新增、修改還是既有」是一條要求,屬於 Rule File;需要的話請改用 skill-derive-rule 展開這一步。
```

## good example
- 邊界:這句話提到了箭頭的寫法,看起來在講格式,但**使用者要的是「依情況選對哪一種」**,所以不抽樣板
```
使用者:Phase 1 Step 3 提出的類別圖,繼承、實作、組合、聚合、關聯、相依要選對箭頭。

templates/ 不新增任何檔案

回覆:「選對箭頭」要看兩個類別之間是哪一種關係才能決定,樣板表達不了,屬於 Rule File;需要的話請改用 skill-derive-rule 展開這一步。
```

## bad example
- 邊界:同一句話,因為提到寫法就**抽成了樣板**;執行的人會把六種箭頭都畫出來
```
使用者:Phase 1 Step 3 提出的類別圖,繼承、實作、組合、聚合、關聯、相依要選對箭頭。

templates/class-diagram.mmd
  classDiagram
      {{子類別}} --|> {{父類別}}
      {{實作的類別}} ..|> {{介面}}
      {{整體}} *-- {{組合的部分}}
      {{整體}} o-- {{聚合的部分}}
      {{持有者}} --> {{被持有者}}
      {{使用者}} ..> {{被使用者}}
```

# Rule 2 [must] - 一次抽出只動一步與一份樣板
- 抽出前後的差異只有兩處:指定那一步的那一行,以及那一步的樣板(骨架與範例兩個檔),樣子如下

```
首次抽出(那一步還沒有點名樣板)
  before  <M>. <動詞> <動作描述>
          templates/ 底下沒有這一步的樣板
  after   <M>. <動詞> 依骨架 `templates/<樣板名字>.<格式>` 與範例 `templates/<樣板名字>.example.<格式>` <動作描述>
          templates/<樣板名字>.<格式>           ← 新開
          templates/<樣板名字>.example.<格式>   ← 新開

再次抽出(那一步已經點名樣板)
  before  <M>. <動詞> 依骨架 `templates/<樣板名字>.<格式>` 與範例 `templates/<樣板名字>.example.<格式>` <動作描述>
          templates/<樣板名字>.<格式>           ← 已有的骨架
          templates/<樣板名字>.example.<格式>   ← 已有的範例
  after   <M>. <動詞> 依骨架 `templates/<樣板名字>.<格式>` 與範例 `templates/<樣板名字>.example.<格式>` <動作描述>   ← 這一行不變
          templates/<樣板名字>.<格式>           ← 改成這次的格式
          templates/<樣板名字>.example.<格式>   ← 跟著骨架一起改
```

- 目標 skill 的其他步驟、其他樣板與所有 Rule File 都不動;要抽另一步,就再跑一次
- Rule File 裡若已經有 Rule 在講同一件格式,只在回覆裡提,由使用者決定要不要另外處理
- 為什麼:樣板是流程跑過之後才一步一步補上的,一次只動一步,補上之後產出哪裡變了,才對得回是哪一份樣板造成的

## good example
- 使用者指定 Phase 1 Step 3;**前後只差那一行與一份新的樣板**,Step 1、Step 2 一字未動
```
before
  ## Phase 1: 提出類別圖
  1. Read 這次開發會動到的現有程式碼。
  2. Think 設計這次開發的類別組織。
  3. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發。

after
  ## Phase 1: 提出類別圖
  1. Read 這次開發會動到的現有程式碼。
  2. Think 設計這次開發的類別組織。
  3. Ask 依骨架 `templates/class-diagram.mmd` 與範例 `templates/class-diagram.example.mmd` 用 Mermaid 提出設計,問使用者是否可以進入開發。

  templates/
  ├── class-diagram.mmd           ← 新開
  └── class-diagram.example.mmd   ← 新開
```

## bad example
- 同一次抽出,但**順手把 Step 2 也抽了**;使用者只指定了 Step 3,這一次就動了兩步與兩份樣板
```
before
  ## Phase 1: 提出類別圖
  1. Read 這次開發會動到的現有程式碼。
  2. Think 設計這次開發的類別組織。
  3. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發。

after
  ## Phase 1: 提出類別圖
  1. Read 這次開發會動到的現有程式碼。
  2. Think 依骨架 `templates/design-notes.md` 與範例 `templates/design-notes.example.md` 設計這次開發的類別組織。
  3. Ask 依骨架 `templates/class-diagram.mmd` 與範例 `templates/class-diagram.example.mmd` 用 Mermaid 提出設計,問使用者是否可以進入開發。

  templates/
  ├── design-notes.md             ← 也新開
  ├── design-notes.example.md     ← 也新開
  ├── class-diagram.mmd           ← 新開
  └── class-diagram.example.mmd   ← 新開
```

## good example
- 邊界:`rules/類別圖-規範.md` 已經有一條 Rule 在講「標出新增、修改還是既有」,和這次的樣板重疊;**Rule File 不動,只在回覆裡提**
```
templates/
├── class-diagram.mmd           ← 新開,含 <<{{新增、修改或既有}}>>
└── class-diagram.example.mmd   ← 新開

rules/類別圖-規範.md             ← 一字未動

回覆:〈標出每個類別是新增、修改還是既有〉和這次的骨架講的是同一件事,這次沒有動它,要不要拿掉由你決定。
```

## bad example
- 邊界:同一次抽出,覺得重複了就**順手把那條 Rule 刪掉**;看起來是在收尾,但使用者同意的只有抽樣板,Rule File 被改了他並不知道
```
templates/
├── class-diagram.mmd           ← 新開,含 <<{{新增、修改或既有}}>>
└── class-diagram.example.mmd   ← 新開

rules/類別圖-規範.md             ← 刪掉〈標出每個類別是新增、修改還是既有〉
```

# Rule 3 [must] - 指定那一步點名骨架與範例兩個路徑
- 〈一次抽出只動一步與一份樣板〉的首次抽出,在那一步的動詞後面接上「依骨架 `templates/<樣板名字>.<格式>` 與範例 `templates/<樣板名字>.example.<格式>`」,兩個完整路徑都要寫
- 為什麼:路徑出現在步驟裡,執行的人才會去讀那個檔;只寫骨架,他不知道還有範例,填出來的內容就沒有東西可以對照

## good example
- **骨架與範例兩個路徑都在**,執行的人走到這一步會把兩個檔都讀進來
```
3. Ask 依骨架 `templates/class-diagram.mmd` 與範例 `templates/class-diagram.example.mmd` 用 Mermaid 提出設計,問使用者是否可以進入開發。
```

## bad example
- 同一步,但**只點名了骨架**;範例明明寫好了,卻沒有任何一步會去讀它
```
3. Ask 依骨架 `templates/class-diagram.mmd` 用 Mermaid 提出設計,問使用者是否可以進入開發。
```

## good example
- 邊界:這一步原本就點名了一個 Rule File,行變長了,但**兩個路徑仍然各自寫完整**
```
3. Ask 依 `rules/確認-規範.md`、骨架 `templates/class-diagram.mmd` 與範例 `templates/class-diagram.example.mmd` 用 Mermaid 提出設計,問使用者是否可以進入開發。
```

## bad example
- 邊界:同一步為了縮短,用萬用字元一次帶過;看起來涵蓋了兩個檔,但**沒有任何一個完整路徑**,執行的人得自己去列目錄猜
```
3. Ask 依 `rules/確認-規範.md` 與 `templates/class-diagram.*` 用 Mermaid 提出設計,問使用者是否可以進入開發。
```

# Rule 4 [must] - 指定那一步只多出樣板的指標
- 那一步的編號、動詞、原本的動作描述與行尾的分支照原樣;原本就有的「依 `rules/<檔名>`」也留著
- 樣板的內容留在樣板,不寫進步驟
- 為什麼:使用者同意的是替這一步固定生成內容的格式,不是改這一步做的事;編號或動詞一變,別處的「跳至 Phase N Step M」也會跟著指錯

## good example
- 前後**只差「依骨架 … 與範例 …」這一段**,原本那一句與行尾的分支一字未動
```
before  3. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發;若使用者要修改 → 跳至 Phase 1 Step 2。
after   3. Ask 依骨架 `templates/class-diagram.mmd` 與範例 `templates/class-diagram.example.mmd` 用 Mermaid 提出設計,問使用者是否可以進入開發;若使用者要修改 → 跳至 Phase 1 Step 2。
```

## bad example
- 同一次抽出,但**把骨架的段落順序也寫進了步驟**,動作描述不再是原本那一句
```
before  3. Ask 用 Mermaid 提出設計,問使用者是否可以進入開發;若使用者要修改 → 跳至 Phase 1 Step 2。
after   3. Ask 依骨架 `templates/class-diagram.mmd` 與範例 `templates/class-diagram.example.mmd` 用 Mermaid 依序列出類別、職責與關係,問使用者是否可以進入開發;若使用者要修改 → 跳至 Phase 1 Step 2。
```

# Rule 5 [must] - 樣板以那一步的產出物命名
- `<樣板名字>` 取那一步做完留下的產出物,不取這次使用者提到的那一段格式;`<格式>` 取那份產出內容的副檔名
- 為什麼:之後再抽同一步,改的是同一份樣板;名字綁在第一次提到的那一段上,整份骨架其他的部分就名不符實

## good example
- 邊界:這次使用者只提到「標出新增、修改還是既有」,但**名字取的是那一步的產出物「類別圖」**,之後關係、職責的格式都改得進同一份
```
3. Ask 依骨架 `templates/class-diagram.mmd` 與範例 `templates/class-diagram.example.mmd` 用 Mermaid 提出設計,問使用者是否可以進入開發。

templates/
├── class-diagram.mmd
└── class-diagram.example.mmd
```

## bad example
- 邊界:同一次抽出,名字取自這次提到的那一段,看起來更精確,但**骨架裝的是整張類別圖**,下次要固定關係的寫法時,這個名字就對不上了
```
3. Ask 依骨架 `templates/class-status-mark.mmd` 與範例 `templates/class-status-mark.example.mmd` 用 Mermaid 提出設計,問使用者是否可以進入開發。

templates/
├── class-status-mark.mmd
└── class-status-mark.example.mmd
```
