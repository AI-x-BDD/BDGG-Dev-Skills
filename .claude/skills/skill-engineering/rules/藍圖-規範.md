# Rule 1 [must] - 重畫的範圍是根因所在的整個 Phase
- 根因落在哪個 Phase,就重畫那一整個 Phase:它的每一步,以及這些步驟點名的每一個檔
- 根因是「錯位」,或落在不只一個 Phase、不只一支 Skill 時,重畫牽涉到的每一支 Skill 的整份 SOP
- 創建全新的 Skill 時,範圍是整支 Skill
- 範圍以外的一律不動,在主幹裡照現況的原文寫;演練時看到範圍以外的問題,只在回覆裡提,由使用者決定要不要另外處理
- 為什麼:只動根因那一行,同一個 Phase 裡配合它而存在的步驟與 Rule 會原封不動留下來,改出來的只是在舊結構上多貼一塊;範圍沒有上限,使用者同意的是修這個落差,拿到的卻是整支改寫過的 Skill,對不回是哪一個改動修好了問題

## good example
- 根因在 Phase 1 Step 3;**Phase 1 的四步與它們點名的 Rule File 整個重畫,Phase 2 不動**
```
根因:Phase 1 Step 3,rules/類別圖-規範.md〈畫出完整的相依鏈〉,多

重畫的範圍
  Phase 1 Step 1 到 Step 4
  rules/類別圖-規範.md 的每一條 Rule

不動
  Phase 2 Step 1、Step 2
```

## bad example
- 同一個根因,但**只處理那一條 Rule**;同一個 Phase 裡的其他步驟與 Rule 沒有人重新看過,用不到的照樣留著
```
根因:Phase 1 Step 3,rules/類別圖-規範.md〈畫出完整的相依鏈〉,多

重畫的範圍
  rules/類別圖-規範.md〈畫出完整的相依鏈〉
```

## good example
- 邊界:演練時看到 Phase 2 Step 2 沒有寫必須偏離類別圖時怎麼辦;它在範圍以外,**不動它,只在回覆裡提**
```
根因:Phase 1 Step 3,rules/類別圖-規範.md〈畫出完整的相依鏈〉,多

重畫的範圍
  Phase 1 Step 1 到 Step 4
  rules/類別圖-規範.md 的每一條 Rule

回覆:Phase 2 Step 2 沒有寫必須偏離類別圖時怎麼辦。這次的根因不在 Phase 2,沒有動它,要不要另外處理由你決定。
```

## bad example
- 邊界:同一個發現,覺得既然看到了就**順手把 Phase 2 也重畫**;使用者同意的根因只在 Phase 1,Phase 2 被改了他並不知道
```
根因:Phase 1 Step 3,rules/類別圖-規範.md〈畫出完整的相依鏈〉,多

重畫的範圍
  Phase 1 Step 1 到 Step 4
  Phase 2 Step 1、Step 2
  rules/類別圖-規範.md 的每一條 Rule
```

## good example
- 邊界:根因是「錯位」,那條 Rule 要從 Phase 2 載入的檔搬到 Phase 1 載入的檔;**兩個 Phase 都牽涉到,重畫整份 SOP**
```
根因:Phase 1 Step 3,rules/實作-規範.md〈類別圖不超過七個類別〉,錯位

重畫的範圍
  Phase 1 Step 1 到 Step 4
  Phase 2 Step 1、Step 2
  rules/類別圖-規範.md 與 rules/實作-規範.md 的每一條 Rule
```

## bad example
- 邊界:同一個根因,因為偏離點在 Phase 1 就**只重畫 Phase 1**;那條 Rule 原本所在的 `rules/實作-規範.md` 沒有人看,搬過去之後原處還留著一份
```
根因:Phase 1 Step 3,rules/實作-規範.md〈類別圖不超過七個類別〉,錯位

重畫的範圍
  Phase 1 Step 1 到 Step 4
  rules/類別圖-規範.md 的每一條 Rule
```

# Rule 2 [must] - 主幹從產出往回推
- 先寫產出鏈:從驗收產出往回列出要先交出哪些產出,一路列到輸入;鏈上的每一環都是做完會留下來、可以檢查的東西
- 範圍內的每個 Phase 交出產出鏈上的一環,步驟只留交出那一環所必需的;主幹寫完之後才對照現況列出變更
- 為什麼:從現況的步驟開始改,既有的結構會被當成前提,改出來的只會是在原本的流程上再疊一步;從產出往回推,現況的每一步都得回答「交出這個產出為什麼需要它」

## good example
- **先列產出鏈,再從 Phase 1 要交出的那一環往回推出三步**;寫完才對照現況,看出現況的 Step 2 往回推時沒有出現
```
產出鏈:需求 → 使用者確認過的類別圖 → 實作好的類別

Phase 1 要交出「使用者確認過的類別圖」,必需的步驟
  讀會動到的現有程式碼 → 設計類別組織 → 提出設計並等使用者確認

對照現況的 Phase 1
  Step 1 Read 這次開發會動到的現有程式碼     對得上「讀會動到的現有程式碼」
  Step 2 Think 整理剛才讀到的內容            往回推時沒有出現
  Step 3 Think 設計這次開發的類別組織        對得上「設計類別組織」
  Step 4 Ask 用 Mermaid 提出設計             對得上「提出設計並等使用者確認」
```

## bad example
- 同一個根因,但**從現況的四步開始改**;四步都被當成前提,為了排解衝突又在中間多疊了一步
```
現況的 Phase 1,加上這次的修改
  Step 1 Read 這次開發會動到的現有程式碼
  Step 2 Think 整理剛才讀到的內容
  Step 3 Think 設計這次開發的類別組織
  Step 4 Think 檢查設計出來的類別有沒有超出這次涉及的範圍   ← 這次新增
  Step 5 Ask 用 Mermaid 提出設計
```

## good example
- 邊界:產出鏈只列**做完會留下來、可以檢查的東西**,所以只有三環
```
產出鏈:需求 → 使用者確認過的類別圖 → 實作好的類別
```

## bad example
- 邊界:把現況每一步做完的狀態都列成一環,看起來更完整,但**它只是把現況的步驟換個說法抄了一遍**;照它往回推,主幹會和現況一模一樣
```
產出鏈:需求 → 讀過的程式碼 → 整理過的內容 → 類別設計 → 使用者確認過的類別圖 → 開發順序 → 實作好的類別
```

# Rule 3 [must] - 範圍內現有的內容通過拿掉測試才留下
- 範圍內現況的每一步、每條 Rule、每份樣板、每支腳本,除了根因指到的那一段,逐一問:拿掉它之後,它所在的 Phase 要交出的那一環產出會不會變;它是 Rule 時再問,它的「為什麼」要防的後果會不會發生
- 答案都是不會,就列為刪;有一個是會,就留下
- 為什麼:現有的內容不會自己消失;沒有人逐一問過,它們就一直留著,每次執行都要載入、要對照,真正要守的那幾條也更容易被蓋過去

## good example
- 範圍內根因以外的每一項**都問過一次**;Step 2 拿掉之後產出不變,列為刪
```
Phase 1 Step 1 Read 這次開發會動到的現有程式碼   拿掉:沒有東西可以設計,產出會變              留
Phase 1 Step 2 Think 整理剛才讀到的內容          拿掉:下一步照樣從讀到的程式碼設計,產出不變   刪
Phase 1 Step 3 Think 設計這次開發的類別組織      拿掉:沒有類別組織可以提出,產出會變          留
Phase 1 Step 4 Ask 用 Mermaid 提出設計           拿掉:類別圖沒有經過使用者確認,產出會變      留
〈只畫這次開發涉及的類別〉                        拿掉:畫哪些類別沒有人管,產出會變            留
〈每條關係都標出方向〉                            拿掉:它的「為什麼」要防的後果會發生          留
```

## bad example
- 同一個範圍,但**只處理了根因那一條,其餘的沒有問**;Step 2 因為本來就在而留下
```
〈畫出完整的相依鏈〉   根因,刪
其餘的照現況留下
```

## good example
- 邊界:〈每條關係都標出方向〉和這次的落差無關,拿掉它這次要的 5 個類別照樣畫得出來;但**它的「為什麼」要防的後果還是會發生,所以留下**
```
〈每條關係都標出方向〉
  為什麼:沒有方向,看圖的人分不出是誰相依誰
  拿掉之後:終態的 Phase 1 仍然會畫關係,方向沒有人管,這個後果會發生
  結果:留
```

## bad example
- 邊界:同一條 Rule,因為和這次的根因無關就**列為刪**;敢刪不是把這一次用不到的都拿掉
```
〈每條關係都標出方向〉
  為什麼:沒有方向,看圖的人分不出是誰相依誰
  拿掉之後:這次要的 5 個類別照樣畫得出來
  結果:刪
```

# Rule 4 [must] - 留下的內容照現況的原文
- 通過〈範圍內現有的內容通過拿掉測試才留下〉的步驟、Rule、樣板與腳本,在終態裡照現況的原文寫,不換說法
- 前面的步驟或 Rule 刪掉、加進來時,步驟的編號、Rule 的流水號與別處的「跳至 Phase N Step M」跟著順移,不算換說法
- 為什麼:重畫的時候換一種說法很順手,但那一步做的事可能就跟著變了;對不回任何根因的改動,使用者不會知道要去看

## good example
- Step 1 通過了拿掉測試;**終態照現況的原文寫**
```
現況   1. Read **這次開發會動到的現有程式碼**。
終態   1. Read **這次開發會動到的現有程式碼**。
```

## bad example
- 同一步通過了測試,卻**順手換了一種說法**;多出來的「與測試」對不回任何根因,這一步做的事被改了,使用者並不知道
```
現況   1. Read **這次開發會動到的現有程式碼**。
終態   1. Read **這次開發會動到的現有程式碼與測試**。
```

## good example
- 邊界:前面的 Step 2 刪掉了,這一步的編號與行尾的「跳至」跟著順移;**其餘的字照現況的原文**
```
現況   4. Ask 用 Mermaid **提出設計**,問使用者是否可以進入開發;若使用者要修改 → 跳至 Phase 1 Step 3。
終態   3. Ask 用 Mermaid **提出設計**,問使用者是否可以進入開發;若使用者要修改 → 跳至 Phase 1 Step 2。
```

## bad example
- 邊界:同一步,既然編號要改就**把整句也重寫了**;「等使用者確認」和原本的「問使用者是否可以進入開發」問的不是同一件事
```
現況   4. Ask 用 Mermaid **提出設計**,問使用者是否可以進入開發;若使用者要修改 → 跳至 Phase 1 Step 3。
終態   3. Ask 用 Mermaid **呈現類別組織**並等使用者確認;若使用者要修改 → 跳至 Phase 1 Step 2。
```

# Rule 5 [must] - 部位依判定表由上往下選
- 這次要加或要換的每一件要管的事,依下表由上往下判定放進哪一種部位,先符合的先用;照〈留下的內容照現況的原文〉留下的內容不重新判定

| 要管的事 | 部位 |
|---|---|
| 結果只由輸入決定(計數、比對、轉檔、套公式) | 腳本 |
| 生成的內容長什麼樣子(有哪些段落、什麼順序、哪些字固定) | 樣板 |
| 需要判斷(該不該、多少、選哪一種),而且是使用者講明要把關的,或根因指到的 | 規則 |

- 三列都不符的,不掛部位;需要判斷、卻沒有使用者講明也沒有根因指到的事屬於這一種,只在回覆裡提
- 為什麼:越上面的部位越不靠執行的人自律:腳本每次算出一樣的結果,樣板照著填就對,規則卻每次都要讀、要判斷;放錯部位,固定的事會被做得每次不一樣,需要判斷的事會被照抄成同一個樣子。沒有依據就掛上去的規則,每次執行都要載入,卻沒有人遇過它要防的事

## good example
- 要管的是每個類別框裡多出哪一行;**每個類別都要有、不需要判斷該不該寫,是內容的樣子,放進樣板**
```
要管的事:提出的類別圖,每個類別框的第一行標出新增、修改或既有
判定:不是只由輸入決定的結果;是生成的內容長什麼樣子 → 樣板
```

## bad example
- 同一件事,因為聽起來像一條要求就**放進規則**;每次提出類別圖都要逐條對照有沒有標,漏標了也只能靠執行的人自己發現
```
要管的事:提出的類別圖,每個類別框的第一行標出新增、修改或既有
判定:這是一條要求 → 規則
```

## good example
- 要管的是數出來的數字對不對;**同樣的 Rule File 每次都該數出同樣的數字,放進腳本**
```
要管的事:每個 Rule File 的 Rule 條數與各條的強度要數對
判定:結果只由輸入決定 → 腳本
```

## bad example
- 同一件事,但**寫成一條提醒執行的人仔細數的 Rule**;數的人還是同一個,條數一多照樣會數錯
```
要管的事:每個 Rule File 的 Rule 條數與各條的強度要數對
判定:要仔細才數得對 → 規則,加一條〈條數要逐條數過〉
```

## good example
- 邊界:實作類別需要判斷,也想得到「每實作完一個類別就跑一次測試」值得把關;但**使用者沒有講明,根因也沒有指到這一步,所以不掛,只在回覆裡提**
```
步驟:Phase 2 Step 2 Write 依這個順序**逐一實作類別**。
想到的事:每實作完一個類別就跑一次測試
判定:需要判斷,但使用者沒有講明要把關,根因也沒有指到這一步 → 不掛

回覆:另外想到「每實作完一個類別就跑一次測試」也可以把關,這次沒有放進藍圖,需要的話再告訴我。
```

## bad example
- 邊界:同一步,因為它需要判斷就**先掛上一個 Rule File**;之後每次實作都要載入並對照它,卻沒有人遇過它要防的事
```
步驟:Phase 2 Step 2 Write 依這個順序**逐一實作類別**。
想到的事:每實作完一個類別就跑一次測試
判定:需要判斷 → 規則,替這一步掛上 Rule File
```

# Rule 6 [must] - 新掛的部位不先寫進主幹
- 主幹的步驟只保留現況已有、終態也留著的指標;這次新掛的部位寫在變更與它自己的那一段,它的指標等轉交 skill-derive-rule、skill-derive-template 或 skill-derive-script 時才掛上
- 為什麼:這三支是看那一步有沒有點名來分辨首次還是再次的;主幹先寫了指標,它們會把新掛的當成再次,去改一個還不存在的檔

## good example
- Step 3 這次要新掛一份樣板;**主幹裡那一行還沒有樣板的指標**,掛上之後的寫法留在它自己的那一段
```
主幹
  3. Ask 用 Mermaid **提出設計**,問使用者是否可以進入開發;若使用者要修改 → 跳至 Phase 1 Step 2。

新掛的樣板:Phase 1 Step 3
  掛上之後的步驟:3. Ask 依骨架 `templates/class-diagram.mmd` 與範例 `templates/class-diagram.example.mmd` 用 Mermaid **提出設計**,問使用者是否可以進入開發;若使用者要修改 → 跳至 Phase 1 Step 2。
```

## bad example
- 同一份藍圖,但**主幹先把樣板的指標寫上去了**;轉交 skill-derive-template 時,它看到那一步已經點名樣板,會去改兩個還不存在的檔
```
主幹
  3. Ask 依骨架 `templates/class-diagram.mmd` 與範例 `templates/class-diagram.example.mmd` 用 Mermaid **提出設計**,問使用者是否可以進入開發;若使用者要修改 → 跳至 Phase 1 Step 2。

新掛的樣板:Phase 1 Step 3
  掛上之後的步驟:3. Ask 依骨架 `templates/class-diagram.mmd` 與範例 `templates/class-diagram.example.mmd` 用 Mermaid **提出設計**,問使用者是否可以進入開發;若使用者要修改 → 跳至 Phase 1 Step 2。
```

## good example
- 邊界:Step 2 點名的 `rules/類別圖-規範.md` 現況已有、終態也留著;**它的指標照樣寫在主幹裡**
```
主幹
  2. Think 依 `rules/類別圖-規範.md` **設計這次開發的類別組織**。
```

## bad example
- 邊界:為了一致,把既有的指標也從主幹拿掉,打算之後一起掛回去;但**那個檔還在,這一步卻不再點名它**,轉交 skill-derive-rule 時它會當成首次,另開一個新的 Rule File
```
主幹
  2. Think **設計這次開發的類別組織**。
```

# Rule 7 [should] - description 第一句寫使用情境
- 藍圖新寫或改寫 description 時,第一句寫什麼情況下要用這支 Skill:使用者正要做什麼、手上有什麼
- 做法、背景與這支 Skill 的來歷放在使用情境之後,或不寫
- 為什麼:模型是拿 description 去比對使用者的請求來挑 Skill 的;Skill 一多,清單裡每一筆 description 會被截短,排在後面的字最先消失,第一句不是使用情境,這支 Skill 就比對不到

## good example
- **第一句就是使用情境**:使用者正要新增或修改類別、還沒開始寫程式
```
- description:要新增或修改類別、寫程式之前,用這支 Skill 先以 Mermaid 類別圖提案類別組織,使用者確認後才按圖開發;使用者提到類別圖、class diagram、類別設計、先畫圖再寫時使用。(未驗證)
```

## bad example
- 同一支 Skill,但**先講做法與組成**,使用情境排到後面;description 一被截短,剩下的字比對不到任何請求
```
- description:這支 Skill 採用 Mermaid classDiagram 語法,分成提案與實作兩個階段,並搭配骨架與範例樣板,適用於要新增或修改類別、寫程式之前;使用者提到類別圖、class diagram、類別設計、先畫圖再寫時使用。(未驗證)
```

## good example
- 邊界:第一句先寫了一個條件「既有的程式碼裡已經有類別」才講動作;**這個條件就是使用者手上有什麼,仍然是使用情境**
```
- description:既有的程式碼裡已經有類別、這次要再新增或修改類別時,用這支 Skill 先以 Mermaid 類別圖提案類別組織,使用者確認後才按圖開發;使用者提到類別圖、class diagram、類別設計、先畫圖再寫時使用。(未驗證)
```

## bad example
- 邊界:同一支 Skill,第一句讀起來像在講適用的場合,但**說的是這支 Skill 的定位,沒有說使用者正要做什麼**
```
- description:這是一支給重視架構的團隊用的類別設計 Skill,會先以 Mermaid 類別圖提案類別組織,使用者確認後才按圖開發;使用者提到類別圖、class diagram、類別設計、先畫圖再寫時使用。(未驗證)
```

# Rule 8 [should] - description 列出使用者實際會講的詞
- 藍圖新寫或改寫 description 時,在使用情境之後列出使用者提這類需求時實際會講的詞,常用的英文說法也列
- 為什麼:使用者不會照 Skill 的名字或它內部的用語下指令;description 裡沒有他會講的詞,模型拿他的請求來比對時就對不上這支 Skill

## good example
- 使用情境之後**列出使用者嘴裡的詞**,中文與英文的說法都有
```
- description:要新增或修改類別、寫程式之前,用這支 Skill 先以 Mermaid 類別圖提案類別組織,使用者確認後才按圖開發;使用者提到類別圖、class diagram、類別設計、先畫圖再寫時使用。(未驗證)
```

## bad example
- 同一支 Skill,但**一個詞都沒有列**;使用者說「先畫個 class diagram 給我看」時,description 裡沒有任何字對得上
```
- description:要新增或修改類別、寫程式之前,用這支 Skill 先以 Mermaid 類別圖提案類別組織,使用者確認後才按圖開發。(未驗證)
```

## good example
- 邊界:「先畫圖再寫」不是術語,但**使用者真的會這樣講**,所以列進來
```
使用者提到類別圖、class diagram、類別設計、先畫圖再寫時使用。
```

## bad example
- 邊界:同一個位置也列了四個詞,看起來有照做,但**列的是這支 Skill 內部的用語**;沒有使用者會說「幫我提出主幹」
```
使用者提到主幹、部位、產出鏈、classDiagram 骨架時使用。
```

# Rule 9 [should] - description 用半形標點斷句
- 藍圖新寫或改寫 description 時,句子與子句之間用半形標點斷開:逗號 `,`、分號 `;`、冒號 `:`、括號 `()`;頓號與句號沒有半形,用「、」與「。」
- 為什麼:用空白斷句,讀的人分不出一個條件到哪裡結束;各支 Skill 的標點不一致,要一次改好幾支 description 時,同一個搜尋的寫法對不上每一支,得逐支另外處理

## good example
- 子句之間**都用半形的逗號與分號斷開**,句尾是「。」
```
- description:要新增或修改類別、寫程式之前,用這支 Skill 先以 Mermaid 類別圖提案類別組織,使用者確認後才按圖開發;使用者提到類別圖、class diagram、類別設計、先畫圖再寫時使用。(未驗證)
```

## bad example
- 同一句,但**用空白斷句**;「寫程式之前 用這支 Skill」讀不出前半是條件還是另一件事
```
- description:要新增或修改類別 寫程式之前 用這支 Skill 先以 Mermaid 類別圖提案類別組織 使用者確認後才按圖開發 使用者提到類別圖 class diagram 類別設計 先畫圖再寫時使用(未驗證)
```

## good example
- 邊界:「class diagram」中間有一個空白,但**那是使用者會講的詞本身**,詞與詞之間仍然用頓號斷開
```
使用者提到類別圖、class diagram、類別設計時使用。
```

## bad example
- 邊界:同一段裡一樣有空白,但**這裡的空白是拿來斷開三個詞的**;讀的人分不出「class diagram 類別設計」是一個詞還是兩個
```
使用者提到類別圖 class diagram 類別設計時使用。
```

## good example
- 邊界:頓號與句號是全形的,但**這兩個標點沒有半形**;逗號、分號與括號仍然是半形
```
- description:要新增或修改類別、寫程式之前,用這支 Skill 先以 Mermaid 類別圖提案類別組織,使用者確認後才按圖開發;使用者提到類別圖、class diagram、類別設計、先畫圖再寫時使用。(未驗證)
```

## bad example
- 邊界:同一句把逗號、分號與括號也寫成全形,讀起來沒有任何問題;但**和其他 Skill 的寫法不一致**,用 `(未驗證)` 找還沒驗證的 Skill 時會漏掉這一支
```
- description:要新增或修改類別、寫程式之前，用這支 Skill 先以 Mermaid 類別圖提案類別組織，使用者確認後才按圖開發；使用者提到類別圖、class diagram、類別設計、先畫圖再寫時使用。（未驗證）
```

# Rule 10 [must] - description 以「(未驗證)」結尾
- 藍圖的 description 一律以 `(未驗證)` 結尾:半形括號,接在最後一個句號之後,後面不再有任何字
- description 不在這次的變更裡時也一樣:其餘的字照〈留下的內容照現況的原文〉寫現況的原文,只在結尾補上或改正這個標記
- 標記只由使用者在實際驗證過之後拿掉,藍圖不拿掉
- 為什麼:這個流程寫出來或改過的 Skill 還沒有人實際跑過,不標明,拿到的人會把它當成驗證過的來用;標記的寫法不固定,就沒辦法用同一個搜尋一次找出哪幾支還沒驗證

## good example
- description **以 `(未驗證)` 結尾**,接在句號之後
```
- description:要新增或修改類別、寫程式之前,用這支 Skill 先以 Mermaid 類別圖提案類別組織,使用者確認後才按圖開發;使用者提到類別圖、class diagram、類別設計、先畫圖再寫時使用。(未驗證)
```

## bad example
- 同一句,但**結尾沒有標記**;這支 Skill 才剛寫出來,看起來卻和驗證過的沒有兩樣
```
- description:要新增或修改類別、寫程式之前,用這支 Skill 先以 Mermaid 類別圖提案類別組織,使用者確認後才按圖開發;使用者提到類別圖、class diagram、類別設計、先畫圖再寫時使用。
```

## good example
- 邊界:這次的根因在 Phase 1 的一條 Rule,description 不在變更裡,現況也沒有標記;**其餘的字照現況的原文,只在結尾補上標記**
```
現況   寫程式之前,先用 Mermaid 類別圖提案這次開發的類別組織,使用者確認後才按圖依序開發。
藍圖   - description:寫程式之前,先用 Mermaid 類別圖提案這次開發的類別組織,使用者確認後才按圖依序開發。(未驗證)
```

## bad example
- 邊界:同一個情況,標記有補,但**寫成另一種樣子**;看起來標了,用 `(未驗證)` 找的時候找不到這一支
```
現況   寫程式之前,先用 Mermaid 類別圖提案這次開發的類別組織,使用者確認後才按圖依序開發。
藍圖   - description:寫程式之前,先用 Mermaid 類別圖提案這次開發的類別組織,使用者確認後才按圖依序開發。未驗證。
```
