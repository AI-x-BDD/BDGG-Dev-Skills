# Rule 1 [must] - 錯誤一律用 problem+json 表達
- OpenAPI 每個 4xx/5xx 回應的 content type 是 `application/problem+json`,schema 引用 `#/components/schemas/Problem`(RFC 9457 的 `type`、`title`、`status`、`detail`)
- AsyncAPI 推送給呼叫者的錯誤訊息,payload 同樣引用 `Problem`
- 需求要伺服器把關的每一個條件,在那個回應或訊息的 `x-problem-types` 列出一個 `type` URI;一個 URI 只對應一種不符的原因
- 取代:api-plan/rules/契約-規範.md〈伺服器把關的條件都有具名的錯誤〉
- 為什麼:這個專案的閘道與前端只認 RFC 9457 的錯誤格式;REST 與 WebSocket 各用一套錯誤格式,前端就得寫兩份錯誤處理

## good example
- 結帳的兩個不符原因**各有一個 problem type**,content type 是 problem+json
```yaml
'409':
  description: 購物車是空的,或有商品庫存不足
  x-problem-types:
    - https://errors.shop.example/cart-empty
    - https://errors.shop.example/out-of-stock
  content:
    application/problem+json:
      schema: { $ref: '#/components/schemas/Problem' }
```

## bad example
- 同一個回應,**照 Skill 預設寫成 `x-error-codes` 與 `application/json`**;閘道認不得這個錯誤格式
```yaml
'409':
  description: 購物車是空的,或有商品庫存不足
  x-error-codes: [CART_EMPTY, OUT_OF_STOCK]
  content:
    application/json:
      schema: { $ref: '#/components/schemas/Error' }
```
