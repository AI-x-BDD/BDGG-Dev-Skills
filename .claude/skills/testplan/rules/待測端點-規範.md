# Rule 1 [must] - 待測端點照抄 plan.md 的端點盤點
- 待測端點表的每一列都對得回 `plan.md` § 端點盤點的一個端點:端點序號與名稱、介面規格檔、公開接縫照抄,不新增、不合併、不改名
- 端點盤點有、這次不測的端點照樣列出,在測試等級寫 —,並在測試環境寫為什麼不測、只出現在哪裡
- 跨端點驗收是唯一不在端點盤點上的列
- 為什麼:系統分析已經決定這個功能有哪些端點、各自的介面長什麼樣子;testplan 再規劃一次,兩份文件的端點就會對不上,`/tasks` 照 testplan 切出來的端點節找不到 `plan.md` 的端點,`/implement` 也不知道要交給哪個 subagent

## good example
- **每一列都對得回端點盤點**;E3 這次不測,照樣列出並寫明原因
```
plan.md § 端點盤點:E1 前端、E2 後端、E3 資料庫、E4 部署與網路

| 端點 | 介面規格檔 | 公開接縫 | 測試等級 | 工具 | 測試環境 |
| E2 後端 | `contracts/game.asyncapi.yaml` | WebSocket `/ws?client_id=...` 收發的 JSON 訊息 | E2E(真的 app、真的 MySQL) | pytest + TestClient | `guess_number_test` 庫 |
| E1 前端 | `prototype/room.html` | 不靠後端就看得到的畫面行為 | E2E(真的瀏覽器) | Playwright | 不用假後端 |
| 跨端點驗收 | E1、E2 的規格檔 | 瀏覽器畫面 | E2E(真的瀏覽器、真的後端) | Playwright | 後端 port 8765 |
| E3 資料庫 | `contracts/game.dbml` | — | — | — | 使用者故事 5 不涉及(聊天不寫入資料庫) |
| E4 部署與網路 | `deploy/compose.yaml` | 對外網址 | 📏 人工 | 手機瀏覽器 | 只出現在全域測試區 |
```

## bad example
- 同一份 plan.md,但 **testplan 自己重新切了介面**:多出一個端點盤點沒有的「後端計分模組」,E3、E4 沒有列
```
| 端點 | 介面規格檔 | 公開接縫 | 測試等級 | 工具 | 測試環境 |
| 後端 API | `contracts/game.asyncapi.yaml` | `/ws` 的 JSON 訊息 | E2E | pytest | `guess_number_test` 庫 |
| 後端計分 | — | `score(answer, guess)` | 單元 | pytest | 無 |
| 前端 | — | 瀏覽器畫面 | E2E | Playwright | 後端 port 8765 |
```

## good example
- 邊界:要測的純函式 `score()` 在端點盤點裡屬於 E2 後端;**它是 E2 的一個受測操作,不另立一個端點**
```
| 端點 | 受測操作 | 規格錨點 | 寫法 |
| E2 後端 | `rules.score(answer, guess) -> (a, b)` | — | `rules.score(answer, guess)` |
```

## bad example
- 邊界:同一個函式,因為測試等級是單元、工具不一樣,就**另開一個「E2b 計分」端點**;`/tasks` 會多切出一個 plan.md 沒有的端點節
```
| 端點 | 介面規格檔 | 公開接縫 | 測試等級 | 工具 | 測試環境 |
| E2b 計分 | — | `score(answer, guess)` | 單元 | pytest parametrize | 無 |
```

# Rule 2 [must] - 受測操作寫出規格錨點
- 受測操作表每一列的「規格錨點」欄,寫出這組操作在介面規格檔裡對應的錨點:`<規格檔路徑> § <錨點>`,錨點的寫法和 `/tasks` 的 ⚙ 相同(AsyncAPI 的 `operations.<id>`、`components.schemas.<Name>`,OpenAPI 的 `paths./<路徑>.<method>`,原型的 CSS 選擇器)
- 規格檔裡沒有對應錨點的操作(例如瀏覽器本身的重新整理、模組內部的純函式)寫 —
- 為什麼:`/tasks` 的 ⚙ 是照這一欄寫的;這一欄空著,排任務的人只能自己去規格檔猜錨點,同一組操作在不同任務裡會綁到不同的元素,介面覆蓋表也對不起來

## good example
- **每一列都寫出規格檔路徑與錨點**;瀏覽器本身沒有錨點,寫 —
```
| 端點 | 受測操作 | 規格錨點 | 寫法 |
| E2 後端 | client → server 訊息:`chat` | `contracts/game.asyncapi.yaml` § `operations.sendChat`、`operations.receiveChatMessage`、`components.schemas.ChatMessage` | `/ws` › 送 `chat` |
| 跨端點驗收 | 房間畫面:「訊息」輸入框、「送出訊息」、聊天室 | `prototype/room.html` § `#chat-panel`、`[data-state="chat-waiting"]` | 房間畫面 › 「送出訊息」 |
| 跨端點驗收 | 瀏覽器本身:重新整理 | — | 瀏覽器本身 › 重新整理 |
```

## bad example
- 同一張表,但**規格錨點只寫了檔名**;排任務的人不知道「送出訊息」綁的是 `#chat-panel` 還是整個 `room.html`
```
| 端點 | 受測操作 | 規格錨點 | 寫法 |
| E2 後端 | client → server 訊息:`chat` | `contracts/game.asyncapi.yaml` | `/ws` › 送 `chat` |
| 跨端點驗收 | 房間畫面:「訊息」輸入框、「送出訊息」、聊天室 | `prototype/room.html` | 房間畫面 › 「送出訊息」 |
```

## good example
- 邊界:`chat` 送出後伺服器回的 `error` 也是這組操作會觀察到的;**收到的訊息的錨點一併寫進同一列**
```
| E2 後端 | client → server 訊息:`chat` | `contracts/game.asyncapi.yaml` § `operations.sendChat`、`operations.receiveChatMessage`、`operations.receiveError` | `/ws` › 送 `chat` |
```

## bad example
- 邊界:同一列,**只寫了送出的那個 operation**;驗「長度不符回 error」的任務 ⚙ 少了 `receiveError`,介面覆蓋表上它就沒有測試
```
| E2 後端 | client → server 訊息:`chat` | `contracts/game.asyncapi.yaml` § `operations.sendChat` | `/ws` › 送 `chat` |
```

# Rule 3 [must] - 上游沒寫到的登記成待決問題
- 規劃測試需要、但 plan.md、規格檔、techstack.md 與 research.md 都沒寫到的事(測試工具、測試環境、接縫的公開介面、某個操作的錨點),列成待決問題,在 Phase 1 提出待測端點時一起問,決定後登記到 `plan.md` 的待決問題
- 不在 testplan 裡自己補上一個做法當成既定事實
- 為什麼:testplan 自己補的做法只有 testplan 知道;`/tasks` 與 `/implement` 照的是 plan.md,兩邊的約定就分岔了,而且這個決定沒有經過使用者

## good example
- techstack.md 沒寫前端 E2E 的工具;**列成待決問題,附可選的做法與先採用的那一種**
```
待決問題
Q21 前端 E2E 用什麼工具?techstack.md § 測試只寫了 pytest。
    可選:Playwright(兩個 browser context 扮演雙方)/ Cypress(一次一個分頁)
    先採用:Playwright
```

## bad example
- 同一個缺口,**直接在待測端點表寫上 Playwright**;使用者沒有決定過,plan.md 也沒有這一筆
```
| 跨端點驗收 | E1、E2 的規格檔 | 瀏覽器畫面 | E2E | Playwright | 後端 port 8765 |
```

## good example
- 邊界:techstack.md § 測試已經寫了 Playwright;**照抄就好,不必登記待決**
```
techstack.md § 測試:前端 E2E 用 Playwright 1.64,兩個 browser context
| 跨端點驗收 | E1、E2 的規格檔 | 瀏覽器畫面 | E2E | Playwright,兩個 browser context 扮演雙方 | 後端 port 8765 |
```

## bad example
- 邊界:同一份 techstack.md 已經寫了,**還是列成待決問題**;使用者被問了一個上游早就決定過的事
```
待決問題
Q21 前端 E2E 用什麼工具?可選:Playwright / Cypress
```

# Rule 4 [must] - 每個替身至少有一個不用它的實跑案例
- 待測端點表的「替身」欄列出這個端點的測試用哪個替身代替哪個真元件,寫成 `替身(代替的真元件)→ 實跑案例 ID`,指到接真元件的實跑案例;一個端點有好幾個替身時以 `<br>` 分隔,沒有替身寫「無」,這次不測的端點寫 —
- 替身指的是測試裡代替真元件產生輸入、輸出或狀態的任何東西:mock、monkeypatch、假的外部工具或服務、合成的資料(例如合成的逐字稿)、直接寫入的狀態(例如直接塞進資料表的工作列),以及 TestClient 這類不經真伺服器的呼叫方式
- 實跑案例的驗證方式是 📏 量測或 📏 人工,「假如」或「當」寫明接真的哪個元件;同一個替身換個環境跑不算實跑
- 拿不到真元件時寫 `替身(代替的真元件)→ 無法實跑:原因`,`/implement` 的完成報告把它列為未驗證,不寫成已驗證
- 為什麼:替身是照作者對真元件的理解寫的,程式也照同一個理解寫;理解錯了,測試照樣全綠。作業三的訂閱 bug 靠假 yt-dlp 過關,舊工作頁點不進去也要到真瀏覽器才現形

## good example
- 測試用假 yt-dlp;**替身欄指到 US3-AJ-04,那個案例讓真的 yt-dlp 讀一個公開頻道**
```
| 端點 | 介面規格檔 | 公開接縫 | 測試等級 | 工具 | 測試環境 | 替身 |
| E2 後端 | `contracts/notes.openapi.yaml` | HTTP `/subscriptions` | 整合(真的 app、真的 SQLite) | pytest | 暫存資料夾的 SQLite | `tests/fixtures/fake_ytdlp`(yt-dlp)→ US3-AJ-04 |

| US3-AJ-04 | 頻道訂閱 | 📏 量測 | `POST /subscriptions` | image 內真的 yt-dlp,不設 `YTDLP_BIN` | 訂閱一個公開頻道並觸發一次更新 | 則1:新影片清單至少 1 筆,標題和頻道頁相同 | … | FR-012 |
```

## bad example
- 同一個替身,**指到的案例還是用假 yt-dlp,只是換到容器裡跑**;對 yt-dlp 輸出格式的誤解一樣驗不出來
```
| E2 後端 | `contracts/notes.openapi.yaml` | HTTP `/subscriptions` | 整合(真的 app、真的 SQLite) | pytest | 暫存資料夾的 SQLite | `tests/fixtures/fake_ytdlp`(yt-dlp)→ US3-AJ-04 |

| US3-AJ-04 | 頻道訂閱 | 📏 量測 | `POST /subscriptions` | 容器裡跑 pytest,沿用 `fake_ytdlp` | 訂閱一個公開頻道並觸發一次更新 | 則1:新影片清單至少 1 筆 | … | FR-012 |
```

## good example
- 邊界:替換規則是純函式,測試沒有代替任何真元件;**替身欄寫「無」**,不必為它另開實跑案例
```
| E2 後端 | — | `corrections.apply(text, rules)` | 單元 | pytest parametrize | 無 | 無 |
```

## bad example
- 邊界:同一個純函式,**硬要指到一個開瀏覽器的實跑案例**;正確率要看逐筆結果,瀏覽器什麼都沒多驗到,還多了一個要人看的 📏 任務
```
| E2 後端 | — | `corrections.apply(text, rules)` | 單元 | pytest parametrize | 無 | 替換規則(瀏覽器)→ US1-AJ-07 |
```

## good example
- 邊界:asr-gateway 這週停機,真元件拿不到;**照實寫無法實跑與原因**,完成報告會把它列為未驗證
```
| E2 後端 | `contracts/notes.openapi.yaml` | HTTP `/jobs` | 整合 | pytest | 暫存 volume | `FakeOpenAI`(asr-gateway)→ 無法實跑:asr-gateway 停機維護到 11/20,沒有其他相同模型的服務 |
```

## bad example
- 邊界:同一個情況,**改接本機的 whisper 模型當成實跑**;它是真的模型,但不是 asr-gateway 背後的 breeze-asr,辨識結果與錯字分佈都不同,量到的正確率不代表正式環境
```
| E2 後端 | `contracts/notes.openapi.yaml` | HTTP `/jobs` | 整合 | pytest | 暫存 volume | `FakeOpenAI`(asr-gateway)→ US1-AJ-05 |

| US1-AJ-05 | 正確率 | 📏 人工 | 筆記頁 › 「校正逐字稿」 | 0.5.0 容器改設 `ASR_BASE_URL` 指到本機 whisper | 校正 4 支驗收影片 | 則1:替換正確比例至少 90% | … | SC-001 |
```

# Rule 5 [must] - 寫出分層的測試指令
- 「測試指令」表寫出兩層:快速層與全部,各寫一條可以直接執行的指令
- 快速層排除真瀏覽器、真網路、固定 port 的伺服器與單支超過 1 秒的測試;全部是這個專案的完整測試指令;「大約時間」寫實測的時間,不寫估計
- 「包含」欄寫出這一層含哪些資料夾或 marker;慢的測試要怎麼標(例如 pytest 的 `-m "not e2e"`、資料夾 `tests/e2e`),照專案現有的方式寫,沒有就在待決問題登記一題
- 為什麼:`/tdd` 綠燈與重構的小步只跑任務的測試檔,重構前後跑快速層,全部留給合併後與 Checkpoint;沒有分層時,做事的人只能每一步都跑全部,或自己猜哪些相關。colab-gpu-bridge 002 的 E2 subagent 把 98 個真瀏覽器測試算成「相關」,每個紅綠任務等 110 秒,61% 的時間在等測試

## good example
- **兩層都寫出可以直接執行的指令**,快速層排除 e2e,寫明大約時間
```
### 測試指令

| 層 | 指令 | 包含 | 大約時間 |
|---|---|---|---|
| 快速層 | `uv run pytest tests/unit tests/integration -q -p no:cacheprovider` | 單元與整合(替身、暫存 SQLite);不含 `tests/e2e`、`-m realrun` | 約 25 秒 |
| 全部 | `uv run pytest -q -p no:cacheprovider` | 上面加上 `tests/e2e`(Playwright、固定 port 的 uvicorn) | 約 6 分 |
```

## bad example
- 同一個專案,**只寫「全部」**;subagent 每個綠燈只能跑 6 分鐘的全部,或自己挑一支覺得相關的 e2e
```
### 測試指令

| 層 | 指令 | 包含 | 大約時間 |
|---|---|---|---|
| 全部 | `uv run pytest` | 全部 | 約 6 分 |
```

## good example
- 邊界:專案很小,全部測試 10 秒就跑完;**照樣寫兩層,快速層就寫同一條指令**,並註明為什麼一樣
```
| 快速層 | `uv run pytest -q` | 全部 18 個測試都是單元測試,沒有慢層 | 約 3 秒 |
| 全部 | `uv run pytest -q` | 同上 | 約 3 秒 |
```

## bad example
- 邊界:同一個小專案,因為「反正很快」就**把快速層寫成只跑一支**;之後加了 e2e,沒有人回來改,快速層一直漏掉其他單元測試
```
| 快速層 | `uv run pytest tests/test_calc.py` | 計算機的測試 | 約 1 秒 |
| 全部 | `uv run pytest -q` | 全部 | 約 3 秒 |
```
