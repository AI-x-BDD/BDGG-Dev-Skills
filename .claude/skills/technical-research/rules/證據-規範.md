# Rule 1 [must] - 標「實測」的證據要這次真的執行過
- 只有這次研究中實際執行過、親眼看到輸出的結果,才標成 `實測(<量測環境>)`;量測環境寫出實際執行的機器、版本與樣本
- 沒有在這次執行的,依它的來處標成 `估算(<依據>)`、`查證(<來源>)` 或 `判斷`,不標實測
- 為什麼:讀 research.md 的人會依「實測」兩個字決定還要不要再驗;憑記憶、文件或別人的紀錄寫出來的數字標成實測,錯的時候不會有人回頭去量,決策就建立在一個沒有人看過的結果上

## good example
- 這次在桌機上**真的執行了 `heif-thumbnailer`**,看到輸出才標實測,環境照實際執行的寫
```
執行:docker run … heif-thumbnailer -s 256 IMG_0001.heic out.png   (重複 10 次)
輸出:每張 26–27ms

- 實測(桌機 i5-9400F,Docker,libheif 1.23.4,12MP 有 320×240 內嵌縮圖的 HEIC):每張 26–27ms,含行程啟動與 PNG 輸出。
```

## bad example
- 同一條理由,但**這次沒有執行任何指令**,數字是照印象寫的,卻標成實測
```
執行:(無)

- 實測(桌機 i5-9400F,Docker,libheif 1.23.4,12MP 有 320×240 內嵌縮圖的 HEIC):每張 26–27ms,含行程啟動與 PNG 輸出。
```

## good example
- 邊界:數字確實有人量過,但**量的是上一份研究,不是這次**;照它的來處標成查證並寫出來源
```
來處:上一個專案的 research.md R1,2026-09 量測

- 查證(上一個專案的 research.md R1,2026-09 量測):heif-thumbnailer 有內嵌縮圖時每張約 27ms。
```

## bad example
- 邊界:同一個數字,因為「有人實際量過」就**標成實測**;看起來有憑據,但這次沒有人看過輸出,版本與樣本也可能已經不同
```
來處:上一個專案的 research.md R1,2026-09 量測

- 實測(桌機 i5-9400F,Docker):heif-thumbnailer 有內嵌縮圖時每張約 27ms。
```

## good example
- 邊界:這次只在桌機上執行,要推到部署的 NAS 上;**桌機的結果標實測,推到 NAS 的部分另標估算**
```
執行:桌機上 heif-thumbnailer,沒有內嵌縮圖的 HEIC,每張 1.22–1.31 秒

- 實測(桌機 i5-9400F,Docker,12MP 沒有內嵌縮圖的 HEIC):每張 1.22–1.31 秒。
- 估算(桌機實測時間 × 1,000 張 ÷ 8 個併發):NAS 上 1,000 張約 165 秒。
```

## bad example
- 邊界:同一次執行,但把**推出來的 NAS 數字也寫進實測**,量測環境寫成沒有執行過的那台機器
```
執行:桌機上 heif-thumbnailer,沒有內嵌縮圖的 HEIC,每張 1.22–1.31 秒

- 實測(NAS i5-13500,8 個併發):1,000 張約 165 秒。
```

# Rule 2 [must] - 幾秒內能實測的技術事實不標判斷
- 決策依賴的技術事實(SDK 或函式庫呼叫某個參數時的行為、既有程式碼的某個函式做了什麼),能在 session 暫存區用幾秒寫一支探針跑出來的,就實測,不標 `判斷`
- 為什麼:標成判斷的事實,讀的人不會回頭驗;它一旦是錯的,錯的不是一行理由,而是建立在它上面的決策,要到下游實作時才會被撞出來,整個研究項得重來

## good example
- 研究 R4「沒有 key 時怎麼不送 `Authorization`」,**在暫存區執行 `OpenAI(api_key="")`**,看到輸出才標實測,決策照實測結果定
```
執行:OpenAI(api_key="")
輸出:OpenAIError: Missing credentials

- 實測(桌機,`openai` SDK 3.41):`OpenAI(api_key="")` 丟出 `Missing credentials`。
決策:改走佔位值加 `openai.omit`
```

## bad example
- 同一個事實,**沒有執行就標判斷**,決策定在這個沒有人驗過的行為上;system-analysis 才回報 SDK 3.41 不接受空字串 key
```
執行:(無)

- 判斷:SDK 以空字串 key 建 client 就不會送 `Authorization`。
決策:以空字串建立 client
```

## good example
- 邊界:asr-gateway 的模型清單是否都回 OpenAI 格式,要等實作完成、對真的服務操作才量得到,**不是幾秒內能實測的**;標 `判斷` 並列進「待驗證」
```
執行:(無;要對真的 asr-gateway 操作,實作完成前量不到)

- 判斷:asr-gateway 的模型清單都回 OpenAI 格式。
待驗證:實作完成後對 asr-gateway 呼叫模型清單,確認格式
```

## bad example
- 邊界:同一件事,為了符合「能實測就實測」,**拿一個自己寫的假服務回 OpenAI 格式,標成實測**;量到的是假服務,不是 asr-gateway
```
執行:在暫存區起一個回 OpenAI 格式的假服務,呼叫它的模型清單

- 實測(桌機,自寫假服務):asr-gateway 的模型清單回 OpenAI 格式。
```

# Rule 3 [must] - 查證既有程式碼要讀到函式本體
- 要說既有程式碼「已經會做某件事」,讀到那個函式的本體、找到做這件事的那幾行,才標 `查證(<檔案>:<函式>)`;只看函式名稱、參數或簽名,不算查證
- 為什麼:憑簽名推論的事實標成查證,讀的人會以為有人看過程式碼,不會回頭驗;它一旦是錯的,建立在它上面的決策要到下游實作時才會被撞出來,整個研究項得重來

## good example
- 邊界:要說「001 的 `remote_asr._status_error` 會把 key 從回應內容移除」,**讀了函式本體**,看到 `api_key` 只用來分辨 `MISSING_API_KEY` 與 `INVALID_API_KEY`、沒有任何一行把它從訊息裡拿掉,查證照讀到的寫
```
讀:app/adapters/remote_asr.py 的 _status_error 本體

- 查證(app/adapters/remote_asr.py:_status_error):`api_key` 只用來分辨 `MISSING_API_KEY` 與 `INVALID_API_KEY`,沒有去敏。
決策:002 補上去敏
```

## bad example
- 邊界:同一個函式,**只看到簽名 `_status_error(response, api_key: str)` 收了 key**,就寫成已經會去敏;implement T022 才發現它沒有去敏
```
讀:_status_error(response, api_key: str) 的簽名

- 001 已有的錯誤訊息去敏處理(`remote_asr._status_error` 會把 key 從回應內容中移除)。
決策:沿用到模型清單與測試連線
```

# Rule 4 [must] - 探針先看一筆真實樣本,限時跑最小組合
- 跑批次量測之前,先取一筆樣本親眼看過(影片抽一張畫面、資料取一列),確認它符合這次要量的條件,也沒有會干擾量測的內容
- 先跑一個參數組合並設逾時,算出單次耗時與總耗時;總耗時超過幾分鐘就先減少組合或樣本,寫明減了什麼
- 為什麼:批次跑完才發現樣本不對,結果整批不能用;沒有逾時又一次跑全部組合,使用者要等完才知道走錯方向,第二輪還可能被逾時終止、什麼都沒留下

## good example
- 要量疊上去的字幕;**先抽一張來看,發現背景本身有字幕,先換樣本再跑**
```
1. 抽一張合成畫面來看:OBS 錄影本身有字幕與播放器控制列,會和疊上去的字幕重疊 → 換背景
2. 一個組合、timeout 60:每張 0.5 秒,11 組 × 45 張約 4 分鐘
3. 減成 3 組,其餘寫明沒有量
```

## bad example
- 同一個探針,**沒看樣本就跑 11 組**;40 句只中 4 句才發現背景有字幕,換背景重跑又逾時,500 秒沒有留下結果
```
1. 直接跑 11 種組合 × 40 句,不設逾時
2. 40 句只中 4 句 → 背景本身有字幕,結果不能用
3. 換背景重跑 11 組,500 秒被終止
```

## good example
- 邊界:探針只是查版本,**沒有樣本、幾秒就結束**;不必看樣本,也不必試跑
```
執行:tesseract --version
輸出:tesseract 5.5.0
```

## bad example
- 邊界:同一個探針,照規則也**先試跑一個組合再估總耗時**;沒有組合可以減,多出來的步驟什麼都沒確認
```
1. 試跑 tesseract --version,估算總耗時:幾毫秒
2. 正式跑 tesseract --version
```

# Rule 5 [must] - 定門檻與參數之前看過真實樣本的逐筆輸出
- 決策是門檻或參數值時,用這次要處理的那種真實資料,取前後相鄰的幾筆,看過每筆的原始輸出(信心值、文字框、實際文字),不只看彙總數字;相鄰幾筆之間的差異寫進理由
- 看不到真實資料時標 `判斷`,並列進「待驗證」
- 為什麼:彙總的行數與正確率在合成資料上可以全部漂亮,卻看不出同一內容在相鄰幾筆之間跳動;值卡在跳動的範圍裡,結果時有時無,要到使用者看到成品才發現

## good example
- 同一句字幕連續三秒的 `conf` 都看過;**看到值跨過門檻,把這件事寫進理由**
```
實測(clarify 影片第 12–14 秒,同一句字幕,逐字詞 conf):
  00:12 第 49、Spec-Kit 14;00:13 第 44、Spec-Kit 15;00:14 第 16、Spec-Kit 78
決策:門檻 50 會讓字時有時無,所以比對時要合併相似的行
```

## bad example
- 同一個決策,**只看合成字幕的彙總數字**;門檻 50 看起來最好,定案後才發現真實影片的字時有時無
```
實測(灰色動態雜訊背景的 20 句字幕):門檻 50 抓到 20/20、正確率 99.8%;門檻 85 正確率 97.6%
決策:門檻 50
```

## good example
- 邊界:決策是預設每秒抽幾張,要看的是相鄰畫面**有沒有漏句**;逐筆的時間點與文字就是原始輸出
```
實測(clarify 影片第 60–70 秒,每秒一張,逐張文字):每句字幕出現 2–4 張,沒有漏句
決策:預設間隔 1 秒
```

## bad example
- 邊界:同一個決策,用**彙總行數**當作證據;行數相近的兩種間隔,看不出哪一種漏句
```
實測(clarify 影片 45 秒):間隔 1 秒 21 行、間隔 2 秒 19 行
決策:預設間隔 1 秒
```

# Rule 6 [must] - 再多一批也不會改變決策就停,超出原問題要寫明依賴
- 每批探針跑完,先問下一批可能的結果會不會改變決策;不會就停,還想看的樣本與條件列進「待驗證」
- 要查研究項原問題以外的事時,先判斷這個研究項的決策是否依賴它:依賴就查,並在理由寫明依賴什麼;不依賴就不查,列進「待驗證」
- 下一批是為了找出可能推翻決策的反例,且現有樣本都沒有涵蓋這種情況時,不算不會改變決策
- 為什麼:〈探針先看一筆真實樣本,限時跑最小組合〉只管單批的耗時,每批都合規,批數還是能一直加;多出來的樣本沒有改變決策,卻讓使用者多等,原問題以外的查證也會混進決策,看不出這個研究項到底回答了什麼

## good example
- 候選門檻已經分不出差異,**不再加樣本**,其餘列進「待驗證」
```
實測(clarify 180 張,63 句,深底與亮底都有):門檻 30–60 的字元正確率只差 0.9 個百分點,70 起才開始掉字
下一批:再標兩支同樣條件的影片,結果只會在平坦區內移動,不會改變決策 → 停
決策:門檻 50
待驗證:整支影片的門檻表現
```

## bad example
- 同一個結果,**又多標了兩支影片**;門檻仍是 50,平坦區也還在
```
實測(clarify 180 張,63 句):門檻 30–60 的字元正確率只差 0.9 個百分點
再加兩支影片、標 48 句:30–60 只差 0.4 個百分點
決策:門檻 50
```

## good example
- 邊界:門檻是在某種前處理上量的,**決策依賴它,所以查,並寫明依賴**;退回做法不影響門檻,不查
```
研究項:信心門檻
查:前處理 —— 門檻的數字只在同一種前處理下成立
不查,列進待驗證:空白畫面退回未縮放
```

## bad example
- 邊界:同一個研究項,**沒判斷依賴就一路查下去**;退回做法試完沒有採用,也沒有寫它和門檻的關係
```
研究項:信心門檻
查:前處理
查:空白畫面退回未縮放 → 沒有採用
```

## good example
- 邊界:真實樣本都沒有只差一兩個字的相鄰不同句,而假合併會推翻合併規則;**這批是找反例,要跑**
```
現有樣本:假合併 0 組,但沒有只差一兩個字的相鄰不同句
下一批:合成影片放 5 組這種句子 → 可能推翻規則,要跑
結果:相似度 0.8 有 2 組假合併,規則加上高信心替換不合併
```

## bad example
- 邊界:同一個情況,**因為假合併是 0 組就停**;沒有涵蓋的情況不算量過,規則上線才發現會吃掉句子
```
現有樣本:假合併 0 組
下一批:不會改變決策 → 停
決策:相似度 0.8 就合併
```

# Rule 7 [must] - 定門檻或規則時留一份沒看過的樣本驗收
- 決策是門檻或規則時,開始調整之前就把樣本分成調整用與驗收用;驗收用的那一份,門檻或規則定案之前不看它的內容、標準答案與結果;〈探針先看一筆真實樣本,限時跑最小組合〉看的那一筆取自調整用的樣本
- 分配之前只看檔名與筆數;已經讀過內容的樣本不算沒看過,只能當調整用
- 看過驗收樣本的結果又調整,這份就改標「調規則」,不再算沒看過;要驗收就換一份,沒有別的樣本時,把這個決策的正確率列進「待驗證」
- research.md 寫出每份樣本的用途;要說明達到 SC 的數字,只能來自驗收用的樣本
- 為什麼:邊調邊看的樣本一定會越調越好,它的零誤改只說明規則背下了這份樣本;拿它當達標的證據,誤改要到換一批資料才現形,那時規則已經定案、下游都照它做了

## good example
- clarify 用來調,**specify 留到定案才跑**;一跑就現誤改,所以改標調規則,再留第三支驗收
```
調整用:clarify;驗收用:specify 46 分鐘(定案前不看)
定案後跑 specify:想像→想象 3 次、file→Filte → 看過又調整,specify 改標「調規則」
再驗收:artifact-to-skill 13 分鐘(定案後才看)

| 樣本 | 用途 | 替換筆數 | 明顯誤改 |
| clarify | 調規則 | 5 | 0 |
| specify 46 分鐘 | 調規則 | 23 | 0 |
| artifact-to-skill 13 分鐘 | 未用於調整 | 3 | 0 |
```

## bad example
- 同一個研究項,**只在 clarify 上邊看邊調**;零誤改寫進理由,要到後來有人跑 46 分鐘影片才現大量誤改
```
| 樣本 | 替換筆數 | 明顯誤改 |
| clarify | 27 | 0 |
決策:規則定案,SC-001 達標
```

## good example
- 邊界:specify 跑過之後**只收緊了一條條件**,看起來它幾乎沒被用來調;但收緊是因為看了它的結果,所以不再算沒看過,達標的數字改列待驗證
```
specify 的誤改 → 收緊「英文相似度至少 0.6」
specify 用途:調規則
待驗證:SC-001 的 90%,沒有別的未看過樣本
```

## bad example
- 邊界:同一次收緊,因為規則只改一條就**繼續把 specify 算成驗收用**;它的 23 筆全對,正是因為規則剛依它改過
```
specify 的誤改 → 收緊「英文相似度至少 0.6」
specify 用途:驗收,23 筆全對 → SC-001 達標
```

## good example
- 邊界:規則沒有依 store-c 調過,但**列檔時就把它的品項與答案印出來了**;內容影響過規則的設計,所以照實改標,達標的數字列待驗證
```
列印樣本時讀過 store-c 的品項與答案
store-c 用途:調規則(讀過內容)
待驗證:SC-001 的 95%,沒有別的未看過樣本
```

## bad example
- 邊界:同一份樣本,因為**只有結果沒看過**就標「未用於調整」;讀過內容的人寫規則時已經想著它,5/5 不能當驗收的成績
```
列印樣本時讀過 store-c 的品項與答案
store-c 用途:未用於調整,5 筆全對 → SC-001 達標
```

## good example
- 邊界:決策是選工具版本,**沒有東西是依樣本調出來的**;不必分樣本
```
實測(同一支影片):Tesseract 5.5 比 5.3 快 12%,輸出相同
決策:用 5.5
```

## bad example
- 邊界:同一個決策,也**硬留一支影片不看**;版本之間沒有參數可以背下樣本,多留的樣本什麼都沒驗到
```
調整用:clarify;驗收用:specify(定案前不看)
決策:用 5.5
```

# Rule 8 [must] - 規則型決策寫出可重現的完整定義
- 決策是一組判斷條件(比對、替換、分類、過濾)時,research.md 的決策寫出完整定義:每個詞怎麼切、怎麼比較、判斷順序、每個例外與每個參數值;只看文字就能重寫出同一支探針
- 寫完逐條對照探針的程式碼;文字和探針有一處不同,就改到相同,不留差異
- 為什麼:決策只寫大意時,探針測的是一套規則,下游照文字做的是另一套;表裡的數字仍然好看,結構檢查也會過,要到分析或實作才發現數字不屬於寫下來的這套規則,研究項要重來

## good example
- 探針實際的判斷**全部寫進決策**:近音、連字號、大小寫都有明文,照文字重寫得出同一支探針
```
- 中文:兩字以上、字數相同;lazy_pinyin 不計聲調,zh/z、ch/c、sh/s、ing/in 視為相同後逐字相等
- 英文詞:比較時去掉空白、-、_、. 並轉小寫,相似度至少 0.6;比對鍵相同時,舊詞有空白且新寫法有連字號才換;只差大小寫一律不換
```

## bad example
- 同一套探針,**文字只寫大意**;探針把 `鉗子/前置` 算同音、把連字號去掉再比,文字都沒寫,實作照文字做出來的筆數就對不上
```
- 中文:同音才替換
- 英文詞:只含英文與數字、拼法相近才替換,大小寫不同的縮寫要換
```

## good example
- 邊界:difflib 的比對細節由函式庫決定,**寫出函式與參數就能重現**,不必重述演算法
```
- 對齊:difflib.SequenceMatcher(autojunk=False) 的 opcodes,只看 replace 區塊
```

## bad example
- 邊界:同一個對齊,**只寫「用相似度比對」**;換一個函式或開著 autojunk,對齊結果就不同,文字重現不出探針
```
- 對齊:用相似度比對兩段文字
```

# Rule 9 [must] - 規則型決策的數字用最終定義重跑
- 規則型決策標「實測」的筆數與正確率,都要由最終定義的探針跑出來;定義改過,包括寫 research.md 時才改的條件,就重跑,看到新數字才寫上去
- 中間版本的結果可以留在理由裡說明為什麼改,要寫明它是哪一版,不和最終結果放在一起比
- 為什麼:定義最後改的那一筆最容易沒重跑,因為改動看起來很小;數字留在舊版,讀的人卻會當成寫下來這套規則的成績,而被改掉的條件可能正好影響筆數

## good example
- 寫 research.md 時才決定只差大小寫不換,**重跑之後數字變了就照實改**
```
定案:只差大小寫一律不換
重跑最終探針:artifact-to-skill 由 4 筆變 3 筆
表格寫 3 筆
```

## bad example
- 同一次改動,覺得只動一個條件就**沿用舊數字**;文字寫不換,表格裡的 4 筆卻含一筆大小寫替換
```
定案:只差大小寫一律不換
未重跑
表格寫 4 筆
```

## good example
- 邊界:看起來只改了措辭,但**只憑文字確定不了判斷結果不變**,照樣重跑,逐筆清單相同才算確認
```
「只含英文與數字」改寫成「只含英文、數字與 .-_+'」,對照探針本來就允許這些字元
重跑:逐筆清單與前一次相同,數字不變
```

## bad example
- 邊界:同一次改寫,**憑印象認定只是措辭**;其實探針的字元集比原文寬,改寫後才相符,但沒有人確認過
```
「只含英文與數字」改寫成「只含英文、數字與 .-_+'」,只是措辭,不重跑
```
