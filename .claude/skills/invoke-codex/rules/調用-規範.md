# Rule 1 [must] - 非互動執行必用 codex exec
- 在 subshell、腳本或 automated agent 工具中調用時，必須使用 `codex exec` 子指令，禁止裸調用 `codex`
- 為什麼:裸調用 `codex` 會啟動互動式 TUI，在非互動的終端或 headless 環境中會因缺乏 TTY 終端而立即失敗或卡住

## good example
- 使用非互動子指令 `codex exec`
```bash
codex exec -C . -o /tmp/codex_out.txt - < /tmp/prompt.md
```

## bad example
- 裸調用 `codex`，在非互動環境觸發 TUI
```bash
codex "請幫我重構 OrderService"
```

# Rule 2 [must] - 以檔案或 stdin 傳遞 prompt
- 傳遞給 `codex exec` 的提示詞必須存成暫存檔並以 stdin 重導向傳入（如 `- < /path/to/prompt.md`），禁止在 shell 命令列以字串參數直接傳入多行 prompt
- 為什麼:多行字串在 shell 命令列容易遭遇雙引號、單引號、變數展開 `$VAR` 或特殊字元截斷，導致語法錯誤使命令執行失敗

## good example
- 將 prompt 存為檔案後透過 stdin 導向傳給 `codex exec`
```bash
codex exec -C /project --dangerously-bypass-approvals-and-sandbox -o /tmp/codex_out.txt - < /tmp/task_prompt.md
```

## bad example
- 在命令列以多行字串直接作為 prompt 參數傳入
```bash
codex exec -C /project --dangerously-bypass-approvals-and-sandbox -o /tmp/codex_out.txt "重構函式：process_tax\n請注意變數與引號"
```

# Rule 3 [must] - 明確指定沙盒與授權策略
- 調用 `codex exec` 時必須明確提供沙盒與審批授權參數，例如在外部受控環境使用 `--dangerously-bypass-approvals-and-sandbox`，或在需要工作區保護時使用 `-s workspace-write --approve-for-me`
- 為什麼:未指定沙盒與授權旗標時，Codex 預設會以 `OnRequest` 等待使用者在 stdin 互動確認，在 automated CLI agent 環境中會因無人輸入而逾時或失敗

## good example
- 明確指定沙盒與自動審批旗標
```bash
codex exec -C /project --dangerously-bypass-approvals-and-sandbox -o /tmp/codex_out.txt - < /tmp/task_prompt.md
```

## bad example
- 未指定沙盒與審批授權參數，導致等待 stdin 確認
```bash
codex exec -C /project -o /tmp/codex_out.txt - < /tmp/task_prompt.md
```

# Rule 4 [must] - 指定輸出檔與工作目錄
- 調用 `codex exec` 時必須使用 `-C <dir>` 指定目標工作根目錄，並使用 `-o <file>` 指定輸出檔案路徑以完整捕獲最後產出訊息
- 為什麼:未指定 `-C` 會導致 Codex 在未預期的目錄執行而找不到檔案或寫錯路徑；未指定 `-o` 會使執行結果混在標準輸出的日誌中難以乾淨提取

## good example
- 同時指定工作目錄 `-C` 與輸出檔 `-o`
```bash
codex exec -C /home/user/repo --dangerously-bypass-approvals-and-sandbox -o /home/user/repo/.codex_out.txt - < /tmp/task_prompt.md
```

## bad example
- 缺少 `-C` 與 `-o`，目錄依賴當前環境且無法單獨取得最後訊息
```bash
codex exec --dangerously-bypass-approvals-and-sandbox - < /tmp/task_prompt.md
```

# Rule 5 [must] - 調用前確認 git baseline
- 在執行 `codex exec` 前，必須先執行 `git status --porcelain` 確認或記錄當前工作區狀態，確保無未預期的未追蹤或未提交改動
- 為什麼:調用前工作區若有未提交的髒檔案，調用完成後無法透過 `git diff` 清楚辨別哪些變更是 Codex 產生的，導致驗收無依據

## good example
- 調用前先檢查工作區並確認乾淨基準
```bash
git status --porcelain
codex exec -C /project --dangerously-bypass-approvals-and-sandbox -o /tmp/codex_out.txt - < /tmp/task_prompt.md
git diff
```

## bad example
- 調用前未檢查 git 狀態即直接執行，無法分辨變更來源
```bash
codex exec -C /project --dangerously-bypass-approvals-and-sandbox -o /tmp/codex_out.txt - < /tmp/task_prompt.md
git diff
```
