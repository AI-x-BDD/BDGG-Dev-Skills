# Rule 1 [must] - 驗收案例對應已確認成果
- 新建用代表性輸入走完整流程；優化重跑原失敗案例，並檢查受改動影響、原本應正常的情境。改到觸發或分支時涵蓋相應邊界。
- 寫出每個案例的輸入、預期、實際結果與證據；有工具或外部寫入的操作，在隔離副本或明確授權範圍內執行。
- 為什麼：格式合規只能證明文件結構正確，不能證明使用者的不滿已消除。

## good example
- 重複提問的優化同時檢查兩條路徑。
完整且已確認的格式直接寫入；缺少格式時詢問缺口。記錄實際在哪一步停下與哪些檔案改變。

## bad example
- 同一次優化只看檔案樣子。
看到 Ask 新增條件，就宣稱重複提問已解決，沒有跑完整資料與缺資料的案例。

# Rule 2 [must] - 驗收對照實際檔案的整合狀態
- 讀回成品，核對適用 Forms 的把關結果、資源引用、跳轉位址、上下游輸入輸出、已移除內容的使用端，以及重複或無人使用的部件。
- 所在 repo 有鏡像要求時，同步本次變更並比較內容；保留無關的使用者變更。
- 為什麼：每個部件個別合格，仍可能在組合後出現斷鏈、錯誤跳轉或兩份規則互相矛盾。

## good example
- 同一個刪步驟操作完成後檢查實物。
讀回 SOP，發現行尾仍跳到已刪的 Step 4，修正後再核對資源與上下游；鏡像也包含相同修正。

## bad example
- 同一個操作只檢查草稿。
草稿中的跳轉正確就回報通過，實際檔案仍指向 Step 4，另一個 skills 目錄也未更新。

# Rule 3 [must] - 驗收失敗回到造成問題的階段
- 實作不符方案時，在已確認範圍內修正後重驗；方案本身不足時回到 Phase 3 Step 2，根因被推翻時回到 Phase 2 Step 1，預期改變時回到 Phase 1 Step 1。
- 新建沒有舊診斷可推翻時，依問題回到預期或方案；不要為了套流程虛構舊 Skill 的根因。
- 外部依賴或資料不足時，說明阻礙與已完成項目，暫停受影響的驗收；不能以待驗證當成通過，也不反覆修改無關內容。
- 為什麼：不同原因需要不同處理，盲目補規則會把驗收失敗變成新的維護負擔。

## good example
- 邊界：結果推翻原假說時重做診斷。
完整交接後仍重問，紀錄顯示下游無條件 Ask；回到診斷，提出新證據並等待確認，才重做方案。

## bad example
- 邊界：同樣推翻原假說卻繼續疊加。
仍沿用「上游漏傳」診斷，在入口再加一條「一定要完整交接」，沒有處理下游證據。

# Rule 4 [must] - 交付區分實測與推演
- 回報改了什麼、刪了什麼及原因、哪些案例通過、哪些只做文字推演或受阻；未經使用者實際驗證的 Skill 保留「未驗證」標記。
- 根因假說與尚未驗證事項不能因為檔案寫完就變成已證實；提供使用者可直接試用的情境。
- 為什麼：使用者需要知道成果的可信範圍，才能決定如何採用與回饋。

## good example
- 靜態核對完成時如實交付。
「引用與鏡像一致；已推演診斷閘門，尚未在實際對話試用，維持未驗證。可用一次不滿意的輸出測試是否先停在診斷確認。」

## bad example
- 同樣只有靜態核對卻擴大結論。
「所有情境均通過，已驗證能找到根因。」沒有任何對話實測證據。

# Rule 5 [must] - Skill 成品可脫離本次對話執行
- 目標 Skill 包含日後獨立執行所需的資訊，不依賴本次對話。
- 診斷與方案可留在對話或既有工作紀錄；驗證紀錄不混入目標 Skill 的執行指令。
- 為什麼：日後執行者看不到這次討論，把必要指令留在對話會缺資訊，把歷史紀錄混入流程則會增加無關上下文。

## good example
- 成品包含必要資訊，歷史紀錄另外保留。
Skill 寫明輸入欄位與缺漏處理；這次如何發現缺欄位、用了哪筆測試資料，留在工作紀錄。

## bad example
- 同一成品依賴只有本次對話才知道的資訊。
Skill 寫「依剛才確認的欄位處理」，沒有列出欄位；日後執行者必須找回原對話才能使用。
