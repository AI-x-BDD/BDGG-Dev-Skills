# Rule 1 [must] - 只判跨檔的問題
- 列進問題表的,是兩份以上產出物對不上的地方:互相矛盾、一邊有一邊沒有、任務做不出需求、任務追溯不到需求、產出物違反憲法
- 單份文件內的模糊、重複與 TODO 佔位不列為問題,寫進「轉交 `/clarify-over-specs`」,寫出哪裡模糊、下游因此沒辦法做什麼
- 為什麼:單份文件內的缺口由 clarify-over-specs 分面向盤點與澄清;這裡也判一次,兩支 Skill 的判準會不一致,同一個缺口還可能被兩邊各改一次

## good example
- `spec.md` 的 NFR-002 只寫「結帳頁要快速載入」,別的產出物都沒有和它衝突;**這是單份文件內的模糊,寫進轉交表**
```
轉交 /clarify-over-specs
| `spec.md` § NFR-002 | 「結帳頁要快速載入」沒有可量測的門檻,下游沒辦法據以設計與驗收 |
```

## bad example
- 同一條 NFR-002,但**列進問題表、還給了嚴重度**;它沒有和任何一份產出物對不上,要它回 /specify 改,改法也只能由這一步自己猜門檻
```
| A7 | 遺漏 | HIGH | `spec.md` § NFR-002 | 結帳頁沒有效能門檻 | `/specify` |
```

## good example
- 邊界:NFR-002 寫「結帳頁 LCP ≤ 2.5 秒」,`research.md` § R5 卻決定結帳頁每次都即時算運費、預估要 4 秒;**模糊的字一個也沒有,是兩份產出物互相矛盾,列為問題**
```
| A7 | 矛盾 | HIGH | `spec.md` § NFR-002;`research.md` § R5 | NFR-002 要 LCP ≤ 2.5 秒,R5 決定即時算運費、預估 4 秒 | `/technical-research` |
```

## bad example
- 邊界:同一個情況,因為「牽涉到效能門檻」就當成模糊轉交;**門檻本身寫得很清楚**,clarify-over-specs 拿到也問不出東西,矛盾留到實作才被發現
```
轉交 /clarify-over-specs
| `spec.md` § NFR-002 | 結帳頁的效能要求不清楚 |
```

# Rule 2 [must] - 每個問題至少引用兩處產出物的原文
- 位置欄列出至少兩處,每一處寫成 `檔案` § 錨點;錨點是那份檔裡找得到的編號、段落名、operation、schema、Table、`data-state` 或 `#id`
- 摘要寫出各處原文分別怎麼寫;找不到原文依據的懷疑不列
- 憲法問題的其中一處是憲法條文:`constitution/<skill>/<產出物>.md` 〈Rule 名稱〉
- 為什麼:讀報告的人要回到原檔確認才會動手修;只寫結論,他得自己再找一次,找不到就會懷疑這一條是不是誤判

## good example
- 期限對不上的兩邊**都寫到錨點,摘要引了兩邊的原文**
```
| A2 | 矛盾 | HIGH | `spec.md` § FR-007;`contracts/shop.dbml` § `Table orders` | FR-007 寫「下單後 30 分鐘內未付款自動取消」,`orders.payment_expires_at` 的 note 寫 15 分鐘 | `/data-plan` |
```

## bad example
- 同一個問題,但**位置只寫檔名、摘要只有結論**;讀的人得把 DBML 從頭讀一遍才知道是哪一欄
```
| A2 | 矛盾 | HIGH | `contracts/shop.dbml` | 付款期限和需求不一致 | `/data-plan` |
```

## good example
- 邊界:「一邊有一邊沒有」的遺漏,沒有的那一邊找不到錨點;**有的那一邊寫錨點,沒有的那一邊寫到它應該出現的段落**
```
| A3 | 遺漏 | HIGH | `spec.md` § 使用者故事 3 驗收情境 2;`plan.md` § 端點盤點 | 驗收情境要「逾時取消的訂單在『我的訂單』顯示已取消」,端點盤點的 E1、E2 需求出處都沒列使用者故事 3 | `/system-analysis` |
```

## bad example
- 邊界:同一個遺漏,因為「沒有的那一邊沒有原文」就只寫一處;**讀的人不知道該去哪份檔補**
```
| A3 | 遺漏 | HIGH | `spec.md` § 使用者故事 3 驗收情境 2 | 這個驗收情境沒有被做出來 | `/system-analysis` |
```

# Rule 3 [must] - 嚴重度依判定表
- 依下表由上往下判定,先符合的先用

| 嚴重度 | 判準 |
|---|---|
| CRITICAL | 違反憲法 MUST 條文;核心需求在所有規格檔都沒有落地 |
| HIGH | 兩份產出物互相矛盾;驗收情境做不出來或測不到;技術決策沒有落地 |
| MEDIUM | 任務追溯不到需求;同一個概念在不同產出物叫法不同 |
| LOW | 措辭或冗餘,不影響實作 |

- CRITICAL 與 HIGH 會擋 `/implement`;不確定時選較高的一級,在摘要寫出理由
- 為什麼:嚴重度決定能不能開始實作;每次憑感覺給,同一種問題這一輪擋、下一輪不擋,判定就沒有人會信

## good example
- AsyncAPI 的 `Error` 缺 `traceId`,違反的是憲法 MUST 條文;**依表第一列,CRITICAL**
```
| A1 | 憲法 | CRITICAL | `constitution/api-plan/error.md` 〈錯誤回應一律帶 traceId〉;`contracts/shop.openapi.yaml` § `components.schemas.Error` | 憲法要求每個錯誤回應帶 `traceId`,`Error` 的 `required` 只有 `code`、`message` | `/api-plan` |
```

## bad example
- 同一個問題,因為「只差一個欄位」就給 MEDIUM;**憲法 MUST 被稀釋成可以晚點再修**,`/implement` 照樣開工
```
| A1 | 憲法 | MEDIUM | … | `Error` 少一個 `traceId` 欄位 | `/api-plan` |
```

## good example
- 邊界:原型把取消的訂單標成「已失效」,需求寫「已取消」;字不同但指的是同一個狀態,**是叫法不同,不是矛盾,MEDIUM**
```
| A6 | 矛盾 | MEDIUM | `spec.md` § 使用者故事 3 驗收情境 2;`prototype/orders.html` § `[data-state="cancelled"]` | 原型標「已失效」,需求寫「已取消」 | `/ui-plan` |
```

## bad example
- 邊界:同一個差異,因為類別寫了「矛盾」就給 HIGH;**兩邊指的是同一個狀態**,擋住實作卻沒有任何行為會做錯
```
| A6 | 矛盾 | HIGH | … | 原型標「已失效」,需求寫「已取消」 | `/ui-plan` |
```

# Rule 4 [must] - 回哪一步選最上游出錯的產出物
- 先找出對不上的幾份產出物裡,哪一份寫錯了;「回哪一步」寫那一份的 Skill,依下表對照
- 寫錯的不只一份時,寫最上游的那一份,下游在修正順序裡重跑

| 產出物 | Skill |
|---|---|
| `spec.md` 寫錯 | `/specify` |
| `spec.md` 寫得模糊 | `/clarify-over-specs` |
| `research.md`、`techstack.md` | `/technical-research` |
| `plan.md` | `/system-analysis` |
| OpenAPI、AsyncAPI | `/api-plan` |
| DBML | `/data-plan` |
| `prototype/` | `/ui-plan` |
| `deploy/` | `/deploy-plan` |
| `tasks.md` | `/tasks` |
| `constitution/` | `/constitution` |

- 為什麼:只修下游,上游那份錯的還在;下次有人照它重跑下游,同一個問題又會出現

## good example
- OpenAPI 沒有查訂單列表、原型沒有訂單頁,但根因是 `plan.md` 的端點盤點漏了使用者故事 3;**回最上游的 `/system-analysis`**
```
| A3 | 遺漏 | HIGH | `spec.md` § 使用者故事 3 驗收情境 2;`plan.md` § 端點盤點 | … | `/system-analysis` |
修正順序:1. `/system-analysis` 補需求出處(A3),再依序重跑 `/api-plan`、`/ui-plan`
```

## bad example
- 同一個遺漏,但**分別回 `/api-plan` 與 `/ui-plan`**;兩支補完了,`plan.md` 的端點盤點還是漏的,下次重跑系統分析又會少掉
```
| A3 | 遺漏 | HIGH | `contracts/shop.openapi.yaml`;`prototype/` | 沒有訂單列表 | `/api-plan`、`/ui-plan` |
```

## good example
- 邊界:FR-007 寫 30 分鐘,DBML 與 OpenAPI 都寫 15 分鐘;**上游的 spec.md 沒有寫錯**,錯的是兩份下游,兩支都要回
```
| A2 | 矛盾 | HIGH | `spec.md` § FR-007;`contracts/shop.dbml` § `Table orders`;`contracts/shop.openapi.yaml` § `checkout` | … | `/data-plan`、`/api-plan` |
```

## bad example
- 邊界:同一個矛盾,照「上游優先」機械地回 `/specify`;**spec.md 寫的才是對的**,要它改成 15 分鐘等於把需求改成遷就錯的實作
```
| A2 | 矛盾 | HIGH | … | … | `/specify` |
```

# Rule 5 [must] - 上一輪的問題沿用原編號
- 已有 analysis.md 時,上一輪還沒解決的每個問題都寫進「上一輪的問題」表,沿用原編號重判:已修正、已澄清或仍存在
- 仍存在的問題不另開新號;這一輪新找到的問題,編號接續目前最大的編號
- 為什麼:編號跨輪固定,前後兩輪才比得出哪些修好了;換了編號,讀的人只能逐條比摘要,修過的問題看起來像是又冒出新的

## good example
- 第 1 輪最大的編號是 A5,A4 這一輪仍存在;**A4 照原編號寫進上一輪的問題表**,新問題從 A6 起
```
### 上一輪的問題
| A4 | ❌ 仍存在 | `tasks.md` 還是沒有逾時取消的排程任務 |

### 新問題
| A6 | 矛盾 | MEDIUM | … |
```

## bad example
- 同一個情況,但**A4 換成新編號重列**;讀的人以為 A4 修好了,又多了一個 A6
```
### 新問題
| A6 | 無法實作 | HIGH | `research.md` § R3;`tasks.md` | 沒有逾時取消的排程任務 | `/tasks` |
```

## good example
- 邊界:修 A3 時新增的訂單頁,把取消的訂單標成「已失效」;**這是修正帶出的新問題,不是 A3 沒修好**,A3 標已修正,新問題另開 A6
```
### 上一輪的問題
| A3 | ✅ 已修正 | `plan.md` § 端點盤點的 E1、E2 列入使用者故事 3 |

### 新問題
| A6 | 矛盾 | MEDIUM | `spec.md` § 使用者故事 3 驗收情境 2;`prototype/orders.html` § `[data-state="cancelled"]` | … | `/ui-plan` |
```

## bad example
- 邊界:同一個情況,因為問題出在同一個頁面就把 A3 標成仍存在;**A3 要的訂單頁已經做出來了**,判定會因為一個 MEDIUM 的叫法差異而被擋住
```
### 上一輪的問題
| A3 | ❌ 仍存在 | 訂單頁取消狀態的文字不對 |
```

# Rule 6 [must] - 修正順序從上游往下游排
- 修正順序依產出物的上下游排:`spec.md` → `research.md`、`techstack.md` → `plan.md` → 規格檔與原型 → `tasks.md`
- 每一項寫出要回的 Skill、要修什麼與問題編號;修完會牽動下游的,寫出接著要重跑哪幾支
- 最後一項是重跑 `/analyze`
- 為什麼:先修下游,上游改完還得再修一次;漏了重跑,修正有沒有帶出新問題沒有人知道

## good example
- **`/system-analysis` 排第一、`/tasks` 排最後**,最後一項重跑 `/analyze`
```
1. `/system-analysis` 把使用者故事 3 補進 E1、E2 的需求出處(A3),再依序重跑 `/api-plan`、`/ui-plan`
2. `/api-plan` 補 `traceId`(A1)、期限改 30 分鐘(A2);`/data-plan` 期限改 30 分鐘(A2)
3. `/tasks` 補排程任務(A4)、刪 T031(A5),並涵蓋第 1 步新增的介面元素
4. 重跑 `/analyze`
```

## bad example
- 同一批問題,但**照編號排**;`/tasks` 先補完任務,第 1 步重跑 `/api-plan` 之後又多了介面元素,`/tasks` 得再跑一次
```
1. `/api-plan` 補 `traceId`(A1)
2. `/tasks` 補排程任務(A4)
3. `/system-analysis` 補需求出處(A3)
```

## good example
- 邊界:這一輪只有一個轉交項,沒有任何問題;**修正順序仍然寫出來,最後一項重跑 `/analyze`**
```
1. `/clarify-over-specs` 澄清 NFR-002
2. 重跑 `/analyze`
```

## bad example
- 邊界:同一個情況,覺得「只是澄清」就不寫修正順序;**NFR-002 澄清後的門檻,可能和 research 的決策對不上**,沒有人會回來重跑
```
### 修正順序
(無)
```
