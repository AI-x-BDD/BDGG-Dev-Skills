# Rule 1 [must] - ⚙ 只列這個任務做出來或測到的介面元素
- ⚙ 列的是這個任務做完時必須照規格成立的元素:實作任務列它做出來的,測試任務列它斷言的
- 這個任務只是讀到、拿來對照、不負責做出來的元素,寫進 📎,不寫進 ⚙
- 為什麼:⚙ 是這個任務的完成範圍,執行的人會逐一對照每個錨點;混進只是讀到的元素,他會去改不屬於這個任務的檔,真正要做的那幾個反而被淹沒

## good example
- 測試任務**只列它斷言的兩個 operation**;要知道錯誤碼怎麼寫,是從 📎 的 Q12 查
```
- [ ] T050 [P] [US2] 撰寫 `backend/test/rooms/secret.test.ts`:合法時只有本人收到 `secret.confirmed`、"1123" 回 `DIGITS_REPEATED`…
  - ⚙ `contracts/game.asyncapi.yaml` § `operations.receiveSecretSet`、`operations.sendSecretConfirmed`
  - 📎 `spec.md` § FR-009、FR-010;`plan.md` § 待決問題 Q12
```

## bad example
- 同一個任務,但**把讀到的 `Digits` 與 `Error` 也列進 ⚙**;執行的人以為這個測試要負責 `Digits` 的格式,又寫了一遍 T010 已經測過的案例
```
- [ ] T050 [P] [US2] 撰寫 `backend/test/rooms/secret.test.ts`:合法時只有本人收到 `secret.confirmed`、"1123" 回 `DIGITS_REPEATED`…
  - ⚙ `contracts/game.asyncapi.yaml` § `operations.receiveSecretSet`、`operations.sendSecretConfirmed`、`components.schemas.Digits`、`components.schemas.Error`
  - 📎 `spec.md` § FR-009、FR-010
```

## good example
- 邊界:前端畫面任務**做出原型的狀態,也送出與接收訊息**;兩種都是它做出來的,都列進 ⚙
```
- [ ] T064 [US2] 在 `frontend/src/pages/room.js` 加入「開始遊戲」:只有房主看得到;按下送 `game.start`
  - ⚙ `prototype/room.html` § `.js-start`、`[data-state="host-ready"]`;`contracts/game.asyncapi.yaml` § `operations.receiveGameStart`
  - 📎 `spec.md` § FR-008
```

## bad example
- 邊界:同一個任務,覺得前端只是「照著合約送」,**把它送出的 operation 移到 📎**;覆蓋表的 `receiveGameStart` 就少了前端這一端,前端漏送也沒有人發現
```
- [ ] T064 [US2] 在 `frontend/src/pages/room.js` 加入「開始遊戲」:只有房主看得到;按下送 `game.start`
  - ⚙ `prototype/room.html` § `.js-start`、`[data-state="host-ready"]`
  - 📎 `spec.md` § FR-008;`contracts/game.asyncapi.yaml` § `operations.receiveGameStart`
```

# Rule 2 [must] - 介面元素歸到第一個需要它的 phase
- 每個介面元素第一次列進介面覆蓋表,是在第一個要把它做出來的 phase
- 後面的 phase 擴充同一個元素的行為時,任務照樣在 ⚙ 列它,並在那個 phase 的覆蓋表再列一列,錨點後面標出擴充的範圍(例如 `reason` 的值或遊戲中的路徑)
- 為什麼:元素放在最後才用到的 phase,前面的故事會缺一塊、做不成獨立可交付;同一個元素不標範圍地重複列,看不出哪一列的實作才算數

## good example
- `receiveRoomLeave` **在 US1 做出等待中的離開**,US3 擴充遊戲中的路徑時標出範圍
```
介面覆蓋(US1)| `game.asyncapi.yaml` § `operations.receiveRoomLeave`(等待中) | T039、T043 | T032 |
介面覆蓋(US3)| `game.asyncapi.yaml` § `operations.receiveRoomLeave`(遊戲中) | T077、T081 | T072 |
```

## bad example
- 同一個元素,因為遊戲中離開最複雜就**只放在 US3**;US1 做完時房間不能離開,它的獨立測試跑不過
```
介面覆蓋(US3)| `game.asyncapi.yaml` § `operations.receiveRoomLeave` | T039、T077、T081 | T032、T072 |
```

## good example
- 邊界:`sendError` 每個故事都會送,**歸到第一個做出它的 Foundational**;後面的故事只在任務的 ⚙ 列它送出的錯誤情境
```
介面覆蓋(Foundational)| `game.asyncapi.yaml` § `operations.sendError`、`components.schemas.Error` | T015、T019 | T034 |
```

## bad example
- 邊界:同一個元素,因為每個故事都用到就**每張表各列一次、不標範圍**;三列看起來都對,但看不出哪一列的實作才是 `sendError` 本身
```
介面覆蓋(US1)| `game.asyncapi.yaml` § `operations.sendError` | T019 | T034 |
介面覆蓋(US2)| `game.asyncapi.yaml` § `operations.sendError` | T019 | T050 |
介面覆蓋(US3)| `game.asyncapi.yaml` § `operations.sendError` | T019 | T070 |
```

# Rule 3 [must] - 📎 指到最小的那一段
- 📎 的每個引用寫到能直接找到那句話的位置:FR、NFR、SC、驗收情境的編號,research 的 R 編號,plan.md 的 Q 編號,或段落名
- 不寫整份文件或整個章節;`§ 全檔` 只用在原樣複製整個檔的任務
- 為什麼:📎 是執行的人判斷細節時回頭查的地方;指到一整章,他得自己猜是哪一句,猜錯了就照著錯的那句做

## good example
- 依據**指到兩條 FR 與一個 Q**
```
  - 📎 `spec.md` § FR-009、FR-010;`plan.md` § 待決問題 Q10
```

## bad example
- 同一個任務,但**指到整個故事與整張待決問題表**;故事 2 有 7 條 FR、待決問題有 22 題,執行的人不知道該看哪一條
```
  - 📎 `spec.md` § 使用者故事 2;`plan.md` § 待決問題
```

## good example
- 邊界:跨端點驗收任務要照的就是**故事的獨立測試與整組驗收情境**;寫段落名與情境範圍,已經是最小的那一段
```
  - 📎 `spec.md` § 使用者故事 1 獨立測試、驗收情境 1–5
```

## bad example
- 邊界:同一類任務,寫了 `§` 看起來有錨點,但**錨點是整份文件的大標題**;和只寫檔名沒有差別
```
  - 📎 `spec.md` § 使用者情境與測試
```

# Rule 4 [must] - 一個任務裡有依序的幾件事才拆成帶字尾的子任務
- 任務的完成範圍(⚙ 與要改的檔)已經是一件事,就維持單一編號,不拆
- 一個三位數底下要依序做兩件以上、各自能單獨驗收的事(例如先寫失敗的測試、再實作),才拆成 `T012a`、`T012b`…;每個子任務自己寫 ⚙ 與 📎
- 字尾從 `a` 起、依序不跳號;同一個三位數拆了就沒有不帶字尾的 `T012`,不能 `T012` 與 `T012a` 並存
- 為什麼:拆成帶字尾的子任務,後面的任務與覆蓋表仍引用同一個三位數系列,不必整份重新編號;跳號或並存會讓檢查腳本認不得編號,也看不出缺了哪一步

## good example
- `T050` 要先寫測試再實作,**拆成 `T050a`、`T050b`**,字尾從 `a` 起、沒有不帶字尾的 `T050`
```
- [ ] T050a [US2] 撰寫 `backend/test/rooms/secret.test.ts`:"1123" 回 `DIGITS_REPEATED`,先確認失敗
  - ⚙ `contracts/game.asyncapi.yaml` § `operations.receiveSecretSet`
- [ ] T050b [US2] 實作 `backend/src/rooms/secret.ts`,讓 T050a 轉綠
  - ⚙ `contracts/game.asyncapi.yaml` § `operations.receiveSecretSet`
```

## bad example
- 同一個三位數**跳過 `a` 從 `b` 開始,又保留不帶字尾的 `T050`**;檢查腳本不認這種編號,讀的人也不知道 `T050` 與 `T050b` 誰先誰後
```
- [ ] T050 [US2] 撰寫 `backend/test/rooms/secret.test.ts`:"1123" 回 `DIGITS_REPEATED`
- [ ] T050b [US2] 實作 `backend/src/rooms/secret.ts`,讓 T050 轉綠
```

## good example
- 邊界:一個任務只改一個檔、做一件事,**維持 `T051` 不加字尾**
```
- [ ] T051 [P] [US2] 建立 `backend/src/rooms/secret-view.ts`:只回傳本人的 `secret.confirmed`
```

## bad example
- 邊界:同樣是一件事,**只因為想「留彈性」就寫成 `T051a`、後面沒有 `T051b`**;字尾只用在真的拆成兩件以上
```
- [ ] T051a [P] [US2] 建立 `backend/src/rooms/secret-view.ts`:只回傳本人的 `secret.confirmed`
```

# Rule 5 [must] - 驗收情境經過的每一段處理都有任務
- 每一個驗收情境,從觸發它的操作一路走到使用者看到的結果,經過的每一段處理都要有實作任務負責:背景工作、每一種輸入來源的分支、畫面上顯示這段結果的元素都算;畫面上的元素包含前端腳本在瀏覽器裡的處理:打開編輯器、切換版本、確認對話框,以及切換之後要跟著更新的其他區塊
- 介面元素清單列不到的那一段,另外排一個實作任務,⚙ 寫觸發它的操作,或顯示它的 schema
- 為什麼:`list_elements.py` 只列得出路由、表與 data-state,背景流程、schema 裡的欄位與前端腳本在瀏覽器裡的處理不在清單上;只照清單排任務,這些段落沒有人負責,到實作時才發現驗收情境走不完

- 「上傳影片後看到筆記」要經過上傳路由、背景整理流程、筆記頁;**整理流程接上傳來源的那一段不是介面元素,另外排一個任務**,⚙ 寫觸發它的操作

# Rule 6 [must] - 為了讓介面元素成立而必須改的既有檔都有任務
- 介面元素要照規格成立、卻不在介面元素清單上的既有檔,每一個都要有任務負責,或寫進某個任務的檔案清單:
  - 原型增補的樣式要搬到的共用樣式檔
  - 讓樣板與路由共用同一個函式的註冊點
  - 被改掉或移除的符號在既有程式裡的每一個呼叫端;呼叫端從既有程式搜出來,不憑記憶列
  - 新增列舉值、狀態或類型時,同一個概念的每一份清單(常數、對應表、樣板裡的列表);以既有的同類值從既有程式搜出來,逐份判斷新值要不要加
- 為什麼:介面元素清單只列規格檔裡的元素,為了讓它們成立而要跟著改的既有檔不在任何規格檔上;沒有任務提到它們,implement 做到一半才發現要改,只能塞進某個任務再回 plan.md 追認,使用者確認任務清單時看不到這些改動,任務的完成範圍也對不上實際改到的檔

## good example
- `app/config.py` 拿掉推導屬性,**搜出用到它們的 4 個檔,寫進同一個任務的檔案清單**

# Rule 15 [must] - verify-plan.md 的每一項都有任務
- spec.md 所在的資料夾有 verify-plan.md 時,每個 V 編號至少有一個任務,任務寫出它的實跑做法、通過條件與護欄,放在那個對象所屬的 phase
- 沒有這個檔時,這條不適用
- 為什麼:規劃了不排任務,實作時就會回到只跑自動測試;護欄不抄進任務,做事的 subagent 看不到
