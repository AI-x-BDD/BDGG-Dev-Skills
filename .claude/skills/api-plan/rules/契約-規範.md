# Rule 1 [must] - 伺服器把關的條件都有具名的錯誤
- 需求要伺服器把關的每一個條件:誰能呼叫、什麼狀態下能呼叫、輸入的格式與範圍,都要在那個操作的 `x-error-codes` 寫出一個具名的錯誤碼
- 一個錯誤碼只對應一種不符的原因;不同原因不共用同一個錯誤碼
- 為什麼:沒有錯誤碼的條件,實作的人只會在畫面上把按鈕藏起來,伺服器照樣受理;共用一個錯誤碼,呼叫的一方分不出要提示「先登入」還是「庫存不足」

## good example
- 結帳要把關三個條件,**每一個條件都有自己的錯誤碼**
```yaml
  /checkout:
    post:
      operationId: checkout
      x-callers: 已登入的買家,購物車不為空
      responses:
        '401':
          description: 未登入
          x-error-codes: [NOT_LOGGED_IN]
        '409':
          description: 購物車是空的,或有商品庫存不足
          x-error-codes: [CART_EMPTY, OUT_OF_STOCK]
```

## bad example
- 同一個操作,但**只寫了一個籠統的錯誤碼**;三個條件哪一個不符,呼叫的一方都只拿到同一個碼
```yaml
  /checkout:
    post:
      operationId: checkout
      x-callers: 已登入的買家,購物車不為空
      responses:
        '400':
          description: 結帳失敗
          x-error-codes: [CHECKOUT_FAILED]
```

## good example
- 邊界:「數量 1 到 99」看起來只是輸入框的限制,schema 也寫了 `minimum`、`maximum`;但**需求要伺服器把關數量範圍,所以它也有一個錯誤碼**
```yaml
  /cart/items:
    post:
      operationId: addCartItem
      x-callers: 任何訪客
      responses:
        '400':
          description: 數量不在 1–99
          x-error-codes: [INVALID_QUANTITY]
        '404':
          description: 商品不存在或已下架
          x-error-codes: [PRODUCT_NOT_FOUND]
```

## bad example
- 邊界:同一個操作,因為 schema 已經有 `minimum: 1`、`maximum: 99` 就**沒有寫錯誤碼**;直接呼叫 API 送 `quantity: 0`,沒有任何一個錯誤碼說明伺服器要怎麼回
```yaml
  /cart/items:
    post:
      operationId: addCartItem
      x-callers: 任何訪客
      responses:
        '404':
          description: 商品不存在或已下架
          x-error-codes: [PRODUCT_NOT_FOUND]
```

# Rule 2 [must] - 回應與推送寫明收件者與可見欄位
- 每個成功的回應與每個訊息都用 `x-recipients` 寫出誰收得到
- 同一個事件對不同收件者可見的欄位不同時,每一種收件者各寫一個訊息與各自的 schema,不共用一份
- 為什麼:只寫一份「訂單狀態」,實作的人會把同一份資料送給每個收件者,需求要保密的欄位(買家地址、付款細節)就送到了不該拿到的人手上

## good example
- 付款完成時,買家與賣家要看的不一樣;**兩種收件者各一個訊息,賣家那一份沒有付款細節**
```yaml
  messages:
    orderPaidForBuyer:
      name: order.paid
      x-recipients: 訂單的買家
      payload:
        $ref: '#/components/schemas/OrderPaidForBuyer'
    orderPaidForSeller:
      name: order.paid
      x-recipients: 訂單的賣家
      payload:
        $ref: '#/components/schemas/OrderPaidForSeller'
```

## bad example
- 同一個事件,但**只有一個訊息、一份 schema**;賣家照樣收到卡號末四碼
```yaml
  messages:
    orderPaid:
      name: order.paid
      x-recipients: 訂單的買家與賣家
      payload:
        $ref: '#/components/schemas/OrderPaid'
```

## good example
- 邊界:商品列表對每個訪客都一樣,看起來不需要分收件者;**仍然寫出 `x-recipients`**,只是一種
```yaml
      responses:
        '200':
          description: 這一頁的商品摘要與總數
          x-recipients: 呼叫者
```

## bad example
- 邊界:同一個回應,因為大家看到的都一樣就**沒有寫收件者**;之後加了只給賣家看的成本價,沒有人會想到這裡要分收件者
```yaml
      responses:
        '200':
          description: 這一頁的商品摘要與總數
```

# Rule 3 [must] - 只寫對外的介面,不寫內部實作
- 規格檔只寫呼叫的一方看得到的東西:路徑或訊息名稱、參數、回應、推送、錯誤碼、格式與計時
- 不寫類別、函式、資料表、欄位的儲存方式、伺服器上的檔案路徑
- 為什麼:這些屬於其他介面(資料、部署)的分析步驟;規格檔先寫了,那幾步會被當成已經定案照抄,或者兩邊各寫一套互相打架

## good example
- 庫存不足時,**只寫呼叫的一方會拿到的錯誤碼**
```yaml
        '409':
          description: 購物車是空的,或有商品庫存不足
          x-error-codes: [CART_EMPTY, OUT_OF_STOCK]
```

## bad example
- 同一個回應,但**寫了庫存怎麼扣、存在哪張表**;這是資料分析那一步的範圍
```yaml
        '409':
          description: OrderService.checkout() 在 transaction 裡 UPDATE inventory SET stock = stock - ?,不足時 rollback
          x-error-codes: [CART_EMPTY, OUT_OF_STOCK]
```

## good example
- 邊界:「訂單編號是 `ORD-` 開頭」看起來像資料庫怎麼存;但**它是呼叫的一方拿到、會顯示給買家的格式**,屬於對外的介面
```yaml
        orderId:
          type: string
          pattern: '^ORD-[A-Z0-9]{8}$'
```

## bad example
- 邊界:同一個欄位,也在講編號,但**寫的是它在資料庫裡怎麼產生**;呼叫的一方看不到,也不該依賴
```yaml
        orderId:
          type: string
          description: 由 orders.id 的 AUTO_INCREMENT 加上 ORD- 前綴產生
```

# Rule 4 [must] - 前幾步定下的照原文用,不另起
- 理由欄點名的前幾步產出裡已經定下的名稱、參數、格式與簽章,在規格檔裡照原文使用,不改名、不換格式、不重新設計
- 照原文用會和需求或這次的介面衝突時,不自行改寫,把衝突列進交出時的待決問題
- 為什麼:前幾步的產出是同一個功能其他介面的依據,那幾步已經照它寫完了;這裡改了名稱或格式,兩份產出對不上,實作時才會發現要整個重做

## good example
- 前一步 S1 分析金流商時定下通知的參數與回應;**這次照原文用,沒有換成自己的命名**
```yaml
    PaymentNotify:
      type: object
      required: [MerchantTradeNo, RtnCode, TradeAmt, CheckMacValue]
    PaymentAck:
      type: string
      enum: ['1|OK']
```

## bad example
- 同一個通知,但**把參數改成自己喜歡的命名**;金流商不會照我們的名字送,這個端點收不到任何一筆通知
```yaml
    PaymentNotify:
      type: object
      required: [orderId, success, amount, signature]
    PaymentAck:
      type: object
      required: [ok]
```

## good example
- 邊界:S1 定的交易編號最多 20 碼,但需求要的訂單編號超過;**照原文用會衝突,不自己改,列進待決問題**
```
待決問題
- Q1:S1 規定 MerchantTradeNo 最多 20 碼,FR-012 要求的訂單編號 ORD- + 店號 + 日期 + 流水號共 24 碼;要縮短訂單編號,還是另給金流一組對照編號?
```

## bad example
- 邊界:同一個衝突,**自己決定另給金流一組編號**;看起來解決了,但這個決定改到 S1 的對照方式與需求的訂單編號,沒有人同意過
```yaml
        paymentTradeNo:
          type: string
          maxLength: 20
          description: 另外產生給金流用的 20 碼編號
```
