# Double Diamond Principle(雙鑽石原則)

> 驗證狀態:**未驗證** —— 尚未經學員在真實專案上連續使用並觀察。已用 skill-creator 的評測機制做過兩輪 agent 對照測試(2026-10-05,測試題在 `evals/evals.json`),並依結果修訂過;那是 agent 測 agent,不能取代人的觀察。

## 它是什麼

Double Diamond 是英國 Design Council 於 2004 年發表的設計流程示意圖。兩顆鑽石各代表一次「先把問題或選項**打開**(divergent thinking,發散),再**收攏**成明確的行動(convergent thinking,收斂)」:

```
        第一顆鑽石                    第二顆鑽石
   「designing the right thing」  「designing the thing right」
      做對的事                       把事做對

      ╱‾‾‾‾‾‾‾╲                    ╱‾‾‾‾‾‾‾╲
挑戰 ◇ Discover  Define ◇ 明確的問題 ◇ Develop  Deliver ◇ 成果
      ╲_______╱                    ╲_______╱
       發散      收斂                 發散      收斂
```

四個階段(Design Council 原文):

| 階段 | 原文的說明 |
|---|---|
| **Discover** | 幫助人們**理解、而不是直接假設**問題是什麼。做法是去和受這個問題影響的人交談、相處。 |
| **Define** | 從 Discover 得到的洞察,可以幫你**用不同的方式定義這個挑戰**。 |
| **Develop** | 鼓勵人們對這個已經清楚定義的問題**給出不同的答案**,向別處尋找靈感,並與不同的人共同設計。 |
| **Deliver** | **小規模地測試**不同的解法,淘汰行不通的、改進行得通的。 |

它存在的理由,是我們太容易跳過第一顆鑽石:需求一到手就開始想怎麼做,結果把一個沒人需要的東西做得很好。

## 重要:這不是一條直線

原文特別強調這不是線性流程。三件事會讓你往回走,而且都是正常的:

- **對根本問題有了新的認識**,可能把你送回起點。
- **製作並測試非常早期的想法,本身可以是 Discover 的一部分** —— 有時候要先做個粗糙的東西,才問得出真正的需求。
- **沒有任何想法是「完成」的**。上線之後會持續收到回饋,持續改進。

所以每個階段結束時都問一句:「我剛才學到的東西,有沒有動搖前面的結論?」有就回去改,並且說出來。

## 套用到一次軟體功能開發

> 下面的對應是**本 skill 的詮釋**。Double Diamond 原本是通用的設計流程,官方頁面沒有規定它在軟體開發中該怎麼做;這裡把每個階段的原意轉譯成開發時可以實際採取的動作。

按需求的不確定程度調整深度(見〈適用條件與例外〉),但四個階段都要走過、都要留下紀錄。

### 1. Discover —— 發散:搞清楚實際情況

目標是把「我以為」換成「我看到」。原文的關鍵字是 *understand, rather than simply assume*,以及去接觸**受影響的人**。

- **質疑這個需求本身**。使用者說的是他想要的解法,還是他遇到的問題?「加一個匯出按鈕」背後可能是「我每週要把數字貼給主管」。
- **找出受影響的人**。誰會用?在什麼情境下用?他們現在怎麼解決?這次改動還會波及誰(其他功能的使用者、維運的人、之後維護的人)?
- **去問人**。能問使用者的事就直接問,不要猜 —— 這是整個流程中最接近「和受影響的人相處」的動作。一次問最關鍵的幾題,不要把所有細節都丟回去。
- **去看現況**。讀相關的程式碼、既有行為、資料長相、過去的 issue 或 commit。現有系統本身就是一種受訪者。
- **把假設列出來**,標明哪些已經確認、哪些還只是猜測。

這個階段刻意要廣:先不要評斷哪些資訊有用,也先不要想解法。

### 2. Define —— 收斂:寫下這次要解決的問題

把 Discover 得到的東西收成一份簡短的 **brief**。依 Design Council 對這個階段的描述,它要做的是弄清楚使用者的需求與問題如何對上,產出一份「根據這些洞察清楚定義挑戰」的 design brief。

brief 至少要有:

- **問題陳述**:誰,在什麼情境下,遇到什麼困難。用使用者的角度寫,不要寫成解法。
- **這次的範圍**:要做什麼,以及**明確不做什麼**。
- **成功的樣子**:怎樣算解決了?要能驗證(可以直接變成驗收條件或測試)。
- **限制與前提**:技術、時間、相容性上不能動的東西。

注意原文說的是 *define the challenge in a different way* —— 經過 Discover 之後,問題陳述和使用者一開始說的**可以不一樣**,而這往往正是這個階段的價值。如果重新定義了問題,要明白告訴使用者差在哪裡、依據是什麼。

**brief 寫完後先給使用者確認,再往下走。** 這是兩顆鑽石之間的腰,在錯的問題上發展解法,後面做得再好都是浪費。

問不到使用者的時候(例如被交付任務後獨立執行,對方不在線上),不要停在這裡空等,也不要假裝確認過:依手上的證據寫出 brief、把它標成「未經確認」、把想問的問題留下來,然後繼續做;回報時把這幾項放在最前面,讓使用者一眼看到哪些是你替他決定的。

### 3. Develop —— 發散:提出不只一個做法

對著 brief(而不是最初的那句需求)提出**多個真正不同**的做法,通常兩到三個。原文的關鍵字是 *different answers*、*seeking inspiration from elsewhere*、*co-designing*。

- **做法之間要有實質差異**(不同的切入點、不同的取捨),不是同一個做法的三種命名。「什麼都不做」或「用既有功能加一點設定」經常是值得列出來的選項。
- **向別處找靈感**:這個 codebase 裡類似的問題是怎麼解的?標準函式庫或既有相依套件有沒有現成的?業界常見的 pattern 是什麼?
- **和使用者一起設計**:把選項攤開來,用使用者看得懂的方式呈現(見下方原則二),請他們一起評估,而不是只端出結論。
- 每個做法寫出:怎麼運作、優點、代價與風險、要多少工、它如何滿足 brief 的成功條件。

這個階段也是刻意要廣:先不要在想到第一個可行做法時就停下來。

### 4. Deliver —— 收斂:小範圍測試,淘汰與改進

原文在這裡說的不是「把東西做完交出去」,而是 *testing out different solutions at small-scale, rejecting those that will not work and improving the ones that will*。

- **先小規模試**。在投入完整實作之前,用最便宜的方式驗證最不確定的那一點:一個 spike、一個只走通主流程的薄切片、一段會失敗的測試、一個可以讓使用者實際操作的粗略版本。
- **根據結果淘汰與改進**。試出來行不通的做法就放掉,並記下原因;行得通的就依測試結果修正。
- **選定一個做法**,完成實作,用 brief 裡的成功條件驗證。
- **回頭檢查**:實作過程中學到的事,有沒有改變對問題的理解?有就回到 Define 更新 brief(必要時回到 Discover),不要默默偏離原本講好的範圍。

## 四項設計原則

Design Council 的 Framework for Innovation 在流程之外列了四項原則,貫穿四個階段:

| 原則(原文) | 開發時的意思(本 skill 的詮釋) |
|---|---|
| **Put people first** —— 從理解使用服務的人、他們的需求、長處與期望開始 | 任何決定先問「這對使用的人有什麼差別」,而不是「這在技術上漂不漂亮」 |
| **Communicate visually and inclusively** —— 幫助人們對問題與想法有共同的理解 | 用對方看得懂的形式溝通:範例輸入輸出、流程圖、畫面草稿、對照表,少用只有開發者懂的術語 |
| **Collaborate and co-create** —— 一起工作,並從別人正在做的事得到啟發 | brief 與方案都拿出來和使用者一起調整;借用既有的做法,不要閉門重造 |
| **Iterate, iterate, iterate** —— 及早發現錯誤、避開風險、對想法建立信心 | 小步試、早點拿給人看、錯了就回頭 |

## 適用條件與例外

Double Diamond 是一張描述流程的圖,不是規定。官方頁面引用的一句話:*"It's not an instruction manual on how to design, it's an invitation to get involved."* 所以要依情況調整深度(以下為本 skill 的詮釋):

| 情況 | 怎麼調整 |
|---|---|
| 需求模糊、牽涉的人多、做錯代價高 | 完整走。Discover 與 Define 多花時間,brief 一定要經使用者確認 |
| 需求已經很明確(附了驗收條件或完整規格) | Discover 縮成**查核**:規格有沒有和現況矛盾?有沒有漏掉受影響的人?然後照樣寫下 brief 與至少一個替代做法 |
| 很小的修改(改錯字、調一個設定值、調整輸出格式) | 四個階段都在腦中走過,但每個階段只留一行(用〈留下紀錄〉的精簡版)。不要整個跳過 —— 至少確認「這真的是問題所在」以及「有沒有更簡單的做法」;也不要反過來為它寫出整份設計文件 |
| 緊急修復(production 正在出事) | 先止血。事後補做 Discover(根本原因是什麼)與 Develop(長期解法有哪些) |
| 使用者明確表示不要這個流程、直接做 | 照做;若過程中發現需求有重大疑點,仍要提出來 |
| 探索性質的工作(本來就是要試試看) | 這本身就是 Discover 的一部分 —— 原文明說早期的製作與測試可以屬於 Discover。把學到的東西帶回 Define |
| 問題橫跨多個組織或系統、牽涉結構性因素 | 超出這張圖原本的設計範圍;Design Council 為此另有 Systemic Design Framework(Explore / Reframe / Create / Catalyse) |

另外,官方的 Framework for Innovation 還包含 methods bank(Explore / Shape / Build 三類方法)與成功的文化條件(leadership、engagement)。後者是組織層級的事,不在單次功能開發可以決定的範圍;細節見 `references/framework.md`。

## 留下紀錄,並依事情的大小決定寫多少

紀錄是和使用者對齊的工具,也是事後檢查「這次有沒有真的走過兩顆鑽石」的依據。但紀錄的份量要跟著事情的大小走 —— 為一個改兩行的需求寫出整頁表格,使用者得翻過一堆格子才找得到他關心的結果,這份紀錄就失去了用處。

**小修改用精簡版。** 需求明確、只動到一個行為、做錯了也很容易改回來的事(調整輸出格式、改一個預設值、修一個明顯的錯字或小 bug),每個階段一行:

```markdown
**Double Diamond(精簡)**
- Discover:<確認了什麼現況、影響誰;最關鍵的一個發現>
- Define:<這次改什麼;刻意不改什麼>
- Develop:<考慮過的另一個做法,以及為什麼沒選>
- Deliver:<怎麼驗證的、結果>
```

**其餘情況用完整版**(需求模糊、有多種解讀、牽涉的人多、做錯代價高、或問題被重新定義過):

```markdown
## Double Diamond 紀錄:<功能名稱>

### Discover —— 我了解到什麼
- 受影響的人與情境:
- 現況(看過的程式碼 / 資料 / 行為):
- 已確認的事實:
- 仍是假設的事:

### Define —— 這次要解決的問題
- 問題陳述:
- 範圍內 / 範圍外:
- 成功的樣子(可驗證):
- 與最初需求的差異(若有):
- 使用者是否已確認:

### Develop —— 考慮過的做法
| 做法 | 怎麼運作 | 優點 | 代價與風險 |
|---|---|---|---|

### Deliver —— 小範圍測試與結果
- 測試了什麼、怎麼測、結果:
- 淘汰的做法與原因:
- 選定的做法與依測試所做的修正:

### 回頭修正
- 過程中回到了哪個階段、因為學到什麼(沒有就寫「無」)
```

沒有內容可填的欄位直接省略,不要為了填滿而寫「無」或重複前面說過的話。

## 完成後的回報

回報是寫給使用者看的,所以依他關心的順序排:

1. **結果先講**:做了什麼、現在的狀態、怎麼用(一兩句,必要時附實際輸出)。
2. **需要使用者決定或確認的事**:尤其是沒經他確認的問題定義、仍是假設的事、你想問卻沒機會問的問題。這些會影響他要不要採用,不要埋在紀錄的中間。
3. **Double Diamond 紀錄**(上面的精簡版或完整版)。問題陳述和最初的需求不同時、或過程中回頭修正過時,要在這裡說清楚差在哪、為什麼。

同一件事只說一次:紀錄裡寫過的,不要在回報的其他段落換句話再講一遍。
