# Rule 1 [must] - 提出至少兩個具實質差異的做法
- 針對問題簡報必須提出至少兩個(通常二至三個)具實質差異的方案,每個方案清楚列出運作方式、優點、代價與風險
- 差異必須是切入架構、相依套件或取捨權衡上的本質差異,不可僅是函數命名或參數名稱不同的同一做法
- 為什麼:偽多選或單一方案無法達成發散思考,容易忽略更輕量或更穩定的替代路徑

## good example
- **具實質取捨差異的兩個方案**:一個改寫演算法一次讀入,另一個引入記憶體快取
```markdown
方案 A(一次讀入並於記憶體累計):將檔案單次載入為 list,在記憶體一次累計,耗時從 12 秒降至 0.8 秒;代價為若資料過大會佔用記憶體。
方案 B(SQLite 檔案快取):將 spend.json 同步轉入 SQLite 並建立 index;優點是查詢快,代價是多引入外部相依與檔案同步邏輯。
```

## bad example
- **同一個做法換三種寫法**:實質上全都是同一個快取,只是套件或名字不同
```markdown
方案 A:使用 dict 做快取
方案 B:使用 functools.lru_cache 做快取
方案 C:使用 cachetools 做快取
```

# Rule 2 [must] - 借鏡既有解法與原本需求
- 方案發散時應優先檢視 codebase 既有慣例與標準函式庫,避免閉門重造輪子
- 若使用者最初有明確提議解法(例如「幫我加快取」),候選方案中應包含該解法以進行公正比較,並以客觀代價說明其適用性
- 為什麼:借鏡既有 pattern 風險最低;將使用者原提議列入比較能讓淘汰或選定理由具備說服力

## good example
- **納入使用者提議並客觀評估**:方案包含使用者提到的快取,同時提出一次性讀取方案對照
```markdown
方案 A(使用者提議之快取):為 spend list 加上記憶體快取;優點是快,風險是新增資料時需精準處理快取失效(cache invalidation),否則出現過期資料。
方案 B(單次讀取與計算優化):消除每筆迴圈內的重複 open,一次讀入處理;優點是無過期風險,速度同為 1 秒內。
```

## bad example
- **忽略使用者原提議且自創非標準做法**:對使用者的提議隻字不提,且另寫複雜非標準架構
```markdown
完全忽略使用者提出的快取考量,也不說明為何快取不適用,直接端出自己想寫的非標準檔案索引方案。
```

# Rule 3 [must] - 規格已定案者不重新比較
- 若既有規格文件已對某些架構、指令介面或做法做出明確決定,不可將這些已定案事項重新列為候選方案相互比較
- Develop 階段僅針對規格中「尚未決定」或有實質疑慮的開放問題提出方案選項
- 為什麼:重新比較已定案的決策會浪費溝通成本,且可能推翻團隊已有的共識

## good example
- **尊重已定案決定並只針對未決定項目比較**:規格已定獨立 summary 指令,僅比較小計相同時之排序
```markdown
已定案:規格已決定為獨立指令 `spend summary`,不在 list 加 flag,不重新翻案。
未決定項目比較:小計金額相同時,方案 1「依類別名稱字母序」 vs 方案 2「依最近一筆交易時間排序」。
```

## bad example
- **把規格已選定項目重新攤開比較**:規格已寫明新指令,卻花篇幅比較「新指令 vs 在 list 加參數」
```markdown
規格已明確指示「功能 2 為獨立指令 spend summary」,仍列出「方案 A:新指令 spend summary / 方案 B:在 spend list 加 --summary 參數」請使用者重新選。
```
