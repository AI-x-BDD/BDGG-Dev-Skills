# Rule 1 [must] - 理解而非假設問題
- 質疑需求本身,區分使用者提出的表面解法與背後真正要解決的問題,並以受影響者的實際情境為核心
- 使用者要求「加快取」「加一個按鈕」時,先探究操作流程與受影響對象,而非直接實作該解法
- 為什麼:需求一到手就直接做使用者提議的解法,容易把沒有人需要或根本無效的功能做得很好

## good example
- **質疑解法並探究根本原因**:使用者要求加快取,先量測確認瓶頸並找出真正原因
```markdown
使用者:「spend list 最近變得很慢,幫我加個快取。」
Discover 動作:不直接加快取,而是實際量測 spend list 在 3000 筆資料上的耗時,發現每筆都重新讀檔重算,真正瓶頸在重複 I/O 與重算,非快取問題。
```

## bad example
- **照單全收直接假設問題**:未探究根本原因,直接把使用者的提議當成唯一真理
```markdown
使用者:「spend list 最近變得很慢,幫我加個快取。」
Discover 動作:直接認定系統就是缺快取,跳過量測與探索,直接開始設計快取機制。
```

# Rule 2 [must] - 現況與假設查核
- 查閱相關程式碼、既有行為、測試資料與既有文件,清楚列出受影響的人、已確認的事實與仍待確認的假設
- repo 內已有需求規格文件時,將規格與程式碼/資料現況比對,主動查核是否存在矛盾
- 使用者不在線上或無法即時詢問時,將想問的問題與所依據的假設明確記錄下來,不可默默猜測並假裝已確認
- 為什麼:不看現況與矛盾會導致後續設計建立在錯誤前提上;默默猜測會讓關鍵決策缺乏依據

## good example
- **比對現狀查核矛盾並記錄假設**:查出規格欄位與資料不符,且使用者離線時記錄假設
```markdown
現況查核:發現 docs/需求.md 寫 cat 欄位,但 spend.json 實際欄位為 category,記錄此矛盾。
使用者不在線上:記錄「假設應以現有資料 category 欄位為準,待使用者上線確認」,並列出問題,不私自猜測。
```

## bad example
- **忽視現況矛盾且默默猜測**:看到矛盾不記錄,離線時自作主張不留假設
```markdown
現況查核:規格寫 cat 但資料是 category,覺得無所謂或私自改成 cat 導致既有測試壞掉。
使用者不在線上:心裡猜測使用者應該是要這樣,沒有記錄任何假設與問題,假裝一切都已確認。
```
