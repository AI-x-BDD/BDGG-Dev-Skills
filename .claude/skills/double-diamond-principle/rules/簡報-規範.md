# Rule 1 [must] - 問題簡報四要素
- 問題簡報(brief)必須清楚包含四項要素:問題陳述、這次的範圍(明確列出範圍內與範圍外)、成功的樣子(可量化或具體驗證的驗收條件)、限制與前提(不可破壞的相容性或既有行為)
- 為什麼:缺少範圍外會導致功能不斷膨脹;缺少成功的樣子會導致實作完成後無法客觀驗收

## good example
- **四要素齊備的 brief**:包含問題、範圍內外、成功樣子與限制
```markdown
- 問題陳述:行政人員每月需匯出上月支出給事務所,現有系統無法匯出,手動整理易出錯
- 範圍內:新增可指定月份之匯出指令,格式為事務所要求的四欄
- 範圍外:不提供圖表產生、不支援其他報表格式
- 成功的樣子:產生符合四欄順序之 CSV,Windows Excel 開啟不亂碼,測試全數通過
- 限制與前提:不修改既有 spend list 輸出格式與欄位
```

## bad example
- **要素殘缺且無範圍界定**:只有一句籠統要做的事,無範圍外與驗收標準
```markdown
- 要做的事:加一個匯出功能
- 做法:寫個指令把資料匯出來
```

# Rule 2 [must] - 問題陳述以使用者角度撰寫
- 問題陳述必須以使用者的情境與困難出發,不寫成特定技術解法
- 經過 Discover 後若發現根本問題與使用者最初描述不一致,應以客觀數據或事實重新定義問題陳述,並清楚說明與原始需求之差異與依據
- 為什麼:用解法定義問題會抹殺更好解法的可能性;不說明依據就擅自改動問題會引起使用者困惑

## good example
- **以使用者角度重新定義問題並說明依據**:指出根本原因與原始需求之差異
```markdown
原始需求:「加個快取讓 spend list 變快」
重新定義之問題陳述:使用者在資料量成長至 3000 筆時,執行 spend list 需等待約 12 秒,體驗不佳
差異與依據:實測發現耗時在於每筆資料重複讀檔重算,快取無法解決寫入後即時更新的問題,且讀取瓶頸在磁碟 I/O,故將問題定義為「減少重複讀檔重算」
```

## bad example
- **直接抄表面解法或默默變更**:以解法當作問題,或未向使用者解釋即偏離
```markdown
問題陳述:系統缺乏快取機制,需要建立快取模組
```

# Rule 3 [must] - 既有規格即簡報
- 若 repo 內已存在定義這次工作的需求規格文件,該規格文件即為 brief,不可另開一份內容重疊的設計或 brief 檔案
- 查核過程中發現的矛盾、確認的決定或新學到的事,應直接寫回既有規格文件中
- 很小的修改(如改錯字、調對齊)簡報應精簡為一行,不另寫冗長設計文件
- 為什麼:同一件事存在兩份文件遲早會不同步;小修改寫整份文件只會造成溝通負擔

## good example
- **以既有規格為 brief 並寫回新發現**:不另立新檔,直接在 docs/需求.md 補充定案
```markdown
動作:以既有的 docs/需求.md 作為 brief,在文件中直接補註「已確認欄位依資料庫 category 為準,非 cat」,未另開 design-brief.md。
```

## bad example
- **另開重疊文件且重複抄寫**:規格已存在,仍另建新檔重複抄錄
```markdown
動作:雖然已有 docs/需求.md,卻在 docs/brief.md 另開新檔將需求.md 的內容重抄一遍,造成兩份文件內容重複。
```
